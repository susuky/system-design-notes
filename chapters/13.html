CHAPTER 13 · Protect clients

保護客戶端：讓依賴故障停在邊界內

遠端服務變慢時，呼叫端會付出什麼代價？這一章把時間、並行數、重試量與故障範圍當作有限預算，避免一個通知供應商拖垮整個文件平台。

學習目標

  • 分清楚非阻塞 I/O、非同步工作流與真正完成的承諾。
  • 畫出斷路器的三種狀態，選擇合適的錯誤分母與恢復方式。
  • 用隔艙和隨機分片縮小爆炸半徑，並計算隔離的限制。

13.1 Synchronous and asynchronous clients：等待方式也是容量設計

同步 API 通常讓呼叫者等到操作得到結果；非同步工作 API 則先回覆已接受，再透過輪詢、事件或回呼取得結果。但非同步 I/O 與非同步業務流程不同：一個使用事件迴圈的 HTTP 客戶端仍然可能在業務上等待同一個請求結果。避免把「用 async/await」等同於「可以無限並行」。每個未完成的 future 仍持有記憶體、連線、回呼和狀態。

在全課的文件平台基準中，一萬租戶每天提交一百萬份文件，日均約 11.57 份／秒，尖峰約 115.74 份／秒。每份轉換平均兩個 CPU-seconds，是處理資源假設，不等同於端到端完成時間。下載、排隊與外部辨識可能另需數十秒。上傳 API 適合回覆 202 Accepted 與任務 ID；狀態查詢、取消和權限驗證則保留短延遲的同步路徑。

非同步契約可以定義為：POST /jobs 在同一筆交易保存任務紀錄與 outbox 發送意圖後回覆已接受；發送器重送未確認的 outbox，工作者依任務 ID 冪等處理。GET /jobs/{id} 回傳 queued、running、succeeded、failed 或 cancelled。完成通知若丟失，客戶仍可查詢持久化結果。接收延遲與任務完成時間分別設定 SLO，才能同時看見快速受理和後續積壓。

重試需要跨越不確定性。客戶提交後沒收到回應，服務可能完全沒執行，也可能已完成寫入。用租戶範圍的 Idempotency-Key 搭配請求內容摘要，讓同一鍵與同一內容返回原本任務；同一鍵換內容應拒絕。保存冪等紀錄的時間至少覆蓋契約允許的重試窗口。外部通知也要有穩定事件 ID，接收端按事件去重，不能假設網路能保證一次且僅一次。

deadline 應沿呼叫鏈傳遞。若整個狀態查詢剩 800 ms，閘道已花 100 ms，不能讓下游再各等兩秒。把剩餘預算分給連線建立、讀取、必要重試和返回處理，並為 DNS、TLS 及連線池等待建立量測。取消訊號要傳到實際工作處，否則畫面上的逾時只會製造「使用者已放棄、後端仍忙」的隱形負載。

假設三層服務各自允許「原始一次加兩次重試」，最下層一次使用者請求最多可能遭遇 3 × 3 × 3 = 27 次呼叫。比較安全的策略是在理解語意的一層集中重試，設全域重試預算和總 deadline，採指數退避及抖動，並區分暫時性失敗與永遠不會成功的參數錯誤。AWS 對重試、退避與抖動的說明可用來核對這些機制。參考：Timeouts, retries, and backoff with jitter。

練習：收到 202 之後，客戶可以立刻顯示「文件轉換成功」嗎？

不可以。202 只表示目前已接受處理，並不保證完成。畫面應顯示已提交和可追蹤狀態；只有讀到持久化的成功結果才顯示完成。若產品允許接受後拒絕，還須清楚定義失敗通知、退款或重新提交流程。

13.2 Circuit breaker：讓持續失敗的依賴有喘息空間

斷路器可避免已知很可能失敗的呼叫持續消耗本地資源，但依賴本身的故障仍需修復。Closed 狀態正常放行並記錄結果；在樣本足夠且失敗或慢請求比例超過政策時轉 Open，直接回覆可辨識的依賴不可用；經過冷卻時間後進入 Half-open，只允許少量探測，成功達標才回 Closed，失敗則再次 Open。狀態名稱是「電路是否導通」，不要把 Closed 誤以為停止服務。

斷路器像封橋：為什麼先放一台車？

郵件供應商的起始政策可設為：最近 30 秒至少 40 次有效呼叫，逾時或服務端故障比例超過 50% 時開路，冷卻 10 秒後允許三個探測。只將實際發往該依賴且符合分類規則的結果放入統計；斷路器自己的拒絕、呼叫前就已取消的請求與使用者輸入錯誤另計。429 要依限流範圍處理：單一租戶超額通常只影響該租戶，供應商的全帳戶配額耗盡則需要全帳戶退避。慢呼叫另設比例與耗時門檻，因為即使最後成功，它仍可能長時間占住本地並行位置。

斷路器的粒度決定爆炸半徑。按「整個遠端主機」開路很簡單，卻會把正常的讀取端點和故障的寫入端點一起封鎖；按每個使用者建一個斷路器又可能產生過多狀態。實務上可按供應商、操作類型和重要資源群組分開，並限制狀態鍵的基數。多個實例的本地斷路器各自判定能避免中央依賴，但結果不會完全同步，低流量節點也可能長時間沒有足夠樣本。

開路後怎麼回答，必須由業務定義。通知可標為 pending 並稍後重送；文件預覽可給已知版本的快取；權限驗證失敗不能回「預設允許」。若改用備援供應商，要先確認資料可送給該供應商、語意相容、費用和總容量均可接受。

Half-open 的每個探測都要有 deadline，並設定這輪探測的最長等待時間，避免流量很低或呼叫卡住時長期停在半開。各實例的探測時間加入抖動，恢復時逐步提高並行上限；Closed 狀態只表示恢復放行，漸進升流仍由限流或並行控制執行。參考：Circuit Breaker pattern。

練習：所有 404 都計入斷路器失敗率，會有什麼問題？

大量不存在的資源可能是合法查詢或惡意掃描，並不證明依賴不可用。把它們算作故障會錯誤開路。應根據 API 契約分類，例如連線錯誤、逾時、特定 5xx 才計入依賴失敗；若 404 本身違反已知不變條件，應以另一個資料完整性告警處理。

13.3 Fail-fast design principle：快速失敗，保留修復所需的訊息

Fail-fast 的核心是：已知不可能完成的工作，不要繼續佔用稀缺資源。入口先檢查檔案大小、格式、身份、租戶額度和剩餘 deadline；佇列已滿就明確拒絕；必要依賴斷路時不要再發出一個注定逾時的請求。及早回覆可辨識的失敗，讓呼叫者決定修正輸入、延後或停止。

「快」必須對呼叫者有用。錯誤結果應區分輸入不合法、未授權、容量不足、暫時依賴故障和最終任務失敗，附上可追蹤 request ID、是否可重試與合理等待提示。對外不要洩漏內部機器地址、憑證或安全策略細節；詳細原因寫入受控的診斷系統。錯誤是契約的一部分，不能只有成功 JSON 的 schema。

服務端計算預算可分成「入場等待」和「執行」。例如互動 API 的總預算 600 ms，若拿連線池已等 400 ms，則剩餘 200 ms 不足以完成下一步，應釋放位置而非再啟動昂貴查詢。但如果資料庫寫入已開始且無法安全取消，需記錄操作 ID 並查詢最終結果，不能對客戶說「沒有執行」。逾時描述的是不知道結果，不一定是操作失敗。

Fail-fast 和 fail-closed 不是同一個概念。前者說失敗要及早；後者說授權或安全判定無法取得時拒絕存取。背景通知可延後重試，而租戶隔離檢查不可在故障時省略。對不同操作寫一張失效決策表，才不會讓一個模糊的「盡量保持可用」覆蓋安全需求。

練習：每次逾時都回傳「請立即重試」算 fail-fast 嗎？

即使單次回覆很快，整體系統仍可能陷入忙迴圈。應根據失敗類型設定退避、抖動、最大重試次數和總時間，對不可重試錯誤直接停止。服務端快速拒絕需要客戶端節制，兩者共同形成穩定回授。

13.4 Bulkhead：保住故障以外的工作

船艙隔板的比喻很直覺：一個艙進水，不應拖整艘船下沉。系統的「水」可能是被佔住的執行緒、連線、記憶體或重試。若文件辨識、郵件通知和狀態查詢共用同一個 200 執行緒池，郵件供應商變慢就可能佔滿池子，讓純資料庫讀取也停止。把不同依賴放在獨立的並行 semaphore、連線池或工作程序池，可限制故障傳播。

本平台可先分成三艙：互動查詢保留 80 個並行位置，轉換 100 個，通知 20 個，且各自有短的有界等候區。數字需要負載測試支持；不能把閒置的 80 個位置永久浪費，也不能「借用」到完全失去隔離。可設最低保留加有上限的共享池，讓正常時提高利用率，故障時仍保住關鍵路徑。

隔離必須沿資源鏈檢查。如果三個執行緒池最後共用同一個無上限的資料庫連線池，隔板只是畫在架構圖上。CPU、記憶體、磁碟、網路及下游配額也可能需要分配。程式內隔離成本低，但無法隔離進程崩潰；獨立容器提高隔離，仍可能共用主機；不同節點、可用區和區域的隔離更強，也更貴。選擇與你想抵擋的故障一致的邊界。

實作租戶隔艙時，不一定要為每個客戶開一套服務。一萬租戶逐一保留機器通常浪費很大。可以按服務等級與風險分池，再在池內實作公平排程；對極大或有特殊合規要求的租戶使用專用資源。成本模型應包含保留容量、額外部署和故障演練，而不只機器帳單。

練習：通知池滿了，能借用狀態查詢池把通知清掉嗎？

可以設計受控的共享餘額，但不能無界借用。須保留查詢最低容量、設定借用上限和快速回收機制，且通知工作不能長時間占用不可取消位置。故障期間最好把通知留在可靠佇列，保住使用者仍能查看和取消任務的通道。

13.5 Shuffle sharding：用小子集降低共同故障機率

普通分片把租戶固定分到不重疊資源群組；隨機分片則為每個租戶選一小組資源，不同租戶的子集可能重疊。假設池中有八個工作分片，每個租戶固定選兩個「無序、不同」分片，組合數是 C(8,2) = 28。若另一種設計把第一和第二順位視為不同配置，排列數則是 8 × 7 = 56；必須先講清楚模型，不能混用兩個數字。

租戶 A 分到 {1,4}，B 分到 {4,7}，C 分到 {2,6}。A 的失控工作若壓滿 1 和 4，B 可改走 7，C 的子集則完全分開。固定 A 的兩個故障分片，另一租戶從八個分片等機率選兩個，可直接算出重疊程度：

重疊分片數組合數機率所需處理
0C(6,2) = 1515/28兩個路由都避開這次故障
12 × 6 = 1212/28把失敗路由的流量移到剩餘分片
211/28子集內全部失效

因此完全重疊是 1/28，至少部分重疊則是 13/28。原先平均分攤到兩個分片的流量，切到一個後會使該租戶在剩餘分片的負載加倍；備援容量、重試上限和共同資料庫決定部分重疊能否順利承受。

選擇子集通常要由穩定的租戶鍵和配置版本決定，不能每次重試隨機跑遍整個池，否則隔離被自己拆掉。客戶端或路由器只能在該租戶子集中重試，並遵守 deadline 與重試預算。子集過小會降低單租戶可用容量，過大則更容易與其他租戶重疊；大型租戶可能要更大的子集或專用池。

擴容和移動租戶同樣需要設計。一次重新洗牌所有租戶會造成大量冷快取和連線變動；可以增加配置版本、漸進遷移，保留舊路由直到在途任務排空。若分片包含有狀態工作，還要處理租約、資料位置與重複執行，不能把無狀態服務的路由技巧直接當成資料搬遷方案。

AWS 的 Shuffle Sharding 文章說明以小型重疊子集搭配子集內重試來隔離故障；本節表格採「八選二、無序子集」計算。

綜合練習：某供應商完全故障，斷路器、隔艙和 shuffle sharding 各能解決什麼？

斷路器減少持續無效呼叫；隔艙限制本地被佔住的資源；shuffle sharding 限制某一租戶或某些分片故障波及的客戶集合。若所有分片仍依賴同一個完全故障的供應商，隨機分片無法讓供應商恢復。此時需要延後處理或經驗證的替代路徑，並清楚告知工作仍未完成。
