第 10 章 · Fast delivery

快速傳遞：用批次與壓縮減少浪費

批次攤平每次請求的固定成本，壓縮減少傳輸量。本章計算兩者對吞吐、等待時間、CPU 與記憶體的影響，再處理部分失敗與多租戶公平性。

  • 能計算批次大小帶來的吞吐收益與等待成本。
  • 能判斷壓縮是在節省瓶頸資源，還是把瓶頸移到 CPU。
  • 能為多租戶平台設計有界緩衝、部分失敗處理與可重現的量測。

10.1 批次 Batching

一次網路請求不只付資料本身的成本，還可能付序列化、系統呼叫、協議標頭、認證、排程及往返延遲。若每次只送幾百位元組，固定成本可能比有效工作還多。批次把多個邏輯項目放在同一個傳送或寫入操作裡，讓每個項目只分攤一小份固定成本。這與併行不同：併行增加同時進行的工作，批次改變每次工作的粒度。

本教材共同案例有一萬租戶、每日一百萬份文件、平均每份 5 MB（十進位），尖峰為日均十倍。依此得到日均約 11.57 份／秒、尖峰約 115.74 份／秒與原件 5 TB／日。訊息佇列通常傳 job_id、文件版本及物件儲存位置等小型中繼資料；不應把平均 5 MB 的原始文件誤當作每則事件都要複製的內容。原始文件與事件的批次策略也不必相同。

從固定成本推導吞吐上限

假設某個事件寫入端每次請求固定耗時 a = 2 毫秒，每項額外成本 c = 0.08 毫秒，且單一工作槽串行執行。批次大小為 B 時，服務時間約為 a + Bc，吞吐上限約為 B／(a + Bc)。這是假設資料在批次開始前都已到齊、沒有網路和排隊瓶頸的簡化模型。

吞吐收益要付多少等待？

如果只等滿 B 項才送出，在穩定到達率 λ 的簡化模型下，第一項平均等待約 (B − 1)／λ，整批各項平均等待約 (B − 1)／(2λ)。假設某分區每秒 1,000 項、B = 100，平均填批等待約 49.5 毫秒，第一項約 99 毫秒。這還沒加上排隊、服務與網路時間。稀疏流量的等待更長：每分鐘持續抵達一項、B = 100，第一項約需等 99 分鐘；若後續事件停止，就會一直留在未滿批次裡。

實務使用數量、位元組、時間三重觸發：到 100 項、到 64 KiB，或最舊項目等了 10 毫秒，任何一項達標就發送。以上是一組可測試的參數，時間上限應從該路徑的延遲預算分配。高流量時時間窗內平均等待有時可近似半個時間窗；低流量時，唯一的一項往往要等完整時間窗。也不要把 10 毫秒批次計時器誤認成端到端延遲上限，傳送佇列可能已經堵住。

分區會稀釋可批次的流量。沿用第八章每份文件衍生五則事件的假設，尖峰約 578.7 則／秒；平均分成 24 個分區後，每分區只有約 24.1 則／秒。每分區湊滿 100 則，第一則平均要等約 99／24.1 ≈ 4.1 秒。不能拿整個 topic 的流量估算分區內填批速度。Kafka 的 producer 設定文件也將 batch.size 與分區批次、linger.ms 等待行為分開描述。

批次的失敗與公平性

一批 100 則只代表一起運送，不一定一起提交。批次 API 若回傳每項結果，應只重試失敗或結果未知的項目，並保留各自的 event_id。若 API 只回一個整體成功或失敗，則必須查明它是否具備原子性；沒有原子性時整批重送可能重複已成功的一部分。尤其不可把「一次 HTTP 請求」等同於「一筆資料庫交易」。

大批次還會增加失敗影響範圍和記憶體。若 500 個活躍分區各保留一個 64 KiB 緩衝，光內容就約 31.25 MiB；序列化物件、已送未確認批次與重試副本會再增加。使用有界佇列與背壓（backpressure），緩衝滿時讓上游降速、暫停接收或明確拒絕，不應無限制堆在 heap 等待程序被系統終止。

多租戶公平性需要額外照顧。不要讓大租戶的一個超大批次長期占住唯一輸出槽，也不要讓小租戶必須等到自己的低流量桶湊滿。可按資料相容性與安全邊界分桶，在租戶之間使用輪流或加權公平排程，再給每桶最老等待期限。高優先權完成通知與低優先權稽核匯出也可分開；「更大批次」不應自動推翻產品延遲目標。

練習：把批次大小加倍，吞吐變好，但 p99 延遲從 80 毫秒升到 400 毫秒。接著該看什麼？

分解填批等待、發送佇列等待、服務時間及重試等待。檢查低流量分區是否常等滿計時器、單批是否形成隊首阻塞、是否有更大批次超過 API 限制而反覆失敗，以及記憶體壓力是否增加 GC。若 p99 的產品目標是 150 毫秒，不能因總吞吐漂亮就接受 400 毫秒；可以減小時間窗、限制單批大小或分離工作類型，再在同樣流量分布下重測。

10.2 壓縮 Compression

壓縮以計算換取較少的傳輸或儲存位元組。文件平台的 JSON 事件重複出現欄位名、租戶識別和狀態值，通常比已壓縮的 JPEG、ZIP 更有可壓縮空間。因此先抽樣真實資料類型，再選壓縮位置；不能把文字測試的高壓縮比套用到所有上傳文件，更不能假設 5 TB／日原件一定能再縮成某個比例。

批次與壓縮經常相輔相成：同一批事件之間的重複內容可共用編碼脈絡，逐則各自壓縮則反覆付框架與字典成本。代價是讀一則可能要解開整個區塊，隨機存取的粒度變粗，錯誤隔離範圍也變大。對須隨機讀取文件頁面的用途，可採有索引的獨立區塊，而非把整天所有事件做成一個無法切分的大壓縮串流。

用不等式找出划算的區間

設原始大小為 S、壓縮後比例 r（壓縮大小／原始大小）、有效頻寬為 W、壓縮與解壓時間分別為 C 和 D。在無重疊的串行簡化模型中，不壓縮需 S／W；壓縮需 C + rS／W + D。因此只有當 C + D < (1 − r)S／W 時，壓縮才縮短這段處理的總時間。真實系統可能重疊運算與網路，亦有多核、排隊及共用頻寬，需再量測端到端結果。

本節另設一個教學批次大小為 1 MiB、頻寬 20 MiB／秒、壓縮比 r = 0.25、壓縮 3 毫秒、解壓 1 毫秒。原傳輸約 50 毫秒；壓縮後是 3 + 12.5 + 1 = 16.5 毫秒，節省 33.5 毫秒。若頻寬升到 1,000 MiB／秒，原傳輸只需 1 毫秒，壓縮後反而約 4.25 毫秒。高速網路是否該壓縮，仍要分別評估單一請求延遲與全系統頻寬成本；兩個目標可能有不同最佳解。

演算法選擇應以實測為準。較強的壓縮等級往往付出更多壓縮時間，卻不保證相同比例增加解壓成本；不同實作和資料分布也會改變結果。可把 gzip、LZ4、Zstandard 等受平台支援的選項放在同一測試矩陣中，固定輸入、硬體、並行度與版本。RFC 8878定義 Zstandard 格式，可用來核對框架、解碼及資源限制。

壓縮放在哪裡，決定誰節省、誰付費

若生產端壓縮後 broker 保留壓縮形式，複寫與多次消費有機會重用節省下來的位元組；消費端則各自付解壓成本。若中介層必須檢查內容或轉碼，可能要解壓再壓縮。Kafka 的批次壓縮設計會讓 broker 驗證批次，而不能簡化成「broker 永遠不解壓」；具體路徑還受格式及設定影響。可對照 Kafka 的端到端批次壓縮說明。

一般而言先壓縮再加密，因為良好的密文不應保留容易壓縮的模式。但壓縮和安全也有交互作用：若攻擊者可控制部分輸入、機密資料與它共用壓縮脈絡，而且能反覆觀察輸出長度，就可能形成側通道。多租戶平台不應隨意把不同安全域的秘密混進可被探測的壓縮字典或批次。加密保護內容，未必隱藏長度。

解壓端必須把輸入視為不可信任，限制壓縮前後大小、字典／視窗需求、CPU 時間和並行度；不能只檢查壓縮包是 1 MB，就接受它解開後無限膨脹。RFC 8878 的安全考量也要求解碼器約束記憶體需求。對文件平台，可把解壓與文件解析放在受限工作環境，超限時明確終止，避免無限重試同一個輸入。

誤區：壓縮讓流量減半，所以成本一定減半。 端到端成本還包含運算、固定儲存費、請求次數、複寫、解壓後記憶體與多個消費群組。應同時報告每千份文件成本、每原始 GiB 成本與尾端延遲，而非只有壓縮比。
練習：壓縮使網路用量下降 60%，但 broker CPU 飆高。應直接關閉嗎？

先確認 CPU 花在哪裡：批次驗證、轉碼、重新壓縮，還是本來就變多的流量。比較使用同一種生產／broker 編碼、降低壓縮等級、調整批次大小及只壓縮高收益資料的方案。若成本已轉移到 CPU 並傷害 SLO，關閉或降低壓縮可能合理；若節省的是昂貴跨區頻寬，也可能值得增加算力。用整體目標決定，不用單一百分比決定。

本章實驗：找出可接受的操作區間

  1. 準備相同的正常、尖峰、小租戶稀疏及故障重試流量。
  2. 交叉測試批次大小、等待時間、壓縮演算法及等級。
  3. 記錄吞吐、p50／p99、最老訊息年齡、CPU、峰值記憶體、實際網路位元組與重送量。
  4. 只選擇同時滿足延遲、可靠性、公平性及成本限制的組合，保留回退設定。
