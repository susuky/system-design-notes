CHAPTER 12 · Protect servers

保護伺服器：把有限容量變成明確契約

系統常常在所有機器都還活著時陷入最危險的狀態：機器忙著處理已經來不及完成的工作。本章從過載形成的回授開始，設計擴容、卸載與限流如何共同保住有效吞吐量。

學完你應該能做到

  • 從佇列、延遲與資源飽和區分過載和單純高流量。
  • 推導有暖機時間的擴容需求，設計安全的控制迴路。
  • 選擇在哪一層拒絕哪些工作，解釋公平性和一致性的成本。

12.1 System overload：過載如何自我放大

全課共同基準是：一萬租戶、每天一百萬份文件、平均每份 5 MB（十進位），日均約 11.57 份／秒，尖峰為日均十倍，每份轉換平均耗用兩個 CPU-seconds。以下局部算例會另外說明假設。想像這個「多租戶文件處理與通知平台」：企業客戶上傳文件，平台做文字辨識、產生摘要，再寄出完成通知。查詢任務狀態通常只需數毫秒，辨識一份大型掃描檔卻可能佔用工作程序數十秒。同樣一千次請求，成本可以相差幾個數量級。因此容量必須描述成「某種工作組合，在某個延遲目標下，每秒能完成多少工作」，不能只報一個漂亮的 QPS。

令到達率為 λ、穩定完成率為 μ。如果 λ 長時間大於 μ，未完成工作必然累積。即使平均 λ 小於 μ，突發流量、重尾服務時間和單一熱租戶也會造成局部排隊。在穩定觀察窗口內，Little's Law 表示平均系統內工作數 L = λW；若每秒完成 500 次請求，平均停留時間從 0.2 秒上升到 4 秒，系統內平均請求數就從 100 增至 2,000。每個請求若持有記憶體、連線或鎖，延遲本身便會製造下一輪資源壓力。

先用較輕工作做一個獨立的局部佇列算例，不沿用全課每份兩個 CPU-seconds 的成本假設：假設有 10 個工作程序，每個每秒完成 4 份標準文件，容量約 40 份／秒。行銷活動把輸入推至 70 份／秒，兩分鐘後就多出 3,600 份待處理文件。流量回到每秒 30 份時，每秒只剩 10 份淨消化能力，清完還要 360 秒。若使用者逾時後又提交新任務，而且缺乏冪等鍵，排隊量甚至不會按這個速度下降。這是「服務已恢復正常流量，使用者卻持續受害」的典型原因。

判斷過載至少要看四組訊號：有效完成率、端到端尾延遲、排隊年齡，以及限制資源。限制資源可能是 CPU、工作執行緒、資料庫連線、檔案描述符、外部供應商配額或磁碟 IOPS。CPU 只有 20% 並不代表健康：全部執行緒可能正在等資料庫。成功率也不能單獨使用，因為一個把所有請求快速拒絕的服務，內部延遲看起來可能很好。

常見誤區

「先放進無限佇列就不會丟資料」只是把立即失敗換成不可控等待。佇列需要長度、位元組與最老工作年齡上限。容量耗盡時，應明確回報結果；若先回覆成功卻讓任務無限懸置，使用者無法知道該怎麼處理。

請求數需要搭配資源成本與重要性解讀；Google SRE 的 Handling Overload 說明了如何依這些訊號決定保留與拒絕哪些工作。

練習：固定 50 個連線，平均資料庫等待從 20 ms 變成 500 ms，理論等待段吞吐上限如何改變？

若每個請求獨占一條連線且此等待是瓶頸，粗略上限從 50 / 0.02 = 2,500 次／秒，降到 50 / 0.5 = 100 次／秒。真實上限還要扣除其他處理時間和保留容量。增加前端實例若也增加連線數，可能進一步壓垮資料庫，因此先控制資料庫並行度。

12.2 Autoscaling：擴容是有延遲的供給調整

垂直擴容增加單機資源，適合狀態難拆或單工作記憶體需求較大的場景；水平擴容增加實例，適合工作可切分、狀態外置的服務。垂直擴容可能需要重啟，也有機型上限；水平擴容會提高資料庫連線、快取冷啟動與跨節點協調成本。若真正瓶頸是單一外部 API 的每秒配額，再多工作程序只會產生更多限流錯誤。

第一個簡化控制器可以按目標使用率估算：期望實例數 = 向上取整（目前實例數 × 目前平均使用率 / 目標使用率）。例如 12 個相同規格實例、平均 CPU 75%、目標 50%，算得 18 個。使用 Kubernetes HPA 的 CPU utilization 時，百分比的分母是 Pod 內容器設定的 CPU requests；兩邊須採同一基準。這個比例模型適合 CPU 為瓶頸且負載均勻的情況；阻塞式 I/O 與熱分區還要看等待量和各分區負載。參考：Horizontal Pod Autoscaling。

對非同步文件任務，可以從新增工作成本和清空期限推算容量。設到達率 λ = 120 工作單位／秒，現有積壓 Q = 12,000 單位，希望從現在起 T = 300 秒清完，每個就緒實例安全處理 c = 10 單位／秒。若容量立即到位，需要 ceil((λ + Q/T)/c) = 16 個實例。文件成本差異很大時，工作單位可採 CPU 秒或頁數，讓積壓反映實際待完成的成本。

加入暖機後，先算新容量到位時還剩多少工作。假設原容量 μ₀ = 100 單位／秒，啟動時間 d = 120 秒，期間輸入維持不變：

Q_start = max(0, Q + (λ − μ₀) × d) = 14,400 單位
剩餘清空時間 = T − d = 180 秒
μ_new ≥ λ + Q_start / (T − d) = 200 單位／秒
就緒實例總數 ≥ ceil(μ_new / c) = 20

原有 10 個實例持續工作，因此要新增 10 個；忽略暖機會少算 4 個。這個定速模型要求 0 ≤ d < T。若新容量到位已超過期限，就得提早擴容、降低新接收量或調整交付時間。各批工作有各自的 deadline，還要另查最老工作年齡，才能判斷個別任務是否準時。

實例從宣告建立到能服務，可能經過排程、映像下載、模型載入、快取預熱及健康檢查。假設流量以每分鐘增加 30 份文件／秒的速度上升，暖機需兩分鐘，就要承受約每秒 60 份的額外需求。可預測的月底批次應提前擴容；不可預測尖峰則需要預留容量和卸載，不能等待控制器救火。

縮容通常比擴容慢：先停止接收新工作，再等在途任務完成或安全交還佇列；確認 lease 到期和冪等處理，不可直接終止正在寫入結果的工作程序。保留最低實例數以吸收短尖峰，採用遲滯和穩定窗口避免上下震盪。這些參數應依負載測試和成本／延遲取捨設定，別人的預設值仍需在自己的環境驗證。

練習：四十個實例都在等一個限額固定的文字辨識供應商，佇列持續長大。你會繼續擴容嗎？

不會先盲目擴容。先量測外部成功吞吐、配額、等待時間和重試放大率；按供應商限額限制外呼並行及速率。可在授權範圍內調高配額、切換經驗證的替代服務，或改交付時間。擴本地實例只有在本地也是瓶頸時才有效。

12.3 Autoscaling system design：設計一個可稽核的控制迴路

一個完整擴容系統至少包含觀測器、決策器、執行器、狀態儲存與防護欄。觀測器收集分租戶到達成本、服務時間分布、最老任務年齡、實例 Ready 數、外部限額和資料庫負載。決策器產生帶有理由與版本的目標數量。執行器把「目標狀態」交給編排系統，持續比對實際狀態，而不是一次性呼叫建立機器就宣告成功。

  1. 明確控制目標：互動查詢希望 p99 小於 300 ms；背景辨識希望 99% 在五分鐘內完成。兩種工作分開擴容，不用同一個 CPU 平均數掩蓋對方。
  2. 整理觀測窗口：短窗口偵測尖峰，較長窗口抵抗雜訊；標記遺失或過期的數據，避免把「沒有收到指標」誤判為「流量為零」。
  3. 算候選容量：分別以 CPU、並行需求和積壓清除時間算出候選值，再選能滿足限制的數量；下游配額作為上限，而非盲目取最大。
  4. 套防護欄：最小值、最大值、每次增減幅度、區域容量與預算界線。預算已滿時，讓卸載策略接手，並發出「需求超過可供容量」告警。
  5. 確認生效：只把 Ready 且通過實際小流量驗證的實例算進供給。Pending 實例列為建置中，避免每輪控制又重複建立。

決策記錄可以是 {observed_at, policy_version, current_ready, desired, reason, constraints}。控制器重啟後從狀態儲存恢復；兩個控制器同時運行時，用 leader lease 或帶版本的條件更新避免互相覆寫。執行動作須冪等，例如目標是「總數 18」，而非「每輪再新增 6」。

假設擴容後 p99 更差，CPU 卻下降，這不是控制器應再加倍的充分理由。新實例可能一起預熱快取，打爆資料庫；也可能連線池總容量隨實例數線性增長。為此應限制每區域的新實例啟動速率，對快取載入加抖動，並建立全域下游並行預算。容量模型要把依賴鏈納入：增加某一層的處理能力，可能把壓力推到更脆弱的一層。

驗收控制器不只測穩定流量。應重播階梯、斜坡、短脈衝、指標中斷、部署變慢、區域無可用機器和資料庫退化。觀察恢復時間、總丟棄量、擴縮次數與資源成本；目標是可預測地保住服務品質，並非使機器數量永遠貼著理論最低值。

12.4 Load shedding：在便宜的地方拒絕來不及完成的工作

限流通常根據契約或政策控制進入速度，卸載則根據當下容量保護系統。兩者可以重疊，但問題不同：付費租戶還有配額，不代表系統此刻有能力完成；系統非常空閒，也不表示未授權的流量能無限制使用。應在耗費昂貴資源前卸載，盡量在讀取小型標頭、驗證身份和估算成本之後、下載大檔與啟動辨識之前拒絕。

文件平台可以保留「取消任務、讀取結果、安全管理」通道，暫停低優先批次重算；已承諾完成時限的工作優先於可延遲的匯入。服務降級則可以只產生文字結果、延後摘要和預覽圖。不過不能把降級冒充完整成功，回應必須帶上狀態與缺少的欄位。若工作涉及權限或資料完整性，不能為了可用性跳過驗證。

對每個進來的請求估算：預計排隊時間 + 預計服務時間，是否小於剩餘 deadline？如果根本來不及，及早失敗通常比佔著連線更有用。這是估算而非保證，重尾工作應保留餘裕。佇列還需清掉取消或已過期工作，避免它們搶走仍有價值的容量。

回應要能讓客戶端做正確決策。配額超限可用 429；服務暫時無法接收可以用 503，必要時提供合理的 Retry-After。HTTP 的 429 定義見 RFC 6585；503 與 Retry-After 語意見 RFC 9110。狀態碼不會自動建立安全重試語意，仍要搭配冪等鍵、重試次數、總時間上限與抖動。RFC 6585 §4、RFC 9110 §15.6.4。

練習：能否一律丟棄最舊的工作，讓新請求看起來很快？

不可以把它當通用策略。若舊工作已支付費用或接近交付期限，丟棄會破壞承諾；對即時位置更新，舊資料可能已被新資料取代，丟棄才合理。先定義工作價值、是否可合併、承諾期限和補償方式，再選 FIFO、優先佇列、最新值覆蓋或截止時間排序。

12.5 Rate limiting：依成本分配租戶額度

固定窗口容易實作，但窗口交界可能讓客戶在很短時間內使用兩倍額度。滑動日誌能精確回看最近一段時間，卻需保存每次事件；滑動窗口計數以較小狀態近似；token bucket 以速率 r 補充 token、最多儲存 b 個，允許短暫突發；leaky bucket 常用於把輸出整形成較穩定速度，但具體實作可能是排隊或拒絕，必須講清楚。

把配額畫成硬幣：突發與平均速率一眼看懂

以 token bucket 為例，租戶每秒補充 20 個 token，桶容量 100。一次文件提交花 5 個、狀態查詢花 1 個，成本是服務模型設定而非固定標準。空閒後可立即提交 20 份文件，之後平均每秒最多 4 份。還需要「同時正在處理的大文件數」上限，因為速率限制不能阻止少數超長工作持續佔滿記憶體。速率、並行度、總位元組和累積儲存配額是不同維度。

分散式限流的關鍵是額度是否被重複計算：

方式全域額度怎麼守住代價
集中原子判定所有節點共用同一份計數或桶狀態每次請求增加一次協調；故障切換須保留已消耗狀態
每節點獨立桶五個節點各配 100，合計可放行 500；須把全域額度拆分到各節點固定切分可能讓忙節點拒絕、閒節點仍有額度
中央預留、分批租出同一配額窗口先預留總額度，同一批只交給一個節點失聯節點的未用額度暫時閒置；回收要防舊節點繼續使用

以固定窗口的總配額為例，五個閘道各剩 20 個已預留的 token，失聯後合計可再用 100 個，這 100 個已算在全域預算裡。若政策允許每個閘道在預留用完後額外放行 20 個，才會增加最多 100 個的超發量。租用額度要帶期限與世代，節點重啟後不能把已消耗的配額恢復成滿桶；中央只有在舊配額確定失效後才能重發。Envoy 的 quota 模式提供按節點分配與重新平衡額度的實作例子。

若要維持連續 token bucket 的全域突發上限，還要控制所有節點的可用配額。簡單做法是把各節點的補充速率與桶容量切分，分別滿足 Σrᵢ ≤ r、Σbᵢ ≤ b；重新分配時先讓舊份額失效再啟用新份額。若中央在配額發出後立即補滿，而節點又長期保留未用 token，就可能囤出超過 b 的瞬間放行量。

計數器鍵使用已驗證的租戶身份與操作類型。未驗證流量先依來源做粗粒度保護，驗證後再套租戶限制，避免 NAT 後的正常使用者共用一份過小配額。補充與扣除 token 必須在同一個原子操作完成；本地用單調時鐘計算經過時間，共享桶則使用一致的時間基準。儲存故障時，可對低風險讀取給有限應急額度，高成本寫入則暫停接收。

連續補充的 token bucket 在任意長度為 Δt 的區間內，最多放行 b + r × Δt 個 token 成本。若請求成本 k 大於桶容量 b，等多久都無法通過；應回報成本上限。當 k ≤ b 且 r > 0，目前有 x 個 token，補足配額至少要等 max(0, (k − x)/r) 秒，可用來產生 Retry-After；其他請求也會消耗同一桶，所以重試時仍需重新判定。

公平排程還要防止大租戶長期擠壓小租戶。可給每個租戶保留最小份額，再分享閒置容量；按工作成本計量的加權公平佇列，會比按請求個數公平。優先級也應設防飢餓機制，讓低優先工作隨等待時間提高權重。容量不足時，產品方案必須明確說明什麼是保證、什麼只是盡力。

綜合演練：某租戶批次匯入讓全站任務延遲增至二十分鐘，請列出第一輪修正。

先限制該租戶提交速率與在途成本，把批次處理隔離到有界佇列，保留互動查詢與取消通道。停止無效重試，讓過期工作退出。以實際工作成本和最老任務年齡推算擴容，確認下游容量。短期清積壓，長期加入公平排程、最大工作大小及容量壓力演練。不要只調高佇列上限。
