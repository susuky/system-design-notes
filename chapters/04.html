第四章 · Fundamentals / Communication

通訊基礎：把「收到」與「做完」分開

一份文件從上傳、病毒掃描、文字辨識，一路到寄出完成通知，至少跨越了三種本質完全不同的邊界：網路傳輸、程序執行以及業務責任。在急著挑選通訊協定或訊息佇列之前，我們必須先釐清最核心的合約：每一次網路回應，系統到底對呼叫端許下了什麼承諾？

情境設定：租戶上傳文件後取得工作編號，平台在背景執行耗時的文字辨識（OCR），處理完畢後提供下載並通知使用者。原始檔案存放在物件儲存（Object Storage）中；而在各服務之間傳遞的訊息，只攜帶租戶識別碼、文件版本、工作編號與物件參照。各小節中的計算案例均明確列出負載與時間假設。

4.1 同步與非同步通訊（Synchronous vs asynchronous communication）

很多工程師在討論「同步」與「非同步」時容易混淆，因為這個詞同時出現在業務互動、程式語言 API 以及作業系統核心三個不同層次。在系統架構層面，同步互動意味著呼叫端在這次請求的生命週期內，必須拿到最終的業務運算結果，才能推進後續流程。舉例來說，使用者在介面上點擊「預覽第一頁」，前端就必須拿到該頁渲染後的圖片資料，否則畫面根本無法呈現。

相對地，非同步互動的核心概念是把「提交請求」與「取得最終結果」在時間維度上徹底解耦。使用者提交了一份 200 頁的 PDF，API 伺服器在將任務寫入持久化儲存後，立刻回傳一張「掛號收條」（工作編號 job_id），隨即結束本次 HTTP 連線。至於耗時數十秒的辨識工作，則交由背景工作者慢慢執行，使用者稍後可以透過主動輪詢、伺服器推送（WebSocket/SSE）或 Webhook 回呼取得最終結果。這純粹是業務互動契約的設計取捨，與底層執行緒當下是否在等待 I/O 無關。

這也解釋了一個常見的觀念盲點：同一個 HTTP 請求可以「同步」取得「任務已被系統受理」的確認，但這項工作本身卻是「非同步」進行的。依照 RFC 9110 的標準規範，HTTP 202 Accepted 僅代表請求已被接受排入佇列，完全不保證最終會處理成功，更不代表當下已經完成。因此，API 應回傳包含查詢狀態的 URI 或任務編號，切勿將 202 粗暴地解讀為「文件已處理完畢」。詳細語意可參考 RFC 9110 HTTP 202 語意規範。

從排隊理論推導容量需求。為什麼架構師總喜歡把耗時工作改成非同步？我們可以用 Little 法則（$L = \lambda W$）給出精確的數學量化。假設系統處於平穩狀態，平均每秒有 40 件文件提交（$\lambda = 40$ req/s），而每份文件的端到端辨識需要 8 秒（$W = 8$ 秒）。若採用同步阻塞式架構，用戶端與伺服器之間的連線必須維持直到完成，系統中常態掛著的在途連線數為 $40 \times 8 = 320$ 條。每條掛著的連線都會吃掉檔案描述符（fd）、Socket 緩衝區與伺服器執行緒記憶體，一旦遭遇網路抖動或負載攀升，連接池與線程池會瞬間被耗盡。

反之，若改採非同步設計，API 伺服器只負責將任務規格寫入資料庫並派發 job_id，平均耗時降至 0.12 秒（$W = 0.12$ 秒）。此時 API 層維持的在途連線數僅有 $40 \times 0.12 = 4.8$ 條。這意味著面對突發流量，API 網關依然能從容回應。但必須保持清醒：非同步並沒有把那 8 秒鐘的 CPU 辨識工作變不見，它只是把系統的壓力點從「高並行網路連線」轉移到了「後端任務排隊佇列」。原始推導細節可見 Little 的原始排隊論文。

非同步模式雖然能削峰填谷，但天下沒有免費的午餐，它帶來的代價是狀態複雜度的暴增。同步 API 只有成功或失敗兩種結果；非同步架構卻必須維護一整套分散式狀態機：queued、running、succeeded、failed、canceled。此外，還得處理任務卡死時的逾時回收、客戶端重複取消的冪等邏輯，以及提供輪詢或推送的額外端點。因此，對於耗時極短（例如幾十毫秒內的權限校驗或餘額檢查），同步是乾淨俐落的最佳解；只有當處理時間長、下游不確定性高時，非同步架構帶來的韌性才物有所值。

網路故障下的認知邊界。在非同步實作中最危險的架構反模式，就是 API 伺服器在記憶體中啟動一個 background goroutine 或 thread，接著立刻向用戶端回覆 202。如果伺服器程序在 50 毫秒後因 OOM 或部署而重啟，這個尚未持久化的任務承諾將無聲無息地蒸發。更常見的情境是：API 已經將工作寫入資料庫，但回傳 202 的網路封包在中途遺失，導致用戶端逾時。此時「逾時」只代表「結果未知」，絕對不等於「伺服器沒有執行」。若前端盲目重試而沒有帶上唯一的冪等鍵（Idempotency Key），系統就會重複排入兩次相同的工作，浪費寶貴的計算算力。

常見錯誤：把「非同步」當成「免等待」、以為用了 HTTP 就只能做同步、誤把用戶端中斷連線當作伺服器背景運算已終止，以及把網路逾時直接當作業務失敗。這些錯誤本質上都忽略了分散式系統各節點的獨立觀察邊界。

練習：系統每秒接收 120 件請求，單件後端處理耗時 3 秒；若改為非同步提交，接收 API 僅需 0.15 秒即可返回。兩種模式下的在途請求數差多少？

在同步模式下，系統長態在途等待請求數為 $120 \times 3 = 360$ 個；而在非同步提交階段，API 在途連線數僅有 $120 \times 0.15 = 18$ 個。但請注意：這絕不代表整體處理能力暴增 20 倍。後端背景工作者依然必須具備每秒消化 120 個任務的吞吐能力，否則佇列將會無限積壓，最終導致任務延遲失控。

4.2 非同步訊息模式（Asynchronous messaging patterns）

一旦決定將系統拆分為非同步通訊，工程師面臨的第一個抉擇往往是：該用哪種訊息拓撲？在挑選 RabbitMQ、Kafka 或 SQS 之前，必須先釐清語意上的責任歸屬：這則訊息究竟是命令（Command）還是事件（Event）？命令代表「期望某個服務去執行特定動作」（例如 ProcessDocument），它可能因權限不足或參數錯誤而被拒絕，通常應該由單一指定的處理者承擔；而事件則是「已經發生的不可抹滅事實」（例如 DocumentProcessed），訂閱者只能聆聽並做出反應，無權否定事實的存在。

從平台需求選訊息拓撲
模式責任與案例要付出的成本
工作佇列／競爭消費者（work queue / competing consumers）辨識工作交給一位可用工作者；其他工作者分擔其他工作失敗會重新投遞；必須容忍同一工作先後或暫時同時執行
發布訂閱（publish–subscribe）完成事件分別送到通知、搜尋索引與稽核三個訂閱每個訂閱都有自己的積壓、保留期限與失敗處置
請求回覆（request–reply）命令帶 correlation_id，回覆以相同識別碼配對要處理遲到回覆、重複回覆，以及呼叫者已不再等待
協調式流程（orchestration）工作控制器依序安排掃描、辨識、彙整控制器需持久狀態與恢復機制；也比較容易查明停在哪一步

實務上最慘烈的一種架構事故，是把「發布訂閱」誤配成「競爭消費者」。假設系統有「發信通知」與「全文檢索建立索引」兩個獨立服務，如果我們讓兩者共用同一個佇列，那麼每個 DocumentProcessed 事件只會隨機被其中一個服務搶走——結果就是某些文件建了索引卻沒寄信，另一些文件寄了信卻找不到索引！正確的做法是透過 Fanout 交換器，為通知與搜尋分別建立各自專屬的佇列；每個佇列再由該業務的多個 Worker 進行負載平衡與競爭消費。關於 AMQP 的交換器、佇列綁定模型，可參考 RabbitMQ AMQP 核心概念。

雙重寫入困境與 Transactional Outbox 模式。當 OCR 工作者辨識完畢後，它必須做兩件事：在資料庫把任務標記為成功，並發送 DocumentProcessed 訊息給訊息代理。這兩步如果在程式碼中分開執行，必然會落入「雙寫不一致」的陷阱：若先更新資料庫再發送訊息，若程式在發送前崩潰，資料庫已標記完成，下游卻永遠等不到通知；若反過來先發訊息再更新資料庫，一旦資料庫寫入因衝突或磁碟已滿失敗，下游就會收到一則幽靈完成通知，回頭查詢資料庫卻發現根本沒這筆記錄！

解決這個經典問題的標準武器是 Transactional Outbox 模式。利用關聯式資料庫的本機 ACID 交易，將「業務狀態更新」與「待發送事件記錄（Outbox 表）」封裝在同一個交易中提交。只要資料庫交易成功，事件就一定持久化入庫；隨後由獨立的轉發程序（Relay）讀取 Outbox 表並推送到訊息佇列。轉發成功後再將 Outbox 記錄標記為已發送。即使轉發程序在確認前崩潰重啟導致重複推送，下游也可以透過固定的 event_id 實現冪等消費，徹底保證了業務與訊息的最終一致性。

// 概念偽碼：兩筆寫入在同一個本機資料庫交易中完成
transaction:
    update_job(tenant_id, job_id, state="SUCCEEDED", result_ref=result_ref)
    insert outbox(event_id, tenant_id, job_id, document_id, version, "DocumentProcessed")
commit
// 另一個程序負責讀取 outbox 並投遞；連線中斷重試時沿用同一個 event_id

在容量規劃方面，假設系統每秒產生 100 個完成事件，每個事件都要廣播給 3 個獨立業務訂閱，則訊息代理每秒要支撐的邏輯投遞吞吐量為 $100 \times 3 = 300$ 則訊息（不含重試）。如果通知服務因外部郵件閘道限流，每秒只能消化 70 則，那麼通知專屬佇列每秒就會積壓 30 則。因為佇列在實體上是隔離的，搜尋索引服務依然能以每秒 100 則的速度全速前進。這就是非同步發布訂閱帶來的故障隔離效益。

常見錯誤：事件 Payload 只放 document_id，等到下游讀取時該文件早已被更新成下一版；失敗重試沒有退避機制，引發每秒數萬次的高速重試風暴；遇到中毒訊息（Poison Message）直接無限死循環重試卡死隊列；或者把訊息隨便扔進死信佇列（DLQ）就當作處理完畢。死信佇列必須具備告警指標、明確的根因歸屬、保留期限以及修復後的重放腳本。

練習：通知與搜尋索引服務都必須接收每一則文件完成事件，它們能共用同一個 RabbitMQ 佇列嗎？

絕對不行。若共用同一個佇列，兩者會變成競爭關係，各自只搶到大約一半的事件。正確架構是讓 Fanout Exchange 將事件廣播複製到「通知佇列」與「搜尋佇列」兩個獨立實體中。訊息封套必須攜帶 event_id、tenant_id、job_id、document_version，重送時嚴格沿用同一個 event_id 供下游去重。

4.3 網路協定（Network protocols）

網路協定本質上是一組分層的契約承諾。傳輸層負責在兩個主機端點之間可靠或盡力地傳送資料封包；應用層則賦予這些位元組具體的業務語意（如 HTTP 的方法、標頭與資源路由）。TLS 提供了傳輸層的加密通道與身分驗證，但它完全無法替你的業務邏輯判斷「租戶 B 究竟有沒有權限下載文件 A」。在系統設計中，必須把可靠傳輸、通訊加密、存取授權與業務成功這四個層次明確切割開來，千萬不要誤以為「因為我們架構走 HTTPS，所以一切都是安全且一致的」。

本平台可能用到的協定及其邊界
協定提供什麼不應推論什麼
TCP可靠、有序的位元組串流沒有保留應用訊息邊界；一次 send 不對應一次 recv；傳輸確認不是資料庫提交
UDP保留資料報邊界的傳輸本身不提供可靠重送或排序；應用若需要就必須另外實作
QUIC在 UDP 上提供安全、多路串流傳輸不同串流可獨立交付，但仍可能共享壅塞控制與連線級流量限制
HTTP方法、狀態碼、標頭等應用語意200 或 202 的業務意義取決於資源與契約；並不是所有操作都已完成

查閱基礎網路規範能幫我們建立清晰的心智模型：RFC 9293（TCP）、RFC 768（UDP） 以及 RFC 9000（QUIC）。在評估傳輸效能時，永遠要記住：協定規格書上宣稱的理論優勢，在實際落地時可能被其他瓶頸吃掉。

文件上傳首選 HTTP/HTTPS，原因在於它能無縫接軌現有的 API Gateway、邊緣驗證機制與 S3 預簽名上傳（Presigned URL）；內部微服務之間的高頻呼叫則適合採用基於 HTTP/2 或 QUIC 的 gRPC，利用長連線多路複用與二進位傳輸降低開銷；而即時進度推送則可挑選 Server-Sent Events（SSE）或 WebSocket。在做技術選型時，必須綜合考量代理轉發支援、逾時設定、除錯便利度以及客戶端生態系相容性。切忌僅以「QUIC 握手只需 0-RTT」為由盲目替換，因為在傳輸 50 MB 的大文件時，決定總耗時的絕對是頻寬上限與磁碟寫入速度，而非那短短幾毫秒的連線握手。

單位陷阱與傳輸耗時估算。假設一份 20 MiB 的 PDF 文件，網路鏈路能提供穩定的 10 MiB/s 有效淨載吞吐量，純傳輸耗時為 $20 \div 10 = 2$ 秒（另計 TCP 慢啟動、TLS 握手與後端寫入延遲）。但如果雲端業者標示的頻寬規格是 10 Mbit/s（請注意小寫 b 代表 bit），換算下來傳輸耗時將是 $(20 \times 1024 \times 1024 \times 8) \div 10,000,000 \approx 16.78$ 秒，兩者相差了整整八倍以上！架構師在容量估算時，必須嚴謹區分 Byte、bit 以及二進位（MiB）與十進位（MB）的差別。

TCP 黏包問題的本質。初學者在原始 TCP Socket 上自行開發通訊協定時，常犯的經典錯誤是：發送端連續 send() 了兩個 JSON 字串，接收端卻在一次 recv() 中讀到了兩個黏在一起的 JSON，或者只讀到了半個 JSON 而噴出語法解析錯誤。這並非 TCP 發生了 bug，而是因為 TCP 是一個純粹的「無邊界位元組流（Byte Stream）」。應用層若要在 TCP 上傳遞訊息，必須自行實作訊息分框（Framing）機制——最常見的做法是在訊息開頭固定加上 4 個位元組的長度前綴（Length-Prefixed），接收端先讀取長度，再精確收取指定長度的封包。同時，必須對最大封包長度設定硬性上限，否則惡意攻擊者只要送出一個宣告長度為 2 GB 的假標頭，就能輕易誘發伺服器 OOM 崩潰。

常見錯誤：把「TCP 保證單一連線內的順序」擴大腦補成「跨多條連線仍具備全域順序」；迷信 QUIC 徹底消除了所有隊首阻塞（其實多串流仍受限於共用的壅塞窗口與流量控制）；將網路重試次數設為無窮大；或者以為 TLS 握手成功就代表呼叫端具備業務授權。

練習：應用程式從 TCP Socket 讀取到 700 bytes，但通訊協定標頭宣告該訊息長度為 1,000 bytes。此時可以判定資料損壞並中斷連線嗎？

不能。TCP 是流式協定，700 bytes 僅代表底層接收緩衝區目前收到的分段。應用層必須維護自己的緩衝區，將已收到的資料暫存，繼續等待後續封包補齊剩下的 300 bytes，直到湊滿 1,000 bytes 才能送入業務反序列化。只有在連線遭遇非預期 RST、EOF 關閉或逾時，才能判定傳輸異常。

4.4 阻塞與非阻塞 I/O（Blocking vs non-blocking I/O）

在討論 I/O 模型時，最重要的事情是建立清晰的垂直層次觀。阻塞（Blocking）指的是當執行緒向作業系統發起 I/O 系統呼叫時，若資料尚未就緒，該執行緒會被核心掛起（進入休眠態），主動讓出 CPU 核心排程，直到資料抵達並被複製到使用者空間後才會被喚醒。非阻塞（Non-blocking）呼叫則完全相反：若當下沒有資料可讀，核心會立刻返回錯誤代碼（如 EAGAIN 或 EWOULDBLOCK），呼叫端執行緒不會被休眠，能夠立刻轉去處理其他事務。

不要把使用者等待與執行緒等待混為一談

程式 API呼叫返回時操作已完成，還是稍後以 future／callback 通知？等待儲存完成的 future
執行緒／系統呼叫無資料可讀時，執行緒睡眠等待還是立即返回？阻塞 recv 或非阻塞 recv

現代高並行網路服務的核心基石是I/O 多路複用（I/O Multiplexing），例如 Linux 的 epoll、macOS 的 kqueue。它允許單一執行緒同時監看數以萬計的檔案描述符。但必須牢記：epoll_wait 回報的「可讀事件」，僅僅代表「底層核心緩衝區有資料了，現在發起 read() 不會被卡死」，絕對不代表完整的應用層訊息已經到齊，更不代表業務邏輯處理完成！特別是在邊緣觸發（Edge-Triggered）模式下，應用程式必須在收到通知後使用非阻塞讀取持續 drain 緩衝區，直到返回 EAGAIN 為止，否則殘留的資料將再也不會觸發通知而發生死鎖。具體細節可研讀 Linux epoll(7) 核心手冊。

// 示意：真實版本還須處理 EOF、錯誤、公平性與緩衝上限

        data = nonblocking_read(connection)
        if data == WOULD_BLOCK: break
        if data == EOF: close_and_record_state(); break
        append_to_bounded_buffer(data)

            dispatch(parse_one_frame())

架構取捨：多執行緒 vs 事件驅動迴圈。傳統的「每連線一執行緒（Thread-per-connection）」模型最符合直覺的線性思考，除錯容易；但當面對 100,000 條長連線時，光是執行緒的呼叫棧記憶體（預設通常 2 MB 至 8 MB）與核心上下文切換開銷，就會直接把伺服器壓垮。事件驅動迴圈（如 Node.js、Netty、Go runtime 底層的 netpoller）能以極少量的執行緒支撐海量並行連線。然而，事件驅動模型最致命的阿基里斯之腱，就是絕不能在事件迴圈中執行長時間的 CPU 密集運算或阻塞呼叫。

假設系統的事件迴圈期望每 10 毫秒輪詢一次各連線的網路封包，但某個工程師在回呼函式中直接呼叫了一段耗時 250 毫秒的影像特徵提取程式碼，那麼在接下來的四分之一秒內，整個事件迴圈將被完全凍結！在這段期間，伺服器上所有的連線握手、心跳封包與資料收發通通無法處理，外部客戶端會看到原本 5 毫秒的延遲突然跳出可怕的尾端毛刺（Tail Latency Spike）。正確的架構作法是：事件迴圈只專注處理網路分框與協定解析，耗時的 CPU 運算必須派發至有容量上限的有界執行緒池（Bounded Thread Pool）非同步執行。

常見錯誤：看到程式碼裡寫了 await 就盲目以為「沒有任何阻塞發生」；把 Non-blocking 誤以為是「零等待」（在自旋迴圈裡不斷重試 EAGAIN 導致單核心 CPU 使用率飆滿 100%）；忘記 write() 在 Socket 緩衝區填滿時也只會寫入部分位元組；只監控執行緒數量，卻忽視了事件迴圈延遲（Event Loop Lag）早已惡化。

練習：如果將某個阻塞式的第三方 SDK 包在大小為 10 的執行緒池中，系統是否就能應對任意規模的並行請求？

不能。底層真正能並行執行的阻塞任務上限依然死死卡在 10 個。其餘的請求只能在佇列中排隊或直接被拒絕。若單次呼叫耗時 1 秒，該執行緒池每秒的極限吞吐量就是 10 次。上層的非同步包裝只是避免了事件迴圈卡死，絕對不可能憑空創造出下游的硬體與運算容量。

4.5 資料編碼格式（Data encoding formats）

網路實體層只負責傳送原始的位元組串流，但接收端的應用程式需要的卻是具備欄位名稱、型別與結構的物件。序列化（Serialization）解決的是「記憶體資料結構如何映射為位元組」；字元編碼（如 UTF-8）解決的是「文字字元如何對應到位元組」；而壓縮（如 Gzip, Zstandard）則是「透過消除位元組重複樣式來縮小傳輸體積」。這三者處於資料管線的不同階段，各有其職責。JSON 的優勢在於人類可讀與生態系無處不在，但它的結構鬆散且 Payload 偏大；Protocol Buffers 等二進位格式則要求雙方依循預先定義的 Schema，透過緊湊的二進位欄位編號（Field Tag）進行傳輸，執行效能與頻寬消耗都遠優於文字格式。

在分散式架構中，訊息封套的定義必須嚴謹標準化。我們平台傳遞的所有事件，至少必須具備以下核心中繼欄位：event_id（全域唯一 UUID）、tenant_id（多租戶隔離）、job_id（特定處理實體）、document_id（業務物件）、document_version（資料版本號）、schema_version（結構演進版本）、occurred_at（以毫秒精度 UTC ISO-8601 或 Unix 時間戳記錄的發生時間）以及 payload。此外，大型檔案絕對不可直接硬塞進訊息體，而應僅傳送安全簽名的物件參照（Object URI），避免訊息代理記憶體瞬間爆發。

編碼體積的算例對比。以一筆簡短的資料為例，在不含換行與多餘空白的情況下，JSON 字串 {"pages":150} 以 UTF-8 編碼長度為 13 個位元組。若改用 Protocol Buffers 定義 uint32 pages = 1;，整數 150 以 Varint 編碼為 0x96 0x01（2 bytes），加上欄位標籤 (1 << 3) | 0 = 0x08（1 byte），總共僅需 3 個位元組。對於高頻交換且以數值型別為主的微服務鏈路，Protobuf 能直接為網路頻寬省下 60% 至 80% 的傳輸負載。相關底層細節可參考 Protobuf 傳輸編碼規範。

致命的數值精度踩坑案例。在微服務實務中，一個極具隱蔽性的 Bug 源自於雪花演算法（Snowflake ID）與 JSON 的結合。雪花演算法產生的 64 位元整數 ID 最大可達 $2^{63}-1$；然而在 JavaScript 與多數現代動態語言中，預設的數值型別依循 IEEE 754 雙精度浮點數，其精確整數表示的安全上限僅為 $2^{53}-1$（9,007,199,254,740,991）。一旦租戶或訂單 ID 超過這個數值，前端在 JSON.parse() 後末兩位數值將會自動被四捨五入改寫，導致使用者更新了別人的資料！RFC 8259 第 6 節特別警告了不同語言實作對數值精度的互通性陷阱。最佳實踐是：所有只做識別而不做算術運算的 64 位元 ID，在 API 與 JSON 序列化中一律強制宣告為字串型別。

Schema 平滑演進的鐵則。分散式系統的一大常態是：新舊版本的微服務會長期並存。在 Protobuf 的架構演進中，刪除舊欄位時必須明確宣告 reserved 其欄位編號與名稱。若有新工程師未來重新使用了同一個 Tag 編號，歷史舊訊息或尚未升級的消費者在解析時，就會把舊欄位的值錯解為完全不同的新欄位型態，造成致命的業務語意污染，詳見 Protobuf 欄位廢棄規範。同樣地，若要對訊息進行數位簽章或快取鍵計算，絕不能直接對序列化後的位元組做雜湊，因為不同語言實作的 Key 排序可能不同，必須先經過嚴格的正規化（Canonicalization）處理。

常見錯誤：把微基準測試中的序列化耗時等同於真實生產環境表現；認為「只要新增欄位就絕對向下相容」；把 JSON 解碼成功等同於資料內容具備業務合法性；未限制 JSON 巢狀解析深度或未限制 Gzip 解壓後的最大體積（引發 Zip Bomb 阻斷服務攻擊）。

練習：在 Protobuf 定義中，如果將 uint32 page_count = 1; 改名為 uint32 pages = 1;，在二進位通訊層上是否相容？

在純二進位 Wire 格式層面上是相容的，因為二進位封包中只傳遞 Tag 編號（1）與 Varint 數值，根本不包含變數名稱。然而，在以 JSON 映射（JSON Mapping）、反射（Reflection）、前端產生的 SDK 或日誌監控依賴欄位名稱的系統中，這項改動仍會引發相容性崩潰。更重要的是，若業務語意改變（例如從「總頁數」變成「已完成頁數」），就絕不能沿用舊 Tag，必須建立全新的欄位並妥善規劃雙寫遷移。

4.6 訊息確認（Message acknowledgment）

在分散式系統中，「確認（Acknowledgment, ACK）」是一個被嚴重濫用的詞彙。當一個工程師說「訊息已經 ACK 了」，你必須第一時間追問：這是哪一層網路協定？哪個實體發出的？到底在何時發出的？TCP ACK 只代表傳輸層封包已經寫入目標作業系統的核心緩衝區；訊息代理的 Publisher Confirm 代表訊息已抵達 Broker 並按規則持久化；而 Consumer ACK 則代表消費者已接管責任，Broker 可以將該訊息自待派發佇列中安全刪除。這三者彼此獨立，任何一個環節都無法替代另一個。

以 RabbitMQ 為例，其架構清晰地劃分了兩種確認語意：發布確認（Publisher Confirms）與消費確認（Consumer Acknowledgements）。自動 ACK 雖然簡單，但在高可用架構下是自殺行為——當訊息剛從 Socket 讀出就被自動 ACK，若 Worker 隨即崩潰，該訊息將在世界上徹底失蹤。因此，嚴肅的系統必須採用手動 ACK（Manual ACK）。更詳細的機制請參考 RabbitMQ 確認機制文檔 與 可靠性指南。

Publisher Confirm 的黑洞陷阱。許多工程師誤以為「只要收到 Broker 回傳的 Publisher ACK，訊息就一定安全進入佇列了」。這是一個極其危險的誤解！在 RabbitMQ 預設行為中，若訊息發送至 Exchange 後，發現完全沒有任何 Queue 與之綁定，Broker 依然會毫無保留地向發送端回傳 ACK，隨後默默將訊息丟進黑洞銷毀！要防堵這個慘劇，發送端必須在發布訊息時設定 mandatory=true。當訊息無法路由時，Broker 會先回傳一則 basic.return 告知路由失敗，隨後才送出 ACK。發送端程式必須監聽 Return 事件，將 Outbox 表中的紀錄保留重試，並立即發出告警檢查 Exchange 與 Queue 之間的 Binding 拓撲。

針對消費者端的時序，唯一的正確防線是：先將業務結果、工作狀態變更與事件去重記錄一併在資料庫交易中成功提交，最後才能向 Broker 發送 ACK。若在提交與 ACK 之間程序崩潰或網路中斷，Broker 會在連線關閉後將訊息重新投遞給其他 Worker。此時新接手的 Worker 會在交易中發現該 event_id 已存在於去重表，確認意圖相同後直接返回既有結果並補發 ACK。這個模式徹底守住了「至少一次（At-Least-Once）投遞」下的業務正確性。

消費端預取限制（Prefetch Count）與記憶體容量。消費端在連線時必須合理設定預取數量（Prefetch）。假設系統每秒處理 200 件辨識任務，每件從接收到資料庫持久化平均耗時 0.4 秒，平均並行在途工作量約為 $200 \times 0.4 = 80$ 件。若每份 PDF 載入記憶體解析需要 2 MiB，光是在途任務的記憶體淨開銷就達到 160 MiB。如果工程師把 Prefetch 設成無上限（預設值），單一最快啟動的 Worker 可能一口氣把 Broker 裡的數千則任務全部抓進本機記憶體，造成單機記憶體爆表崩潰；同時其他剛啟動的 Worker 卻無事可做，發生嚴重的負載傾斜。將 Prefetch 設為可用 CPU 核心數量的 1 到 2 倍，是兼顧高吞吐與故障容錯的最佳折衷。

常見錯誤：把「至少一次投遞」妄想為「系統保證最終必定成功」；誤以為只要訊息系統支援「精確一次（Exactly-Once）」，外部世界的所有副作用（如扣款、發信）就真的只會發生一次；以及收到郵件供應商的 HTTP 200 就宣稱「用戶已成功讀取信件」。任何可靠性承諾都必須標註儲存期限、重試策略、去重邊界與對帳手段。

練習：平台呼叫外部第三方郵件 API 寄送完成信，但因網路超時未收到回應。此時可以立刻生成一個全新的 notification_id 重新呼叫嗎？

絕對不行。在網路超時的當下，第三方的真實狀態是「結果未知」——郵件可能早已成功寄出。如果換上全新的 notification_id，第三方系統會將其視為全新請求，導致使用者收到兩封一模一樣的重複通知。正確做法是：沿用原本的業務冪等鍵（Idempotency Key）進行重試，或主動發起狀態查詢端點確認該工作是否已成立。

本章帶走的設計思維：把任務提交回應與最終處理結果徹底分開；為每一則訊息明確定義唯一的責任歸屬與結構版本；切記網路傳輸、執行緒排程、資料編碼與 ACK 確認各自都只提供極其有限的保證。下一章我們將探討由重試帶來的重複資料，以及因頻繁查詢引發的負載挑戰：快取必須為系統的正確性邊界服務，而不是用來掩蓋糟糕的架構瑕疵。
