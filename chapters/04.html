第 04 章

一次請求穿過網路之後

請求送出、對方收到、業務提交、回覆抵達，各有一個時間點。把它們放上同一條時間軸，就能理解同步、訊息、ACK 與重試。

先回任務ID，之後怎麼交結果

同步呼叫把結果放在同一次往返內交付。查詢文件狀態通常適合這種方式：客戶送出請求，API 讀資料後回傳。長時間 OCR 則可先保存任務並回 202 與 job_id，之後查詢或接收事件取得結果。

非同步流程把「受理」和「完成」各自變成可查狀態。接收端在保存任務與 outbox 發送意圖的同一筆交易提交後回覆；背景發送器投遞工作，worker 完成後保存結果。重試提交沿用操作 ID，就能找到原任務。

時間預算跟著使用者路徑走。若狀態查詢總預算 800 ms，閘道已花 100 ms，下游取得的是剩餘預算；逾時後把取消訊號傳到仍在執行的工作，能釋放連線與其他資源。

畫面收到 202，應顯示什麼狀態？

看推導

顯示「已提交」與任務進度入口。查到持久化的 succeeded 結果後，再顯示「完成」。

三台worker分工，三種功能各收一份

工作佇列把每份工作交給一個處理者，適合多台 OCR worker 分工。發布訂閱讓多種功能各自收到事件，適合辨識完成後同時更新搜尋、通知和稽核。可重播日誌則讓每個群組維護自己的讀取位置，落後的群組之後追上。

同一消費群組內的成員分攤工作；不同群組各自讀一份事件。若通知與稽核需要每筆都收到，就讓它們有獨立進度。訊息正文帶穩定事件 ID、資源版本與必要參數，消費端可以辨認重送與過時事件。

資料庫提交與訊息投遞跨越兩個系統時，outbox 把「要發出哪則事件」先與業務狀態一起保存。發送器可重試，消費者按事件 ID 處理重複，兩邊各自有明確恢復位置。

三台寄信 worker 應使用一個消費群組，還是各一個？

看推導

若每封信只需由其中一台處理，放同一群組分工。每台獨立群組會使每封信被三個群組各讀一次。

位元組送到了，業務走到哪裡

TCP 提供有序位元組流；應用程式用長度欄位或訊息格式辨識邊界。UDP 傳送資料報，應用依需求處理遺失、順序與重送。QUIC 建在 UDP 上，把可靠多串流與加密連線整合進傳輸層，HTTP/3 使用這套傳輸。

可靠傳輸會確保交付的位元組符合協定；業務是否保存結果，仍由應用層回覆與狀態決定。選 HTTP API 時，同時設連線與整體請求期限，確認 DNS、TLS 建連和連線池等待在哪個預算內。

HTTP/2 的多個串流共用一條 TCP 連線，TCP 遺失造成的有序交付等待可能一起阻塞它們。QUIC 各串流有自己的資料順序，能縮小這類串流間阻塞；應用共享的 CPU、資料庫和流量控制仍要各自配置。

接收端實際拿到什麼？

協定交付單位與行為應用如何接續
TCP有序、可靠的位元組串流以長度或分隔規則解析訊息；以業務回應確認提交
UDP一份份資料報，可能遺失或換順序依需求加入序號、重送與到期處理
QUIC在 UDP 上建立安全連線與多條可靠串流各串流獨立交付資料，連線共用壅塞與流量預算
HTTP方法、狀態碼、標頭與內容的語義202 後以 job_id 查進度；結果提交後呈現成功

TCP 成功傳送請求後，客戶沒收到應用回覆，接著如何知道工作結果？

看推導

用原操作 ID 查詢狀態，或以相同 ID 做具冪等語意的重試。業務結果可能尚未產生，也可能已提交而回覆遺失。

等待兩秒，需要多少在途資源

阻塞 I/O 讓執行緒等操作結束；非阻塞 I/O 讓執行緒先處理別的工作，待 socket 就緒後再繼續。事件迴圈特別適合大量等待網路的連線，CPU 密集的轉檔仍會占用計算時間，適合另交給工作池。

用 Little's Law 估算等待中的資源：每秒 100 個外部請求、平均等待兩秒，平均約有 200 個請求在途。改用 async 後，執行緒數可以下降，但每個請求仍持有 socket、緩衝區與狀態。並行上限應對準下游容量與本地記憶體。

    while connection.read_budget_remaining():
        data = nonblocking_read(connection)
        if data == WOULD_BLOCK:
            return
        if data == EOF:
            close_and_record_state(connection)
            return
        append_to_bounded_buffer(data)

每次只讀取有限資料量，再讓事件迴圈服務其他連線。輸入緩衝或 worker 佇列滿時，暫停讀取或回覆忙碌，把背壓傳回上游。

事件迴圈內執行五秒的純 CPU 轉檔，其他連線會怎樣？

看推導

在該迴圈有機會讓出執行權之前，其他回呼會等待。把 CPU 工作交給其他程序或適當的工作執行緒，讓 I/O 迴圈維持短工作。

同一份資料，怎麼讓新舊服務都讀懂

資料格式影響傳輸大小、解析成本與升級方式。JSON 容易閱讀與除錯，Protobuf 以欄位編號與型別編碼，適合有明確 schema 的服務通訊。比較時用實際 payload 量大小與 CPU，而非只看格式名稱。

版本演進最常踩到的是欄位含義改變。新增可選欄位通常容易逐步部署；刪除 Protobuf 欄位後應保留其編號，避免舊資料被新欄位誤讀。金額用整數最小貨幣單位或明確 decimal；跨 JavaScript 的大整數 ID 可編成字串，避免超過安全整數範圍。

事件同時需要 schema 版本與資源版本：前者說明如何解析，後者說明狀態的新舊。消費者看到較舊資源版本時，才能選擇略過或依事件模型累加。

把新舊版本一起放進格式選擇

讀寫情境候選表示一起決定的規則
跨組織 API 與人工除錯JSON大型整數、日期、重複鍵、未知欄位與大小限制
受控服務與產生型別程式碼Protobuf 等 schema 格式新舊讀者共存，刪除後保留欄位編號
大量離線分析欄式檔案與分區布局常讀哪些欄、過濾哪些區間、資料如何壓縮

64-bit ID 大於 2^53−1，透過 JSON 傳給 JavaScript 時如何保留精度？

看推導

把 ID 編碼成字串，兩端約定字串格式。若用 JSON number 並轉成 JavaScript Number，部分整數會被四捨五入。

ACK應該在提交前，還是提交後

ACK 是接收方對某一步的確認。Broker 確認已接收、consumer 確認已處理、資料庫確認已提交，對應不同完成點。把每個 ACK 旁寫上它確認的狀態，就能沿故障路徑判斷下一步。

consumer 在業務提交前確認訊息，之後崩潰可能使工作被移出待處理集合；提交後才確認，若 ACK 遺失則可能再次收到相同工作。常見做法是先原子提交業務效果與事件 ID，再 ACK，重送時重用既有結果。

多個工作並行完成時，進度要提交到連續完成的前綴。例如 10、12、13 完成，11 尚未完成，將「下一筆要讀」提交為 11；等 11 完成再前進到 14。這讓故障重啟能重新取得未完成的缺口。

業務已完成但 ACK 遺失，重送到另一台 worker 時如何避免再次收費？

看推導

以同一事件 ID 查持久化的處理紀錄，並讓這份紀錄與收費狀態在同一原子提交範圍內保存。另一台 worker 因而能回傳先前結果。
