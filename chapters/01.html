第 01 章 · Introduction

導論：從需求推導架構

系統設計不是在比誰背的元件多，而是一連串可以被檢驗的取捨與決定：你要為誰解決問題、承載怎樣的流量波動、哪些錯誤絕對無法容忍，以及團隊願意為了這些保證付出多少資源與維運成本。

1.1 課程介紹（Course introduction）

想像你正在接手一個多租戶（multi-tenant）的文件處理與通知平台。公司的企業客戶會上傳各類文件，系統必須把原件轉成可預覽的格式、擷取內文關鍵字，讓用戶隨時查詢進度，最後在處理完成時以 Email 或 Webhook 發送通知。最單純的第一版可能很直覺：一台應用程式伺服器、一個資料庫，再加上一個檔案儲存空間。只要能把功能跑通，它就是一個完整且能創造價值的系統；至於什麼時候該引入訊息佇列、快取快取層、資料分片或跨區域部署，絕不是憑感覺提早套用，而是要看實際遇到了什麼瓶頸與數據證據。

在一般寫演算法題時，輸入規模、輸出格式和單機環境往往是預先給定的。但在分散式系統設計裡，最關鍵的第一步反而是釐清邊界：上傳者最多能容忍等幾秒？同一個文件會不會因為網路抖動被重複上傳？轉檔成功但通知失敗，對用戶來說算不算完成？如果某個大客戶突然在尖峰時段灌入十萬份文件，會不會把共用資源吃光，連帶拖垮其他租戶？這些問題會直接決定 API 契約、資料模型與容錯策略。要是略過這些前提，就算架構圖上畫滿了最時髦的分散式元件，也沒人能斷定這套設計到底合不合理。

本書會貫徹一套實戰思考法，用四個問題檢驗每個設計決策：主張、理由、代價、驗證。舉例來說，如果主張是「把轉檔移到背景非同步工作」，理由是「避免耗時的轉檔卡住 API 請求」，那麼代價就是「使用者必須接受狀態延後完成，前端也需要能查詢進度」；而驗證方式則是「實測 API 接收延遲、佇列排隊時間、端到端完成率，以及 worker 崩潰後的重試復原」。光說一句「用 Queue 來提升效能」是遠遠不夠的，因為佇列本身並不會憑空變出運算能力，如果後端處理速度跟不上，它只會把系統過載包裝成越來越漫長、甚至無上限的排隊等待。

為了讓後續章節的容量估算有一致的基準，我們先設定一組貼近實務的教學假設：平台服務一萬個企業租戶，全天處理一百萬份文件；每份原件平均大小為 5 MB，尖峰時段的抵達速率約為全天平均的十倍，而每份轉檔平均需耗用 2 個 CPU-seconds。後續所有關於頻寬、儲存量與運算資源的計算，都會圍繞著這組負載展開。除特別註明外，本書提到的 MB、GB、TB 均採十進位計算，MiB、GiB 則採二進位標準。若特定章節有調整假設，會在題目中明確標出。

每日秒數 = 24 × 60 × 60 = 86,400
平均到達率 = 1,000,000 ÷ 86,400 ≈ 11.57 份／秒
尖峰到達率 ≈ 115.74 份／秒
每日原件大小 = 1,000,000 × 5 MB = 5 TB

容量估算心法：平均每秒 11.57 份只是全天的平攤值。在實際系統規劃中，千萬不能拿平均值當作容量標準，必須針對五分鐘尖峰突發、大檔案極端值、重試雪崩，以及大客戶集中灌入流量等極端情境預留彈性。

實戰思考：如果業務或產品經理提出「我們的系統必須做到即時處理」，身為工程師，你必須追問哪兩個關鍵問題？又該如何把這句話轉換成工程上能驗證的具體指標？

參考解答與推理

首先要追問：「這裡說的『即時』，是指客戶收到『系統已收件』的確認回應，還是指『拿到轉檔結果』？」接著再問：「這個目標適用於哪些檔案格式、多大的容量上限，又是在多大的併發流量下成立？」一個可測量的替代需求可以這樣寫：「在每秒 100 份、單檔不大於 10 MB 的合法 PDF 負載下，99% 的上傳接收請求需在 300 ms 內回覆完成；且 95% 成功接收的任務需在 60 秒內轉檔完畢。」把接收與處理拆開來量測，才不會讓一個看似很快的 202 回應掩蓋了背後嚴重的佇列積壓。

1.2 適合誰學習（Who will benefit from the course and how）

如果你已經能獨立寫出跑得動的 Web 服務，但在面對「如果流量成長十倍要怎麼擴充」或「資料庫突然掛掉時使用者會看到什麼」這類問題時感到猶豫，這本教材就是為你設計的。無論是正在準備系統設計面試的工程師、需要跨團隊評估架構取捨的 Tech Lead，或是想搞懂 SLA 承諾與雲端帳單關聯的產品負責人，都能從中獲益。不同崗位或許不需要鑽研完全相同的實作細節，但都必須具備將架構決策與終端用戶價值連結起來的能力。

閱讀本書所需的先備知識並不嚴苛：只要懂得基本函式、常用資料結構、HTTP 請求原理，以及對關聯式資料庫有讀寫操作的經驗即可。你完全不需要先成為 Kubernetes 大師或雲端認證專家。在面對各種陌生名詞時，最實用的習慣是先問它到底在解決哪種物理約束：負載平衡是為了解決單點吞吐限制；複寫是為了解決單機故障時的資料可用性；分片是為了解決單一儲存節點的容量瓶頸；快取則是為了減少昂貴的重複計算與磁碟讀取。很多產品名稱看起來相近，背後的語意保證與失效模式卻大相逕庭。

讀者情境建議練習方式學習後能展現的成果
初涉後端架構先理清一條端到端的請求路徑，再標記所有會持久化狀態的節點能把接收、處理、失敗、重試四種生命週期說得一清二楚
準備系統設計面試先主動用假設限縮邊界，再挑選一到兩個核心瓶頸深入剖析能在有限時間內對比兩種方案的優缺點，並清楚解釋不選另一個的具體原因
維運線上既有系統從歷史事故與監控指標中，揪出當初架構假設與現實脫節的地方能提出具備灰度驗證、可快速回滾且有明確停止條件的重構方案
產品經理與技術主管把空泛的「又要快、又要穩、又要省錢」轉化為有明確邊界的 SLA 承諾能清楚預判每提高一個可用性層級，會連帶增加多少工程成本與架構複雜度

在學習過程中，建議拿同一個業務案例做三種不同規模的迭代練習。第一次只規劃服務十個企業客戶、每天一千份文件，目標是把流程做正確，並盡可能維持最低的維運負擔；第二次將規模放大到一萬家客戶、每日百萬份文件，這時就必須認真推導容量並加入多租戶資源隔離；第三次則帶入極端故障情境：例如單一可用區（AZ）完全斷電、第三方通知供應商中斷服務一小時，或是某個租戶惡意灌入大量壞檔案。這種分階段思考能幫你理清：哪些架構可以沿用，哪些機制必須升級，而不是一開始就把第三階段才需要的複雜度全部塞進第一版設計中。

評估架構能力的高低，關鍵在於「能否推導出系統行為」，而不僅僅是「能否背出名詞定義」。許多人能倒背 eventual consistency（最終一致性），卻無法解釋當使用者剛點擊刪除檔案時，為什麼同一秒在搜尋列還能搜出該筆資料；但偏偏就是這些細節，會直接衝擊前端介面呈現、權限校驗與客服成本。如果你能在白板前明確指出「搜尋索引可以接受秒級非同步延遲，但下載原檔時的授權檢查必須對權威資料庫進行即時校驗」，你就已經把抽象的理論轉化為明確的系統工程邊界了。

常見思維誤區：盲目套用一線科技巨頭超大規模架構的設計。架構圖上每多劃一個微服務，團隊就得額外承擔一整套部署、鏈路追蹤、鑑權、網路逾時與版本兼容的維護開銷。對於早期團隊來說，一個架構乾淨的模組化單體配合雲端託管資料庫，往往比盲目拼裝十幾種分散式開源工具更可靠、更容易落地。

實戰思考：如果你的團隊只有三位工程師、專案必須在六週內上線，預估每日文件量僅有一千份。這時有同事提議第一天就採用跨區域 Active-Active 雙活架構並自建分庫分表，你會如何給出有說服力且具體的評估？

參考解答與推理

不要直接否定或只說好與不好，而是從限制與成本切入。先確認業務是否存在嚴格的跨國低延遲要求、政府資料在地化法規，或不可妥協的跨區域災難復原指標。如果沒有這些前提，最合理的選擇是先以單一區域多可用區的託管資料庫、簡單的工作佇列與模組化架構快速驗證業務價值；同時在資料表預留 tenant_id 與乾淨的 API 介面，為未來的水平擴充鋪路。反之，如果業務真的有極端的區域災難指標，就必須坦白說明：以目前的時程與人力，必須重新調整功能範圍或採用昂貴的雲端全託管方案。架構選擇靠的是約束與取捨，而不是個人的技術偏好。

1.3 課程總覽與學習方法（Course overview）

本書的學習路徑是層層遞進的：從最源頭的需求分析開始，走過底層硬體與網路通訊，再深入探討 API 設計、儲存引擎、快取機制、非同步訊息傳遞與分散式協調，最終彙整至完整的端到端實戰案例。這樣的編排有嚴密的因果邏輯：如果連要保護哪條核心用戶旅程都還沒說清楚，你就無法定義什麼叫可用性；如果不知道資料在實體硬體上的搬運成本，就無法評估跨網路呼叫的真實代價；而如果不知道網路呼叫隨時可能卡住或失敗，就根本不可能設計出安全的重試機制。後面介紹的先進元件，永遠無法掩蓋前面邏輯推導上的漏洞。

在研讀每個章節時，建議隨手維護一份屬於你自己的「架構決策紀錄（Design Log）」。第一欄寫明具體的需求目標與業務假設；第二欄記錄當下採用的技術方案；第三欄寫下被你否決或決定暫緩的備選方案與理由；第四欄則清楚定義「看到什麼監控指標或事件時，必須重新啟動評估」。舉例來說，紀錄中寫的「現階段暫不進行資料分庫分表」，並不代表永遠不分，而是清楚約定「當主資料庫磁碟容量達到 70%、單次寫入延遲超過 100 ms 或維護窗口無法完成索引重建時，立刻重啟分片討論」。這樣的紀錄，比單純留下一張看似完美的最終架構圖，更能幫助團隊在未來穩健演進與交接。

  1. 澄清需求：列出核心用戶、關鍵行為路徑、成功條件、排除事項與品質承諾。
  2. 推導規模：算出每秒請求量（QPS）、儲存增長速率、網路頻寬消耗與併發工作量；每個數字都要附上嚴謹單位。
  3. 提出最小可行架構：確保資料從客戶端輸入到最終結果落地，每一段路徑都有明確的負責元件。
  4. 走查失敗情境：在每一次網路呼叫、資料庫寫入與對外通知之間，假設程序隨時可能斷線或崩潰。
  5. 鎖定真正瓶頸並迭代：只針對經過驗證的瓶頸增加機制，並同步寫下新機制帶來了哪些複雜度與風險。
  6. 定義驗證數據：設計負載測試腳本、故障復原演練、權限邊界測試與端到端業務監控指標。

在典型的四十五分鐘系統設計面試或技術討論中，時間分配可以這樣掌握：前 8 分鐘專注於釐清業務邊界與流量估算，接下來 10 分鐘畫出端到端可行的主流程架構，隨後 15 分鐘挑出一到兩個最核心的技術瓶頸深入探討，最後 12 分鐘盤點極端故障應對、架構取捨與未來演進方向。這是一場有節奏的技術溝通，而不是一個人的自言自語。

以同一個「確保任務提交後絕不丟失」的需求為例，你可以選擇用關聯式資料庫的任務狀態表、高可用訊息佇列，或是 Transactional Outbox 模式來實現。在評估方案時，務必清楚交代資料在何時算提交成功、重試責任落在誰身上，以及系統重啟後如何恢復未完成的工作。善用官方文件確認元件的語意保證，研讀原始論文核對演算法的前提假設，並用真實世界的基準測試來決定你的硬體容量規劃。

常見思維誤區：只看不動腦的「直接看解答」。在看到內文寫「此處加入重試」時，先停下來問自己：這個重試會不會不小心建立了兩份重複的轉檔任務？由誰來避免重試風暴把下游打垮？如果原本的請求狀態不明該怎麼辦？先帶著問題思考，再去看後續的保護機制，這樣鍛鍊出來的工程直覺才會真正屬於你。

實戰思考：線上監控回報「API 的 p99 延遲非常健康，但客戶卻不斷投訴系統很慢」。請列出三個可能被監控遺漏的延遲盲點，並說明下一步該如何調查？

參考解答與推理

這通常代表監控測量的範圍不完整。可能遺漏的盲點包括：客戶端上傳大型檔案的網路傳輸時間、任務進入內部佇列後的排隊等待時間，或是後端處理完畢後等待第三方通知發送的延遲；另一種可能是監控只計算了成功到達應用伺服器的請求，卻完全漏掉了前端 DNS 解析超時或連線建立失敗的請求。下一步應該為每個 job_id 埋點記錄關鍵事件節點（如 upload_completed、accepted、started、result_committed、notification_sent），並依據租戶與檔案類型拉出真實的端到端耗時分布。如果系統涉及微服務，務必把分散式追蹤識別碼（Trace ID）貫穿整條呼叫鏈；切記不要盲目加快取，因為你連到底卡在哪個環節都還沒弄清楚。

本章精華：架構設計的專業度，取決於你能否用明確的數據、邊界假設、故障推導與驗證方案來說明你的技術選擇。永遠先完成一條端到端可驗證的核心路徑，再逐步疊加規模與容錯機制。
