第 01 章 · Introduction

導論：從需求推導架構，而不是收集元件名稱

系統設計是一連串可被檢驗的決定：誰需要什麼結果、負載如何變動、哪些錯誤不能接受，以及團隊願意付出多少成本。本教材依公開課綱的主題範圍，透過完整案例、圖解與練習建立系統設計能力。

1.1 課程介紹（Course introduction）

想像你要開發一個多租戶文件處理與通知平台。公司客戶上傳文件，系統將它轉成可預覽的格式，擷取文字，讓使用者查詢進度，最後以電子郵件或 webhook 通知完成。第一個版本可能只需要一個應用程式、一個資料庫、一個檔案儲存空間。這已是一個完整系統；是否需要訊息佇列、快取、分片或多區域部署，必須由後續證據決定。

演算法設計常把輸入、輸出與機器模型先固定。系統設計則要先建立這些邊界：上傳者能等待多久？同一個文件會不會被重送？處理成功但通知失敗算完成嗎？某個租戶一次送入十萬份文件，是否能拖慢其他租戶？這些問題會決定 API、資料模型與故障策略。若省略它們，即使圖上畫滿知名產品，也無法判定架構是否正確。

本書以「主張、理由、代價、驗證」四件事檢查每個設計。例如主張是「把轉檔移到背景工作」，理由是讓短 API 請求不必等待長工作，代價是使用者要接受非同步狀態與延後完成，驗證方式則是測量 API 接收延遲、佇列等待時間、端到端完成時間，以及故障後的重試結果。僅說「用 queue 提升效能」還不夠，因為佇列本身不會增加處理能力，還可能把過載隱藏成越來越長的等待。

為了讓算例能重算，先設定一組教學假設：一萬個租戶，每日一百萬份文件，平均原件為 5 MB，尖峰到達率是全天平均的十倍，每份轉換平均耗用 2 CPU-seconds。這組工作負載作為後續容量推導的共同基準。除另行說明，MB、GB、TB 使用十進位，MiB、GiB 使用二進位。後續章節若改變假設，會在題目內明列。

每日秒數 = 24 × 60 × 60 = 86,400
平均到達率 = 1,000,000 ÷ 86,400 ≈ 11.57 份／秒
尖峰到達率 ≈ 115.74 份／秒
每日原件大小 = 1,000,000 × 5 MB = 5 TB

常見誤區：把估算的小數位當成精準程度。11.57 份／秒是平均值的算術結果，不能證明實際流量均勻；對容量規劃更重要的可能是五分鐘尖峰、最大文件大小、重試比例和單一大租戶的集中流量。

練習：文件平台的銷售說「我們要做到即時處理」。請寫出兩個必須追問的問題，並提出一個可測量的替代需求。

參考解答與推理

先問「即時是指收到接收回覆，還是拿到轉換結果？」以及「適用哪些格式與大小、在多大的流量下？」替代需求可以是：「在每秒 100 份、單份不超過 10 MB 的已驗證 PDF 工作負載下，99% 的接收請求於 300 ms 內完成；95% 的成功接收任務於 60 秒內完成轉換。」接收與完成分開衡量，避免用很快的 202 回覆掩蓋背景積壓；具體數值仍需產品同意與壓力測試。

1.2 適合誰學習（Who will benefit from the course and how）

如果你能寫一個能運作的服務，卻不知道如何回答「流量變十倍怎麼辦」或「資料庫壞掉時使用者看見什麼」，本教材就適合你。它也適合準備系統設計面試的工程師、需要跨團隊討論取捨的技術主管，以及要理解成本與可靠度承諾的產品協作者。不同角色不必記住相同細節，但都應能把架構決定連回使用者價值。

最低先備知識是函式、常見資料結構、基本 HTTP 請求，以及讀寫資料庫的概念。你不必先精通 Kubernetes 或某個雲端平台。遇到陌生術語時，先問它解決哪種約束：負載平衡處理請求如何分配；複寫處理資料如何有多個副本；分片處理資料如何分散；快取處理重複計算或讀取如何減少。相似的產品名稱不代表相同的語意與失敗模式。

讀者情境應練習的行為完成後能展示的成果
初次學習後端設計先畫一條完整請求路徑，再找出持久狀態說清楚接收、完成、失敗、重試四種情況
準備面試用假設縮小題目，挑一個瓶頸深入在有限時間內比較兩種方案，說明不選另一種的原因
維運既有系統從事件與指標找出錯誤假設提出可回滾的改動、驗證方法與停止條件
產品或技術主管把「快速、可靠、便宜」改成有邊界的承諾知道提高哪個目標會增加哪些成本與交付風險

請用同一個案例做三次練習。第一次只服務十個租戶，每日一千份文件，重點是正確性與最小運維負擔。第二次改成一萬租戶、每日一百萬份，加入流量隔離與容量估算。第三次假設一個可用區失效、通知供應商中斷一小時、某租戶上傳惡意文件。設計時要說明哪些機制可以保留、哪些必須升級；第三階段才需要的複雜度，不必提前全部塞進第一版。

評估能力時，要區分「背得出名詞」與「能推出行為」。你可能知道 eventual consistency 的翻譯，卻無法說明使用者剛刪除文件後，為何搜尋結果還短暫出現它。後者才會影響介面、授權與客服。如果你能指出「搜尋索引可延遲更新，但下載授權仍要檢查權威狀態」，就已把抽象一致性轉成可實作的責任邊界。

常見誤區：拿大公司的最大規模架構當成唯一答案。多一個服務，就多一組部署、觀測、權限、網路與版本協調工作。小團隊選擇模組化單體和託管資料庫，可能比自建十種分散式元件更符合需求。

練習：你只有三位工程師、六週開發期，預計每日一千份文件。一位同事提議第一天就採用跨區域主動主動部署與自建分片資料庫。請提出有條件的評估，而不是直接說好或不好。

參考解答與推理

先問是否存在跨區域連續營運、資料在地化或既有平台限制。若沒有，先以單區域多可用區的託管儲存、簡單工作佇列和模組化服務驗證產品較合理；保留 tenant_id、明確 API 與資料匯出能力作為演進基礎。若有不可妥協的區域災難目標，就需重新談交付時間、功能範圍或採用具備相應能力的託管方案。選擇架構時，把約束和理由說清楚，個人偏好不足以支持決定。

1.3 課程總覽與學習方法（Course overview）

學習路徑從需求開始，經過硬體與網路，再走向 API、儲存、快取、訊息傳遞、分散式協調以及整體案例。這個順序有因果關係：不知道要保護哪個使用者旅程，就無法定義可用性；不知道資料住在哪裡，就無法推導一次遠端存取的代價；不知道失敗可能發生在哪一步，就無法設計安全重試。後面的元件不會取代前面的推理。

閱讀每一節時，請在紙上維護一份「設計紀錄」。第一欄寫需求與假設，第二欄寫目前方案，第三欄寫拒絕或延後的方案及理由，第四欄寫什麼觀測會觸發重審。例如「暫不分片」並非永遠不分片，而是當資料庫容量、寫入延遲或維護窗口出現已定義的門檻時重新評估。這樣的紀錄比只有最終架構圖更能幫助交接。

  1. 澄清需求：列使用者、核心行為、成功條件、排除事項與品質目標。
  2. 估計規模：算請求率、儲存增長、資料傳輸與同時工作數；每個數字附單位。
  3. 提出最小完整方案：確保從輸入到可見結果都有責任歸屬。
  4. 走查失敗：在每次網路呼叫、狀態寫入和外部副作用之間，想像程序隨時中斷。
  5. 定位限制並演進：只對確定的瓶頸加機制，寫出它引入的新風險。
  6. 定義證據：安排負載測試、還原演練、權限測試和使用者旅程指標。

面試可將同樣的方法壓縮。例如四十五分鐘的練習，先用約八分鐘確認需求與負載，十分鐘提出可行主流程，十五分鐘深入一至兩個關鍵問題，最後整理故障、取捨與演進。面試時可依對話進度調整時間分配。實務設計則應有更多測量、原型、安全審查與團隊評估，不能把白板上的合理假設當成上線證據。

本書的例題解答刻意揭露假設，不要求唯一產品組合。例如同一個「任務提交後不遺失」需求，可以透過資料庫任務表、可靠佇列，或交易式 outbox 達成不同程度的保證。學習重點是能指出提交與確認的邊界、誰負責重試，以及哪一種故障仍可能留下不一致。官方文件用來確認語意，原始論文用來確認定理的適用條件；教學數字用於練習推導；採購規格則根據實際量測制定。

常見誤區：只讀解答、不先做預測。看到「加入重試」時，先自己問重試是否會建立第二份任務、誰負責限制重試量、原請求的結果不明時怎麼辦，再讀後面的機制。你要練的是建立問題的能力。

練習：平台回報「API p99 很快，但客戶一直抱怨慢」。列出三個可能漏量的時間區段，並寫出一個下一步調查。

參考解答與推理

可能漏了上傳大型文件的時間、任務在佇列等待的時間，以及處理完成後等待通知的時間；也可能只量到達後端的請求，漏掉 DNS 或連線失敗。下一步為每個 job_id 記錄 upload_completed、accepted、started、result_committed、notification_accepted 等事件，以相同租戶與工作類型比較端到端分布。若處理鏈跨服務，應把追蹤識別碼傳遞下去；不要先加快取，因為尚未找到慢在哪裡。

本章帶走：設計品質取決於能否用需求、單位、失敗情境與證據說明選擇。先完成一條可驗證的使用者旅程，再增加規模與故障條件。
