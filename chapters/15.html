短網址：從一次跳轉做到可撤銷

短網址聽起來只是「存一張對照表、回個轉址」。流量一上來，會讓架構開始卡住的是短碼怎麼發才不重複、熱門連結怎麼扛高併發，還有連結一停用，世界各地的快取多久能停掉舊導向。

連結可以停用，快取要多快跟上？

先選一個具體產品：使用者登入後建立公開短網址，可以修改目的地、設定到期日、停用連結，並查看大致的點擊趨勢。公開點擊不用登入；管理操作要驗證連結的擁有者。停用目標訂成六十秒內生效，這會直接決定快取策略。

產品選擇資料與路徑的變化
自訂短碼同一命名空間需要權威唯一性檢查
目的地可修改連結有版本，讀取快取要能更新
私人連結每次跳轉前加入身分與物件權限判斷
六十秒內停用快取有來源新鮮度上限，逾時就回權威狀態
近似點擊趨勢跳轉與統計分開處理，報表標示已處理到的時間

先畫一條建立路徑與一條跳轉路徑。建立量較小，集中處理唯一性與擁有權；跳轉量大，讓熱門讀取靠近使用者。統計在跳轉後非同步收集，避免報表系統的延遲直接加到每次點擊上。

客戶說停用後一秒內就要擋住，最先改哪個條件？

把每次跳轉的授權與連結狀態檢查放到能滿足一秒新鮮度的路徑，重新計算權威查詢量、快取期限與跨區延遲。再測一個刻意延遲失效通知的節點，確認它會在期限內停止使用舊狀態。

停用後，舊連結怎麼又回到快取？

使用者停用短網址，資料庫已經寫成 revoked；一個稍早開始的讀取卻在這時完成，準備把舊資料放回快取。先走一次這個時序，看「刪除快取」後為什麼還可能出現舊連結。

把流量與儲存換成同一套單位

假設每日建立一千萬筆短網址、十億次跳轉，尖峰是平均十倍。以下使用十進位 MB、GB、TB，方便把日量直接換算。

項目計算量級
建立10,000,000 ÷ 86,400平均 115.7／秒，尖峰約 1,157／秒
跳轉1,000,000,000 ÷ 86,400平均 11,574／秒，尖峰約 115,740／秒
一年新資料36.5 億筆 × 300 bytes1.095 TB；三份複本約 3.285 TB
點擊事件十億筆 × 120 bytes每天 120 GB

300 bytes 是本例平均紀錄大小，索引、資料庫頁面開銷與備份另算。目的地 URL 的長度分布也要量，少數很長的 URL 可能改變儲存與快取預算。

短碼的唯一性放在建立交易裡

八位 Base62 有 62⁸ = 218,340,105,584,896 種組合。已有 36.5 億筆時，下一次均勻抽樣撞到既有短碼的機率約 3.65×10⁹ ÷ 62⁸ ≈ 0.00167%。做法是使用合適的隨機來源產生候選碼，以資料庫唯一約束插入；碰撞就重抽。

若連續抽 36.5 億次，預期碰撞配對約有 n(n−1) ÷ (2M) ≈ 30,510 組。總空間很大時，長期仍會遇到碰撞；唯一約束把它變成建立流程中可重試的一步。短碼大小寫、字元集合與編碼規則固定，路由與資料庫使用相同的區分方式。

links(
  code PRIMARY KEY,
  owner_id,
  destination,
  status,
  created_at,
  expires_at,
  version
)
-- owner_id 的索引用於管理列表。
-- 建立請求另存 (owner_id, request_key) 唯一紀錄，
-- 相同鍵比對原目的地與設定後，回傳同一個 code。

同一自訂短碼由一個權威寫入位置裁決，或由具一致性保證的唯一性服務處理。跨區入口可以接請求，再送到該命名空間的權威節點；分配自動短碼也可以預先劃分彼此不重疊的命名空間。

API 對應到使用者看到的狀態

POST /links
Idempotency-Key: 同一次建立意圖的固定鍵
→ 201 { code, destination, version }

GET /{code}
→ 302
Location: https://example.org/page
Cache-Control: no-store

DELETE /links/{code}
→ 204

GET /links/{code}/stats
→ { clicks, complete_through }

這個產品允許修改與停用，所以以 302 回應，並要求瀏覽器與共享 HTTP 快取不儲存跳轉回應。伺服器內部仍可快取連結狀態，但會遵守六十秒的新鮮度目標。管理 API 每次檢查 owner 與物件權限，DELETE 留下停用狀態與較新版本。

建立時只接受產品支援的 http／https 目的地與合理長度，保留原有 query 等有意義的 URL 內容，避免破壞簽名連結。若產品還要抓預覽圖，抓取服務以固定網路政策限制內部位址，每次重新導向都重新檢查目的地，連線使用已驗證的解析結果，TLS 仍驗證原主機名稱。

熱門讀取與停用如何共存

跳轉先讀本地快取，再讀共享快取，最後查權威資料。熱門短碼的讀取可由快取與讀取複本分攤；不存在的短碼可短暫負快取，但自訂短碼剛建立時，要清除或越過舊的「不存在」結果。

看圖中的競爭：讀取 A 先拿到 v7；停用操作提交 v8 並清除快取；A 稍後把 v7 回填。解法之一是把 v8 的版本水位保留下來，回填時原子比較版本，拒絕比水位舊的值。版本水位的保留期間要涵蓋所有可能遲到的讀取；若它已被淘汰，回填流程重新向權威狀態確認。

再給每筆快取一個最後向權威狀態確認的時間。資料從共享快取複製到本地快取時延續這個時間，讓每一層都看見同一份資料的真實年齡。快取剩餘可用時間、時鐘誤差與在途請求時間，共同放進六十秒預算。達到上限就查最新狀態，權威服務無法查詢時，停止使用超過期限的舊連結。

停用短碼先保留 tombstone。若立刻把同一短碼分配給另一人，舊瀏覽器、快取與外部文件都可能指向新目的地；較簡單的產品規則是停用後保留該碼，不再分配。

點擊統計走自己的完成進度

跳轉成功後產生點擊事件，由佇列送到聚合服務，按短碼與時段累加。報表回傳 complete_through，讓讀者知道數字更新到何時。若產品接受近似趨勢，就明確量測重複與丟失量；涉及計費的事件則走持久受理、穩定事件識別與對帳流程。

兩個區域同時建立自訂短碼「sale」，怎麼選出一個擁有者？

讓同一命名空間的兩個建立請求在權威唯一性檢查處競爭，一個成功，另一個收到已佔用。若區域與權威節點斷線，就暫停該碼的建立，或改用已預分配、互不重疊的自動短碼空間。

用流水號再轉 Base62，跟隨機短碼有什麼差別？

流水號的唯一性由序號分配器提供，Base62 只是改變表示法。相鄰碼可被枚舉，也可能透露建立規模；隨機碼較難猜測，但建立時仍由唯一約束處理碰撞。私人連結在跳轉路徑檢查權限，短碼是否容易猜只影響被發現的難度。

本地快取 TTL 30 秒、共享快取 TTL 60 秒，舊值最多會活 90 秒嗎？

若本地每次取到共享快取資料都重新給滿 30 秒，就可能延長總年齡。把權威確認時間隨資料一起傳遞，本地 TTL 取「本地上限」與「全路徑剩餘新鮮度預算」較小值，就能把兩層放在同一條期限內。
