CHAPTER 15 · Practice, part 1

實戰一：從空白白板設計短網址系統

這題的表面是把長網址變短，真正要處理的是讀寫不對稱、名稱唯一性、熱門鍵、快取撤銷與濫用。以下是一份有明確邊界、可以被追問與測試的完整解題示範。

15.1 Guidelines：用問題帶出架構，不用架構套問題

前五分鐘先詢問使用者和成功條件。是公開行銷短鏈，還是公司內部需要登入的文件分享？要不要自訂別名、修改目的地、到期與刪除？點擊統計要求即時還是可落後？網址有沒有地區限制或隱私要求？這些答案會直接改變快取、安全與資料模型。

接著抓住最重要的兩條使用者路徑：建立短鏈和跳轉。先設計單區域能正確工作的版本，再根據量級加讀快取、分片和區域分發。每增加一個元件，說明它解決哪個已知瓶頸、增加什麼新失效，以及如何觀測。面試時間有限，先把主流程講完整，再選兩個最關鍵問題深入；不要在需求還模糊時把半小時花在選 hash 函數。

本章及下一章的數字均為教學假設，並不是某家產品的真實規模或性能保證。估算保留單位和算式，讓面試官能改參數。每個實戰題使用同一套核對清單：需求、量級、API 與資料、架構、失效取捨、面試追問、驗收測試。你可以換工具，但不能省略其中任何一項。

暖身：如果題目只說「設計 bit.ly」，你第一個問題會是什麼？

先確認核心使用者情境與功能邊界，例如「這是一個公開短鏈服務，主要目標是低延遲跳轉，並支援自訂別名、到期和基礎統計嗎？」然後問規模和可用性。不要假設題目要求複製任何現有產品全部功能。

15.2 URL shortening system：短鍵背後的長期責任

自編系統設計案例。以下列出本題的需求、規模與驗收條件。

一、需求與不變條件

設計公開短鏈服務，支援登入使用者建立、查看、停用與設定到期時間；訪客用 GET /{code} 跳轉至目的地。可選自訂別名，但一旦建立，預設不修改目的地；若允許修改，必須另定快取一致性契約。統計提供每小時點擊數和大略地區，不蒐集不必要的完整訪客身份。第一版不處理廣告計費、不承諾防止所有惡意網址，也不把短碼當作私密存取憑證。

三個不變條件是：同一有效短碼只對應一個權威目的地；租戶只能管理自己的短鏈；收到停用成功後，符合契約的服務端跳轉路徑會在宣告的傳播上限內停止導向。已被瀏覽器或第三方永久快取的回應不能保證收回，因此要先選對重新導向策略。讀取 SLO 假設為每月 99.95% 可用、同區域 p99 小於 100 ms；統計允許落後十分鐘，建立則不必與跳轉同樣快。

二、估算假設與容量

短網址設計題的獨立教學假設
項目假設與計算設計含義
新建短鏈每日 1,000 萬；平均約 115.7 次／秒，尖峰乘十約 1,157寫入遠小於跳轉；可單獨擴容
跳轉每日 10 億；平均約 11,574 次／秒，尖峰約 115,740熱門鍵與快取命中率很重要
保留一年36.5 億筆 × 每筆 300 bytes ≈ 1.095 TB 邏輯資料三副本約 3.285 TB，另加索引、WAL、備份與空間餘裕
點擊事件10 億 × 120 bytes ≈ 120 GB／日不應同步寫回每條短鏈的單一計數器

300 bytes 包括平均目的網址和主要欄位的示例；真實網址可能很長，必須限制長度並量測分布。儲存容量只是第一步，還要估算寫入放大、索引記憶體、熱門分片吞吐與跨區域頻寬。不能以「總資料只有幾 TB」推論一台資料庫在尖峰下必定足夠。

八位 Base62 短碼空間為 628，約 2.18 × 1014。保存 36.5 億個碼後，新生成一個均勻隨機碼撞到既有值的機率約 0.00167%，單次很低，但大量插入下「至少發生一次碰撞」並不低。應用安全亂數生成並以資料庫唯一約束保證正確性，碰撞就重新產生，不能把機率低當作不會發生。隨機碼也只是提高枚舉成本，不能取代授權。

三、API 與資料模型

POST /v1/links
Idempotency-Key: client-generated-key
{ "destination": "https://example.org/report", "custom_alias": null,
  "expires_at": "2027-10-01T00:00:00Z" }
→ 201 { "code": "a8P2kQ7z", "short_url": "https://s.example/a8P2kQ7z" }

GET /a8P2kQ7z
→ 302 Location: https://example.org/report

DELETE /v1/links/a8P2kQ7z
→ 204
GET /v1/links/a8P2kQ7z/stats?from=...&to=...
→ 200 { "clicks": 1200, "complete_through": "..." }

寫入主表可用 links(code PRIMARY KEY, owner_id, destination, status, created_at, expires_at, version)。管理清單需要按 owner_id 與建立時間的次級索引；冪等表以 (owner_id, idempotency_key) 唯一，保存內容摘要與結果。自訂別名和隨機碼共享同一名稱空間時，必須共用同一個唯一性約束，並保留管理路徑和易混淆名稱。重複自訂別名回 409，沒有管理權限時不得洩漏別人的詳細資料。

短碼以字串處理並固定大小寫規則；不可讓閘道和資料庫對大小寫的判定不同。目的網址先檢查長度和允許的 http／https scheme，不任意排序 query 參數或刪除字元，因為簽章網址可能因此失效。URL 解析和 UI 顯示分開，顯示時仍要安全跳脫。若需要擷取預覽或檢查目的內容，抓取服務應在隔離網路中防止 SSRF，拒絕內網、localhost、雲端 metadata 等地址，並在每次 DNS 解析和重新導向時重新檢查。

四、端到端架構

建立路徑先驗證使用者與租戶配額，取得或生成短碼，在交易內寫入映射和冪等結果。成功後可預熱快取。若跨區域寫入，第一版可以把建立路由至短碼所屬權威區域；不要在沒有協調的兩個區域同時宣告同一別名建立成功。隨機短碼降低碰撞機率，唯一約束仍需在共同權威中生效。

跳轉路徑先看本地快取，再看共享快取，最後按短碼查權威資料庫。查到有效映射後返回重新導向；不存在可短時間負快取，避免枚舉流量持續打資料庫，但 TTL 不可長到讓剛建立的自訂別名久久不可用。熱門鏈接可能集中在一個 key，應靠副本快取、請求合併與熱點預熱，而不只增加按 key 分片數量。

這裡選 302 搭配明確的 Cache-Control，因為希望保留撤銷彈性；301 和 308 具有永久重新導向語意，可能造成客戶端持久快取。302 也不能靠狀態碼就假設「永不快取」，仍要設定並測試快取標頭。若對非 GET 請求也開放跳轉，要考慮 307／308 保留方法的語意，第一版乾脆只提供 GET／HEAD。HTTP 定義以 RFC 9110 為準。參考：RFC 9110，3xx Redirection。

停用時先在權威儲存寫入 tombstone 與遞增版本，再發送快取失效事件。必須防止「舊讀取晚到」重新填回已停用映射：回填時以版本或撤銷世代做條件檢查，任何比已知 tombstone 舊的值都不得寫入。僅讓每層 TTL 不超過十秒，不能保證十秒內停用，因為下層舊值可能被上層重新計時，或失效後仍有在途舊讀取完成。若採資料年齡上限，所有層都要保留最後一次權威驗證時間，轉存和回填不可重置；權威讀取也須提供符合撤銷契約的一致性。若承諾十秒內停止服務端導向，可改採短效的權威撤銷驗證，將快取時間、在途請求與傳播延遲一併納入十秒預算，並在無法確認時停止導向。TTL 只是整體策略的一部分，不能單獨當作端到端上限。對惡意連結可另有優先的阻擋資料，但也要考慮它的傳播與故障政策。禁止立刻重用已刪短碼，否則舊快取、紙本 QR code 和外部書籤可能被導到另一個人的新內容。

五、失效取捨與安全

映射資料庫失效時，可短時間服務已知有效且未到期的快取，但這會延遲停用生效；對高風險阻擋需求可能必須停止導向。必須依已選契約決定，單說「快取可提高可用性」還無法回答停用何時生效。新建立連結若讀到非同步副本的舊資料，可按路由提示回權威區域讀取，或在建立後等待可見性條件。不要對新鏈的暫時不可見給長 TTL 的 404。

統計先使用有界本地緩衝，再送至持久事件流。緩衝滿時可丟棄統計並記錄損失量，因為本題允許近似分析；若點擊用於計費，就必須重談需求，不能直接沿用這個策略。聚合以事件 ID 去重或接受可量化誤差，按事件時間處理遲到資料，公開完整到哪個時間。機器人點擊與真人點擊應分開定義，不能聲稱每次 HTTP 請求就是一位真實訪客。

安全上需要建立端限流、濫用申訴、停用稽核、可疑目的地檢查和權限控制。把短碼從連續數字改成隨機字串，可降低猜測相鄰記錄的便利性，但敏感內容仍應在目的服務驗證使用者。來源網址、query 參數和 Referrer 可能含個資或 token，日誌應最小化與遮罩，不能為了分析把完整請求永久保存。

六、面試追問與推理方向

為什麼不用長網址的 hash 當短碼？

截短 hash 仍有碰撞，必須處理。相同長網址是否應共享短碼也取決於 owner、到期、統計和管理權限；不同使用者通常希望各自管理。若做去重，應限定租戶範圍並把設定納入語意。hash 也不能代替唯一約束或授權。

若用全域遞增 ID 再 Base62，會怎樣？

可以避免亂數碰撞，實作簡單，但容易枚舉，也可能需要中心發號器。可批次租用號段降低協調成本，接受空洞；或用分區唯一 ID。Base62 只是編碼，不是加密。更長的 UUID 適合內部 ID，但不能只因為規格存在就認定它滿足短鏈長度與保密需求。RFC 9562定義 UUID 格式與相關考量。

全球所有區域都要能建立同一個自訂別名，還要完全不衝突？

必須有協調或單一權威決定勝者，例如共識儲存、全域唯一名稱服務，或把名稱固定分派到權威區域。網路分區時若兩邊都無條件成功，便無法保證唯一性。可以犧牲部分建立可用性保住名稱一致性，而跳轉仍盡量走本地讀取。

七、可操作的驗收測試

  • 唯一性：強制亂數生成器返回重複值，確認重試並保留唯一約束；一百個並行請求爭同一別名，只有一個成功。
  • 冪等：模擬資料已寫入但回應遺失，重送同鍵得到原短碼；同鍵不同內容回明確衝突。
  • 快取撤銷：在每層快取預熱後停用，測量各區域停止導向時間，不能只看資料庫已更新。
  • 熱門鍵：讓單一短碼佔尖峰流量九成，確認不會形成資料庫熱分片和快取擊穿。
  • 統計隔離：停止事件流十分鐘，跳轉仍符合 SLO，且系統能報出遺失與延後事件。
  • 安全：測試惡意 scheme、超長網址、內網預覽目標、跨租戶管理及過期短鏈。

面試收束：這個方案用權威映射與唯一約束保正確，用多層讀快取扛跳轉，用非同步分析隔離非核心負載，再用明確的失效傳播契約處理停用。名稱一致性和快取撤銷需要深入討論，不能把時間都花在短碼轉換函式上。
