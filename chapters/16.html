CHAPTER 16 · Practice, part 2

實戰二：風險判斷、身份邊界與可觀測性

這三題考驗三種不同的正確性：詐欺偵測要面對不確定性，認證授權要維持安全邊界，監控則要在系統出事時仍提供可信訊號。共同原則是把資料流、失效行為和驗收方式說完整。

16.1 Guidelines：先找出最不能犯的錯

設計前先問：錯誤結果的代價是什麼？錯擋一筆正常交易與漏掉一筆詐欺的代價不同；把有效使用者登出與讓外人讀到租戶文件的代價不同；晚到一分鐘的 CPU 指標與完全漏發事故告警的代價也不同。系統設計不能把它們全部塞進「99.9% 成功率」。

每題先畫權威來源和信任邊界，再畫快路徑與慢路徑。快路徑滿足即時要求，慢路徑負責回補、審核、訓練、分析或修復。最後提出一項能否定自己方案的測試。如果任何故障都被回答成「再重試一次」，通常代表缺少冪等、截止時間、隔離或人類決策的設計。

下列方案是原創面試推演，數字皆為獨立假設。它們不取代正式安全審查、法律合規評估或生產負載測試。請用明確契約說明推理，也保留各方案無法處理的風險。

16.2 Fraud detection system：在截止時間內提供可解釋的風險訊號

自編系統設計案例。以下列出本題的需求、規模與驗收條件。

一、需求：把評分與最終處置分開

假設服務為交易平台評估每筆交易的詐欺風險。核心功能是低延遲產生風險分數、規則命中原因、使用的模型與特徵版本，以及建議的下一步，例如正常流程、追加驗證或人工審核。付款執行由交易系統負責；風險服務不直接操作資金，也不因一個模型分數就宣稱某人「確定詐欺」。重要或具爭議的處置需有審核、申訴與稽核軌跡。

要求 p99 評估延遲小於 150 ms、每次請求可追蹤、相同評估 ID 的重試得到相同已定結果；模型迭代不能悄悄改寫歷史決策。可在背景加入後續調查，但必須保存「當時知道什麼」和「後來補充什麼」。資料收集限於必要且有授權的訊號，保留期限和存取權限獨立設定。

二、估算：分類指標與人力也是容量

假設每日一千萬筆交易，日均約 115.7 次／秒，預留尖峰 2,000 次／秒。每筆原始事件平均 1 KB，約 10 GB／日，三十日約 300 GB 邏輯資料，不含副本、特徵、索引和模型產物。每次評估最多讀五組特徵，最壞尖峰就是每秒一萬次特徵讀取；批次讀取和本地快取有助降低往返，但不能把過期或未授權資料混入決策。

若詐欺基準率是 0.1%，每日真實詐欺約一萬筆。某模型召回率 80%、正常交易誤報率 1%，將得到約八千個真陽性，卻也有 99,900 個假陽性，警報精確率約 7.4%。因此「準確率 99%」幾乎無法回答業務問題。要一起看 precision、recall、PR 曲線、金額或損失加權結果、正常用戶被打擾的比例，以及不同情境的校準程度。

假設人工團隊一百人，每人每天能完成六十個案件，總容量六千件／日。若把上述十萬多個警報全部送人工，系統架構再快也救不了隊列。需要分級、追加驗證、具體理由與取樣稽核，並由風險與業務負責人決定可接受政策；不能單純提高閾值到「剛好六千」就宣稱品質不變。人工審核量、等待年齡和申訴處理時間都應是 SLO。

    "reason_codes": ["VELOCITY_CHANGE"], "model_version": "m17",

    "degraded": false }

  "evidence_ref": "...", "reviewer_id": "..." }

score 只有在模型已校準且定義清楚時才可解讀成某種機率，不能任意把 0.73 說成確定有 73% 詐欺可能。reason code 也只是模型或政策使用的訊號，不是犯罪指控。人工結果入口必須驗證角色、限制修改、保存前後版本和證據來源；不能讓被評估的客戶端自己寫「已通過人工審核」。

資料可分成四類：不可變原始事件、線上特徵、模型／政策版本、決策與審核紀錄。事件包含 event_time、received_at、available_at、source_version；線上特徵保存值、窗口、更新時間與缺失狀態。交易 ID 用於去重，評估 ID 用於一個明確版本的判斷。同交易若允許重評，必須產生新評估版本並指向舊版本，不能覆寫原始歷史。

四、架構：快速評估加上延遲回饋

在線流程先做 schema 驗證、授權與評估去重，再平行讀取有限的特徵組、計算廉價規則，使用固定版本模型推論，最後由政策層結合分數、原因和資料品質產生建議。總預算 150 ms 可先粗分入口與去重 15 ms、特徵取得 45 ms、推論 25 ms、政策與持久化 35 ms、網路與餘裕 30 ms；這只是分配起點，需量測端到端分布，不能把各階段 p99 相加當證明。

異步事件流負責更新近期次數、裝置變動等時間窗口特徵，按事件時間處理亂序並設定 watermark／允許遲到範圍。即時風險的當次交易若已被算入特徵，離線重建時也要同樣計入；若訓練採「交易發生前」狀態，線上就不能先更新再讀。這種一個事件的偏移，足以讓離線和線上結果不一致。

訓練資料要做 point-in-time correct join：在決策時刻只能用當時已可取得的資料。某事件雖然 event_time 很早，但 available_at 是隔天，也不可以回填到昨天的線上特徵。退款、拒付、人工判定可能數週後才成熟，不能作為當次交易的輸入。依時間切分訓練與測試，預處理只在訓練資料 fit；對同一帳戶或裝置跨分割的洩漏也應評估。資料洩漏的基本定義可核對 scikit-learn 官方文件。參考：Common pitfalls，Data leakage。

發布新模型時，先離線回測，再以影子流量比較，不改變真實處置；接著小比例灰度，監測延遲、特徵缺失、分數分布、人工量及成熟後的品質。保留模型、特徵、前處理和政策的完整相容版本，能一鍵回到經驗證版本。只替換模型檔案但沿用不相容特徵 schema，是常見的「部署成功、結果失真」。

五、失效與取捨

特徵服務故障時，不可默默把缺失值當成零。回應要帶 degraded 和缺失原因，使用已驗證的降級政策；低風險情境可能追加驗證，高風險或重大處置可能等待人工。採取什麼動作由預先批准的風險政策決定，不能一律全放或全擋。模型逾時同理，應立即停止等待並使用受控替代路徑，而不是讓交易系統超時重試十次。

標籤存在選擇偏差：被系統擋下的交易未必有後續結果，只有被調查的個案才有完整資料，不能把「未被發現」當成「確定正常」。審核人也可能出錯，需要分歧處理、抽樣覆核與品質指標。攻擊者會適應規則，分布也會因活動和季節改變，所以漂移監控與延遲成效評估是服務的一部分。原始研究對 ML 系統中的隱性資料依賴和回饋循環提供了重要警示。參考：Hidden Technical Debt in Machine Learning Systems。

資料安全上，盡量使用最小化的參照 ID，避免把支付憑證、完整敏感內容或無關個資送到模型日誌。細粒度授權、保存期限、加密與稽核適用於特徵和模型產物，不只是原始資料庫。模型品質也要按相關業務情境檢查，不能用總體平均掩蓋某些群體長期受到不合理誤報。

六、面試追問

模型 A 的 AUC 比模型 B 高，就應該上線嗎？

不一定。要看實際可用閾值、precision／recall、審核容量、校準、不同情境表現、推論成本和標籤成熟度。整體排序指標高，不保證在極低誤報區間較好。還應比較相同政策與相同時間窗口下的端到端結果。

使用昨天建立、今天才回補的特徵表訓練，為什麼可能洩漏？

因為表中的值可能含有今天才得知的拒付、補充事件或修正資料。事件時間早，不代表昨天已可取得。必須保留 available_at 或可重建的版本，使用決策當下的可見快照做 join。

人工審核會讓系統太慢嗎？

即時評估可在 150 ms 內給出「需要審核」，而最終審核是另一個有明確等待時間的流程。不能聲稱兩者同時在 150 ms 完成。是否允許等待、追加驗證或取消，由交易契約決定。

七、驗收測試

  • 凍結一個歷史時點，重建當時特徵；任何 available_at 晚於決策時間的值都不可出現。
  • 送入重複、亂序與晚到交易，確認特徵不重複計數，窗口邊界一致。
  • 相同評估 ID 重試，模型部署後仍回原始結果；明確重評才產生新版本。
  • 中斷特徵庫或讓推論超時，回應需標示降級且符合核准政策，沒有無限重試。
  • 以成熟標籤的時間留出集計算誤報與召回，再檢查人工隊列能否承受。
  • 測試稽核者無權改模型、模型服務無權直接改最終人工判定，並驗證跨租戶資料隔離。

16.3 Authentication and authorization system：身份成立，不代表能做所有事

自編系統設計案例。以下列出本題的需求、規模與驗收條件。

一、需求與信任邊界

為多租戶文件平台設計登入、單一登入、工作階段、API 存取與文件權限。Authentication 回答「你是誰」；authorization 回答「你此刻能對這個物件做什麼」。OAuth 2.0 是授權框架，本身不能直接當作完整的終端使用者認證協定。OIDC 在 OAuth 2.0 上建立身份認證語意與 ID Token，應使用經驗證的實作而非自創登入協定。參考：OpenID Connect Core 1.0。

不變條件包括：任何文件操作都驗證資源所屬租戶與操作權限；無法確定敏感操作的授權時不放行；撤銷與離職停權具有明確生效上限；身份提供者回傳的 token 只在預期發行者、受眾和用途內使用。第一版委託成熟身份提供者管理使用者認證與 MFA，平台自己負責租戶成員、角色、文件關係和授權決策。

二、估算假設

假設總帳戶二千萬、每日活躍一百萬，每位每天建立兩次工作階段，共二百萬次／日，平均約 23.1 次／秒，尖峰十倍約 231 次／秒。受保護的 API 峰值卻可能是每秒五萬次，所以不能把每次 API 都等同於一次完整登入。將認證流程、token 驗證與物件授權分開擴容。

若當日二百萬個 session 紀錄各 400 bytes，邏輯資料約 0.8 GB；若保留多日或多裝置，應按實際未過期數估算。授權關係可能遠多於使用者數：一百萬使用者各加入十個群組、每群組再共享許多文件，必須分清直接成員關係、繼承和查詢模式。容量不只看 token 長度，還有政策變更扇出與撤銷傳播。

三、API、資料與 token 語意

GET /login                  → 由後端建立受保護的登入交易並導向 IdP
GET /callback?code=...       → 驗證登入交易，交換 code，建立應用 session
POST /logout                → 撤銷目前 session 與適用的 refresh grant
POST /v1/authorization/check
{ "subject": "user_...", "tenant": "tenant_...",
  "action": "document.read", "resource": "doc_..." }
→ { "allow": false, "policy_version": "p42", "reason": "..." }

最後一個授權 API 是受保護的內部介面，不能信任任意外部客戶端提供的 subject；服務需從已驗證憑證導出身份，並驗證代查權限。使用者表保存平台內部 subject 與經驗證的 issuer、外部 subject 對應。不能只靠 email 相同自動合併帳戶，因為地址可能變更或在不同身份域代表不同人。

資料包括 tenant_membership(tenant_id, subject_id, role, version)、文件 owner／共享關係、session、refresh grant family、政策版本及稽核事件。密鑰由受控金鑰服務管理，日誌不保存原始 token 或認證密碼。若保存 refresh token 的驗證值，使用適合高熵 token 的安全雜湊並保護儲存；使用者密碼的處理則有不同的專用安全要求，應交給成熟身份系統。

ID Token 給登入客戶端證明認證事件；access token 給資源伺服器授權存取指定 API。不能把一個簽章正確的 ID Token 任意當作所有 API 的 access token。JWT 只是格式，不天然代表安全，也不天然代表授權已足夠；某個 scope 允許「讀文件」仍要檢查這份文件是否屬於此租戶、是否被分享給這位使用者。

四、架構與登入流程

瀏覽器採後端協助的登入流程：應用建立具短效期且一次性的登入交易，使用 authorization code flow 搭配 PKCE，並正確驗證 state 等防護；OIDC 流程正確處理 nonce 與回應綁定。callback 的 redirect URI 使用精確註冊值，後端交換 code 後驗證簽章、issuer、audience、有效時間和必要 claims，建立應用 session。依協定與客戶類型採用正式安全建議，避免自己拼湊流程。參考：RFC 9700，OAuth 2.0 Security Best Current Practice。

瀏覽器 session cookie 設置 Secure、HttpOnly 與合適的 SameSite，跨站狀態變更還需 CSRF 防護；cookie 的 path、domain 和生命周期限縮。BFF 模式可讓 API token 留在後端，降低瀏覽器端暴露，但不會自動免疫 XSS 或 CSRF。行動端和其他公開客戶端需用該類型適用的系統瀏覽器／安全儲存流程，不把客戶端秘密寫進可分發的程式。

API 入口驗證 token，再由資源服務執行物件授權。RBAC 適合管理員、編輯者、唯讀者等粗粒度角色；ABAC 可納入資料分類、操作條件與可信的環境屬性；共享文件則可能需要關係式授權。把 policy decision point 和實際強制執行位置分清楚：就算中央政策服務判斷了，資源服務漏檢一次仍會造成越權。

JWT 驗證必須限制允許的演算法、核對適當的 issuer 和 audience、驗證時間欄位，並使用預先信任的密鑰來源。不要跟著未信任 token 內任意提供的 URL 去抓金鑰。RFC 8725 討論演算法驗證與不同 JWT 用途混淆等風險。參考：JSON Web Token Best Current Practices。

五、撤銷、一致性與失效取捨

短效 JWT 能讓資源服務離線驗證，降低中央認證服務的流量與依賴；代價是「撤銷資料庫裡的 session」不會神奇地改變已簽發 JWT。若 access token 五分鐘後到期，再容許三十秒時鐘偏差，單靠到期的撤銷上限可能接近五分三十秒。若要求十秒內停權，必須有線上 introspection、session／user version 查詢、撤銷清單或其他能在十秒內傳播的機制，並處理快取與斷線情況。

refresh token rotation 每次換發新的 refresh token，舊 token 重用可能代表竊取；應記錄 token family 並依政策撤銷。並行刷新是實作難點，需要原子更新或明確的小範圍重送處理，避免正常的兩個請求都換到新 token，或把正常重送誤判為攻擊。撤銷端點語意可參考 RFC 7009，但它不保證所有離線驗證的資源服務瞬間得知。參考：OAuth 2.0 Token Revocation。

簽署金鑰輪替時，新公鑰要先可取得，再開始簽新 token；舊公鑰保留至合法舊 token 的驗證窗口結束。資源服務快取 JWKS，遇到未知 kid 可受控更新，不能每個惡意 token 都觸發外部請求。若懷疑私鑰遭竊，緊急撤銷和一般輪替不同，可能必須立即阻擋舊 key，接受使用者重新登入的影響。

授權快取鍵至少包括租戶、subject、action、resource 和相關政策版本。使用者被移出群組後，過期快取不能無界續命；必要時針對敏感寫入查權威狀態。認證提供者暫停時，既有低風險 session 是否可繼續使用，取決於 token、撤銷及授權新鮮度契約；管理員變更、分享機密文件和提升權限通常不能在無法確認時照常放行。

六、面試追問

JWT 是無狀態的，所以不需要資料庫，對嗎？

只有「驗證某個已簽發 token」可以在一定條件下不查狀態。使用者停權、群組變更、refresh token、裝置 session、撤銷和稽核仍需要狀態。選擇離線驗證只是把延遲與可用性換成有限的新鮮度，不是取消整個身份系統的資料。

API Gateway 驗過 token，微服務可直接相信 tenant_id 嗎？

必須確認內部請求身份和標頭來源不可偽造，也要驗證資源歸屬與操作權限。外部傳入的 tenant_id 不能直接當作已授權租戶。服務間使用受驗證的身份和受保護的上下文，資源服務仍要強制執行物件層授權。

登入成功就能把某人的帳戶加入管理員群組嗎？

不行。身份驗證和權限授予是兩個不同操作。管理員角色的建立、修改和委派要由已授權者執行，具有獨立稽核和必要的再次驗證，不能根據客戶端自稱的角色或不可信 email 網域自動提升權限。

七、驗收測試

  • 使用正確簽章但錯 issuer、錯 audience、錯 token 類型、過期和未到生效時間的 token，皆不得被錯誤接受。
  • 使用者 A 的 token 配租戶 B 的文件 ID，所有讀寫端點與批次 API 都拒絕。
  • 停權、登出、撤銷群組後，實測所有區域、快取和長連線的生效延遲符合契約。
  • 兩個並行 refresh 請求與網路重送不得產生無限制有效 token，也不得遺失稽核。
  • 金鑰正常輪替期間合法請求持續通過；緊急撤銷時舊 key 在指定窗口內停用。
  • 中斷身份與政策服務，確認各類操作依既定失效表處理，沒有默認全部允許。

16.4 Monitoring system：監控也需要自己的失效設計

自編系統設計案例。以下列出本題的需求、規模與驗收條件。

一、需求：收集資料與讓人採取行動是兩件事

為五百個服務、每服務二十個實例的環境設計監控。支援 metrics、logs、traces、儀表板與告警；最近兩週查詢快速，長期資料可降解析度。事故告警希望在條件成立後兩分鐘內送達指定值班目的地，重複訊息要合併，恢復要關聯原事故。監控內容包含使用者體驗和依賴健康，不只機器 CPU。

metrics 適合聚合數值與時間序列，logs 適合離散事件和診斷上下文，traces 連接一次工作跨服務的因果路徑。三者互補：從延遲指標發現問題，以 trace 找到慢依賴，再以受控日誌查細節。不能把每筆 trace 原封不動變成 metric label，否則序列數會失控。

二、估算與基數預算

假設一萬個實例，每個暴露一千條活躍序列，每十五秒收集一次，合計一千萬條序列、每秒約 666,667 個樣本。若只作教學粗估，每個壓縮後樣本平均兩 bytes，則每日樣本本體約 115.2 GB，十五天約 1.728 TB；這不是實際儲存保證，還要加標籤索引、WAL、副本、區塊 metadata 和壓縮差異。容量規劃應用實際負載量測。

假設每實例每秒五 KB 日誌，全環境每秒五十 MB，一天約 4.32 TB，遠高於上面的樣本本體。trace 若尖峰每秒十萬請求、每請求十個 span、每 span 平均 500 bytes，尖峰完整保存速率是每秒約五百 MB；取樣 1% 後約每秒五 MB。只有假設此尖峰流量持續整日，才會得到約 432 GB／日的規劃上界；實際每日量應依流量曲線積分，不能直接把瞬時尖峰當成日平均。資料保留、取樣和索引策略必須在設計架構時決定，不能留到上線後再想。

標籤組合會乘法成長：20 個 endpoint × 5 個狀態類型 × 3 個區域 × 100 個實例已有三萬條序列；再加一百萬個 user_id 就可能變成三百億種組合。URL 路徑應標準化為 /documents/{id}，不要包含真實文件 ID。Prometheus 官方 instrumentation 指南提醒每組標籤都會形成額外序列，應限制高基數維度。參考：Instrumentation。

三、API 與資料模型

metric identity = tenant + name + canonical_label_set
sample          = timestamp + value + type
log             = timestamp + service + severity + trace_id + redacted_body
span            = trace_id + span_id + parent_span_id + start + duration + attributes
alert identity  = rule_version + stable_group_labels

POST /v1/telemetry/batch
{ "producer_id": "...", "batch_id": "...", "items": [...] }
→ { "accepted": 950, "rejected": 50, "reason": "label_limit" }

此處為教學介面；正式實作可採現有遙測協定與成熟 Collector，避免重造每一種 SDK。入口驗證租戶身份、schema、時間範圍、標籤數量和大小上限，回覆部分拒絕時需讓生產者知道哪些類型被拒絕。租戶查詢權限與資料寫入身份分開；不能因為有人能送資料，就允許查整個平台。

不同 metric 類型具有不同語意：counter 通常只增不減但重啟會歸零，rate 計算要處理 reset；gauge 表示某時點狀態；histogram 保存分桶或相容的分布統計，可先合併再算整體分位數。不要把每台機器自己的 p99 做平均，宣稱得到全站 p99。若要跨服務或時間聚合，應選可合併的統計表示與一致的單位。

四、架構：資料入口、查詢與告警各自隔離

應用 SDK 或主機 agent 先收集資料，在本地做必要的遮罩、批次與有界緩衝，送到區域 Collector。Collector 負責驗證、租戶配額、採樣和路由，後接持久緩衝或事件流，再分送時序儲存、日誌搜尋與 trace 儲存。查詢服務有快取、時間範圍和並行上限，不能讓一個「搜尋所有日誌一年」的查詢拖垮即時攝入。

metrics 可用 pull 方式定期抓取，方便識別目標是否消失；短命工作或跨網路邊界情境可能適合 push，但失聯如何判斷須另行設計。選擇時，要說明發現機制、身份、安全邊界和背壓如何配合。系統需監控最後成功接收時間、落後量與資料缺口，而不只把沒有數據顯示成零。

區域 Collector 有 queue 和 retry 不表示資料一定不丟。記憶體佇列會因程序退出消失，持久佇列仍有磁碟滿與保存窗口；若下游長時間不可用，必須選擇丟棄哪一類資料、保留多久及如何報告損失。OpenTelemetry 的 resiliency 文件說明 sending queue、重試與持久化等機制，部署時應確認各 exporter 的實際支持。參考：Collector Resiliency。

trace 的 head sampling 在請求開始就決定是否保留，簡單且成本可控，但可能丟掉後來才變慢的請求；tail sampling 等收到更多 span 再決定，可保留錯誤或慢請求，但需要緩衝、trace 一致路由和明確等待窗口。晚到或不完整 trace 必須可辨識。取樣率不同時，若要估算總量須理解加權和偏差，不能把被偏重保留的錯誤 trace 比例當成真實錯誤率。

五、告警設計與失效

告警從可採取行動的條件開始：文件在承諾時間內完成的比例、互動錯誤率和隊列最老年齡。CPU 高可以是線索，不一定值得立刻打擾人。以 99.9% 成功 SLO 為例，可接受錯誤率是 0.1%；若觀測錯誤率為 1%，錯誤預算燃燒率約為十倍。短窗口辨識快速事故，較長窗口確認持續性，實際門檻需配合流量、值班負荷和 SLO 窗口校正。

告警流程由規則評估器產生穩定身份的 alert，再經去重、分組、抑制與路由送通知。資料庫故障造成一百個服務報錯時，可保留使用者影響告警，抑制已知從屬雜訊；抑制規則本身要可檢查，不能把真正獨立事故一起藏掉。每個告警應包含時間、影響、近期變更線索、可用的 runbook 和責任人。確認已接手不等於事故已解決，狀態要分開。

監控控制面和被監控系統不能完全同生共死。至少保留外部黑箱探測、獨立的關鍵通知路徑和端到端心跳。若監控資料攝入停止而儀表板維持最後數字，使用者應看見「資料過期」，不是穩定的綠燈。規則評估器缺數據時採何種狀態需逐條定義；缺少付款成功資料和缺少一台已退役測試機的指標，不能用同一個答案。

若告警供應商回應逾時，不確定訊息是否已送達，就用穩定事件 ID 和冪等／去重機制重送；設上限、退避與備援目的地。單點通知成功回應也不等於人已看到，重要事故可以有經批准的升級路徑。對外部通知目的地的授權、值班排程和靜音時間要明確，不由監控系統任意猜測。

六、面試追問

把所有資料都存起來，是否最安全？

不一定。無限保存提高成本、敏感資料暴露和查詢負荷，也可能使關鍵訊號淹沒。按目的設定保留與解析度，先遮罩、限制索引欄位，對安全稽核與一般除錯採不同管道。刪除政策要覆蓋副本、備份和衍生資料，並由實際要求決定。

如何監控監控系統？

檢查攝入延遲、拒絕率、丟失量、查詢延遲、規則評估落後與通知成功；另外使用獨立黑箱探測與端到端測試告警，驗證訊號真的從應用送到接收端。只讓同一個壞掉的資料管線報告自己健康，會形成循環盲點。

十個實例的 p99 平均是 200 ms，全站 p99 也是嗎？

不是。實例流量權重和延遲分布不同，分位數不能直接平均。應合併適當 histogram 的計數與樣本總數，再估計整體分位數，或直接量測端到端。也要記得 histogram 桶界線決定估算精度。

七、驗收測試

  • 注入高基數 label 和超大 batch，確認單租戶被限制，其他租戶攝入仍正常。
  • 關閉下游儲存、填滿本地 queue，再重啟 Collector，確認持久化與損失量符合宣告。
  • 製造 counter reset、時間偏移、遲到樣本和缺失區間，查詢與告警不得悄悄產生誤導數字。
  • 觸發真實測試告警，量測從條件成立到指定目的地接收的端到端時間，驗證去重與恢復關聯。
  • 斷開主監控區域，外部黑箱仍能揭露故障，關鍵通知路徑仍可用。
  • 檢查日誌與 trace 不含原始密碼、token 或未授權敏感內容；跨租戶查詢必須被拒絕。

三題的共同收束：風險服務保存不確定性與證據，身份服務保存權限邊界，監控服務保存訊號的可信度。把它們都設計成「一個 API 加一個資料庫」雖然容易，但真正的工程工作發生在資料變晚、結果過期和依賴失效之後。
