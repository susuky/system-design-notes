一次交易，三條需要說清楚的路徑

交易要判斷風險，API 要知道誰能做什麼，值班的人要及時看見服務異常。這三種系統都會遇到延遲、舊資料與重送，卻有不同的完成條件。最後一章用三個案例，把前面的設計方法接到真實決策。

同樣慢五秒，哪個決策會改變？

同樣是「資料晚了五秒」，在三個系統裡的影響完全不同。反詐服務可能少看到剛發生的交易；授權服務可能繼續接受剛被撤銷的權限；監控服務則可能晚五秒通知值班的人。從這個影響往回推，就能選出真正要控制的時間與狀態。

系統一次工作何時完成優先釐清的問題
反詐在交易期限內保存一個可追溯的決策誤擋、漏抓與人工複查各能承受多少
認證與授權依正確身分與有效權限處理這次操作撤銷多久生效、權限依哪個物件判斷
監控觀測成為可判讀的狀態，必要通知送達資料多久到、缺資料時顯示什麼

每個案例都分成即時路徑與後續處理。即時路徑有明確 deadline，後續路徑保存決策、對帳或聚合。兩邊用穩定識別連起來：evaluation_id、session_id、事件與告警識別，讓重送與故障恢復都能回到同一份狀態。

先畫服務圖，還是先選一個失敗案例？

先選一個會改變設計的案例。例如「角色剛被撤銷，舊 token 還剩五分鐘」會直接決定是否需要線上授權版本檢查。接著才畫出誰保存權限、誰驗證、快取多久，以及失聯時這條操作怎麼回應。

抓到八千筆詐騙，為何多了十萬件複查？

假設每天一千萬筆交易，其中 0.1% 真的是詐騙。模型抓到 80% 的詐騙，同時把 1% 的正常交易誤判為可疑。看起來很小的誤判率，會送多少案件到人工複查？

交易種類每日數量被標為可疑
詐騙10,0008,000
正常交易9,990,00099,900
全部警示107,900其中約 7.4% 真正是詐騙

精確率為 8,000 ÷ 107,900 ≈ 7.4%。一百位審查員、每人每天六十件，只能看六千件。這時要一起調整門檻、風險分級與處理方式：高風險直接依政策處理，中間區間要求額外驗證，最需要判斷的案件才送人工，並依可能損失與可處理量排序。

把一次評估固定下來

請求帶 evaluation_id、交易資料與決策期限。服務保存分數、理由碼、模型版本、特徵版本與政策版本，然後回傳決策。相同 evaluation_id 重送時，回傳當時那份結果；想使用新模型重新評估，就建立新的 evaluation_id，並關聯原交易。

這樣在模型部署前後重試，付款服務得到的仍是同一次評估。決策與後續動作也分開保存：風險服務決定「要求額外驗證」，交易系統再記錄驗證是否完成，讓整條流程有明確狀態。

150 ms 怎麼分

先抓一個尖峰每秒 2,000 次評估的量級來分配預算：每次讀五組特徵，就是每秒 10,000 次特徵讀取。給入口與驗證 15 ms、特徵讀取 45 ms、模型推論 25 ms、政策與持久化 35 ms，再留 30 ms 回應與緩衝，合計 150 ms。

這些是各階段可用的時間預算。端到端 p99 由整次評估的起訖時間量測，並用 trace 找出超時花在哪一段。特徵服務變慢時，依產品政策回傳可識別的降級決策，例如要求額外驗證，或只允許低額交易。

讓模型只看見當時知道的資料

一筆事件保留三個時間：發生時間、系統收到時間，以及特徵真正可供查詢的時間。離線訓練重建某次交易時，只用在決策當下已可取得的特徵。三天後收到的拒付紀錄，可以成為標籤，卻要等標籤成熟後才納入評估。

訓練與驗證按時間切開，正規化等前處理只從訓練資料學習。線上更新另處理遲到與重複事件，並說清楚「最近一小時交易次數」是否包含正在評估的這筆交易；離線與線上採用相同定義。

每日一千萬事件、平均 1 KB，原始資料約每天 10 GB，三十天約 300 GB。特徵狀態、索引、複本與標籤另算。先把事件保留需求與回溯期間定好，才能重建當時的決策。

特徵讀取失敗時，把「最近一小時交易次數」填成 0，會怎樣？

模型會把「資料未知」解讀成「真的沒有交易」。為缺失值保留明確狀態，訓練時也納入同樣情境；政策層依缺失特徵與交易風險採取額外驗證或其他既定處理。監控另外統計缺失比例與降級決策量。

進階：新模型如何比較

先讓新模型影子執行，保存它的決策但沿用原政策處理交易，再逐步分流。模型、特徵定義與政策以相容版本一起發布。比較結果時等標籤成熟，並追蹤被攔截交易造成的觀測差異：被擋下的交易通常不會留下與放行交易相同的後續結果，需要額外設計抽樣複查與評估資料。

Token 還有效，這份文件能讀嗎？

租戶 A 的使用者帶著有效 token，把網址裡的文件 ID 換成租戶 B 的文件。API 會在哪一步拒絕？先切換文件歸屬，再把 token 有效期拉到零，觀察身分驗證與物件權限各在哪裡決定結果。

登入結果與 API 權限各有使用者

OIDC 提供登入後的身分資訊，OAuth 提供對資源的存取授權。登入 client 驗證 ID token；API 驗證發給自己使用的 access token，並檢查這次操作的範圍與物件權限。使用者在本地的穩定對應採 (issuer, subject)，帳號顯示的 email 可以更新。

假設系統有兩千萬帳號、一百萬每日活躍使用者，每人每天登入兩次工作階段，就是一天兩百萬次——平均每秒 23.1 次，十倍尖峰約 231 次／秒。但一般 API 呼叫可能每秒五萬次，所以「登入發證」跟「每次請求授權」的容量必須分開估算。同時線上保留兩百萬份、每份 400 bytes 的 session，紀錄本身大約只佔 0.8 GB。

瀏覽器登入走一條可追蹤的交易

瀏覽器這端採用 BFF（Backend for Frontend）：瀏覽器只帶 session cookie 呼叫自己的後端，access token 與 refresh token 都安全留在後端。BFF 會為每次登入建立一次性的登入交易，綁定瀏覽器、預期 issuer、redirect URI、state、nonce 與 PKCE verifier，並搭配 authorization code 流程和 S256 challenge。

  1. 瀏覽器被導向已設定的身分供應商，登入交易保留在後端。
  2. callback 回來後，檢查 state 與這次登入交易，確認回應來自預期 issuer。
  3. BFF 使用 code 與 PKCE verifier 向 token endpoint 換取 token。
  4. 驗證 token 的簽章、允許的演算法、issuer、audience、有效時間與這次登入的 nonce。
  5. 消耗該登入交易，建立新的 session，再把瀏覽器導回應用。

瀏覽器 cookie 可用 __Host-session; Secure; HttpOnly; SameSite=Lax; Path=/，不設定 Domain。修改狀態的請求另做 CSRF 保護，session 在登入、權限升級等重要轉換時重新建立，讓新身分對應到新的工作階段。

到物件層才知道能做什麼

「這個人是 editor」還需要配上作用範圍。API 從已驗證的 session 取得使用者與租戶，載入文件的擁有者或關係，判斷 使用者 × 動作 × 物件。角色適合描述一組常見權限，屬性與關係則補上「自己租戶的文件」「被分享的資料夾」等條件。

角色撤銷了，五分鐘 token 還能用多久？

管理員剛移除了角色，舊 token 卻仍在有效期內。這次要控制的是權限變更傳到各服務的時間。若 API 只依 token 到期時間接受存取，token 剛發出便撤銷，五分鐘有效期加上 30 秒容許時鐘誤差，最長可能再接受約 330 秒。要把撤銷目標縮到十秒，就讓 API 檢查線上 session／權限版本，或使用最多十秒內更新的狀態；快取與在途處理一起放進這十秒預算。

撤銷紀錄保存新版本與時間，權威服務拒絕舊版本操作。各節點顯示目前讀到的版本與資料年齡，超過新鮮度上限時，依該操作的政策回權威查詢或拒絕，避免在失聯期間繼續使用過期權限。

同一 session 的三個 API 同時發現 access token 過期，誰刷新？

每個 session 同一時間只安排一次 refresh，其餘請求等待該次結果。多個 BFF 實例使用共享狀態的原子條件更新取得刷新權，並以 session 版本保存新的 token 組，避免較晚回來的舊結果蓋過新狀態。

供應商已輪替 refresh token、回應卻丟失時，依供應商提供的恢復或重試契約處理；若原 token 已失效且無法恢復，就重新開始登入。盲目同時重送舊 token 會觸發重播偵測或讓整個 token family 失效。

進階：驗證金鑰如何輪替

先發布新公鑰，讓驗證端取得，再使用對應私鑰簽發新 token。舊公鑰保留到最後一枚舊 token 超過有效期與時鐘餘裕。遇到未知 kid 時可更新金鑰集合，但為更新頻率與併發設上限，讓偽造的隨機 kid 無法把金鑰端點變成每次請求的遠端依賴。

圖表全綠，是正常還是沒資料？

服務圖全是綠色，但某個 collector 已經十分鐘沒送資料。這時監控應顯示「資料過期」，並讓值班的人看到最後一次成功觀測的時間。先把沒有錯誤與沒有新資料分開表示，整套監控才有可判讀的狀態。

訊號常用來回答保留方式
Metrics多少、多久、在哪個服務變差固定維度的時間序列與分布
Logs某次事件發生了什麼結構化事件、必要的關聯識別
Traces一次請求的時間花在哪裡跨服務 span 與因果關係

監控資料的量，先按每天算一次

500 個服務、每個 20 個實例，共一萬個實例。每個實例產生一千條時間序列，每 15 秒收一次，就是一千萬條序列、每秒約 666,667 個樣本。

資料本例假設輸入量
Metrics每樣本暫估 2 bytes每天約 115.2 GB；十五天約 1.728 TB，另計索引與中繼資料
Logs每實例每秒 5 KB每秒 50 MB，每天 4.32 TB
Traces每秒十萬請求，每次十個 span、每個 500 bytes全收每秒 500 MB；取 1% 約每秒 5 MB

這裡把速率視為全天持續，方便算儲存上限；實際容量再代入各時段流量與保留策略。2 bytes 是壓縮樣本的估算值，序列更替、標籤與索引成本會另外改變總量。

標籤數常比樣本大小更快失控。20 種 endpoint、5 種狀態、3 個區域、100 個實例，就有最多 20 × 5 × 3 × 100 = 30,000 種組合；再乘上一百萬個 user_id，就到三百億種。Metrics 用固定的路由樣板與有限標籤，個別使用者與完整 URL 放在適合查詢的事件資料裡。

先合併分布，再讀整體尾端

要看整個服務的 p99，先合併各實例的延遲分布。以下使用 classic histogram，所有實例採相同 bucket 邊界，對每條累計計數先算 rate，再依 service 與 le 合併。

histogram_quantile(
  0.99,
  sum by (service, le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)

先算 rate 能按各實例處理 counter 重置。若目標是「99% 在 300 ms 內」，直接比較 le="0.3" 的 bucket 計數與總計數，便能計算準時比例；bucket 邊界選在業務門檻上，解讀也更直接。

收集、重送與丟棄都有可見狀態

應用程式把資料交給 collector，collector 用有界佇列批次送出。需要在重啟後續送的資料使用持久佇列；滿載時依已定義的優先順序丟棄，並增加 dropped 計數。pull 模式中的目標失聯則顯示抓取失敗與資料年齡，原來的數字留在原時間點。

OTLP 的 partial_success 回應會提供遭拒的 span、資料點或 log 數量。收到這種回應後，結束這批請求並記錄拒收量與原因，修正後續輸出；協定規定不重送該請求。若設計自己的逐筆重試 API，則在回應中提供可辨認的失敗項目，搭配穩定事件識別。

Head sampling 在請求開始時決定是否保留，成本較容易控制。Tail sampling 等看見結果再挑出慢請求與錯誤，需要把同一 trace 路由到能彙整它的處理者，並為等待中的 span 保留緩衝與逾時策略。

告警的時間也有一筆預算

若目標是異常後兩分鐘內通知：收集等 15 秒、傳輸 10 秒、規則評估等 15 秒、條件持續 30 秒、送出通知 20 秒，共 90 秒，還有 30 秒可容納延遲波動。部署時用真實的端到端事件量這條路徑。

告警識別使用租戶、規則 ID 與穩定標籤；目前數值與描述放在註解，避免每次數值變動都長出新告警。同一事故分組、去重、更新與恢復通知共用這個識別。通知供應商受理、值班者收到、值班者確認處理，分成不同狀態。

SLO 若為 99.9%，容許錯誤比例是 0.1%。當觀測錯誤率為 1%，錯誤預算消耗速度就是 1% ÷ 0.1% = 10 倍。用短窗確認快速惡化、長窗確認持續影響，再決定通知強度。

監控系統本身故障，誰會通知？

安排獨立路徑定期檢查外部可見的服務行為，同時追蹤收集器、規則評估與通知管線的最後成功時間。用一個測試事件走完整條通知路徑，並從另一個故障範圍觀察它是否準時出現；值班畫面把缺資料與正常分開呈現。

一台實例 p99 是 100 ms，另一台 900 ms，整體 p99 是 500 ms 嗎？

需要兩台的請求數與延遲分布。各自的 p99 只給了一個位置，平均後會丟失流量權重與尾端形狀。合併 histogram bucket 或原始樣本後再取分位數，才能得到整個服務的 p99；若使用 summary 的預先計算分位數，就保留為單實例觀察。
