第 11 章 · Large scale

大規模處理：分區、路由與安全交接

加機器只有在工作能分開、流量能送對地方、擁有權能安全交接時才有用。本章由文件平台的容量需求出發，逐步建立分區策略，最後說明一致性雜湊解決什麼，以及它無法替你解決什麼。

  • 能由平均工作量、尖峰與恢復目標推導消費能力。
  • 能依排序、查詢和租戶隔離選分區鍵，辨識熱點。
  • 能設計包含版本、追趕與舊擁有者隔離的重新平衡流程。
  • 能計算一致性雜湊的預期搬移量，並交代其假設。

11.1 如何擴展訊息消費？ How to scale message consumption

先問「慢在哪裡」，再問「加幾台」。文件平台每天一百萬份文件、尖峰為日均十倍，因此尖峰約 115.74 份／秒。每份轉換平均需要 2 CPU-seconds，代表尖峰約需要 231.48 CPU-seconds／秒。若假設算力可近似線性擴展，且希望平均使用率控制在 60%，僅轉換計算就需要約 231.48／0.6 ≈ 386 個核心。這是共同案例的教學估算，不包含解析額外成本、重試、資料庫和作業系統開銷。

容量還須承受故障。假設每台有 64 個同等效能核心，七台共 448 核，看似超過 386；但失去一台後只有 384 核，已略低於上述目標。八台失去一台仍有 448 核，才在這個簡化模型下留有餘額。真實配置必須以效能測試校準，尤其文件大小與格式可能有重尾分布；平均兩秒不保證每一份都在兩秒完成。

另一方面，5 MB 原件乘上尖峰 115.74 份／秒，光原件讀取約為 578.7 MB／秒，尚未算輸出、複讀及複寫。如果 CPU 很閒、物件儲存下載卻被限流，增加核心只會多出等待者。對每一步分別看 CPU、記憶體、外部 API 配額、磁碟、網路與連線池，找出真正的最小容量。

消費群組與並行度的精確關係

在 Kafka 一般採分區獨占指派的消費群組中，同一分區在同一群組內同時指派給一個成員；若有 P 個分區、C 個成員，能獲得分區的成員數最多為 min(P, C)。這不是所有訊息系統的通則，也不表示單一分區內永遠只能使用一個 CPU。工作者可把不同文件交給有界執行緒池並行處理，但必須維持所需的同鍵排序，以及第九章的連續完成 offset 水位。不同的分享消費協議或工作佇列有不同模型，不能混為一談。

若稽核與通知都要看每一個事件，應使用不同消費群組，各自維護進度；把它們放進同一群組是分工，每則只會分給其中一個成員，而不是兩個功能都收到。反過來，如果所有 worker 都是做相同文件轉換，錯用不同 group_id 就會讓每台都做一遍，浪費算力並增加重複副作用。

追平積壓需要額外容量

如果系統每秒正好處理新到達量，既有積壓永遠不會消失。在到達率 λ、總處理率 μ、積壓 Q 都近似穩定，且 μ > λ 時，追平時間約為 Q／(μ − λ)。例如尖峰仍是 115.74 份／秒，量測總處理率為 150 份／秒，積壓 18,000 份，約需 18,000／34.26 ≈ 525 秒，也就是 8.8 分鐘。若要十分鐘內追平，所需處理率至少為 115.74 + 18,000／600 = 145.74 份／秒。

自動擴展（autoscaling）不應只看 CPU。CPU 低可能是外部限流，也可能是分區熱點把單一工作者塞滿，而其他工作者閒置。可聯合觀察最老工作年齡、按成本加權的 backlog、每分區輸入／處理率及擴展啟動時間。新 worker 若要下載模型或恢復狀態，也不是建立容器後立刻有完整容量；擴展冷卻期則可避免反覆加入退出導致持續重新平衡。

練習：16 個分區，增加到 40 個普通 consumer 成員，吞吐為何可能不變？

因為最多只有 16 個成員能取得分區；也可能原本瓶頸就在下載、資料庫或外部配額。先檢查每分區負載和工作者利用率，再選擇增加分區、在分區內對獨立文件並行、拆開工作階段，或提升真正瓶頸的容量。直接再加 40 個 consumer 並不能診斷問題。

11.2 真實系統中的分區 Partitioning in real-life systems

分區（partitioning）把資料或工作切成可獨立分配的單位；複寫（replication）則為同一份資料建立多份副本。前者主要增加可平行處理的範圍，後者主要改善故障容忍與某些讀取能力。四個分區各三份副本是十二份分區副本，不等於十二條互不相關的寫入序列。

再分清邏輯分區與實體放置。平台可先將文件鍵映射到 256 個邏輯桶，再以目錄將桶映射到工作者或資料節點。增加機器時搬移部分桶，不必立刻改變文件到桶的函數。這種間接層讓分配較有彈性；代價是要維護桶目錄、版本與交接流程。Kafka 的 topic partition 也可在 broker 之間移動；移動既有分區和增加分區數，是兩種不同的操作。

同一個分區鍵不必沿整條管線照抄。如果工作事件按文件分區，通知端按供應商限額分組，系統就在此處重新分配資料（repartition）。重分配會付出網路、緩衝與新排序範圍的成本；跨分區 join、全租戶聚合及全域唯一約束也需要額外協調。面試時說「hash 一下就能擴展」仍漏掉了這些操作。

產品提供的分區常同時是容量與順序邊界。例如 Amazon Kinesis Data Streams 的概念文件說明 partition key 經雜湊映射到 shard 的鍵範圍。本文不把特定產品當下的配額數字當成永久規則；實際規劃要查目前容量模式、帳戶限制與讀寫方式。對任何系統，都要問「一個熱鍵可以用到多少容量」，而不只問整個叢集容量。

分區數也有成本：每分區的記錄、檔案、索引、緩衝、複寫任務及監控都占資源。分得太少會限制分工，分得太多則增加控制面與小批次成本，亦可能讓恢復更慢。合理做法是以預期工作負載、成長空間和已量測的每分區開銷選初始範圍，並先設計可執行的擴展路徑。

練習：把 broker 數從三台增加到六台，既有 partition 數一定翻倍嗎？

不會。實體節點、分區數與複寫因子是不同維度。可以把原有分區副本重新放到六台，改善每台負載，卻維持原本分區數與鍵映射。若另外增加 topic 分區數，producer 的鍵到分區映射可能改變，必須另行處理同鍵排序與切換問題。

11.3 分區策略 Partitioning strategies

分區鍵會影響資料模型，選擇時也要考慮負載平衡以外的要求。先列出哪一些操作必須在一起：同一文件的版本變化可能需要序列化，不同文件的文字擷取則可以完全獨立。若只需要每文件有序，就不應為了方便而要求整個租戶的所有文件都走同一條序列。

具體看熱點：假設一個大型租戶占尖峰 40%，也就是約 46.3 份文件／秒。以 tenant_id 為鍵，不論有 32 個還是 3,200 個分區，這個租戶仍只落到一個分區。若該分區的工作者串行處理每份兩秒，服務率只有每秒 0.5 份，佇列會快速增長。更多不相干的空分區無法幫忙。

把鍵改成（tenant_id, document_id），可把不同文件分散，仍讓同文件的狀態在一起。若希望租戶可整體搬移，可再採 tenant_id → 多個子桶的目錄。這不會解決單一超大文件：要拆成頁面／區塊工作，再由彙整器組合，並處理順序、缺頁、重試及部分失敗；否則單一工作本身就是不可再平行化的最小單位。

加鹽（salting）是在熱鍵附上子鍵，使一個邏輯鍵分成多條實體流。拆開之後，讀取需要查多桶再合併，全鍵排序也需要協調，這些都是額外成本。若正在統計可交換的頁面計數，分桶後相加很自然；若正在套用「發布、撤回、再發布」的狀態變化，隨機撒到不同桶卻沒有版本規則就會錯。

還要區分鍵數均勻、位元組均勻、運算成本均勻。一萬個小文件和一個巨大掃描 PDF 可能鍵數極不均卻成本相似，反之亦然。可用頁數、格式或歷史耗時估計工作成本，但這些估計有誤差，應保留尾端處理與租戶配額。若依負載任意改變同鍵目的地，則需要路由版本和狀態交接，否則容易失去排序。

練習：只要用「租戶＋時間」當鍵，就能讓最新事件平均分散嗎？

取決於時間粒度與分區方法。按租戶與當天範圍分區，今天的所有寫入仍集中於少數分區；對完整高精度時間做雜湊雖可分散，卻可能把同一文件的連續事件打散。若只需要文件有序，文件鍵通常更直接；日期可以用於查詢索引或儲存布局，不必同時作為事件排序鍵。

11.4 請求路由 Request routing

知道「文件屬於桶 72」還不夠，客戶端仍需知道桶 72 現在由哪個節點或 leader 負責。這裡有兩個函數：key → logical partition，以及 logical partition → current owner。第一個可以長期穩定，第二個會因擴展、故障與維護而改變。將兩者分開，是避免每次換機器都重算所有業務鍵的關鍵。

常見路由模式有三種。智慧客戶端（smart client）取得分區目錄並直接連 owner，少一跳但 SDK 複雜；路由代理（routing proxy）集中處理目錄和重試，客戶端簡單但增加一層容量與延遲；任意節點轉送（forwarding）讓客戶端先連到任一節點，由節點轉到 owner，但要限制轉送次數與迴圈。選擇取決於客戶端種類、可控性與請求成本。

快取目錄不可避免會過期。假設客戶端拿著版本 12，把請求送到舊 owner A，但桶已以版本 13 交給 B。A 應回傳明確的過期路由或重新導向資訊，客戶端更新可信目錄後，以原本冪等鍵重試。不要無限 A → B → A 轉送，也不要在結果未知時以新 key 重建工作。更新路由、重試與整體 deadline 仍需遵守第九章的限制。

路由資訊和授權是不同事情。知道 tenant_id 該送到哪裡，不代表有權存取該租戶；每一個實際處理請求的服務都應驗證授權。多租戶環境尤其不能把使用者提供的 tenant_id 直接當作可信任的路由及權限依據。路由版本也不是對外洩露全部叢集拓樸的理由，公開 API 可由代理封裝內部細節。

故障期間，目錄控制面可能暫時不可用。快取既有映射能讓未受影響的分區繼續工作，但無法憑空安全選出新的寫入 owner。若要求單寫入者語義，就需要權威的 leader／擁有權協議；「連不上 A，就自行猜 B」會導致兩個節點都接受寫入。控制面可用性、資料面可用性與一致性承諾必須一起設計。

練習：一筆請求在舊 owner 完成後，客戶端才收到路由過期錯誤。直接送到新 owner 安全嗎？

只有在原操作具有可跨交接保留的冪等識別／去重狀態，或可以先查核結果時才安全。路由層錯誤不自動證明原操作沒有生效。遷移方案需包含業務狀態與去重狀態，而非只搬主要文件資料；重送仍須沿用同一個業務 key。

11.5 重新平衡分區 Rebalancing partitions

重新平衡是改變誰負責哪些分區，可由成員加入、退出、失聯或容量變化觸發。先區分兩種工作：broker 分區副本的搬移，涉及儲存、複寫與 leader 放置；consumer 指派的變化，涉及消費進度、記憶體／本地狀態及未完成副作用。它們都叫 rebalance，卻不是同一個操作。

最簡單的消費交接是全體停下、重算分配、再一起開始，容易推理但影響範圍大。增量／合作式交接只轉移需要移動的分區，未受影響者繼續工作。這可以減少停頓，卻不會消除狀態恢復或外部副作用的交接責任。Kafka 4.1 的 consumer rebalance protocol 文件說明新版協議的增量特性與版本設定；不能把某一版本的 heartbeat 參數用法當成所有協議通用。

一個可推理的交接時序

  1. 準備：協調者決定桶從 A 移到 B，為交接分配新的 ownership epoch。
  2. 停止新工作：A 不再接收此桶的新任務；已執行工作在有界時間內完成，或留下可重試狀態。
  3. 保存進度：只保存已真正完成的連續進度，並持久化必要狀態與去重記錄。
  4. 撤銷舊權：權威儲存拒絕舊 epoch 的後續寫入，避免 A 復活後繼續修改。
  5. 恢復與接手：B 載入快照及後續變更，從權威進度開始；未完成工作可以重播。
  6. 核對：檢查 lag、錯誤、重複效果與 owner 版本，穩定後才清理舊狀態。

這是概念協議，不是可以套到任意儲存系統的六行腳本。某些協議會先複製再暫停，另一些會用交易或租約控制交接；真正必要的是交接前後有清楚的權威點，且舊擁有者不能在新擁有者開始後破壞不變量。

為什麼要隔離權杖（fencing token）？A 可能只是長時間暫停，不是真的死掉。協調者將桶交給 B 後，A 恢復並完成先前的 SQL 更新；即使 broker 已拒絕 A 提交 offset，外部資料庫仍可能接受它的舊寫入。若外部寫入要求 epoch 與目前權威版本一致，並以原子方式檢查與更新，就能拒絕舊 owner。只在處理開始時讀一次 epoch，不足以阻止檢查後發生的交接。

對不支援 fencing 的外部郵件 API，仍需使用供應商冪等鍵或承認剩餘窗口。不要以為消費群組重新分配完成，所有背景執行緒就神奇地停止。需要取消、限時排空、禁止舊任務提交，以及可恢復的結果記錄。把 heartbeat timeout 調得非常小也可能把暫時的 GC 或網路抖動誤判成死亡，造成反覆搬移。

狀態搬移與恢復時間

假設每分區本地索引為 8 GiB，有四個分區需要轉移。若它們共用 200 MiB／秒的有效復原頻寬，光搬移 32 GiB 就約需 163.84 秒，還不含重放增量、索引建置與外部限流。若直接以「四個分區並行，每個都用 200 MiB／秒」估算 40.96 秒，就是把共享瓶頸算了四次。

常用改善包括黏著指派（sticky assignment）、小步擴展、限制同時遷移量、預先恢復備用狀態，以及保留穩定成員身分來減少短暫重啟的無謂搬移。這些都涉及取捨：少搬移可能保留較不均勻的負載；多留備援增加費用；等候舊成員的時間長，真正故障時接手也較慢。指標應包含分區可服務時間，而不只是「協議執行花了幾毫秒」。

練習：新 owner 已開始，舊 owner 稍後才回報 offset 500 完成。能接受這個提交嗎？

不能只因數字比較大就接受。必須驗證這個提交屬於目前有效的 ownership epoch，且 500 前的工作都符合正確的完成定義。舊 owner 的提交可能跨過新 owner 尚未確認的缺口。它產生的外部副作用也要以去重或 fencing 處理，不能僅靠拒絕 offset 來修正已發生的寫入。

11.6 一致性雜湊 Consistent hashing

先看直接取餘數：owner = hash(key) mod N。當節點數由四變五，同一個雜湊值對 4 與 5 的餘數往往不同。在雜湊均勻、節點編號保持對應的理想模型中，約只有五分之一的鍵留在原編號，其餘約 80% 需要換地方。擴展一台機器卻搬大部分資料，對快取命中和持久儲存都可能很昂貴。

一致性雜湊將雜湊空間看作一個首尾相接的環，把節點放到環上的位置。鍵也映射到環上，沿指定方向找到下一個節點作為 owner。加入節點只切走相鄰的一段範圍；移除節點時，其範圍由後繼節點接收。它改善的是成員集合變動時的鍵搬移範圍，名稱裡的「一致性」不是資料庫的強一致性承諾。

用 0 至 99 的小型教學環：A 在 20、B 在 50、C 在 80，採順時針下一個節點。原本鍵 51 至 80 歸 C；加入 D 在 65 後，鍵 51 至 65 改歸 D，66 至 80 仍歸 C，其他鍵保持原 owner。環跨過 99 回到 0，所以 81 至 99 及 0 至 20 由 A 負責。此小環只示意映射，不假設它本來就完全均衡。

虛擬節點與預期搬移量

每台實體機器只放一個隨機位置，切出的範圍可能很不平均。虛擬節點（virtual nodes，vnodes）讓同一台機器占有多個 token，將許多小範圍加總，以改善分布與搬移粒度；較大的機器也可按容量取得更多 token。Dynamo 論文第 4.2 節討論了這個做法及異質節點問題。

在理想均勻分布與等容量節點下，由 N 台增加到 N + 1 台，新節點最終應承擔約 1／(N + 1) 的鍵，因此一致性映射可把需移動的量控制在接近此比例。四增五是約 20%，相較直接取餘數的約 80%。這是期望值與模型，不是任何資料分布都能精準達成；鍵大小不一時，20% 的鍵也不一定等於 20% 的位元組。

也不是所有一致性雜湊都必須使用環。Rendezvous hashing 可以按鍵與候選節點的分數選 owner；jump consistent hash 使用很少記憶體計算桶，但有連續桶編號等使用限制。Lamping 與 Veach 的論文明確列出 jump 方法的適用限制。選演算法要看任意節點加入／移除、權重、複本放置及目錄需求，而非只看程式碼短不短。

一致性雜湊無法代替的五件事

  1. 熱鍵處理：一個占 40% 請求量的 tenant_id 仍映射到一個 owner；更多 vnode 不會把同一鍵拆開。
  2. 資料一致性：環不會選出唯一合法 leader，也不會防止網路分割後兩方同時寫入。
  3. 實際資料搬移：演算法給出新目的地，但資料仍要複製、追趕、切換、驗證與清理。
  4. 複本故障隔離：相鄰 token 可能屬於同一實體機器；副本需跨實體節點及所要求的故障域放置。
  5. 查詢與交易：跨鍵 join、全域排序或跨分區原子交易，不會因為換了雜湊函數就免費完成。

回到文件平台，較完整的方案是：以（tenant_id, document_id）或明確的子桶規則識別獨立工作，以穩定邏輯桶隔離業務鍵與實體機器變動；若需要減少節點變更的搬移，使用適合的一致性映射；再配上帶版本的目錄、冪等事件、可查詢工作狀態與安全交接。這些機制各解一個問題，組合後才是可運作的系統。

練習：一個節點 CPU 95%，其他都 20%。增加 vnode 一定能改善嗎？

不一定。若原因是大量一般鍵剛好落在過大的範圍，更多且合理配置的 vnode 或重新放置可能改善。如果原因是單一熱鍵、特殊大型文件、外部依賴慢或某節點硬體異常，就需要拆鍵／拆工作、隔離租戶、調整限流或修復節點。先量測每鍵及每分區的成本分布，再決定改映射還是改工作模型。

章末設計題：一個完整擴展提案

假設平台在尖峰時累積 18,000 份文件，且最大租戶占 40% 工作量。請提出一份能在十分鐘內追平、單台故障仍能服務的擴展計畫，並交代排序、路由及重平衡。

展開參考推理

首先需至少約 145.74 份／秒的有效總處理能力，並以 2 CPU-seconds／份估計基本計算量。若仍用 60% 使用率目標，約需 486 核可用算力，尚須加其他開銷與故障餘裕。這個恢復目標比只承受正常尖峰的 386 核更高。

不以 tenant_id 單鍵序列化大型租戶，改按文件切分或採租戶子桶；同文件的狀態以版本及冪等事件維持。新增機器只提升非瓶頸資源沒有用，需同時驗證約 729 MB／秒的原件讀取能力（145.74 × 5 MB，尚未算其他 I/O）。選定邏輯分區與有界分區內併行後，量測熱點與公平性。

擴展時以版本化目錄逐批交接，保存權威 offset／去重狀態，以 fencing 或等價原子條件拒絕舊 owner；監控最老工作年齡與實際追平速率。若新容量啟動需要數分鐘，還須把啟動期間新增的積壓算進十分鐘目標。不能只把 486 核寫進提案，就宣稱已證明 SLO。
