第 09 章 · Reliable delivery

可靠傳遞：讓失敗有明確的結果

「發出請求」與「完成業務」之間，隔著網路、程序、儲存與外部服務。本章把這些邊界拆開，回答逾時後究竟能不能重試，以及如何讓訊息重送而不重複改變業務狀態。

  • 能把逾時、失敗與結果未知分開處理。
  • 能設計帶冪等鍵、退避、總期限與重試預算的呼叫流程。
  • 能畫出 offset 與外部副作用之間的故障窗口，並說明 exactly-once 的範圍。

9.1 還要知道哪些可靠性原則？ What else to know to build reliable scalable fast systems

沿用「多租戶文件處理與通知平台」：租戶上傳文件，API 建立工作，工作者執行文字擷取，資料庫保存結果，最後寄送完成通知。這段流程至少有四個獨立的提交點，無法視為單一動作。若文字擷取完成後工作者斷線，文件可能已處理成功，通知卻還沒發出；若郵件供應商接收後回應丟失，我們甚至不知道通知是否已寄出。

先寫下不變量（invariant），再選技術。本章的設計目標是：同一個文件版本只產生一份正式結果；同一個業務工作只計一次費；已受理的工作可追蹤至成功或有原因的終止；不同租戶的權限不得因重試而混用。至於通知，若供應商沒有去重功能，必須明說可能重複，不能拿訊息佇列的保證替供應商背書。

可靠性不是「永遠成功」。 它也包括準確地拒絕、保留待處理狀態、讓操作者能恢復，以及在承諾無法達成時讓使用者知道。顯示「失敗」但實際繼續計費，比明確顯示「結果確認中」更危險。

將工作建模成狀態機（state machine），例如 accepted → processing → completed；另有 retry_wait、rejected、needs_review。狀態更新帶有版本號，以條件寫入避免舊工作者覆蓋新結果。每個請求同時記錄 tenant_id、job_id、event_id、attempt_id：job_id 代表業務意圖，event_id 代表事件，attempt_id 代表一次嘗試。不能每重試一次就換 job_id，否則系統會把重試當成新工作。

將「成功」分成可驗證的邊界

也要區分安全性（safety）與活性（liveness）。「不重複計費」是安全性；「所有已受理工作最終被處理」是活性。永久停工可以避免重複計費，卻失去活性；無限制地重試可以顯得很積極，卻可能拖垮整個系統。可靠設計要同時說明故障假設、恢復路徑及有界資源。只選一個交付語義，還無法回答故障後該怎麼辦。

練習：API 回傳 202 Accepted，是否代表可以立刻刪除原始文件？

不一定。202 表示受理，並不表示處理完成。只有當平台已將所需原始資料可靠保存，且契約允許客戶刪除本機副本，才可如此操作。若 API 只是把一個短期下載網址放入記憶體佇列，尚未保存原始文件，就不能作出這個承諾。設計時應讓工作狀態與文件保存狀態分開可查。

9.2 逾時 Timeouts

逾時是呼叫端停止等待，不代表服務端停止執行，更不代表服務端沒有提交。沒有逾時時，一個卡住的依賴會占住連線、執行緒、記憶體和並行名額。以 Little’s Law 的穩態近似看，若每秒有 200 個請求、平均占用資源 0.1 秒，約有 20 個在途請求；若平均卡到 10 秒，就可能需要約 2,000 個名額。這些數字是教學假設，實際仍須考慮排隊及流量波動。

常見計時器至少有四種：連線逾時（connection timeout）、讀取逾時（read timeout）、單次嘗試逾時（attempt timeout）、整體期限（deadline）。讀取逾時有時只限制兩次資料讀取之間的空白，若對方持續每秒吐一個位元組，整個請求仍可能拖很久。必須查清 SDK 的計時範圍，特別是 DNS、TLS 握手、連線池等待、串流及重新導向是否算在內。AWS 的逾時設計說明也特別提醒計時範圍與冷連線的差異。

假設「建立工作」API 的端到端期限是 1,000 毫秒，入口已用掉 80 毫秒，還要保留 120 毫秒封裝回應與緩衝，那麼下游所有嘗試加等待只能使用 800 毫秒。不能給資料庫 800 毫秒、佇列也 800 毫秒，然後宣稱 API 仍會在一秒內完成。期限應沿呼叫鏈傳遞；每一層以剩餘預算減去自身必要開銷，決定是否還值得發出下一次請求。

剩餘預算 = 整體期限 − 已花費時間 − 回應安全餘額

下一次嘗試允許時間 = min（單次上限，剩餘預算 − 預定退避時間）

如何挑初始值？量測同區域下游的延遲分布，依可接受的誤判率選一個高分位數，再加網路與冷啟動餘額。例如 p99.9 為 180 毫秒不等於應盲設 180 毫秒：樣本是否含失敗？是否只量到服務內部而漏了排隊？大文件與小文件是否混在一起？使用者跨洲時又多了多少延遲？這些問題比背一個「標準 timeout」更重要。

大量並行依賴還會放大尾端機率。假設 20 個獨立呼叫各有 0.1% 機率超過門檻，至少一個超過門檻的機率約為 1 − 0.99920 ≈ 1.98%。真實世界可能有共同網路故障，並不獨立，因此不能把此公式當作可靠性的精準預測。它只提示我們：單次呼叫的漂亮百分位不會自動等於整條鏈路的百分位。

誤區：HTTP 連線斷掉就等於工作取消。 取消是一個需要合作的控制訊號。服務端可能沒收到，或已跨過不可撤銷的提交點。文件處理應有可查詢的 job_id；必要時另設明確的取消狀態及取消檢查點。
練習：期限剩 350 毫秒，退避 120 毫秒，單次上限 300 毫秒，需保留 50 毫秒回應。還能重試嗎？

最多只剩 350 − 120 − 50 = 180 毫秒給下一次嘗試。若此 API 的最小有效預算低於 180 毫秒，可以用 180 毫秒上限試一次；若連建立連線通常都需要 200 毫秒，應停止同步重試，回傳可查詢的待確認結果或明確失敗。不能因為單次上限是 300 毫秒，就借用不存在的時間。

9.3 請求失敗了怎麼辦？ What to do with failed requests

先分類失敗原因，再決定是否「重送」。若檔案格式不支援，重試一萬次仍不會變成支援；若暫時限流，等待可能有用；若回應在提交之後丟失，必須查詢原操作或使用相同冪等鍵。把三種情況都轉成同一個「發生錯誤」會迫使上層猜測，也讓客服無法定位。

失敗分類與平台處置
觀察到的情況含意合理下一步
內容驗證失敗相同內容不會因等待而修好回傳欄位或格式問題，不重送原請求
限流或短暫不可用未來可能恢復，現在可能過載遵守服務契約、退避、限量重試
連線中斷／提交結果未知業務可能已生效查詢原操作，或持相同冪等鍵重送
工作者程式無法解析訊息可能是毒丸訊息或版本不相容隔離、保留診斷資訊、修正後受控重播
已確定部分業務完成跨系統不一定能原子回滾持久化進度，繼續未完成步驟或執行補償

對非同步工作，可設重試佇列（retry queue）與死信佇列（dead-letter queue，DLQ）。DLQ 是隔離與調查機制，不是垃圾桶。至少保存事件識別、原始版本、錯誤類別、首次失敗時間、最後失敗時間及嘗試次數；文件正文及個資不應任意複製到無限制保留的錯誤日誌。監控也要看最老失敗工作的年齡，不能只看今日 DLQ 新增量。

重試佇列會改變排序。假設同一文件版本先有「已完成」，後有「撤銷分享」；若前一則移到延遲佇列，後一則直接通過，消費端就不能只靠佇列順序推斷狀態。可選擇停住該文件鍵、攜帶單調版本並拒絕過期狀態，或讓操作本身可交換。選哪一種，要看業務要求。維持全分區停住雖然簡單，可能讓同一分區的其他租戶一起等。

跨系統補償（compensation）也不是時間倒流。例如已寄出的郵件不能撤回；可以寄更正通知，但那是另一個可見事件。若處理失敗要退回工作點數，應記錄「沖回原計費項目」的獨立帳目，並讓沖回本身也有冪等鍵。把資料表數值直接減回去，可能被併行操作或第二次重試破壞。

練習：一則無法解析的訊息一直卡住分區，應立即跳過嗎？

先看契約。如果跳過會讓後續狀態不完整，需隔離該業務鍵或暫停分區並告警。如果事件彼此獨立，可以把原事件可靠寫入 DLQ 後才提交原進度，並記錄明確的終止狀態。DLQ 寫入本身也可能失敗，不能「嘗試寫一下」就提交 offset。修復後的重播要保留原事件識別，避免把重播當成新業務。

9.4 何時重試？ When to retry

重試要同時通過三道門：失敗可能是暫時的、操作可安全重做、剩餘時間與容量仍容許重做。HTTP 狀態碼只是訊號，不是完整決策。429 常需延後，503 常代表暫時不可用；401 可能需要更新認證，卻不該拿同一組失效憑證無限重送；400 通常需要修改輸入。特定 API 可以有不同契約，例如短暫的資源傳播延遲，因此決策表應依服務文件建立。

冪等性（idempotency）指多次執行同一個意圖，產生與一次相同的目標效果。它不要求所有回應位元組都相同；第一次刪除可能回傳已刪除，第二次回傳不存在，但最終資源都不存在。HTTP 的方法語義與自動重試限制見 RFC 9110 §9.2.2。實務上也不能只看方法名稱：若錯把寄信寫成 GET，那仍然具有副作用。

文件平台的建立工作 API 接收 Idempotency-Key。去重鍵應包含租戶與操作範圍，例如（tenant_id, operation, key），避免兩個租戶偶然使用相同 key 而拿到彼此結果。伺服器同時保存請求內容摘要：同一 key 搭配不同文件版本時回傳衝突，不能悄悄把新的意圖當成舊操作。一次真正的新處理應使用新 key；同一次因網路失敗而重試則沿用舊 key。

BEGIN TRANSACTION
  嘗試插入 request_keys(tenant_id, operation, key, payload_hash)
  若已存在：驗證 payload_hash，回傳既有 job_id／狀態
  若新插入：建立 job，建立待發送的 outbox 事件
  保存 key 對應的 job_id
COMMIT

這裡的關鍵是「建立去重記錄」與「產生業務效果」處於同一筆可原子提交的交易。先寫 key 再做事，可能在兩者間崩潰而永久漏做；先做事再寫 key，可能在崩潰後重複做。唯一索引則處理兩個相同 key 同時到達的競爭，不能用「先 SELECT，查不到再 INSERT」而沒有唯一約束。AWS 的冪等 API 討論說明了以呼叫者識別碼區分意圖的重要性。

還有保留期間（retention）問題。若 key 只存 24 小時，延遲兩天抵達的舊請求可能又被當成新請求。保留期間須涵蓋最大合理重試與重播窗口；若不能永久保存，可搭配請求建立時間、工作版本與拒絕過舊操作的契約。要讓重試安全，得一起定義鍵的範圍、原子性、併行處理和有效期間。單獨建立一個資料表還不夠。

練習：把完整請求內容的雜湊當作冪等鍵，就不用讓客戶傳 key 嗎？

不一定。同一租戶可能真的想對同一份文件執行兩個獨立工作，例如重新以新模型處理。內容相同不代表業務意圖相同。呼叫者提供的 key 表示「這是同一個請求」，內容摘要則負責檢查 key 是否被誤用；兩者的目的不同。

9.5 如何重試？ How to retry

立即重試對偶發封包丟失可能有效，對過載卻可能是加速器。假設每層最多共嘗試三次，三層各自重試，最下游最多看到 3 × 3 × 3 = 27 次呼叫。注意「三次嘗試」與「三次重試」不同，後者通常包含首次後的三次，會變成每層四次。設計文件應明寫 total attempts，避免配置解讀歧義。

指數退避（exponential backoff）以 k 從 0 起算，k = 0 代表首次重試，等待上限為 min(cap, base × 2k)；全抖動（full jitter）則在零到此上限間隨機選等待值。例如 base = 100 毫秒、cap = 1,600 毫秒，前四次上限是 100、200、400、800 毫秒，均勻分布下平均等待分別是 50、100、200、400 毫秒。這只是本例的策略，不是對所有工作都適用的預設值。

只有退避仍不夠。若一萬個客戶端都在最大等待上限反覆重試，持續負載仍可能過高。加入重試預算（retry budget）：例如每秒正常請求約 1,000 次時，額外重試長期限制在 100 次，並容許很小的短期突發。可以用 token bucket 管理，也要分租戶限制，避免單一大客戶吃光預算。這是控制放大率的手段，不代表所有失敗都能在期限內補救。

安全的流程依序為：檢查取消訊號與整體期限 → 判斷錯誤是否可重試 → 檢查操作冪等性 → 取得重試配額 → 計算退避 → 檢查等待後還有足夠嘗試預算 → 使用相同業務識別重送。若服務提供 Retry-After，應依其契約作為不得過早重試的限制；客戶端期限若比建議等待短，就停止同步重試，而不是忽略建議。

在多層系統裡，選定一個主要重試層，明確知道 SDK、代理和工作佇列是否還有內建重試。斷路器（circuit breaker）可在依賴明顯失效時暫停呼叫，再以有限探測恢復；併發限制和負載卸除（load shedding）則阻止過量在途工作。三者與退避互補，但狀態轉換、半開探測和恢復行為都需要故障測試。

練習：平均每次失敗率為 10%，最多共嘗試三次，流量會增加多少？

若假設每次失敗彼此獨立且失敗率固定，期望嘗試數為 1 + 0.1 + 0.01 = 1.11，也就是增加約 11%。三次都失敗的機率是 0.001。這個漂亮結果不適用於過載：過載時失敗高度相關，重試又會提高失敗率，必須使用壓力測試與重試預算，而不能拿獨立模型保證可用性。

9.6 訊息交付保證 Message delivery guarantees

「至少一次」與「恰好一次」必須帶著主詞：哪一則訊息、哪個消費群組、哪一段流程、哪些可觀察的效果？最多一次（at-most-once）容許遺失但避免重送；至少一次（at-least-once）容許重送，並在其保留、持久性與恢復假設內努力確保處理機會；恰好一次（exactly-once）要求指定範圍的可觀察結果等同處理一次。它不表示 CPU 永遠只跑一次，也不表示所有外部世界的行為都被納入同一交易。

同一封信寄兩次，不能扣兩次款

左右對照：觀察「回應遺失」之後，重試如何影響副作用。

離開圖畫，回到工程：Exactly-once 必須說清楚涵蓋哪個邊界；訊息層的保證不會自動包住第三方副作用。

看兩個最小故障窗口就能理解：若先標記訊息完成，再修改資料庫，程序在中間崩潰，資料庫永遠漏掉這件事；若先修改資料庫，再標記完成，程序在中間崩潰，訊息會被重送，資料庫可能多做一次。把這兩步交換順序，無法同時消除兩個窗口。解法是同一原子交易、在效果端去重，或接受並明確管理這個限制。

對平台內部資料庫，可建立 inbox 表，以（consumer_name, tenant_id, event_id）為唯一鍵，consumer_name 區分不同處理功能，並在同一資料庫交易中插入 inbox、更新文件結果及寫入通知 outbox。交易提交前崩潰，所有更改都不存在；提交後重播，唯一鍵讓第二次跳過已完成效果。outbox 發送器把通知事件送到 broker 時仍可能重複，因此通知消費端也要檢查事件識別。這種「可重送的運送＋效果端去重」是整體設計，不是單靠 broker 的設定。

Kafka 的冪等 producer 可避免特定 producer 重送造成日誌中的重複；Kafka 交易可以把寫入多個 Kafka 分區和輸入 offset 更新納入同一交易，並配合讀取已提交資料的消費端，形成 Kafka 讀取、處理、寫回的原子邊界。它不會自動把任意 SQL 資料庫、付款 API 或郵件寄送一起提交。這個邊界由 Kafka 4.1 設計文件說明。應用程式以新身分重新送出相同業務事件，也不是 producer 協議能任意辨識的同一意圖。

比較其他產品時也要看細則。例如 Google Cloud Pub/Sub 的 exactly-once 說明限定了訂閱方式與區域範圍，並要求消費端管理處理進度及確認結果。這些有用的交付保證，仍不等於能撤銷一封已經寄出的外部郵件。對通知供應商有冪等鍵時，沿用 notification_id；沒有時，需在「可能漏寄」與「可能重寄」之間作產品選擇，或另做狀態核對。

練習：郵件已寄出，工作者在寫入 sent = true 前崩潰。只加一張本地去重表能保證不漏寄也不重寄嗎？

不能。若寄之前標記 sent，標記後寄之前崩潰就漏寄；若寄之後標記，寄後標記前崩潰就可能重寄。除非供應商參與相同交易、支援可靠的冪等請求，或提供足夠的查詢核對協議，否則本地表無法消除外部副作用的未知窗口。應把保證縮小到「平台只建立一個通知意圖」，並交代供應商層的限制。

9.7 消費進度 Consumer offsets

日誌型訊息系統的 offset 是分區內的位置，不是跨分區的時間戳，也不是業務完成證明。以 Kafka 一般消費群組為例，committed offset 通常表示重新啟動時要讀取的下一個位置。若完成到 offset 104，就提交 105。要分開三個數字：已拉取的位置、已真正處理完成的位置、已持久化提交的位置。三者混在一起，最容易造成「明明抓到資料卻漏處理」。

上例最多只能提交 101，表示從未完成的 101 重新開始。若因為 103 已完成就提交 104，重啟會跳過尚未完成的 101。可維護完成集合與連續完成水位（contiguous completion watermark），或讓同分區串行。若日誌存在控制記錄或已移除記錄造成的 offset 間隙，演算法要依實際取得的記錄序列與客戶端提供的位置管理，不能假設每個整數都必有一則業務訊息。

自動提交也不等於工作完成。若 poll 把一批訊息交給執行緒池後立即繼續 poll，自動提交可能早於背景任務的副作用完成。手動提交則給我們控制，但依然不能把外部資料庫交易和 broker 提交變成原子操作。Kafka 的 KafkaConsumer 官方 API說明了將處理結果與 offset 存入同一外部儲存交易的模式。

我們的平台可選兩種不同方案。方案甲：結果和 inbox 去重在同一資料庫交易中提交，然後提交 Kafka offset；若中間崩潰，重讀但不重複效果。方案乙：把每個分區的 next_offset 與結果存入同一資料庫交易，恢復時以這張表 seek，並使用擁有權版本阻止舊工作者繼續寫入。方案乙需要自己正確處理分區交接與權限；不能一邊以資料庫為準，另一邊又讓 broker 的舊 offset 覆蓋它。

非同步提交還要避免進度倒退。例如 offset 200 的提交失敗，稍後 250 已成功；這時不應無條件重送舊的 200。單純多重送通常只造成重播，但若再搭配不正確的副作用處理，問題會擴大。正確策略需依客戶端的回呼與排序契約設計，分區被撤銷時尤其不可讓舊回呼替新擁有者提交。

監控 consumer lag 時要註明算的是「日誌末端減讀取位置」還是「減已提交進度」。前者漂亮可能只是把大量訊息堆到工作者記憶體。另加最老未完成事件年齡、業務成功率、每分區落後量及重播率。offset 是位置；一則大型文件可能比一千則小通知更耗時，單靠筆數無法估算恢復時間。

練習：結果資料庫與 next_offset 已在同一交易提交，但 Kafka 提交失敗。重新啟動應從哪裡讀？

取決於事先選定的權威來源。如果採用外部 offset 方案，以已提交的資料庫 next_offset 為準，完成分區擁有權驗證後 seek；Kafka 的舊進度不應推翻它。如果採用 inbox 去重方案，可從 Kafka 舊位置重播，由資料庫唯一鍵避免重複效果。兩者都能正確運作，但不能沒有明確契約地混用。

本章設計檢查

  • 每個遠端呼叫都有明確計時範圍與整體期限。
  • 重試會保留業務識別，有退避、抖動、次數及容量預算。
  • 每一個 exactly-once 主張都寫明交易邊界、故障假設與外部限制。
  • offset 只跨越真正完成的連續前綴；副作用與進度之間的窗口有明確處理。
