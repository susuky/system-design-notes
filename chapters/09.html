重送之前，先知道做到哪裡

使用者按下轉檔，畫面轉了十秒後顯示逾時。後台可能已經存好結果，帳單也可能已經記上一筆。這一章替這段空白補上可查詢的狀態，再決定哪些工作可以重送、何時重送，以及重送後如何接回原來那份工作。

回了成功，使用者拿到結果了嗎？

先跟著一份文件走一次：API 接受工作、worker 開始轉檔、資料庫記錄結果、通知服務寄信。每個階段都能回傳「成功」，但它們說的是不同進度。使用者要的是可下載的檔案；broker 的確認則表示訊息已按設定交付。把完成點寫進 API 契約，前端才知道何時顯示「已收到」，何時顯示「轉檔完成」。

完成點保存什麼下一個請求怎麼接續
工作已受理job_id、文件版本、目前狀態用 job_id 查進度
結果已提交結果位置、狀態版本、計費紀錄回傳同一個結果
通知已受理notification_id、供應商回條查詢這封通知的狀態

這裡有三種識別：job_id 跟著整份工作，event_id 跟著某次業務事件，attempt_id 記錄一次嘗試。同一事件重送時，前兩者延續，第三個才換新。記錄裡因而看得出「同一件事試了三次」，也能將三次嘗試收斂成一筆正式結果。

再寫下兩條業務規則：同一文件版本只有一份正式結果；同一次計費意圖只扣一次款。 worker 更新狀態時帶上版本，例如只允許 processing, version=7 轉成 completed, version=8。慢了半拍的舊 worker 遇到版本不符，就讀取已提交的結果。

API 已回 202，worker 隨即當機，重新整理頁面應該看到什麼？

頁面使用已保存的 job_id 查詢，得到 queued 或 processing，以及可重新排程的工作狀態。受理回應發出前，工作紀錄與待發事件要已落在持久儲存；可以把 job 與 outbox 放進同一筆資料庫交易，再由 relay 發送事件。

十秒沒回應，後台現在做到哪裡？

逾時是在替等待設上限。請求離開客戶端後，伺服器可能正在排隊，也可能已經寫完結果，只差回傳。客戶端等到期限就釋放自己的等待資源，後續用 job_id 查結果；需要停止計算時，另外傳遞取消訊號，讓服務在合適的檢查點停下來。

等待會佔容量。每秒進來 200 個請求，平均停留 0.1 秒，同時在途約 200 × 0.1 = 20 個；停留拉長到 10 秒，就成了 2,000 個。連線、記憶體與工作槽位會一起被卡住，這正是逾時要處理的問題。

假設整個請求的期限是 1,000 ms，入口處理已花 80 ms，回傳還要保留 120 ms，後面的排隊、連線、呼叫與重試共用 800 ms。每一層都把剩餘時間往下傳，越靠後的呼叫就拿到越小的預算。

時間設定實際要確認的計時範圍
連線逾時DNS、等待連線池、TCP、TLS 各由哪個計時器負責
讀取逾時等待第一個位元組，或兩次讀取之間的空檔
單次嘗試上限這一次呼叫最多用多久
整體 deadline排隊、退避、所有嘗試與回應的總額度

挑逾時值時，從依賴服務的延遲分布與可接受的誤判率開始。例如每個呼叫只有 0.1% 超過門檻，連做 20 次獨立呼叫，至少一次超過的機率已是 1 − 0.999²⁰ ≈ 1.98%。多層呼叫要回頭量端到端延遲。

還剩 350 ms，要退避 120 ms、保留回傳 50 ms，下一次最多能跑多久？

350 − 120 − 50 = 180 ms。下一次的上限取 180 ms 與單次呼叫上限兩者較小值。若預估需要 240 ms 才能完成，就直接回傳目前的工作狀態，讓後台續跑或讓使用者稍後查詢。

程序內用單調時鐘計算剩餘時間。跨程序傳遞相對剩餘時間，或使用像 gRPC 這類會處理 deadline 傳遞的協定，避免機器時鐘差直接吃掉預算。

失敗後，是重送、查詢，還是退款？

錯誤處理從一個問題開始：這次失敗後，業務進度停在哪裡？ 同樣是沒有得到成功回應，有些請求尚未開始，有些已經完成，還有些完成了一半。

情境現在做什麼留下什麼線索
文件格式錯誤、權限不足回傳可修正的原因欄位或權限檢查結果
暫時限流或服務忙碌依 Retry-After、期限與重試預算排下一次嘗試次數、下一次時間
寫入後連線斷掉，結果未知用原來的業務識別查詢或重送job_id、event_id
某筆訊息每次都讓程式失敗保存到死信佇列，讓後續工作繼續原事件、錯誤、版本、首次與最後失敗時間
已扣款，後續轉檔永久失敗執行退款這個新的業務動作退款識別與原扣款關係

死信佇列是一條可恢復的支線。先確認事件已持久保存到死信位置，再提交原訊息的消費進度。修正程式後重播，沿用原事件識別，也帶回原文件版本；重播較舊版本時，狀態更新依版本規則處理。

重試佇列會改變事件到達的先後。文件的「上傳 v3」正在延遲重試，「刪除 v3」卻先到達時，消費端需要看版本與目前狀態，或把同一份文件的事件交給同一個序列化處理者。選擇哪一種，取決於業務允許哪些狀態轉移。

退款呼叫逾時後，重送要用新的退款 ID 嗎？

沿用原退款 ID。退款是一個新的業務事件，與原扣款有關聯；它自己的多次網路嘗試仍屬於同一次退款意圖。供應商依這個識別回傳原結果，帳務端也用唯一約束避免同一退款事件重複入帳。

同一個按鈕按兩次，只建一份工作

一次適合重試的請求通常同時具備三個條件：失敗原因可能消失、重做有明確的重複處理規則、剩餘時間與容量足夠。文件上傳的 503 符合第一點；同一次提交附上穩定的冪等鍵，才能把「新工作」和「舊工作的重試」分開。

把鍵的範圍定成 (tenant_id, operation, idempotency_key)。第一次接受請求時，記錄文件 ID、文件版本與轉檔設定，再建立工作。相同鍵帶著相同業務參數到達，就回傳同一個 job；若參數改了，回覆衝突，讓呼叫端為新的意圖建立新鍵。

BEGIN;
INSERT INTO accepted_requests
  (tenant_id, operation, request_key, document_id, document_version,
   conversion_profile_version, job_id)
VALUES
  (:tenant, 'convert', :key, :document, :version, :profile_version, :job);
-- 唯一約束：(tenant_id, operation, request_key)
INSERT INTO jobs (job_id, state) VALUES (:job, 'queued');
INSERT INTO outbox (event_id, job_id, kind)
VALUES (:event, :job, 'conversion_requested');
COMMIT;

兩個相同請求同時到達時，由資料庫唯一約束選出第一個成功建立紀錄的人。另一個遇到衝突後讀取既有紀錄，比對業務參數，再回傳同一份結果。這段處理和 job、outbox 共用交易，避免留下「鍵已佔用，工作卻沒建立」的空位。

鍵保留多久，跟最晚可能出現的重試有關。若行動裝置會離線三天、死信佇列一週後才重播，保留一天就會把舊意圖重新當成新工作。可以把短期回應快取和長期業務唯一性分開：回應內容過期後，仍能由業務紀錄找回結果。

使用者換了轉檔設定，又按一次送出，應該重用上一個鍵嗎？

使用新鍵，並把設定版本存進工作。冪等鍵對應一次業務意圖；同一意圖的網路重試延續原鍵，新的轉檔要求建立新鍵。前端在收到受理回應前保留原鍵，重新整理時也能恢復該次提交。

大家一起重試，服務怎麼喘口氣？

入口服務 A 呼叫服務 B，B 使用資料庫驅動連到資料庫。A、B 與驅動各有一層重試：每層都最多嘗試三次，資料庫最多收到 3 × 3 × 3 = 27 次查詢。讓最了解業務期限的一層負責重試，其他層回報可判讀的失敗原因，負載就比較容易計算。

接著把重送攤開。第 k 次重試，從 k=0 開始，退避上限為 min(cap, base × 2ᵏ)；full jitter 在 0 到這個上限之間抽一個等待時間。base 為 100 ms、cap 為 1,600 ms，前四次的上限是 100、200、400、800 ms，平均等待則是 50、100、200、400 ms。

圖中最值得看的是同時重試的尖峰。固定等一秒會讓剛才一起失敗的人再次一起進來；加上抖動後，請求分散到一段時間內。服務回覆 Retry-After 時，把伺服器指定的最早重試時間與本地退避一起考慮，並重新檢查剩餘 deadline。

次數之外，再給重試一份流量預算。例如每 1,000 個正常請求，最多提供 100 次額外嘗試。額度用完就回傳工作狀態或錯誤，讓依賴服務有時間恢復。這樣可以直接看見重試花掉多少容量，而不是讓每個呼叫者各自把流量加倍。

每次獨立失敗機率 10%，最多三次嘗試，平均會送幾次？

第一次一定送，第二次發生的機率是 0.1，第三次是 0.01，所以期望嘗試次數為 1 + 0.1 + 0.01 = 1.11，三次全失敗為 0.1³ = 0.001。

若失敗來自同一台過載服務，這三次的結果會相關，而且重送會提高後續失敗率。此時以實測的重試流量、成功率與服務恢復速度調整預算；上面的獨立模型適合當作基準比較。

ACK 丟了，扣款會再做一次嗎？

worker 已經完成扣款，卻在確認訊息前當機。broker 稍後再交付同一事件，下一個 worker 要如何接手？交付語義的差別，就藏在「做事」與「記住做完」之間。

同一封信寄兩次，不能扣兩次款

左右對照：觀察「回應遺失」之後，重試如何影響副作用。

處理順序當機落在哪裡結果
先確認，再做業務工作確認後、工作前訊息已消失，工作可能漏做：at-most-once
先做業務工作，再確認工作後、確認前訊息再來一次，工作可能重做：at-least-once
去重紀錄與業務結果同一交易交易前或交易後重播時能分辨結果是否已提交

在同一資料庫裡，可以把 inbox(event_id)、業務更新與 outbox 放在同一筆交易。第一次插入 inbox 成功才做業務；相同事件再次到達，讀取既有結果，再確認訊息。整筆交易要麼提交，要麼回滾，去重標記就不會跑在結果前面。

Kafka 的交易可以把輸入 offset 與輸出的 Kafka 記錄一起提交，讀者使用 read_committed 讀取已提交資料。當結果寫到 SQL 資料庫，或呼叫外部支付、郵件服務時，就在那個結果所在的系統安排原子提交或冪等處理。

例如寄信完成後、寫入 sent 狀態前當機，下一個 worker 會遇到未知結果。讓郵件供應商接受穩定的 notification_id，或提供依該識別查狀態的 API，後續嘗試就能接回原通知。若供應商沒有這種能力，產品要明確選擇「可能漏寄」或「可能重寄」的處理方式。

先寫入 inbox，提交後再扣款，能得到什麼結果？

若在兩步之間當機，重播會看見 inbox 已存在，卻找不到扣款。把 inbox 與本地帳務更新放進同一筆交易；外部扣款則建立持久的 payment intent，使用同一個供應商冪等鍵查詢或重送，直到該 intent 進入明確的終止狀態。

102 做完了，101 還沒做完

一個 consumer 取到 offset 100、101、102、103，分派給四個 worker。100、102、103 完成了，101 還在跑。此時可提交的 offset 是 101：它代表重新啟動後的下一個讀取位置。

若直接提交 104，重新啟動就會跳過未完成的 101。維護進度時，把「已抓取」、「各工作已完成」與「已提交」三種狀態分開存；提交點只跨過最前面那段全部完成的記錄。102、103 的結果先保存，等 101 完成後，再一起向前推進。

Kafka offset 可能因交易、壓縮等原因出現缺號。實作時追蹤實際取到的記錄順序與下一個讀取位置，例如取到 100、104、105，100 完成後，下一個未完成的位置就是 104。不要等一筆從未出現的 101。

結果存在哪裡提交做法當機後怎麼恢復
SQL 資料庫先在交易中保存 inbox 與結果，再提交 Kafka offset可能重播，inbox 辨識已完成事件
SQL，並自行管理進度結果與 next_offset 同一資料庫交易取得分區擁有權後，以資料庫進度 seek
Kafka 輸出輸出記錄與輸入 offset 納入 Kafka 交易依已提交交易恢復

分區交給新 consumer 時，舊 consumer 還可能有正在執行的工作。把 owner epoch 帶到結果更新，讓儲存端原子檢查「現在還是不是這一任 owner」。非同步提交的回應也要跟著世代判斷，過期的 offset 提交失敗後，改以目前完成水位處理。

lag 下降了，最老未完成工作卻越來越老，該看哪裡？

檢查分區內是否有一份大型文件或毒性訊息卡在完成水位前端。lag 是記錄位置的差距，工作成本則可能相差千倍；一起看最老未完成年齡、未完成項目數與估計剩餘處理量。必要時將大型文件切成可追蹤的子工作，並為失敗事件安排明確的終止或隔離路徑。
