第 07 章

資料寫進去之後，磁碟做了什麼？

同一筆狀態更新會經過日誌、記憶體、索引與磁碟。沿著這條寫入路徑去推導 B-tree 與 LSM-tree，讀取速度、寫入成本跟崩潰復原自然會接起來。

沿著一筆狀態更新走進磁碟

本章拿文件D的狀態queued→running→succeeded當例子。每次更新都要回答三件事：去哪裡找到最新值、何時可以回覆提交成功、舊版本何時可回收。日誌與索引分別回應保存順序和查詢效率。

共同負載仍是每日一百萬份、每份5MB的原件；原件放物件儲存。資料庫保存中繼資料與狀態事件，若每份有5筆300bytes事件，每天事件正文約1.5GB。把這兩種資料分開估算，就能選擇合適的儲存路徑。

原件5TB／日、事件1.5GB／日，兩者是否適合共用同一套列式資料表保存正文？

看推導

原件適合物件儲存，中繼資料和工作狀態適合可索引、可交易的資料庫；分析事件可另彙整到適合掃描的格式。

資料頁還沒更新，WAL怎麼救回提交

追加式日誌把每次變更寫到檔案尾端。queued、running、succeeded依次保存，復原時沿順序重播就能找回狀態。查最新值若每次都掃全檔很慢，所以再加一份key到最新位置的索引。

預寫日誌（WAL）的關鍵順序是：用來復原的日誌先持久化，之後才允許相對應的資料頁覆寫。提交後資料頁還沒寫完就崩潰，重啟時可以重播WAL，把已提交變更補回去。應用事件日誌保存業務事實，診斷日誌協助查問題，資料庫WAL則服務儲存復原。

每次同步花2ms、逐筆等待時，同步頻率約限制在每秒500次。群組提交把多筆交易共用一次同步，例如100筆一組可攤薄固定成本；批次同時設筆數與等待時間上限，讓低流量時第一筆也能及時提交。

已同步WAL，資料頁尚未更新就崩潰，重啟後如何恢復？

看推導

從可用的checkpoint或資料頁狀態開始，重播後續已提交WAL，使資料頁追上已確認的變更。

先找租戶，再找最近一百筆

索引把查詢要走的路預先整理好。常見問題是「列出某租戶最近的文件」，索引可以從tenant_id開始，再按created_at和id排列；這讓資料庫先定位租戶，再沿順序取一小段。

索引次序要對應篩選與排序方式。索引(tenant_id,status,created_at)適合在租戶與狀態固定時依時間取資料；若不指定status，跨不同狀態的全局時間順序就需要額外處理。用EXPLAIN確認實際掃描範圍和排序成本。

新增索引也增加寫入、磁碟與快取需求。覆蓋索引可讓常用欄位直接從索引取得，但把大段文字塞進每個索引會降低單頁可容納筆數。先列出主要查詢，再用少量針對性的索引支援它們。

從一條查詢反推索引

查詢候選結構寫入或讀取成本
租戶內取單份文件(tenant_id, document_id) 索引把租戶條件放進查詢鍵
租戶內列出某狀態的最新文件(tenant_id, state, created_at) 有序索引狀態更新會移除舊索引位置、加入新位置

查詢固定tenant_id、按created_at排序，(created_at,tenant_id)與(tenant_id,created_at)哪個通常更容易縮小掃描範圍？

看推導

(tenant_id,created_at)。先定位租戶所在的連續區間，再依時間讀取；實際選擇仍用資料分布與執行計畫確認。

多一個標籤，序列數會長多少

時間序列把樣本依時間與標籤組織，例如每分鐘的API延遲。查詢通常指定一段時間和少數標籤，適合按時間切分區，較舊資料整批到期刪除，或降採樣為較粗的統計。

標籤組合決定序列數。1000個租戶×100個API×10種狀態，理論上最多有一百萬種組合；若再放每次請求ID，幾乎每筆都變新序列。查單次請求用log或trace，指標保留有界且可聚合的維度。

計數器保存累計值，查詢時對時間差取rate；延遲分布可用histogram桶計數，跨實例先合併桶再估分位數。平均各台p99會改變統計含義，直接彙總原始分布更符合全體請求的問題。

10台各自p99的平均值，是否等於全部請求合併後的p99？

看推導

通常不同。各台流量與分布可能差很多；合併可聚合的直方圖桶，再對合併後分布求分位數。

用一份日誌做出鍵值儲存

最小鍵值儲存可由追加日誌和記憶體索引組成。set(D,v2)把完整記錄寫到尾端，再讓索引指向v2；get(D)利用索引直接讀那個位置。刪除則追加tombstone，表示這個key目前已刪除。

啟動時掃日誌重建索引；檔案越大，重建越慢，所以定期產生可恢復的checkpoint或索引快照。每筆記錄的邊界、完整寫入處理與尾端殘缺處理依格式定義，復原時只採用完整有效記錄。

壓縮整理只保留仍需要的最新狀態。產生新檔期間，舊檔仍服務讀取；新檔完成後才切換有效檔案集合，再回收已無讀者使用的舊檔。這條更新順序讓整理過程也有清楚的崩潰恢復點。

資料先寫進磁碟，索引再指向它

put(key, value, operation_id):
    with db.writer_lock:
        require(db.writer_state == READY)
        sequence = db.next_sequence
        db.next_sequence += 1
        record = encode_record(key, value, operation_id, sequence)
        try:
            offset = append_all(active_segment, record)
            sync(active_segment)
        except IOError:
            db.writer_state = NEEDS_RECOVERY
            raise UnknownCommitResult
        db.index[key] = (active_segment.id, offset, record.length, sequence)
        return success

recover():
    open_published_segments()
    db.index.clear()
    max_sequence = 0
    for record in scan_complete_records_and_trim_incomplete_tail():
        apply_record_to_index(record)
        max_sequence = max(max_sequence, record.sequence)
    db.next_sequence = max_sequence + 1
    db.writer_state = READY

每筆紀錄保存長度與序號，重啟時從完整紀錄重建記憶體索引；尾端只寫了一半的紀錄會被截掉。這裡的成功回應放在 sync 之後。sync 回報 I/O 錯誤時，先恢復檔案狀態，再依 operation_id 查詢這筆操作是否已有完整紀錄，接續原請求。

日誌是set A=1、set A=2、delete A，整理後應保留什麼？

看推導

保留足以表示A已刪除的狀態，直到所有可能包含A舊值的來源都已被合併或排除，才安全移除tombstone。

一次讀一頁，為什麼能找到幾百萬筆

磁碟一次讀一頁，B-tree把一頁裝成許多分隔key和子頁指標，讓一次I/O排除大量候選。B+ tree常把實際記錄或記錄位置集中在葉節點，葉頁按順序連接，範圍查詢可從起點順著讀。

假設每頁有約200個分支，三層索引就能指向約200³個葉位置量級；根與上層常駐快取後，許多查詢只剩葉頁I/O。實際高度取決於key長度、頁大小、填充率與資料量。

插入發生在對應葉頁，空間不足會分裂頁面並把分隔key往上推。隨機key會讓寫入分散，連續key常集中在樹的一端。監看頁分裂、快取命中與寫入延遲，就能理解索引布局的實際成本。

查詢某租戶最近100筆，B+ tree定位第一筆後如何取得其餘資料？

看推導

沿葉頁順序讀取符合範圍的資料，通常能使用相鄰記錄與頁面的局部性，直到取得100筆或離開範圍。

把資料庫放進應用程序

嵌入式資料庫在應用程序內執行，呼叫通常經函式介面而非網路。SQLite適合本地應用與單機交易資料；RocksDB提供有序鍵值介面，常作為服務內部儲存引擎。它們讓部署更直接，也把檔案生命週期、備份與資源管理交給應用架構。

多個程序或多台機器要共享資料時，先確認引擎的並行模式與檔案系統要求。SQLite有自己的交易與鎖機制，RocksDB有各自的實例與檔案使用規則；擴成遠端服務需要另外設請求、授權、複寫與故障接手。

備份採引擎提供的backup/checkpoint流程或一致的快照方式，讓WAL、資料檔和metadata屬於同一可恢復狀態。

把資料庫檔案直接複製到另一台，何時可能缺少已提交資料？

看推導

當已提交變更仍位於WAL或其他相關檔案，單獨複製主資料檔會漏掉它們。使用引擎的備份介面，或取得包含完整依賴的一致快照。

寫入很快，整理為什麼突然追不上

RocksDB的LSM寫入路徑通常先寫WAL與記憶體memtable，memtable滿後flush成排序SST檔。讀取按新到舊搜尋memtable與相關SST，使用索引、filter和block cache縮小磁碟讀取範圍。

背景compaction把重疊檔案合併，移除過期版本和可回收刪除標記。若前台持續寫入、背景整理跟不上，待整理檔案累積，讀取成本與空間都上升；引擎可能降低寫入速度或進入write stall，讓背景追上。

調整前先看哪條路飽和：WAL同步延遲、flush速度、compaction讀寫量、cache命中和磁碟空間。提高memtable可能減少flush頻率，也會增加記憶體與恢復工作；增加背景執行緒則同時增加磁碟競爭。

前台寫入很快，但幾分鐘後週期性停住，先查哪組指標？

看推導

看待compaction bytes、L0檔案數、flush backlog與write stall原因，確認背景整理是否落後，再調整寫入量或整理資源。

讀、寫與空間，成本放在哪裡

B-tree把更新帶到對應頁面，LSM先累積成排序批次，再在背景合併。兩者把成本放到不同時間：B-tree維護查詢時直接可用的頁布局；LSM把較多整理工作移到flush與compaction。

比較三種放大：讀取放大是一次邏輯讀需要額外查多少資料；寫入放大是實際寫出的bytes相對於使用者寫入bytes；空間放大是保留的物理資料相對於有效資料。LSM的層數、compaction策略與snapshot保留期會改變這三者。

要做選型，拿同一份資料、相同持久化設定與真實讀寫比例，量穩態吞吐、尾延遲、磁碟量和背景成本。高寫入流量且可接受整理成本時，LSM很有吸引力；大量範圍查詢或更新布局合適時，B-tree的直接路徑常更容易掌握。

LSM 像整理單據：快寫入的代價藏在哪？

四幕追蹤同一個鍵的版本，分清 WAL、flush 和 compaction。

寫入100GB，compaction與flush合計寫出500GB，寫入放大是多少？

看推導

在相同統計範圍下是500÷100＝5倍。若數字另外排除WAL或檔案系統寫入，報告時要把這個範圍直接標清。

第二次讀很快，資料存穩了嗎

作業系統page cache把最近的檔案頁留在記憶體，命中時讀取可省去裝置I/O。應用或資料庫也可能有自己的block cache，兩層快取需要一起估記憶體，否則可能重複保存相同資料而壓縮工作空間。

write成功通常表示資料已交給作業系統接受；要達到特定本機持久化契約，依引擎與檔案系統要求完成同步操作。讀取很快和已確認資料如何跨越斷電，分別沿讀取路徑與提交路徑觀察。

冷啟動時快取空，短時間磁碟負載與延遲會變高。容量測試可比較冷、熱兩種狀態，部署時讓新實例逐漸接流量，避免所有實例同時回源。

相同查詢第一次20ms、第二次1ms，下一步想判斷是哪層快取，該看什麼？

看推導

比較資料庫buffer/block cache命中、OS page cache與實際裝置讀取量，並固定查詢和資料範圍。

搜尋壞了，從哪份資料重建

為文件D畫出四個位置：原件物件、任務資料列、事件日誌、搜尋索引。原件位置和版本屬於來源資料；任務狀態以交易提交為準；搜尋索引可由事件或權威資料重建。這個分工讓索引壞掉時有明確的修復來源。

走一次「結果檔已寫入、狀態尚未更新」的故障。重試找到相同job_id與版本的結果後，完成狀態提交；定期清理沒有任何合法任務引用的中間產物。再走相反順序，確認畫面顯示成功時必定能取得對應結果版本。

搜尋索引把一份文件標成完成，權威任務資料列仍是running，畫面用哪個作進度？

看推導

以任務資料列的權威狀態回覆，並檢查事件版本與索引更新順序。搜尋索引提供可重建的查詢視圖。
