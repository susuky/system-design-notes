第 07 章 · Storage internals

07 資料儲存的內部結構：從一筆寫入到故障復原

沿著一筆寫入走過記憶體、日誌、索引、儲存裝置與復原程序，才能解釋成功回應承諾了什麼。本章從追加式儲存開始，推導 B-tree、LSM-tree 與嵌入式資料庫的取捨。

讀完本章，你應該能做到

  • 把「資料已進入程序」「已進入作業系統快取」「本機可復原」「跨機可承受故障」分開說清楚。
  • 依查詢形狀設計鍵、複合索引與時間分割，算出資料量與索引成本。
  • 解釋 B+ tree 的頁面分裂，以及 LSM 的 flush、compaction、tombstone 和三種放大。
  • 為 RocksDB 或 SQLite 的使用範圍、備份方式與資源隔離做出有條件的選擇。

共同案例與單位：文件平台服務 1 萬個租戶，每日接收 100 萬份文件，每份原件平均 5 MB，MB 與 TB 採十進位；原件約 5 TB／日，日均約 11.57 份／秒，假設尖峰是日均的 10 倍，約 115.74 份／秒，每份轉換平均需要 2 CPU-seconds。本章另假設每份文件產生 5 筆狀態事件，每筆事件平均 300 B；文件內容放物件儲存，資料庫主要保存中繼資料、工作狀態與通知事件。

7.1 Log：先記下發生了什麼

想像最小的資料庫是一個只能往後增加的檔案。每次接到「把文件 D 的狀態改為完成」，就在尾端追加一筆記錄，而不是立刻尋找舊狀態所在的位置。追加的優點是寫入位置容易決定，也容易把多筆小寫入合成大區塊。代價是讀取 D 時不能直接把第一個匹配當成答案，因為後面可能還有更新或刪除；記錄不斷增加，也需要清理與索引。

三種 log 不要混在一起：診斷日誌供人調查；事件日誌保存業務事實，讓不同消費者重播；write-ahead log（WAL，預寫日誌）服務資料庫的崩潰復原。WAL 的核心次序是：某項變更需要對持久化資料頁生效之前，足以復原它的日誌必須先符合對應的持久化要求。這樣資料頁即使只寫到一半，也有可用來恢復的線索。各引擎使用 redo、undo、完整頁映像或其他機制，不能把單一實作當成所有 WAL 的形式。PostgreSQL 的 WAL 說明是理解這個次序的好起點。

我們的事件可包含 tenant_id、document_id、event_id、狀態、sequence、payload 長度與 checksum。長度讓復原程序知道一筆記錄的邊界，checksum 用來偵測不完整或損毀的記錄，sequence 協助判斷同一文件的先後。checksum 不能修復損壞，也不能抵抗惡意竄改；安全驗證和備援是另外的責任。不要只用換行區隔任意二進位內容，更不要假設一次 write 呼叫永遠把全部 bytes 寫完。

假設每次同步的延遲為 2 ms，單一寫入者每筆都同步，粗略上限是 1／0.002＝500 批／秒；若每批有 100 筆，同步次數沒有增加，理論上可攤成每秒 5 萬筆。然而這只算同步瓶頸，未計 CPU、實際 I/O 和批次形成等待。批次大小越大，單筆成本常越低，但低流量時第一筆可能為了等同伴而變慢。group commit 的設計應同時限制最大等待時間與最大批次大小。

故障推演：API 已送出「完成」，卻只把事件留在程序緩衝，程序被終止後客戶看到完成但查不到事件。成功回應必須等到已約定的持久化點之後才能送出；「多印一行 log」解決不了這個問題。相反地，事件已落盤但回應在網路上遺失，客戶重試可能再次提交；用穩定的 event_id 或 idempotency key 識別同一次意圖。耐久性與冪等性解決的是不同問題。

練習：每 20 ms 同步一次，能宣稱最多只丟 20 ms 的資料嗎？

不能不加條件地宣稱。20 ms 是排程目標，CPU 停頓、I/O 壅塞與同步失敗可能拉長真正未落盤區間。應量測最近成功同步點與未同步 bytes；要承諾已確認的資料不因本機斷電遺失，就要在相應同步成功之後才確認，並明定儲存裝置與檔案系統假設。非同步模式則應揭露可能遺失已確認寫入。

7.2 Index：為特定問題付出的額外成本

索引是資料的另一種排列，讓某些查詢不必逐筆掃描。它可能保存完整值、主鍵、檔案 offset 或頁面指標。先寫下查詢，再選索引：用文件 ID 取單筆，與「列出租戶 A 最近 100 筆失敗工作」是兩種不同的存取形狀。前者適合等值定位；後者同時需要租戶條件、狀態篩選、時間排序與分頁。

對後者可考慮複合索引 (tenant_id, status, created_at, document_id)。前兩欄等值，後兩欄提供穩定次序；document_id 解決同一時間戳下的排序歧義。下一頁使用上一頁最後的時間與 ID 作游標，而不是越翻越大的 OFFSET。這能避免為第 10 萬頁先跳過大量結果，但若要求整個瀏覽過程完全一致，仍需定義快照或版本，不能把游標誤當交易隔離。

欄位順序不是裝飾。上述索引不能保證讓「所有租戶最近失敗工作」同樣便宜，也不能直接支援只按 document_id 查詢。B-tree 複合索引通常最容易有效縮小左側前綴的範圍；部分引擎及版本有 skip scan 等最佳化，所以正確說法是先估可掃描區間，再用執行計畫驗證，而不是背「缺第一欄一定完全不能用」。PostgreSQL 複合索引文件說明了這些條件。

容量算例：保留 90 天即約 9,000 萬份文件中繼資料。若一個索引 entry 在這個教學模型中平均佔 48 B，原始 entry 約 4.32 GB；再假設平均填充率 70%，頁面空間約為 4.32／0.7＝6.17 GB，尚未計內部節點、版本、WAL 與實作額外成本。五個索引的空間不能當成免費，更重要的是每次更新可能增加五份維護工作。如果狀態欄高度變動，把它放入很多索引會放大寫入量。

常見誤區：「索引越多越快」忽略寫入成本；「有索引就不用回表」忽略查詢所需欄位；「tenant_id 放在鍵裡就安全」忽略應用程式可能查錯範圍。租戶鍵是資料布局，授權是安全邊界，兩者要各自驗證。索引重建或線上建立也需空間、I/O 與失敗回復規畫。

練習：只有 0.1% 文件失敗，是否值得建立只含失敗文件的索引？

可能值得，但要看查詢頻率、引擎是否支援 partial index，以及查詢條件能否被最佳化器證明符合索引條件。還要估文件在成功、失敗、重試中來回切換時的維護成本。用實際分布和查詢計畫比較讀取省下的工作與更新新增的成本，不能只因失敗比例低就直接下結論。

7.3 Time series data：時間不是唯一的維度

時序資料通常是時間戳加上數值，並由一組穩定標籤識別一條序列，例如「區域 A 的 OCR worker，每 15 秒一次 CPU 使用率」。它與業務事件不同：CPU 序列的相鄰樣本常具有相似時間差和數值，可利用 delta 等編碼壓縮；文件完成事件則有獨立身分、業務狀態與重播需求。不要因為兩者都有 timestamp 就放進同一套模型。

本平台可以記錄按區域、處理階段、結果分類的處理量、延遲與錯誤比例。最危險的決定是把 document_id、使用者 ID 或任意 URL 當作 metrics label：每種標籤組合都可能建立新序列，索引和記憶體會跟著成長。Prometheus 的命名指引特別提醒高基數標籤的成本。單份文件的除錯細節應放在可查詢事件或 trace 裡，聚合指標則保留有限且有意義的維度。

算一遍基數：1 萬租戶 × 4 個處理階段 × 3 種結果＝12 萬條序列，若每 15 秒一筆，是每日 6.912 億筆樣本。假設每筆的時間與數值未壓縮合計 16 B，僅樣本約 11.06 GB／日，還沒包含標籤、索引和複本。此處假設每種組合都存在且每 15 秒抓取一次；若只有部分組合活躍，按活躍序列數重算。若再為每份文件建立新的 label，就從可估計的集合變成持續膨脹的集合。

儲存布局常同時用「序列識別」與「時間區間」：先把同一序列相近時間的樣本放在一起，再把舊區間封存成不可變區塊。查詢最近一小時，只讀相關時間區塊；保留期限到期時，整塊刪除比逐筆刪除便宜。但事件有 event time 與 ingestion time 的差別：邊緣節點斷線半小時後補送，資料會晚到。你要決定允許晚到多久、舊區間是否可重寫、晚到數據如何反映在聚合結果。

Prometheus 的本機儲存文件描述了 head、WAL 與時間區塊，也提醒本機儲存自身不是可水平擴充的分散式資料庫。本章借用它說明分層原理，不把某產品的特定 block 長度或預設參數當作普遍標準。長期留存還要規畫備份與遠端儲存，並先決定原始精度真正有用多久。

聚合陷阱：每分鐘 p99 的平均值不是一小時 p99；平均數也不能直接平均，除非每組樣本數相同。若三批作業平均延遲分別是 1、2、20 秒，樣本數是 1,000、1,000、10，總平均應算總耗時除以總筆數，約 1.59 秒，而不是 7.67 秒。預先降採樣要留下足以重組目標統計量的資訊，例如 sum、count 或可合併的分布摘要。

練習：客戶要求看每份文件的處理延遲，是否只能加 document_id label？

不需要。每份文件的 latency 可存在事件或工作中繼資料中，以 tenant_id 與 document_id 查詢；監控系統保留租戶等級或套餐／區域等有限維度的聚合。若 1 萬個租戶也超出預算，可將長尾租戶合併為群組，把付費租戶的明細放到可控的分析儲存。先滿足查詢目的，再選儲存方式。

7.4 Simple key-value database：自己推導一個最小儲存引擎

從 append-only log 出發，增加一張記憶體雜湊表：key → (segment_id, offset, length, sequence)。Put 先把完整記錄追加到 log，符合持久化策略後更新索引；Get 用索引讀到最新值；Delete 追加 tombstone，表示刪除，而不是立刻去檔案中挖洞。這種模型讓定位接近常數時間，但 key 索引需要留在記憶體，也不自然支援範圍掃描。

put(key, value, operation_id):
    with db.writer_lock:                 # 離開區塊時釋放鎖，包含例外路徑
        require(db.writer_state == READY)
        sequence = db.next_sequence
        db.next_sequence += 1
        record = encode_with_checksum(key, value, operation_id, sequence)
        try:
            offset = append_all(active_segment, record)
            sync_if_required(active_segment)
        except IOError:
            db.writer_state = NEEDS_RECOVERY
            raise UnknownCommitResult
        db.index[key] = (active_segment.id, offset, record.length, sequence)
    return success

recover():
    load_published_segment_manifest()
    validate_records_and_recover_complete_prefix()
    rebuild_index_in_sequence_order()
    db.next_sequence = max_valid_sequence + 1  # 空資料庫的 max 為 0
    db.writer_state = READY

append_all 必須處理短寫，將剩餘 bytes 寫完；追加或同步失敗後，寫入者先進入 NEEDS_RECOVERY，避免繼續在損壞尾端後方追加。這次操作回報結果未知；上層若要依 operation_id 自動重試，需同步保留該識別的查詢與去重紀錄。讀者取得索引位置時也要使用同一把鎖或等價的原子發布機制。復原可依格式協定截掉最後一筆不完整記錄；若中段 checksum 錯誤，則停止該分段復原、回報損毀並從副本或備份修復。Linux write 文件說明短寫與延後回報的寫入錯誤。

記憶體算例：若有 5,000 萬個不同 key，每個索引 entry 含鍵及實作 overhead 平均 64 B，光索引就約 3.2 GB；記憶體配置與雜湊表空槽可能使實際用量更大。這解釋為什麼小型 key-value 練習可用全記憶體索引，大型引擎卻需要把有序索引分頁或分層放到磁碟。

為了回收被舊版本占據的空間，compaction 讀取舊 segment，只保留仍有效的最新記錄，寫到新檔案，再原子地公布新的檔案集合。只有最後的 rename 還不夠，發布協定必須完整：新檔案資料完成必要同步，manifest 正確更新並持久化，讀者能看見一致版本，舊檔案等讀者釋放後才移除。若在新檔案寫一半時就先刪舊檔案，一次斷電就可能把唯一可用版本一起帶走。

tombstone 也不能隨手清掉。例如舊 segment 有 D＝完成，新 segment 有 D＝刪除，若只因新檔案很新就移除 tombstone，而舊值仍會被後續掃描讀到，D 就會復活。清理必須證明所有可能遮蔽的舊版本都不再可見，而且沒有仍要讀取它的快照。多副本環境還可能有離線副本，條件更複雜。

練習：將索引每分鐘寫入 checkpoint，啟動後只讀 checkpoint 就夠了嗎？

不夠。checkpoint 只涵蓋它所記錄的完整位置或 sequence；啟動還要重播之後的 log。checkpoint 與所引用的 segment 必須是相容的一致組合，且不能在 checkpoint 尚未安全發布前刪掉舊 log。測試應在發布前、發布中、發布後分別終止程序，確認已承諾的操作不會遺失或復活。

7.5 B-tree index：讓每一次 I/O 都取得更多分支

二元搜尋樹每個節點只有少數分支，若節點分散在磁碟，一次查找可能需要很多次隨機讀。B-tree 家族的做法是把許多分隔鍵與子節點指標放在一個頁面裡，讓一次 I/O 就能決定數百個方向之一。B+ tree 通常將資料記錄或記錄指標集中在葉節點，內部節點負責導引；葉頁有序，範圍查詢可以依序掃描。不同資料庫的命名與頁面布局略有差異。

推導樹高：教學上假設頁面 16 KiB，預留頁首後約可用 15 KiB，每個分隔鍵加指標 32 B，滿載時 fanout 約 480；若考慮空間保留，平均 fanout 取 300。又假設每個葉頁平均容納 200 筆索引記錄，1 億筆需要 50 萬葉頁；約 1,667 個上一層頁、6 個再上一層頁，根頁再指向這 6 頁。一次路徑約經過 4 個頁面；若上層都在記憶體，實際磁碟讀取可能主要集中在葉頁。改變頁面大小、鍵長度或填充率，就會改變分支數與樹高。

插入時若目標葉頁滿了，可能需要分裂成兩頁，把新的分隔鍵插入父頁；父頁也滿，分裂就向上傳遞。刪除則可能留下可重用空間，是否立即合併依引擎策略而定。因此，「修改一個小欄位」也可能超出「只寫那幾個 bytes」的成本：頁面、WAL 與索引維護都可能產生額外寫入。為避免大量更新突然觸發尖峰，應持續觀察混合工作負載；只測一次冷啟動插入，看不到這些累積成本。

順序遞增鍵通常讓新寫入靠近樹的右側，有較好的頁面局部性，卻可能讓大量並行寫入競爭同一熱頁；隨機鍵較分散，但會碰觸更多頁面並影響快取命中。多租戶鍵以 tenant_id 開頭能聚集單一租戶資料，超大租戶也因此容易形成熱範圍。是否加桶或分片前綴，要回到單租戶查詢能否承受多範圍合併，不能只為了把圖畫得平均。

SQLite 的檔案格式提供具體頁面結構，PostgreSQL 的 B-tree 文件則有實作細節。面試時先把「高分支降低樹高、有序葉頁支援範圍」講清楚，再補上更新、頁面管理與崩潰一致性的成本，會比直接背 O(log n) 更有說服力。

練習：根頁命中率 100%，是否表示查詢不需要磁碟？

不是。根頁只決定下一步，後續內部頁、葉頁，以及非 covering index 所需的資料頁仍可能缺頁。應量測整條查詢路徑的快取命中、讀取頁數和尾端延遲；高命中率也不能掩蓋每百筆一次特別昂貴的讀取。

7.6 Embedded database：資料庫與應用程式住在同一個程序裡

嵌入式資料庫通常以函式庫形式存在，應用程式直接呼叫其 API，而不是每次透過網路向獨立伺服器下指令。這可減少網路往返與部署組件，特別適合單機應用、邊緣節點、本機索引與串流處理狀態。SQLite 提供 SQL 與交易，RocksDB 提供有序 key-value 引擎；「嵌入式」描述部署與呼叫方式，並不表示資料只在記憶體，也不表示功能一定簡單。

本平台的轉換 worker 可以使用嵌入式資料庫保存「已下載哪幾個文件區塊」與「本機完成但待回報的任務」。程序重啟後不必從頭下載，但這份資料若只存在暫存磁碟，整台機器被替換仍可能遺失。因此核心工作派發狀態應由共享且有故障策略的控制面負責；本機狀態是可重建加速層，或必須搭配持久卷、備份與復原協定。

把資料庫放進程序，也把維護責任放進程序。你的服務要控制記憶體預算、背景 I/O、版本升級、磁碟滿、校驗錯誤與關閉流程。應用程式崩潰和資料庫程序崩潰變成同一件事；其他語言或其他主機也不能理所當然共用那個檔案。若需要多個服務同時修改同一資料集合，通常應透過有明確並行協定的服務介面，而不是把活躍資料庫目錄掛在共享檔案系統上碰碰運氣。

選擇題的正確問法：若單一 worker 想查本機任務、需要 joins 與少量交易，SQLite 很自然；若要大量依鍵更新本機狀態、已有自己的資料模型與分片層，可評估 RocksDB；若 300 台 worker 都要即時修改同一份工作資料，單靠「每台各開一個嵌入式資料庫」不會自動變成一致的共享資料庫。SQLite 的適用場景文件也把本機與多用戶網路服務的差異說得很清楚。

備份不應只是任意時間複製某一個檔案。引擎可能還有 WAL、共享記憶體或多個 SST／manifest，複製中途也可能跨越兩個不同版本。使用引擎支援的備份、checkpoint 或一致快照介面，再做可讀性與恢復演練。知道檔案在哪裡，只完成了備份問題的一小半。

練習：把共享資料庫換成每個 worker 的 SQLite，延遲降低，是否就能上線？

先說清楚哪些資料是唯一真實來源、誰有權修改，以及 worker 掛掉時由誰接手。若每台保存的是可重建 cache，可合理採用；若每台各自認定自己擁有同一工作，則可能重複處理或遺失工作。必須另外設計租約、版本／fencing 與結果提交規則，不能從本機交易推導跨機正確性。

7.7 RocksDB：讀懂 LSM 引擎背後的工作

RocksDB 是嵌入式有序鍵值儲存引擎。典型寫入路徑把修改寫入 WAL 與 memtable；memtable 滿後變成不可變，背景工作將其 flush 成排序好的 SST。讀取會考慮記憶體與不同層的檔案，找到對指定讀取視圖有效的版本。這是概念路徑，WAL 是否開啟、是否同步、原子操作與交易模式都影響保證。RocksDB 官方概觀是查核功能邊界的入口。

SST 內部按鍵排序，跨檔案的鍵範圍則由 compaction 策略管理。常見 leveled compaction 中，L0 檔案的鍵範圍可能重疊，讀一個鍵可能先碰到多個候選檔；較低層通常在同一層維持不重疊的鍵範圍。Bloom filter 可以快速說「這個檔案一定沒有此鍵」，也可能誤報「可能有」；它不是索引的完整替代品，更不能返回值。在資料完整、建置與查詢使用相同規則時，Bloom filter 對已加入的鍵不會回答「不存在」。

本平台可以用鍵 tenant/document/version 儲存文件處理狀態，並用 tenant/pending/time/job 儲存可掃描的待處理項目。當工作完成時，把「更新狀態」「移除 pending key」「加入待通知事件」放到同一個 WriteBatch，可避免本機引擎內只做了一半。可是如果文件結果放遠端物件儲存，WriteBatch 不會把遠端上傳也納入同一筆原子交易。仍要先完成可驗證的輸出，再以狀態機或 outbox 收斂跨系統結果。

原子批次與讀改寫。WriteBatch 讓一組更新一起可見；若 A、B 都先讀到計數 10，再各自把 11 寫回，即使兩份批次都原子提交，仍只增加一次。需要依讀取值決定更新時，可用 TransactionDB／OptimisticTransactionDB 搭配 GetForUpdate，將讀到的鍵納入衝突檢查；也可由應用程式持鎖涵蓋整段讀改寫。參見 RocksDB Transactions。

為什麼突然停寫？若 flush 或 compaction 長期追不上新寫入，memtable、L0 檔案或待整理 bytes 不斷增加；引擎會放慢甚至暫停寫入，避免資源無限膨脹。這是背壓，不一定是程式死鎖。Write Stalls 文件也指出特定 column family 的壓力可影響整個資料庫的寫入。因此「一租戶一個 column family」不是完整資源隔離，幾千個 column family 還會帶來管理與記憶體成本。

假設邏輯寫入尖峰 30 MB／秒、總主機寫入放大為 12，則儲存路徑至少承受約 360 MB／秒的平均寫入需求，還沒加讀取、備份與尖峰預留。若裝置在這個混合工作負載下只能穩定提供 250 MB／秒，就算前 30 秒看起來飛快，債務仍會累積，最後由停寫償還。擴大 memtable 可延後停寫，但不能永遠彌補輸入超過持續處理能力的缺口。

調校時先看來源：是 flush 排隊、compaction bytes、CPU 壓縮、磁碟頻寬還是 cache 命中？再改少數參數並跑到穩態。不要看到 write stall 就單純把停寫門檻調得極大，也不要把所有背景工作提高到最大，讓前台讀取毫無 I/O 可用。官方調校指引適合對照量測項目；具體預設值與 API 應以部署版本為準。

練習：關閉 WAL 能更快，對 worker 的資料是否安全？

只有在你明確接受該資料丟失且有可靠重建來源時才可能合理，例如可重算本機 cache。若其中包含唯一的任務完成證據、待送通知或去重狀態，關閉 WAL 可能在崩潰後造成遺失或重複副作用。先寫出復原來源、可接受的重建時間和最大遺失範圍，再比較效能。

7.8 LSM-tree vs B-tree：把成本放在哪一條路徑

LSM-tree 的核心思想是先收集更新，再把較大的有序批次合併進持久化結構，用延後與批次化重整來減少許多零散更新的成本。原始 LSM-tree 論文提出這個方向；現代引擎在多層、快取、壓縮與 compaction 策略上已有很多變體。B-tree 家族則傾向維持可直接定位的有序頁面結構。兩者都可能使用 WAL，也都能提供範圍讀取；「LSM 等於 log，B-tree 沒有 log」是錯的分類。

LSM 像整理單據：快寫入的代價藏在哪？

四幕追蹤同一個鍵的版本，分清 WAL、flush 和 compaction。

比較時至少定義三種放大。寫入放大是實際寫入的 bytes 相對於應用程式邏輯寫入的比值，但要說清楚是否包括 WAL、檔案系統與 SSD 內部寫入；讀取放大可定義為一次邏輯查詢觸及的檔案、區塊或 bytes，要先選量測單位；空間放大是實際佔用空間相對於有效邏輯資料的比值，要說明是否含暫存合併檔與複本。分母不同的兩個數字不能直接比較。

LSM 與 B-tree 的條件式比較
面向常見 LSM 傾向常見 B-tree 傾向
新寫入先吸收於 WAL／memtable，背景排序與合併尋找頁面後更新，可能有分裂與 WAL
點查可能跨多個候選 run，依賴 Bloom 與 cache 降低 I/O走一條樹路徑，仍需考慮回表與版本
範圍讀合併多個有序 run，跳過舊版本與 tombstone定位葉頁後依序讀相鄰頁，局部性通常易掌握
背景成本compaction 消耗 I/O、CPU、暫時空間頁面整理、vacuum 或其他回收依引擎而異
容量規畫要容納舊／新檔共存與整理積欠要容納頁面空槽、分裂、索引與版本
最終判斷以相同耐久性、資料量、查詢分布、硬體和長時間穩態測試比較

Leveled compaction 常用較多合併工作換較小讀取與空間放大；tiered／universal 類策略常減少重複合併，卻可能讓多個 run 並存，增加讀取或空間成本。比較時要固定資料量、讀寫比例與快照保留時間。RocksDB 的 compaction 文件提供不同策略的細節。若只以一次 Put 的延遲比較，就像只計餐廳點餐速度、不計廚房出餐能力。

平台取捨：大量追加的任務事件、可批次整理的本機工作狀態，適合把 LSM 放進候選；租戶控制面若有多條關聯查詢、唯一性與跨表交易，成熟關聯式資料庫可能更直接。但 SQL 與 LSM 不互斥，資料模型和儲存引擎是不同層。比較時應列出查詢和一致性要求。「NoSQL／SQL」並不能說明磁碟布局。

穩態測試設計：先填入接近正式規模的資料，再用預期比例混合新增、覆寫、刪除、點讀與掃描，持續到多輪整理與回收都發生。記錄吞吐、p50／p95／p99、裝置寫入量、最小可用空間、復原時間與備份期間表現。加入一個占流量 20% 的大租戶測公平性，再做重啟與磁碟接近滿載測試。不能拿全新空資料庫的五秒 benchmark 代表上線三個月後的行為。

練習：磁碟還有 8% 空間，LSM 仍可讀寫，為何要立即處理？

compaction 可能需要先寫新檔再釋放舊檔；剩餘空間不足會卡住整理，使檔案數與寫入積欠惡化。8% 本身不是普遍危險門檻，關鍵是相對於下一次合併、預期流入、備份及復原的空間需求。應限制入口、擴容或安全移轉，不可任意刪除引擎目錄中的檔案。

7.9 Page cache：快取命中很快，成功回應仍需要契約

作業系統 page cache 在記憶體中保留檔案頁面。程式讀取資料時，若目標頁仍在快取，可能不必再向裝置讀；採 buffered I/O 寫入時，資料也可能先成為 dirty page，稍後才由背景程序寫回。這讓一般檔案 I/O 很有效率，但「write 已返回」不等於「斷電後必定仍存在」。把 page cache 當作耐久性保證，是儲存設計中特別昂貴的誤解。

應用程式快取、資料庫 block cache 與 OS page cache 可能同時存在。以壓縮 SST 為例，OS 可能保留壓縮檔案頁，而引擎 cache 保存解壓縮後的 block；兩者即使來自同一份資料，也有不同 CPU 與記憶體取捨，不應直接全部斥為重複。RocksDB block cache 文件可用來理解各層責任。Direct I/O 可繞過部分 page cache 路徑，但它本身不等於每次寫入都已持久化，也不會自動讓所有工作負載變快。

延遲算例：假設 cache hit 是 0.1 ms、miss 是 5 ms，命中率 99%，平均延遲是 0.99×0.1＋0.01×5＝0.149 ms。平均很好看，最慢的約 1% 仍可能落在 5 ms 等級，實際還會受排隊與多頁讀取影響。若查詢每次需讀 20 個彼此獨立且命中率同為 99% 的頁面，全部命中的機率約為 0.99 的 20 次方，即 81.8%；所以「單頁 99% 命中」不能直接套成「99% 查詢完全無 I/O」。獨立性只是教學假設，真實存取通常有相關性。

大範圍掃描可能把熱資料擠出快取，備份或報表工作也可能與線上點查互相干擾。可採用掃描友善的 cache 策略、I/O hints、查詢資源限制、獨立分析副本或時間安排，但要先量測瓶頸。Linux 的VM 文件描述 dirty page 與寫回相關設定；系統參數不是魔法，調大 dirty 限制常只是把短尖峰留在記憶體，之後仍要償還。

可靠檔案更新還涉及檔案內容與目錄項的持久化次序、同步呼叫是否成功，以及裝置是否履行 flush 契約。SQLite 的原子提交說明展示了為什麼斷電安全需要完整協定。引擎可以用 WAL 等方式讓資料頁延後寫回，仍在自己的承諾範圍內提供耐久性；前提是相關日誌已符合要求，而不是因為頁面剛好躺在 cache 裡。

故障演練：區分程序崩潰、作業系統崩潰、斷電與整個儲存裝置失效。僅殺掉程序，OS cache 仍在，不能證明斷電安全；本機斷電後能復原，也不能證明磁碟永久損壞後資料不丟。測試計畫要對應你對外承諾的故障模型，並在隔離測試環境執行，不能拿正式用戶資料做破壞性試驗。

練習：重新啟動服務後效能突然下降，第一個推測一定是索引損壞嗎？

不一定，可能是 cache 變冷、背景復原、compaction 或連線重建。先比較相同資料與負載下的 cache hit、實際 I/O、CPU、復原日誌和查詢計畫。必要時用受控預熱讀取恢復常用工作集，但不要用全庫掃描把有限快取塞滿，反而擠掉真正熱資料。

章末設計演練：一份文件的真實來源在哪裡？

請為平台列出四份資料：5 MB 原件、約 1 KB 中繼資料、300 B 狀態事件、本機轉換進度。每份都回答五件事：誰寫入、如何定位、保留多久、何時回應成功、整台機器消失時從哪裡復原。接著假設峰值連續維持一小時、最大租戶占 20% 流量、備份同時進行，說明哪個資源先成為瓶頸。

參考推導與容量檢核

原件放有明確耐久性與存取控制的物件儲存，1 百萬×5 MB＝5 TB／日，30 天原件約 150 TB，未含版本與副本。1 KB 中繼資料約 1 GB／日，90 天約 90 GB，之後才加索引、WAL、版本與備援。狀態事件每份 5 筆，約 15 億 B＝1.5 GB／日，30 天約 45 GB，未含格式與索引。轉換進度可放本機嵌入式資料庫，但要能由持久化任務和原件重建。資料庫 transaction 與 outbox 可讓「狀態完成」及「待通知事件」同時存在，不能把遠端物件寫入假裝成同一筆本機交易。

峰值原件入口約 115.74×5 MB＝578.7 MB／秒，光原件頻寬就與中繼資料 I/O 不同量級；轉換純計算需求約 231.48 CPU-seconds／秒，實際核心數還要考慮利用率、併發與服務目標。這說明不應讓大文件 bytes 穿過同一條小型狀態資料庫寫入路徑。最大租戶需有配額、公平排程與儲存監測，避免一個租戶的背景整理拉高所有人的 p99。

把復原時間也放進容量表

儲存大小之外，還要估算恢復服務需要多久。假設一個分片的可用快照是 300 GB，下載與驗證後可持續寫入本機的有效速度為 500 MB／秒，這一段至少約 600 秒；之後需要重播 90 GB 日誌，有效重播速度 150 MB／秒，又需約 600 秒。若兩步必須依序執行，光這兩段就約 20 分鐘，還沒加入排隊、啟動、快取預熱與流量切換。宣稱「備份存在所以五分鐘能恢復」在這組假設下便不成立。

降低恢復時間可以增加快照頻率、縮短待重播區間、預先準備副本或減少單分片資料量，但每個選項會提高平時的 I/O、空間或營運成本。若復原時新事件仍持續進入，追趕速度必須高於新增速度，否則永遠追不上。演練時不只檢查程序能否啟動，還要查驗已確認寫入的邊界、刪除是否復活、索引與本體是否一致，以及租戶權限是否仍正確。復原成功應有資料正確性與服務可用性的驗收條件。

面試自檢：若你的答案只說「用 RocksDB 比較快」，還少了查詢模型、容量、確認點與故障模型。完整答案可以是：「這份狀態可重建、以鍵更新為主，所以先評估嵌入式 LSM；用實際穩態負載驗證寫放大與 p99，控制租戶輸入，並把不可重建的狀態和 outbox 放在有持久化與復原保證的來源。」
