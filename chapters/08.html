第 08 章 · Efficient communication

08 有效率的通訊：找到對方、選擇協定、交付結果

在分散式系統的通訊設計中，工程師必須精確回答三個根本問題：當前到底該找誰連線？用什麼協定傳輸資料最經濟？以及如何確定操作結果真正落實？從底層的 DNS、TCP、QUIC 到應用層的 HTTP/3、gRPC、WebSocket、訊息佇列乃至邊緣 CDN，每項技術都只負責拼圖的一角。服務探索決定目的地，網路協定掌管傳輸效率，而最終的業務一致性與狀態補抓，依然是應用層無法推卸的責任。

讀完本章，你應該能做到

  • 清晰區分主機解析、服務端點探索與對等網路探索，深刻理解快取過期、健康檢查延遲與暫態割裂對路由的影響。
  • 根據延遲容忍度、傳輸量級、背壓處理能力、重試代價與終端硬體限制，精準選用 Push 或 Pull 模式及最適傳輸協定。
  • 精確計算長短輪詢、連線池、影音分段串流與事件大量扇出（Fanout）背後的伺服器資源開銷。
  • 架構出一套具備自動重連、游標補抓、端到端去重與多租戶配額隔離的大規模即時推播通知系統。

沿用平台案例：我們持續探討文件處理平台。平台服務 1 萬個租戶，每日接收 100 萬份文件，每份原件平均 5 MB，日均寫入約 11.57 份/秒，尖峰預估為 115.74 份/秒，每份轉換平均耗費 2 CPU-seconds。本章進一步假設：每份文件在處理歷程中會觸發 5 筆狀態通知事件、每筆事件平均需扇出給 3 位相關使用者，且系統在任何時刻都有約 10 萬個瀏覽器分頁維持在線連線。除記憶體單位採 KiB/GiB 之外，所有網路頻寬與流量皆採十進位制（1 MB = 10^6 bytes, 1 GB = 10^9 bytes）精算。

8.1 Push vs pull：誰決定下一次傳送

Pull 模式是由接收方掌握主動權，依據自身的節奏向發送方索取資料，例如瀏覽器定時向 API 詢問工作進度；Push 模式則是在新事件產生時，由發送方主動沿著既有通道或新建通道將訊息推給接收方。這純粹是應用層的訊息主導權與傳輸節奏差異，絕對不要將其與底層「誰先發起 TCP 連線」混為一談。即便由瀏覽器率先向伺服器建立 WebSocket 或 HTTP 長連線，後續只要是由伺服器主動觸發事件傳遞，它在應用架構上依然是不折不扣的 Push；而使用者在畫面上看見通知提示後，點擊按鈕向伺服器抓取完整文件內容，則是典型的 Push 提示搭配 Pull 實體的複合設計。

我們先來精算最簡單的短輪詢（Short Polling）成本：如果 10 萬個活躍用戶端每隔 5 秒向伺服器發起一次查詢，整個叢集就必須持續承受高達 100,000 / 5 = 20,000 QPS 的純查詢請求。若絕大多數時間文件都還在排隊或轉檔，這每秒 2 萬次請求換來的只是一遍又一遍「處理中」的空轉回覆。在事件隨機均勻發生的假設下，客戶端察覺狀態變更的平均發現延遲大約是輪詢間隔的一半（約 2.5 秒），最糟情況則逼近 5 秒再加上網路 RTT。如果業務端苛求將平均發現延遲壓低到 0.5 秒內，輪詢間隔就必須縮短到 1 秒，這會直接將後端 QPS 暴力推升至 100,000 QPS！這正是輪詢架構最殘酷的本質：你是在用昂貴的無效請求頻寬，去換取那一點點延遲的降低。

Push 模式大幅消除了空轉查詢，但它立刻將負擔轉移為「連線狀態維護」與「慢速客戶端排隊」。假設每條維持活躍的 TCP/TLS 長連線在作業系統核心緩衝區與應用程式層合計占用 32 KiB 記憶體，10 萬條在線連線就至少吃掉 100,000 × 32 KiB ≈ 3.05 GiB 的常駐記憶體，這還尚未計入閘道排程器、連線映射表與突發緩衝區。更危險的挑戰在於網路慢速客戶端：當某 1 萬個用戶端身處弱網環境、每秒只能接收 1 KB 時，伺服器絕不能毫無節制地將新事件硬塞進輸出緩衝區，否則記憶體隨時會被未投遞的佇列打爆。成熟的架構必須實施合併策略（例如只保留最新進度覆蓋舊進度）、設定嚴格的單連線輸出佇列上限，或在逾時後主動斷開連線，要求客戶端重新連線時按游標補抓。Push 並沒有消滅成本，它只是把「何時發問」的頻寬成本，轉移成「維持狀態與控管慢速端背壓」的記憶體與排程成本。

針對我們平台的文件處理流程，轉檔進度條（80%、81%、82%）屬於瞬態的「最新指標」，業務上完全不需要保證每一筆百分比都精確送達；而「轉換完成」「處理失敗」或「權限撤銷」則是不可丟失的重大業務事件。因此極具架構智慧的做法是：透過輕量 Push 通道僅發送微小的變更提示（Ping），再由用戶端帶著 Token 主動透過安全 API Pull 回最新狀態與資料（Push to alert, pull to fetch）。這不僅能徹底避免敏感的文件內容在長連線廣播中洩露，也讓短暫斷線後的狀態補償變得極其單純穩定。

練習：全面導入 WebSocket 推送後，原本查詢工作狀態的 REST API 就可以直接廢棄以節省程式碼嗎？

絕對不行。原因在於：用戶端首次載入頁面、中途斷線重連、本地佇列過期出現缺口，或者推播訊息因網路抖動丟失時，系統都必須仰賴一個具備強一致保證的 REST API 重新拉取權威的真實資料（Source of Truth）。即時 Push 負責加速線上互動的感知延遲，而基於資料庫的查詢 API 才是系統最終一致性的定海神針。如果只把前端收到的最後一則推播當成系統唯一的狀態來源，只要漏掉一則通知，畫面上就會永遠顯示錯誤的過時進度。

8.2 Host discovery：名字如何變成可連線的地址

主機探索（Host Discovery）要解決的根本問題是：「我只知道主機名稱，如何取得可連線的實體網路位址？」在網際網路上最核心的基礎設施就是 DNS（Domain Name System）。客戶端透過本地解析器（Resolver）層層查詢根伺服器與權威伺服器，最終解析出 A（IPv4）或 AAAA（IPv6）位址以建立 TCP 連線。然而，這個解析出來的 IP 可能指向實體伺服器，也可能指向全域負載平衡器（GSLB）、Anycast 路由器或 CDN 邊緣節點；因此 DNS 解析回覆絕對不是「某台特定伺服器必定能成功為你處理請求」的健康保證。RFC 1034 規範是深入理解 DNS 階層架構與快取委派機制的權威起點。

TTL（Time to Live）僅僅是快取記錄的新鮮度期限，絕對不等於災難自動容錯轉移（Failover）的時間保證。即便維運團隊在 DNS 上將 TTL 設為極短的 30 秒，當某個資料中心突發火警時，全球無數的中繼遞迴解析器、作業系統核心以及用戶端應用程式本身的連線池（Connection Pool），都可能繼續沿用快取中的舊 IP 或維持既有 TCP 長連線。將 TTL 從 5 分鐘下調至 5 秒，只會讓權威 DNS 伺服器的查詢負載暴增數十倍，卻絲毫無法主動驅逐或搬遷客戶端已經建立好的長連線。規劃容錯移轉時，必須同時將「舊連線排空週期（Draining）」與「各層解析快取的真實收斂時間」納入設計。

在我們平台中，對外的公網 API 入口通常命名為 api.example.test，指向高可用的雲端負載平衡層；而內部微服務之間則依賴內部服務名稱通訊。如果工程師便宜行事，將各台短期 Worker 的實體 IP 寫死在設定檔中，任何一次伺服器重啟或自動擴容都會迫使所有客戶端重啟設定。引入主機名稱解耦是標準實踐，但也伴隨著新的架構責任：DNS 解析逾時、名稱找不到（NXDOMAIN）與「IP 解析成功但連線遭到拒絕」，屬於完全不同層級的異常，在監控日誌中必須精確分類記錄，絕不能全數打包成一個毫無意義的 500 錯誤。

連線轉移故障演練：當區域 A 的伺服器全面斷網時，部分客戶端仍守著舊連線池嘗試發送請求，另一部分客戶端則解析到新的區域 B。此時客戶端連線池必須為單次請求建立嚴格的連線握手與讀寫逾時，一旦探測到位址失效，立即主動關閉連線並清空連線池重新發起解析。對於建立轉檔任務的 POST 請求，網路逾時絕對不代表伺服器沒有收到工作，重試時必須強制攜帶全域唯一的 Idempotency Key。位址探索機制與應用層的重試冪等語意，必須在架構上一併閉環。

拿到了對方的 IP 位址，也絲毫不代表你可以盲目信任對方。TLS 握手時的主機名稱驗證（SNI 與證書 SAN 驗證）、雙向 mTLS 與服務身分驗證，解決的是「你連到的究竟是不是冒牌者」的安全邊界，這與 DNS 是否回傳可用 IP 完全屬於不同維度。切忌為了「因為更換了 IP 導致連線出錯」就偷懶在客戶端關閉證書校驗，這會直接讓你的系統在中間人攻擊（MITM）面前門戶大開。

練習：如果將權威 DNS 的 TTL 設定為 30 秒，是否就能向主管保證「任何主機故障都能在 30 秒內全自動平滑復原」？

絕對保證不了。首先，監控探針確認主機故障需要經歷多次連續探測（約需 10 至 30 秒）；接著，更新 DNS 記錄並等待全球中繼快取全部失效需要時間（許多 ISP 遞迴伺服器甚至會強制覆寫最小 TTL 為幾分鐘）；第三，用戶端應用程式、JVM 執行環境以及 HTTP 連線池往往有自己的本機 DNS 快取與既有長連線，只要舊連線沒斷，它們根本不會重新查詢 DNS；最後，所有流量湧入備援節點時還可能觸發冷快取與容量塞車。端到端的實際復原時間通常遠大於 30 秒，唯有將健康檢查、連線排空、主動重連退避與後端平滑擴容全部聯動，才能逼近預期的 RTO 目標。

8.3 Service discovery：找到「現在可提供能力」的實例

服務探索（Service Discovery）比單純的主機解析更進一步，它要精準回答：「當前整個叢集中，究竟有哪些實例具備處理 OCR v2 任務的能力，而且現在健康狀況良好、適合立即分派工作？」這不僅包含 IP 位址與連接埠，還動態關聯了版本標籤（Version/Canary）、所屬可用區、負載權重、支援通訊協定與即時健康狀態。主機是網路上的實體座標，而服務則是邏輯能力的動態集合；一台實體機上可以並行跑著十個不同服務的容器，而單一個 OCR 服務更可能橫跨上百台主機。千萬不要只因為兩者常藉由內部 DNS 實作，就抹煞了這兩層抽象的關鍵差異。

在拓撲架構上，服務探索主要分為兩大陣營：客戶端探索（Client-side Discovery）是由客戶端直接向服務註冊中心（Registry）訂閱最新的健康端點清單，並在客戶端內部執行負載平衡演算法自主選路；伺服器端探索（Server-side Discovery）則是客戶端永遠只對準一個穩定的負載平衡器或反向代理，由代理層負責動態對接註冊中心並分派後端。客戶端模式省去了一次網路轉發跳點（Hop），但要求每種程式語言的客戶端都必須維護一套完全一致的選路、熔斷與重試邏輯；伺服器端模式集中治理、對客戶端極度透明，但代理層本身會成為容量規劃與維運維護的關鍵單點。架構評估必須權衡團隊的語言多元性與效能極限，不可單憑「少跳一次一定比較快」做出武斷決策。

Kubernetes Service 架構透過 iptables/IPVS 提供了近乎無縫的穩定虛擬 IP（ClusterIP），使後端 Pod 的動態銷毀與重建對呼叫端完全透明；而 Headless Service 則允許客戶端繞過轉發、直接探索後端所有 Pod 的實體 IP。這些雲原生基礎設施大幅簡化了微服務通訊，但工程師必須清醒意識到：端點存在於清單中，絲毫不等於「向它發送請求就必然會成功」。容器就緒探針（Readiness Probe）的秒級延遲、應用層執行緒池飽和、下游資料庫連線中斷或租戶配額耗盡，都是基礎設施端點清單無法即時捕捉的深層故障。

主流的註冊中心（如 Consul、Etcd 或 Eureka）通常依賴週期性心跳與租約（Lease TTL）來判定實例生死。假設系統約定每 5 秒心跳一次、租約逾時時間為 15 秒，那麼當某個 Worker 遭遇 OOM 崩潰時，它絕對不可能在毫秒級瞬間從全網所有調度節點中蒸發；從最後一次心跳失聯、租約宣告過期到變更廣播至所有客戶端，必然存在 10 到 20 秒的時間黑洞。因此客戶端必須天生具備容忍短暫「過期名單」的韌性。反過來說，網路暫態抖動也極易導致健康實例被註冊中心誤判踢除，因此註冊中心的名單僅能代表網路連通性，絕對無法賦予實例排他的寫入權限；叢集領導者或寫入鎖的唯一性，必須嚴格依賴具備共識保證的租約版本號或 Fencing Token 機制。

平台架構取捨：在我們平台中，OCR Worker 屬於長時運算節點，最佳架構是讓 Worker 主動向訊息佇列拉取任務，完全不需要對每台 Worker 建立直接的點對點 RPC；而對外的文件查詢服務則適合掛載在具備伺服器端探索的負載平衡器後方。當服務註冊中心遭遇短暫網路分割不可用時，資料面的資料流應在有限時間內大膽沿用本地快取的最後已知端點（Serve Stale），並搭配客戶端的被動健康摘除（Outlier Detection）。必須深刻分清：「短暫維持資料面運轉」與「安全執行全域拓撲重新配置」是截然不同的兩件事。

練習：微服務實例在執行優雅關機時，第一步立刻向註冊中心註銷自己，正在執行中的長請求就能平安無事地順利完成嗎？

不能保證。註銷廣播通知到全網所有呼叫端與代理層需要時間，在此期間呼叫端依然會依據本地快取將新請求送往該實例。工業級標準的優雅關機程序是：第一步，將本機的就緒探針（Readiness）標記為失敗並向註冊中心發出下線信號；第二步，強制睡眠等待數秒（Sleep 5~10s），讓全網路由快取充分收斂，確保再無任何新請求流入；第三步，等待內部既有的在途請求全部處理完畢或到達最長優雅停機硬期限；最後才正式終止程序並釋放資源。對於長連線服務，更需要讓伺服器主動、漸進且帶有隨機抖動地通知客戶端重新連線，徹底防止流量懸崖。

8.4 Peer discovery：沒有完整中央名單時怎麼加入網路

在對等網路（Peer-to-Peer, P2P）系統中，節點兼具客戶端與伺服器的雙重身分。新節點剛啟動時對全網拓撲一無所知，它必須先透過少數固定的種子節點（Bootstrap Peers）作為跳板敲開大門，進而逐步探索並融入整個網路。P2P 探索的技術手段豐富多樣，包含固定種子列表、區域網路廣播探索（如 mDNS）、約定會合點（Rendezvous）、流行病協議（Gossip）以及分散式雜湊表（DHT）。工程師必須理清：發現直連鄰居、維護叢集成員健康狀態、精確尋路特定節點，以及定位某份內容的提供者，往往由不同層級的協定協同完成。

Gossip 協定的精妙之處，在於每個節點僅隨機挑選少數幾個鄰居節點定期交換彼此所知的世界狀態，讓「節點加入」「主動離開」或「疑似故障」的訊息如傳染病般在全網以對數級速度蔓延。這種模式徹底粉碎了所有節點兩兩互相心跳所引發的 O(N²) 網路風暴；但其物理特性決定了全網資訊在任何單一瞬態都無法保證百分之百絕對一致。當某個鄰居在一段時間內失去回應，可能是它真的掛了，也可能純粹是排程暫停、網路堵塞或暫態分區；系統通常會引入「疑似故障（Suspect）」過渡狀態與間接多節點協同探測（如 SWIM 協議）來壓低誤判率，但無論如何，都不可直接從 Gossip 的連通狀態推導出分散式全域共識。

DHT 則將整個網路的節點 ID 與內容 Key 映射至同一個虛擬度量空間（如 Kademlia 的 XOR 距離），每個節點只需維護局部精準的路由表，就能在 O(log N) 次跳轉內精準定位出距離目標 Key 最近的節點。libp2p 官方 DHT 規格手冊清晰界定了尋找節點路由（Peer Routing）與尋找內容持有者（Content Routing）的職責邊界。然而請時刻保持清醒：在 DHT 中找到「聲稱自己持有該份檔案的節點」只是第一步，後續仍需真正建立直連、嚴格驗證對方身分與二進位內容 Checksum，並妥善處理 NAT 穿透、防火牆阻擋與離線節點回傳過期資料的混亂局面。DHT 只是定位指標的目錄，絕對不等於把幾十 MB 的大檔案直接塞進 DHT 節點的記憶體中。

平台架構延伸：假設我們同一個大租戶在跨國多個私有資料中心部署了上百台文件轉換節點，彼此希望共享已下載的數百 MB 不可變 OCR 字典檔或深度學習模型權重。此時讓邊緣節點在內部私網中互相探索、透過 SHA-256 內容雜湊驗證並就近透過 P2P 相互傳輸，失敗時再回源抓取，能為企業節省驚人的外網跨區頻寬。然而，針對租戶私密的文件內容，絕對嚴禁只因「雜湊相同」就允許節點間隨意 P2P 傳播；「內容是否相同」是物理檢驗，「是否有權存取」則是安全邊界，兩者絕對不可混淆。P2P 卸載來源頻寬的同時，大幅放大了端點身分認證、配額治理與資料合規的架構複雜度。

選型邊界：在公司封閉且節點規模可控（數百至數千台）的資料中心內，中央註冊中心永遠是維運最清晰、治理成本最低的成熟解法；唯有在節點跨越多個自治組織、高頻動態進出、或天生缺乏單一中央授權中心的環境下，Peer Discovery 才有其不可替代的架構價值。切忌為了追求時尚的「去中心化」名詞，將系統推入難以追蹤、除錯成本極高的錯誤擴散深淵中。

練習：如果 P2P 網路中的所有 Bootstrap 種子節點同時斷網陣亡，整個運作中的 P2P 網路會瞬間全面癱瘓嗎？

不會立即癱瘓。已經成功加入網路且本地路由表中儲存了可用鄰居的既有節點，依然能透過既有連線持續交換訊息與傳遞檔案；真正受到致命衝擊的是「剛啟動的新節點」以及「剛從重啟中復原且本地鄰居快取全數過期的孤兒節點」，它們將徹底失去敲開網路大門的座標。因此成熟的 P2P 系統必然會配置多個獨立自治組織的種子位址、將健康鄰居清單持久化至本機磁碟，並支援動態補充備援種子來源。

8.5 How to choose a network protocol：從需求走到協定

在討論網路協定選型時，必須先嚴格分清協定所處的階層，嚴禁跨層混談。TCP 在傳輸層提供可靠、全雙工且嚴格保證順序的位元組串流（Byte Stream）；UDP 則提供極簡、無連線但不可靠的資料報（Datagram）；QUIC 則在 UDP 之上融合了 TLS 1.3 加密、快速握手與真正的獨立多路複用（Multiplexing）串流；而 HTTP 則是定義請求/回應、動詞與狀態碼的應用層協定；gRPC 更是在 HTTP/2 基礎上封裝了強型別介面定義（IDL）與 RPC 呼叫生命週期。架構師如果在會議上直接提問「我們底層該用 TCP 還是 REST」，就如同在爭論「出門該走高速公路還是該寄包裹」一樣混亂。此外，JSON 或 Protocol Buffers 只是序列化編碼的選擇，TLS 掌管傳輸安全，它們都不是協定本體的同位替代品。

協定選型的推導三部曲極其明確：第一步，檢視資料特質與互動模式。業務文件的二進位位元組必須百分之百精確無誤且依序組裝，遺失一個封包絕不能拿下一張圖充數，這直接排除了不可靠的純 UDP；相反地，視訊會議中的即時語音封包若發生遺失，寧可直接丟棄也絕不能等待重傳，否則延遲累積會讓通話徹底無法進行。第二步，審視終端環境與網路拓撲。呼叫端是公網瀏覽器、原生手機 App、還是內部 VPC 的微服務？企業級防火牆與 CDN 代理是否會粗暴攔截或降級非標準連接埠？第三步，精算綜合開銷：包含 CPU 序列化開銷、TLS 握手延遲、封包標頭大小、連線並行限制以及維運團隊的可觀測性工具鏈成熟度。

HTTP/2 雖然在一條 TCP 連線上實現了多個 Stream 的交錯多工傳輸，但因為底層依然是一條單一的 TCP 連線，一旦實體網路發生微小丟包，TCP 為了維護嚴格的順序交付，會強制卡住整條連線的所有後續封包，引發所謂的傳輸層隊頭阻塞（Head-of-Line Blocking），導致連線上所有並行的 HTTP 請求一同卡死。HTTP/3 改以基於 UDP 的 QUIC 作為底層傳輸，各個 Stream 之間的資料交付彼此完全獨立，單一 Stream 的丟包重傳絲毫不會阻礙其他 Stream 的前進！但在享受 QUIC 優勢的同時，也必須清醒認識到：同一個 Stream 內部依然存在順序約束；多個 Stream 依然共享同一個連接的擁塞控制演算法與 CPU 資源；且若 HTTP 標頭引用了尚未抵達的 QPACK 動態表更新，解碼依然會發生暫態等待（見 QPACK Blocked Streams 規範）。深入研讀 HTTP/2、HTTP/3 與 RFC 9000 QUIC 標準是掌握這場網路革命的必備功課。

延遲預算的殘酷推算：假設某個文件發布流程需要連續串行呼叫三個內部微服務，而每次呼叫的單向網路傳播延遲加上伺服器端處理時間合計為 90 毫秒（80 ms RTT + 10 ms CPU）。那麼這三次串行依賴就必然會穩固累積出高達 3 × 90 = 270 毫秒的剛性延遲！在這種糟糕的串行拓撲面前，工程師即使花費一個月將 JSON 欄位縮短幾個字母，對整體延遲的改善也幾乎是杯水車薪；真正的架構破局點永遠在於：將相依請求改為並行獲取、透過批次 API 合併呼叫，或是將流程重構為非同步事件流。反過來說，如果是在內部微服務之間每秒流轉數百萬次極小請求的高吞吐路徑上，Protocol Buffers 相比 JSON 所省下的 CPU 序列化開銷與記憶體分配量，才會真正轉化為真金白銀的伺服器成本節省。

所有跨網路呼叫都必須在應用層設置嚴格的全鏈路截止時間（Deadline / Timeout Propagation）。如果前端 API 閘道對用戶端的總體延遲承諾是 2 秒，那麼下游呼叫的 Service A、B、C 絕不能各自天真地預設等待 2 秒且各自盲目重試 3 次，否則單點故障會迅速演變成整條呼叫鏈的資源耗盡爆炸。呼叫端必須在通訊標頭中向下傳遞剩餘的可用時間配額，一旦逾時發生，下游所有無用計算必須立即主動自我終止。gRPC Deadline 官方實踐指南深刻提醒：協定只是提供傳遞 Deadline 的載體，你的業務程式碼必須主動監聽 Context 的取消信號並停止執行，才能真正達到保護系統的效果。

練習：用戶端因前端介面逾時主動取消了 gRPC 呼叫，後端伺服器上的大檔案轉換運算就必定會立即終止嗎？

絕對不一定。首先，取消信號（RST_STREAM / CANCEL）在網路傳輸中可能延遲抵達；其次，後端工作執行緒如果正在呼叫不支援中斷的底層 C 函式庫或阻塞式的本機磁碟 I/O，根本無法即時回應中斷請求；更致命的是，運算可能在取消信號抵達的前一毫秒就已經完成並準備發布結果。架構上必須為非同步任務設計可查詢的 job_id、狀態機檢查點（Checkpoint）與冪等提交保證；API 規格必須清晰定義取消語意：究竟是「中斷當前計算」「丟棄尚未開始的階段」還是「運算照常完成但不再發布通知」，絕不可含混帶過。

8.6 Network protocols in real-life systems：沿著完整流程選擇

任何成熟的企業級分散式系統，都絕不可能只靠單一通訊協定打天下。不同資料路徑的物理特性與存取頻率截然不同：文件上傳需要極致相容的網頁通訊；內部服務之間需要低開銷、具備強型別合約的短 RPC；即時進度推播需要輕量長連線；而重型的非同步計算則必須依賴具備持久化保證的訊息佇列。成熟的架構師能夠為系統的每一個通訊邊界清晰給出技術選型的物理理由；而全公司一刀切盲目追求某個「最新協定」，只不過是掩蓋架構思考怠惰的藉口。

gRPC 官方核心概念定義了四種呼叫模型：單元 RPC（Unary）、伺服器端串流（Server Streaming）、客戶端串流（Client Streaming）與雙向串流（Bidirectional Streaming）。它們完美契合了不同的資料互動形狀，但工程師千萬不能把「長串流 RPC」當作萬能且無限容量的持久化訊息佇列。如果 Worker 執行長達 10 分鐘的轉檔任務期間，API 閘道必須持續維持一條脆弱的 gRPC 連線等待其返回，那麼任何一次發布更新、網路抖動或負載平衡器逾時，都會讓整個任務的生命週期陷入失控。將長時任務持久化為可查詢的非同步 Job 實體，才是分散式系統歷久彌新的黃金解法。

HTTP 語意的精準運用更是系統穩健的基石。GET 應當永遠具備安全（Safe）與冪等（Idempotent）特性，絕不能用 GET 請求觸發會扣款或消耗昂貴算力的轉檔任務；但使用 POST 也絕不代表系統會自動獲得「恰好執行一次」的魔法。PUT 與 DELETE 的冪等性規範、基於 ETag 的條件請求以及精準的 HTTP 狀態碼在 RFC 9110 HTTP Semantics 標準中有著嚴謹的定義。永遠記住：底層網路傳輸的成功（200 OK），僅僅代表該次通訊交換圓滿達成，絲毫不代表後續的背景運算、簡訊通知或第三方金融扣款已經全數落實。

分散式狀態脫節的經典故障：客戶端已成功將 5 MB 原件直傳至物件儲存，但隨後向 API 發起「建立轉檔工作」時遭遇網路斷線，導致物件儲存中殘留了無人認領的孤兒檔案；反過來，工作紀錄已提早在資料庫中生成，但客戶端的大檔案上傳中途失敗，導致 Worker 提早被喚醒卻撲了個空。優雅的架構解法是引入上傳工作階段（Upload Session）狀態機：客戶端先申請具備明確有效期的上傳意圖（Presigned URL），檔案傳輸完畢後主動通知伺服器校驗檔案大小與 Checksum，確認無誤後原子地將狀態推進為「待處理」；所有逾期未完成的孤兒 Session 則由後台清理排程自動回收。這種狀態閉環的挑戰，絕不會因為你將協定從 HTTP 改成 gRPC 就神奇消失。

練習：主管提議將所有內部微服務全面從 REST/JSON 遷移為二進位 gRPC，系統整體端到端延遲就必然會成倍改善嗎？

完全不一定。如果經過分散式鏈路追蹤（APM）分析，系統當前的效能瓶頸 95% 都卡在資料庫慢查詢、跨可用區網路傳播、串行呼叫阻塞或大型 PDF 產物的磁碟 I/O 上，那麼 JSON 序列化所耗費的幾個毫秒在總延遲中只占極微小的邊際比例。盲目推動全量重構，反而會引入 API 網關跨協定轉換、瀏覽器端除錯成本劇增、第三方整合困難與二進位合約版本管理的龐大負擔。成熟的做法是：針對高頻、結構穩定且 CPU 序列化占比顯著的內部核心微服務路徑精準引入 gRPC，其餘彈性與相容性優先的路徑則繼續沿用標準 HTTP/JSON。

8.7 Video over HTTP：把連續媒體拆成可取得的片段

影音檔案表面上看是連續不斷的大型資料流，但現代隨選視訊（VOD）與串流直播全面採用了「索引清單＋微小分段」的架構哲學。轉碼伺服器預先將同一份影片內容轉換為多種不同的解析度與位元率（Renditions），並切分成固定長度（例如 2 到 6 秒）的獨立媒體片段（Segments）；播放器先下載索引檔案（Manifest/Playlist，如 HLS 的 .m3u8 或 DASH 的 .mpd），隨後依據當前的網路頻寬、本機緩衝區深度與螢幕解析度，動態向邊緣節點索取最適版本的下一個分段。這項突破性的設計讓原本沉重的影音傳輸能夠無縫利用全球既有的標準 HTTP 快取與 CDN 基礎設施，徹底終結了以往每個觀眾都必須對串流伺服器維持專屬長連線的資源噩夢。RFC 8216 HLS 規範是理解這套機制的經典文獻。

我們以數據親手精算頻寬規模：假設一份 10 分鐘的高畫質教學影片，其編碼位元率為 4 Mbps，每 4 秒切為一個分段，單個分段檔案大小為 (4 Mbps × 4s) / 8 = 2 MB。整部影片總容量約為 300 MB。如果平台同時有 10 萬名企業學員在線觀看這支影片，系統端到端輸出的總頻寬需求將高達驚人的 400 Gbps！如果所有流量都由中央來源伺服器硬扛，沒有任何單體系統能承受這種海嘯。在穩態觀看下，全網每 4 秒就會產生 100,000 次分段請求，相當於高達 25,000 QPS 的純分段下載壓力，這還尚未計入播放清單更新、音軌切換與暫態重試的請求量。

分段時長的設定是經典的工程權衡。採用極短的片段（如 1 至 2 秒）能讓播放器更靈活地在不同位元率之間秒級切換，並大幅拉近直播的即時性；但代價是分段請求數量暴增數倍、Manifest 檔案高頻刷新，且編碼關鍵影格（Keyframe/IDR）過於密集會直接傷害整體壓縮效率。相反地，較長的分段（如 6 至 10 秒）能顯著降低 HTTP 請求頻率並換取更高的視訊畫質，但會增加播放器的初始啟動時間（Time-to-First-Frame）與畫質切換的遲鈍感。切忌盲目斷言「片段越短延遲必定越低」，因為解碼器預取、CDN 邊緣命中、Manifest 快取新鮮度與網路暫態抖動，共同主宰著觀眾端到端的真實體驗。

自適應位元率（ABR）的避震智慧：播放器內部的 ABR 演算法絕不能單純只看「剛才那一個分段的下載秒數」。如果播放器發現剛才 2 MB 的分段在 0.5 秒內極速載入，就興奮地立刻升級到 4K 最高畫質；結果下一個分段遭遇網路短暫抖動，下載耗時超過緩衝區儲備，畫面就會立刻引發痛苦的卡頓轉圈（Rebuffering）。成熟的 ABR 演算法（如 BBA 或 MPC）會同時監控當前可用緩衝區秒數、多段滑動平均頻寬以及畫質跳轉的心理成本，確保畫質平滑過渡。此外，不同畫質梯度的分段在時間軸上必須嚴格關鍵影格對齊，否則在畫質切換的瞬間，解碼器極易引發畫面撕裂或音訊不同步的異常。

平台業務落地：如果我們的文件平台擴充「將大型簡報投影片自動轉成旁白解說影片」的功能，非同步 Worker 轉檔完畢後，應產出多套畫質的不可變分段檔案並上傳至物件儲存。一項極為嚴肅的發布順序鐵律是：只有當某個版本的所有分段檔案與音軌全數上傳校驗完畢後，才能正式發布對應的 Manifest 索引檔案；否則學員播放到一半就會冷不防撞上 HTTP 404 崩潰。對於企業內部機密培訓影片，授權驗證必須在 Manifest 簽名 URL 與每一個媒體分段的邊緣請求上全數落實，絕不能只在進入播放首頁時檢查一次就高枕無憂。

練習：如果直接將整部影片打包成單一 MP4 檔案，透過 HTTP Range 請求也可以按需下載播放，我們還一定需要 HLS 嗎？

不一定，這完全取決於產品需求。對於長度極短（幾秒鐘）、畫質單一且僅供內部少數人觀看的短影音，直接利用支援 HTTP Range 標頭（206 Partial Content）的靜態檔案伺服器是實作最快、架構最輕量的方案；但如果業務場景需要面對跨國公網、多種終端設備（從手機弱網到 4K 螢幕）、要求即時根據頻寬切換畫質，或是涉及即時直播串流，那麼以 HLS 或 DASH 為代表的分段串流架構便是唯一具備工業級彈性與 CDN 極致快取優勢的標準解法。依據播放端相容性、轉碼成本與快取策略精準決策，不可將「影音走 HTTP」死板簡化為單一模式。

8.8 CDN：把重複傳輸搬到靠近使用者的地方

內容傳遞網路（Content Delivery Network, CDN）的核心價值，在於利用廣布全球的邊緣節點（PoP）就近回應終端使用者的重複存取請求，將原本必須跨越大洋的海量流量卸載在網路邊緣，大幅降低中央來源伺服器的頻寬壓力與物理往返延遲。其基本流程是：使用者發出請求後，經由 Anycast 或智慧 DNS 引流至距離最近的邊緣節點；邊緣若快取命中（Cache Hit）則以個位數毫秒直接回應；若快取缺失（Cache Miss）才向上層節點或中央儲存來源發起回源（Origin Fetch），並依據快取原則將資料沉澱在邊緣。然而，CDN 絕不僅僅是一組大型的反向代理叢集，它深刻牽涉到路由引流、快取鍵（Cache Key）設計、過期協商、主動失效（Purge）、回源保護與安全隔離；本節的重點便是透徹推導這些機制交互作用下的架構後果。

首先必須嚴格區分請求命中率（Request Hit Ratio）與位元組命中率（Byte Hit Ratio）的巨大差異。假設某個用戶端連續發送了 99 次 10 KB 的小圖示請求且全數命中，隨後發起 1 次 1 GB 的大文件下載遭遇快取缺失，此時系統的請求命中率高達看起來無可挑剔的 99%，但以實體頻寬來看，99.9% 的流量位元組依然結結實實打在中央來源儲存上！假設我們的文件平台每日對外總輸出流量為 20 TB，若邊緣位元組命中率為 95%，中央儲存每日的實際回源流出量約為 20 TB × (1 - 0.95) = 1 TB；在此之外，還必須另外疊加條件請求的 304 重新驗證開銷、多可用區傳輸費用與故障重試流量。在規劃來源容量與雲端帳單預算時，絕不能拿請求命中率去乘以總資料量來欺騙自己。

快取鍵（Cache Key）就是多租戶安全隔離的生命線。如果系統提供文件預覽的 URL 全都叫 /preview/latest，而來源伺服器純粹依賴 HTTP Request Header 中的 Cookie 來辨識租戶並吐出不同內容；一旦 CDN 節點在設定上忽略了 Cookie 或錯誤啟用了共用快取，租戶 A 請求產生的預覽快照就會直接被租戶 B 撈走，引發嚴重的資訊安全災難！最安全且優雅的設計，是採用不可變且帶有租戶與版本前綴的實體路徑（例如 /tenants/{tid}/docs/{did}/v{ver}/preview.webp），並在邊緣確保每次快取命中時依然驗證動態授權；或者對於高敏感的個人化資料，直接在標頭中標明嚴禁在共用快取留存。使用簽名 URL（Signed URL）時，更必須精確設定 CDN 快取鍵是否納入特定 Query 參數，切忌為了追求虛高的命中率而粗暴忽略所有參數，導致安全校驗形同虛設。

在 RFC 9111 HTTP Caching 規範中，private、no-store、no-cache 以及條件重新驗證具有嚴謹的法律級語意：no-cache 絕非「完全不快取」，而是指令「每次使用快取內容前，必須先向來源伺服器進行驗證（如 304 Not Modified）」；no-store 才是真正的「嚴禁將任何位元組寫入任何實體磁碟或記憶體快取」；private 則明確宣告該內容專屬於單一使用者瀏覽器，嚴禁在 CDN 或公司共用 Proxy 等共享快取（Shared Cache）中儲存。這些標頭是快取控制策略，永遠無法取代真正的身分驗證與存取授權；一旦 CDN 代理層的設定意外覆寫了來源標頭，就必須在 CI/CD 安全測試中第一時間攔截警報。

採用版本化 URL 能讓快取治理變得無比輕鬆：v17 的檔案內容在世界上永遠不可變，當內容異動時直接發布 v18，前端只需更新微小的版本索引指標即可，根本不必大費周章地向 CDN 發送代價昂貴的 Purge 指令。然而，資料的可撤銷性（Revocability）依然需要周全考量：如果授權由邊緣節點校驗，一旦管理員緊急撤銷某使用者的權限，邊緣快取的授權狀態必須能透過短 TTL 或 Pub/Sub 即時更新；而已經被惡意使用者下載存入本機硬碟的位元組，無論如何靠清理 CDN 都已無法追回。若企業因 GDPR 或資安法規要求「被遺忘權」徹底銷毀某份文件，更必須將來源儲存、各衍生縮圖、邊緣快取與冷備份磁帶的生命週期一同連動處置，絕不能單純回傳一個 200 OK 就草草了事。

回源雪崩故障演練：當一份全公司必讀的重大公告文件剛上架時，全球所有邊緣節點在此刻全數快取未命中，數萬個並行請求瞬間同時灌向中央來源伺服器，引爆毀滅性的快取踩踏（Cache Stampede / Thundering Herd）。在架構上，必須在 CDN 啟用請求合併（Request Collapsing / Origin Shield）：讓同一個邊緣節點只向來源發送 1 個回源請求，其餘並行連線在邊緣排隊等待第一個請求返回；同時搭配來源端的限流熔斷與主動預熱（Warming）。對於時效性要求稍寬鬆的公開資料，可透過 stale-while-revalidate 允許邊緣在非同步更新的同時先以舊快取回應；但對於私密權限與刪除狀態，則絕對嚴禁為了追求可用性而任由過期快取在外遊蕩。

練習：如果將靜態資源的 CDN TTL 直接設為 1 年，中央來源伺服器的流量達到理論最低，這是否就是最理想的架構設定？

只有在該資源的 URL 嚴格包含內容雜湊或唯一版本號（如 bundle.a1b2c3d4.js）、且業務保證該版本內容永不修改的前提下，設定 1 年 TTL 才是最佳實踐。如果 URL 缺乏版本號（如 logo.png 或 API 設定檔），盲目設定 1 年快取會讓任何緊急 Bug 修復或內容更換演變成災難，全球 CDN 節點與瀏覽器本機快取的清理成本極高且收斂緩慢；更糟的是，若意外快取了含有錯誤敏感資訊的頁面，長 TTL 會讓危害被無限放大。健全的設計是：將內容實體與版本指標嚴格解耦，實體採長期快取，版本指標採極短快取或強制重新驗證（no-cache）。

8.9 Push and pull technologies：把名稱拆成可比較的機制

短輪詢（Short Polling）：客戶端依固定或自適應的時間間隔反覆發送 HTTP 請求。其實作難度最低，天然相容所有的 HTTP 代理、防火牆與負載平衡設施；搭配 ETag 或 If-Modified-Since 條件請求能大幅節省未變更時的封包 Body，但依然無法消除高頻建立連線與傳輸標頭的巨大成本。設計時必須在輪詢間隔中強制加入隨機抖動（Jitter），防止成千上萬的客戶端在整點同時甦醒發起請求；當瀏覽器分頁切換至後台或隱藏時，應主動拉長輪詢間隔以節省電量與伺服器資源。

長輪詢（Long Polling）：客戶端發起 HTTP 請求後，若伺服器當前沒有新資料，並不立即回覆，而是將該請求在記憶體中掛起（Hang），直到有新事件產生或達到伺服器等待上限（例如 30 秒）時才返回；客戶端在處理完回應後，立即發起下一次長輪詢。這大幅消除了短輪詢的無效空回覆，但長年掛起的連線需要嚴格管控最大並行數，且應用層的掛起逾時時間必須設定得比底層負載平衡器與代理層的 TCP 逾時略短（例如代理逾時 60 秒，應用層設定 45 秒）。在舊請求結束到新請求重新送達的微小空檔中，伺服器可能產生了新事件，因此每次請求都必須攜帶進度游標（Cursor），確保無縫補齊兩次請求之間的資料斷層。

SSE（Server-Sent Events）：伺服器在常規 HTTP 基礎上回應 text/event-stream 內容類型，維持單向長連線，由伺服器向瀏覽器源源不絕地推送文字事件。瀏覽器原生提供的 EventSource API 內建了自動斷線重連與 Last-Event-ID 補發協商機制，規格詳見 WHATWG Server-Sent Events 標準。伺服器可以依據此 ID 從持久化事件儲存中精準補送歷史訊息；而客戶端若需要向伺服器發送指令，則另行呼叫標準的 HTTP POST 請求，職責分離極度清晰。

SSE 的接收游標與業務完成游標：工程實務中存在一個隱蔽的巨坑：瀏覽器在接收到資料區塊時，會「先更新」內部 EventSource 的 last event ID，隨後才觸發 JavaScript 應用程式的回呼函式。如果前端在執行第 42 號事件的業務邏輯時拋出未捕捉異常崩潰，隨後觸發自動重連時，瀏覽器依然會大意地向伺服器送出 Last-Event-ID: 42，導致第 42 號事件徹底遺失！對於需要保證逐筆落實的業務，應用層必須在本地 IndexedDB 或 localStorage 中獨立持久化維護 last_applied_cursor，且唯有在業務真正成功套用後才推進游標；一旦處理失敗，立即主動關閉連線並依據自身的完成游標重啟補抓。深入細節可參閱 WHATWG EventSource 事件派送步驟規範。

WebSocket：在經過單次 HTTP 握手升級後，底層建立一條全雙工、輕量分幀（Framing）的雙向長連線，極度適合高頻雙向互動的場景（如協同編輯或線上對戰）。RFC 6455 規範標準化了資料分幀、Ping/Pong 心跳探測與關閉流程，但它完全沒有替應用層定義持久化信箱、業務級 ACK 確認、斷線重播或恰好一次（Exactly-once）的語意。底層 TCP 的保序性僅限於單一連線之內；當客戶端斷線重連至叢集中的另一台閘道節點時，訊息是否丟失、是否重複發送以及跨連線事件的因果順序，全數依賴應用層自力更生。

Webhook 與系統推播（Push Notifications）：Webhook 是伺服器對伺服器（Server-to-Server）透過 HTTP POST 主動呼叫接收方指定的公開 Webhook 端點，架構上必須嚴格實施 HMAC-SHA256 簽名驗證、時間戳防重放、逾時熔斷與指數退避重試；而行動裝置推播（如 APNs、FCM）則是由作業系統廠商的專屬通道代為管理背景裝置的投遞，牽涉到裝置 Token 輪替、TTL 過期與系統省電凍結。它們雖然都被冠上「Push」之名，但在信任模型、網路拓撲與保證水準上完全不可同日而語。RFC 8030 Web Push 規範完整梳理了現代推播體系的架構角色。

背壓（Backpressure）的數學震撼：假設單一弱網客戶端的實體頻寬每秒只能消化 10 筆通知，而伺服器端此時正以每秒 100 筆的速率瘋狂產出事件，每筆事件大小為 1 KB。如果閘道器沒有任何背壓防禦，短短 10 分鐘內，單單為這一個客戶端累積的未送佇列就會膨脹達到 (100 - 10) × 600 × 1 KB ≈ 54 MB！如果線上同時有 1 萬個這類慢速連線，伺服器記憶體將被硬生生吃掉高達 540 GB，引發連鎖 OOM 崩潰。面對背壓，正確架構絕不是盲目加大閘道記憶體，而是實施狀態合併（只保留最新進度覆蓋舊進度）、主動丟棄非關鍵瞬態訊息、縮小訂閱範圍，或者在緩衝區飽和時狠心切斷連線，迫使其重連後按游標拉取補償。

練習：當後端呼叫 WebSocket 的 send() 函式成功返回時，我們可以在資料庫中直接將該通知標記為「使用者已讀」嗎？

絕對不行。send() 成功返回，在作業系統層級僅僅代表位元組已經成功複製到本地核心的 Socket 發送緩衝區中，甚至連是否已經藉由網卡發送出去都未成定局。即使後續收到前端發回的「網路收到 ACK」，也僅僅代表封包已抵達瀏覽器記憶體，絲毫不代表使用者肉眼已經看到。嚴謹的架構必須將事件的生命週期嚴格切分為五個階段：事件持久化入庫（Persisted）、網路傳輸送出（Dispatched）、客戶端收到（Received）、前端畫面成功渲染（Rendered）以及使用者真正點擊或視窗聚焦的業務已讀（Read）。你的產品需要向用戶承諾哪一種保證，就必須為該語意設計專屬的端到端回報事件。

8.10 Push and pull technologies in real-life systems：混合通常更合理

在真實世界的高併發工業架構中，最頂尖的設計永遠是將 Push 與 Pull 巧妙分配在不同的系統邊界。Apache Kafka 官方架構設計白皮書對此有極為深刻的剖析：在資料發布端，生產者將事件 Push 至 Broker 叢集；但在消費端，Kafka 堅持採用消費者主動 Pull 模式。這賦予了消費者至高無上的自主權——消費者完全依照自身當前的 CPU 與記憶體餘裕控制拉取速率，透過長輪詢批次一次撈取數千筆資料，將網路傳輸與磁碟 I/O 的系統呼叫成本徹底攤平，天生自帶完美的背壓免疫力。如果只用簡單的一句「Kafka 是 Push 還是 Pull 系統」來定性，就會把真正精妙的流量調控邊界完全抹殺。

現代監控領域的 Prometheus 同樣是混合架構的典範：它堅持採用主動 Pull（Scrape）模式定期爬取各微服務的 /metrics 端點，這讓監控系統能精準掌握採樣間隔，並在目標服務失聯時第一時間主動告警。然而面對生命週期只有幾秒鐘的短暫批次運算（Batch Job），任務可能在下一次採樣週期到來前就已執行完畢並銷毀，此時任務可以主動將最終指標 Push 到暫存的 Pushgateway，再由 Prometheus 悠閒地從中 Pull 採樣。Prometheus Pushgateway 官方指引特別提醒：Pushgateway 絕非將整個監控系統改成 Push 模式的萬能後門，過期殘留序列與單點瓶頸都需要額外治理。技術選擇的核心，永遠在於誰能在下一次通訊交換前可靠地存活下來。

手機作業系統的第三方推播通知（FCM/APNs）更是絕對不能被當作可信的持久化信箱。Firebase 官方訊息存活週期文件明確指出：推播訊息可能因為裝置離線、進入極度省電模式、超過 TTL 限制或網路丟失而遭到靜默丟棄。因此在我們平台中，伺服器向手機發送「文件轉換成功」的通知，在 Payload 中僅僅存放最微小的通知提示與工作 ID；當使用者點開推播喚醒 App 時，應用程式必須主動透過帶有鑑權的 REST API 查詢伺服器端的持久化收件匣（Inbox）獲取最新工作真實狀態。不可丟失的重大業務憑據，永遠不能寄生在脆弱的公網推播封包上。

端到端事件交付的完整黃金鏈路：Worker 轉檔完成後，在同一個本機資料庫交易中原子提交「工作狀態標記為完成」與「Outbox 待發布事件」；隨後由可靠的 Relay 程式將 Outbox 記錄投遞至全域訊息 Broker（如 Kafka）；通知微服務作為消費者從 Broker 拉取事件，精確計算出所有相關收件者，並為每位收件者在持久化資料庫中寫入各自的 Inbox 記錄；線上長連線閘道器在收到內部廣播提示後，即時向在線客戶端推送輕量 Ping；離線使用者則由後台透過 APNs/FCM 喚醒手機；最後，當使用者打開應用程式時，帶著本地的 last_seen_cursor 主動拉取未同步事件清單。鏈路中的每個環節都自帶獨立的重試、去重與確認點；端到端去重嚴格基於 (event_id, recipient_id)，使整條鏈路具備隨時容忍網路抖動與重複投遞的鋼鐵韌性。

租戶自訂 Webhook 的資安防線：當平台允許企業租戶自訂 Webhook 回呼網址時，伺服器絕對不能直接拿著這個 URL 在內網隨意發起 HTTP 呼叫，否則外部惡意租戶只要將 Webhook 網址設定為 http://169.254.169.254/latest/meta-data/ 或內部資料庫 IP，就能發動毀滅性的伺服器端請求偽造（SSRF）竊取雲端權證！嚴謹的 Webhook 系統必須強制驗證網址所有權、實施嚴格的私人 IP 與本機環回位址過濾（阻擋 RFC 1918 位址）、防止 DNS 重綁定攻擊（DNS Rebinding，在解析後驗證 IP 並直接對固定 IP 連線），並強制配置專用的隔離轉發代理。此外，Webhook 投遞必須由獨立的佇列與限制速率的 Worker 執行，絕不可因為客戶端接收伺服器當機卡死，而反向把平台核心的文件轉換管線拖垮。

分散式亂序與因果一致性：在重試機制下，「轉檔成功事件」完全可能因為網路抖動重試，反而比稍後發出的「權限撤銷事件」更晚抵達前端！如果客戶端毫無防備地直接套用最後收到的封包，就會將早已被撤銷權限的文件離奇還原。在架構上，每份文件的狀態變更必須具備單調遞增的邏輯版本號（State Version），客戶端嚴格拒絕套用版本號小於或等於本地當前狀態的舊事件；且在真正請求讀取檔案內容時，後端依然必須進行強制即時鑑權。物理時間戳在跨主機情境下存在無法避免的時鐘漂移（Clock Drift），不可作為因果先後的權威判定標準。

練習：系統向企業租戶發送的 Webhook 連續三次逾時失敗，在後台日誌中我們能直接將該事件判定為「客戶絕對沒有收到」嗎？

絕對不能。在網路世界中，「逾時」的物理本質是「狀態未知」——對方的伺服器完全可能已經成功收到事件、寫入資料庫甚至處理完畢，僅僅是在回傳 HTTP 200 回應時遭遇網路斷線或反向代理逾時。每次重試發送時，標頭中的 event_id 必須嚴格保持一致，要求接收方落實冪等去重；在後台管理介面中，系統應當誠實地將投遞狀態標記為「未獲確認（Unacknowledged）」，並提供人工重發與事件歷史查詢介面，切忌主觀武斷地判定為「未執行」。

8.11 Large-scale push architectures：讓斷線成為正常情況

在設計支撐百萬級連線的超大型即時推播系統時，核心架構鐵律是：必須將「不可丟失的事件真實資料」與「使用者此刻連在哪台主機的暫態位置」在實體層面徹底拆開。持久化的事件日誌與收件匣（Inbox）存放在高可用分散式資料庫中，代表無可撼動的事實來源；邊緣推播閘道器（Gateway）只負責維持輕量的 TCP/WebSocket 長連線，完全不承擔資料持久化責任；而中央在線註冊表（Presence Registry，通常為 Redis 叢集）僅保存 user_id / device_id → gateway_node_id 的暫態映射與短暫租約。閘道器節點隨時可以崩潰或滾動重啟，Presence 資訊也允許短暫過期失效；只要資料庫中的 Inbox 安然無恙，使用者重新連線後隨時都能無縫補齊資料。

精算事件傳輸規模：每日 100 萬份文件 × 每份 5 筆狀態事件 = 500 萬筆原始事件/日，平均約 57.87 事件/秒，以 10 倍尖峰估算約為 578.7 事件/秒。每筆事件平均需通知 3 位相關人員，意味著尖峰時段的事件扇出（Fanout）投遞速率約為 578.7 × 3 ≈ 1,736 筆投遞/秒。若每則通知加上封裝標頭平均為 1 KB，純 Payload 頻寬約 1.736 MB/秒（約 13.9 Mbps），這在現代伺服器頻寬面前完全遊刃有餘。真正構成嚴峻工程挑戰的，是線上常駐的 10 萬條並行長連線維護、心跳封包頻率、TLS 握手 CPU 消耗，以及極端巨型租戶一次向 10 萬人廣播所引發的瞬間寫入突刺。

扇出架構絕不可單純依賴全域均值設計。如果某個頂級企業租戶發布了一份全體員工必讀文件，瞬間需向 10 萬名在線成員推送通知，單一事件就會在幾毫秒內引發 10 萬次資料庫寫入與網路推播！架構上必須將龐大的收件者集合拆解為有界的批次非同步工作，在任務佇列中透過游標分批處理，並為每個租戶設定嚴格的每秒扇出上限，防止大租戶的廣播狂潮將其他正常租戶的即時通知完全擠死。在寫入扇出（Fanout-on-Write，寫入時為每位收件者產生 Inbox）與讀取扇出（Fanout-on-Read，全體共用同一份公告，使用者在讀取時動態合併）之間，大型系統通常會依據受眾規模採取動態混合策略。

閘道連線容量的物理推算：假設經過全規模壓力測試驗證，單台 4 核心 8 GB 的閘道節點在兼顧 P99 延遲與作業系統 Socket 緩衝區的前提下，能夠安全穩定維持 20,000 條長連線。那麼要支撐 10 萬條在線連線，理論最低算術值是 100,000 / 20,000 = 5 台。但這絕對不是能直接上線的容量配置！在生產環境中，我們至少應部署 8 台（每台平日承載 12,500 條連線）；當遭遇單一可用區（AZ）整座斷電、瞬間失去 3 台節點時，剩餘 5 台剛好各扛 20,000 條連線，剛好頂住警戒紅線而不致全面雪崩。實體限制取決於作業系統檔案描述符（File Descriptors）、epoll 核心排程、TLS 握手運算與慢速緩衝區記憶體，絕非靠網路上某個未經實測的「單機百萬連線」神話決定。

防範重連海嘯（Thundering Herd Reconnect）：當叢集進行發布或網路短暫抖動時，若 10 萬個客戶端在 10 秒鐘內集體發起重連，後端將瞬間承受高達每秒 1 萬次的 TLS 握手與 JWT 鑑權請求，伴隨著隨後而來的全量狀態補抓查詢，後端資料庫會被瞬間打穿。對此，客戶端必須強制實施帶有全抖動（Full Jitter）的指數退避重連演算法；閘道層配置嚴格的握手速率限制器（Rate Limiter）主動拒絕超額連線以保護既有連線；在維運滾動部署時，應分批對長連線進行漸進式優雅排空。此外，心跳間隔必須謹慎權衡：30 秒一次心跳意味著 10 萬連線每秒產生 3,333 次 Ping/Pong 往返，這會消耗大量伺服器 CPU 並頻繁喚醒行動裝置無線電晶片；心跳僅能證明當前 TCP 管道尚未被 NAT 閘道逾時關閉，絲毫無法證明上層業務訊息已被客戶端完整消費。

徹底消除補抓與即時串流之間的狀態空隙：最優雅的補償演算法是：當客戶端帶著本地的 last_applied_cursor 建立連線時，伺服器先在記憶體中建立可銜接的事件訂閱監聽，並讀取持久化串流的當前高水位線（High Watermark, H）；接著，從資料庫中精確重播 (cursor, H] 區間的所有歷史事件；最後，將即時串流中大於 H 的新事件平滑無縫地交接給客戶端。另一種做法是直接讓分散式 Log 串流（如 Kafka/Redis Streams）原生支援按 Offset 訂閱。關鍵在於這是一條具備原子邊界的確定路徑，絕對嚴禁「先向資料庫撈取歷史資料、隔了兩秒才向 Redis 訂閱新訊息」，那兩秒的資料真空期將成為難以追查的丟訊黑洞。

ACK 確認機制的嚴密語意：客戶端回傳的 ACK 必須帶有明確的累積語意（Cumulative ACK）：宣告「小於等於該游標的事件已在本地百分之百完成持久化套用」，絕不允許跳過中間漏洞單獨 ACK 後續事件。閘道器依據此完成游標動態清除輸出緩衝區；客戶端則依據 event_id 進行本地防重複套用，並比對 document_version 防止狀態倒退。在多終端設備並存的環境下，使用者的「未讀計數」「手機推播抵達確認」與「桌面分頁即時同步游標」是截然不同的業務欄位，萬萬不可偷懶用單一的 last_seen 模糊混用。

安全驗證與立體監控：長連線剛建立時的 JWT 驗證成功，絕不代表該連線在未來的 24 小時內都擁有無限存取權。當使用者的租戶被停權、帳號密碼重設或特定文件的協同權限被撤銷時，伺服器必須具備主動向特定連線發送「權限撤銷並強制踢下線」的控制指令；且客戶端在連線上訂閱的 Topic 必須在伺服器端嚴格校驗權限，絕不可任由前端隨意上報 topic_id 就盲目放行。在維運監控儀表板上，必須全天候監控在線連線數、握手拒絕率、ACK 延遲延宕（ACK Lag）、Inbox 最老未處理事件年齡（Oldest Unprocessed Event Age）、租戶未清佇列積欠與重連突刺。單看閘道節點 CPU 平均 30% 的表面健康，完全可能掩蓋了某個重要租戶的通知早已嚴重延遲半小時的致命盲點。

練習：推播閘道節點在將「轉檔完成事件」剛送入 TCP 緩衝區後、尚未收到客戶端 ACK 前突發斷電重啟，系統應當如何應對？

客戶端感知到連線中斷後，會透過指數退避重新連線至另一台健康的閘道節點，並在連線握手時上報自己最後成功套用的 last_applied_cursor。新閘道器從持久化 Inbox 中重新檢索出該筆未獲確認的事件並再次推播給客戶端。客戶端可能因此收到重複的 event_id，但前端的冪等過濾機制會辨識出該 ID 並直接略過畫面重繪；更關鍵的是，任何涉及真實金流扣款或發送確認郵件的不可逆副作用，必須嚴格由後端交易狀態機在收到鑑權請求後以冪等機制執行，絕不能交由前端瀏覽器「因為收到了 WebSocket 通知就擅自向後端發起不可逆請求」。即時通訊的斷線可恢復性，本質上由應用層的確認補抓協定所捍衛，絕對不是 WebSocket 協定自身所能附贈的神蹟。

章末設計演練：讓「完成通知」可證明、可恢復

請為本章探討的文件處理平台，完整架構出兩條關鍵的使用者體驗路徑：第一條是線上極致即時路徑，當前端瀏覽器保持在線時，要求在轉檔完成後的 2 秒內於畫面上無縫彈出通知；第二條是離線強一致復原路徑，當使用者出差搭機斷線整整 24 小時後重新連線，系統必須百分之百精確補齊所有在保留期內發生的狀態變更。系統架構必須同時滿足三項嚴苛的非功能性要求：單一租戶的突發海量廣播絕對不得無限期霸占其他租戶的頻寬與排程資源；任何推播閘道節點突發當機重啟絕不得導致持久化通知遺失；通知封包在網路中的任何重複投遞絕不得觸發重複的商業副作用。請畫出服務探索、持久化信箱、動態路由與游標補抓的清晰架構邊界，並在架構審查中逐一推演以下極端故障：資料庫交易提交後 Relay 程式突發 OOM 崩潰、手機設備離線時長徹底超過推播服務的 TTL 期限、以及全量推播閘道叢集正在進行無中斷滾動部署。

參考答案：先保留事實，再加即時通道

架構拓撲與資料流：Worker 轉檔完成後，透過資料庫交易在同一個 ACID 邊界內將「文件狀態推進為已完成」與「Outbox 待發送事件」原子寫入磁碟；隨後由具備 At-least-once 保證的獨立 Relay 程式將 Outbox 記錄投遞至 Apache Kafka。專門的通知服務作為消費者拉取該事件，透過 (event_id, recipient_id) 作為唯一約束鍵，為每位目標收件者在 PostgreSQL 分割表中寫入持久化 Inbox 記錄。針對在線路徑，通知服務在寫入資料庫後，向 Redis Pub/Sub 發布微小提示；持有該連線的 WebSocket/SSE 閘道節點接獲提示後，將事件推向客戶端；客戶端本地確認處理完畢後回傳 Cumulative ACK 推進游標。針對離線路徑，FCM/APNs 僅作為喚醒手機的外部提醒通道；當 App 重新進入前景時，直接攜帶本地保存的 last_applied_cursor 向權威 REST API 發起增量拉取。如果客戶端的游標落後時間已經徹底超出伺服器 Inbox 的 30 天保留期限，API 明確回應 410 Gone / RESET_REQUIRED，引導客戶端整庫拉取當前最新的狀態快照與全新的同步基準點，絕不能自欺欺人地默默回傳空陣列。

租戶配額隔離與極限推演：在 Kafka 消費端，每個租戶配置專屬的優先權與速率配額（Token Bucket），任何單一租戶的大型廣播扇出任務會被切分為每批 500 人的微小 Job 異步排隊，確保其他正常租戶的即時通知能在專用佇列中秒級超車。當資料庫提交後 Relay 崩潰時，重啟後的 Relay 會依據資料庫中未發送的 Outbox 記錄重新投遞，由下游通知服務的唯一約束進行冪等去重；當手機離線超過 APNs/FCM 的 TTL 導致推播封包在雲端蒸發時，使用者重新開機聯網後，App 的啟動同步邏輯依然能透過 last_applied_cursor 從伺服器 Inbox 將通知全數補回；當推播閘道叢集進行無中斷滾動部署時，伺服器主動發送 GOAWAY 訊號，分批以 10% 的比例溫和切斷連線，前端捕獲後觸發帶有隨機 Jitter（1~5 秒）的退避重連，平滑遷移至新版閘道節點並藉由 (cursor, H] 演算法無縫銜接即時串流。2 秒的即時端到端承諾，在架構儀表板上被層層拆解為：Outbox 抓取延遲（<200ms）、Kafka 隊列延遲（<100ms）、Inbox 寫入延遲（<300ms）、Redis Pub/Sub 廣播（<50ms）、閘道器隊列等待（<200ms）以及公網網路傳播 RTT（<500ms），每一段皆配置獨立的 SLO 警報門檻；而長期離線的終端設備，在架構 SLA 中被嚴正排除在 2 秒即時保證的名單之外。

通訊架構最重要的四個黃金鐵律：探索得到的位址永遠可能過期。通訊通道的成功絕對不等於業務操作的落實。任何缺乏背壓防禦的無界佇列，只是把系統過載延後成無法挽回的災難性崩潰。所有的即時推播提示，都必須能夠毫無懸念地回退到可查詢、可恢復的權威真實資料來源。
