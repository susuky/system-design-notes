CHAPTER 08 · EFFICIENT COMMUNICATION

08 有效率的通訊：找到對方、選擇協定、交付結果

通訊設計要回答三件事：現在應該找誰、用什麼方式交換資料、怎樣知道結果真的完成。TCP、HTTP、WebSocket、訊息佇列與 CDN 各自解決其中一部分。把這些層次分開，才能避免「連線還在，所以通知一定送達」這種看似合理、實際危險的推論。

讀完本章，你應該能做到

  • 區分主機、服務與對等節點探索，說明快取、健康狀態及過期資訊的影響。
  • 依延遲、流量、背壓、重試與裝置限制選擇 push／pull 和傳輸協定。
  • 算出輪詢、長連線、影片分段與通知扇出的資源成本。
  • 設計可重連、補抓、去重、隔離租戶的大型通知系統。

沿用平台：1 萬租戶、100 萬份文件／日、每份 5 MB，日均 11.57 份／秒、假設尖峰約 115.74 份／秒，每份轉換平均 2 CPU-seconds。以下額外假設每份文件有 5 筆可通知事件、每筆平均通知 3 個使用者、線上同時有 10 萬個瀏覽器連線。假設用來練習估算，不代表真實產品數據；除 KiB／GiB 外，流量單位採十進位。

8.1 Push vs pull：誰決定下一次傳送

Pull 是接收方主動要求資料，例如瀏覽器每隔一段時間查詢工作進度；push 是資料可用時由傳送方沿既有或另建的通道通知接收方。這是應用層的方向與節奏，不等同於誰最先建立 TCP 連線。瀏覽器先建立 WebSocket，之後伺服器推送事件，仍是應用層 push；使用者點開通知再抓文件內容，則是 push 與 pull 的組合。

先算最簡單的輪詢：10 萬個客戶端每 5 秒查一次，平均是 20,000 requests／秒。若大多數時間沒有新事件，許多請求只得到「還沒好」。假設事件相對輪詢時刻均勻發生、請求處理很快，平均發現延遲約是間隔的一半，即 2.5 秒，最壞接近 5 秒再加網路及服務時間。若要求平均 0.5 秒內發現，就可能改成每秒輪詢，請求量上升到 100,000／秒。這是延遲與空查詢成本的直接交換。

Push 減少空查詢，但需要維護連線、路由與慢接收者狀態。假設每個連線總共占用 32 KiB，10 萬條即約 3.05 GiB，尚未包括應用程式、額外佇列與高峰緩衝。當 1 萬個客戶端網路很慢時，不能不斷往其輸出佇列塞資料；要合併可覆寫的進度更新、限制每連線未送 bytes，或斷開並要求按游標補抓。Push 只是把「何時詢問」的成本換成「維持狀態及處理落後」的成本。

對文件平台，處理中的進度可視為「最新狀態」，80%、81%、82% 不必保證每一筆都顯示；完成、失敗、權限變更則可能是需要保留的事件。可用 push 發送小型提示，再由客戶端 pull 已驗證權限的最新狀態。這也避免在通知通道散播完整敏感文件，並使短暫斷線後的重建更簡單。

需要。客戶端首次進入、斷線重連、事件保留期已過、狀態版本出現缺口，都需要重新取得真實狀態。Push 可降低發現延遲，狀態 API 或持久化 inbox 提供可恢復的事實來源。若只把最後一次畫面當成真實來源，漏掉一則通知就可能永遠顯示舊狀態。

8.2 Host discovery：名字如何變成可連線的地址

Host discovery 解決「我知道名稱，怎麼得到地址」。最常見是 DNS：名稱透過 resolver 與權威伺服器得到 A／AAAA 等紀錄，再由客戶端建立連線。名稱可指向實體主機，也可以指向負載平衡器、CDN 或服務入口；因此 DNS 回覆不是「真正處理請求的那台機器」的保證。DNS 的層級、委派與快取原理可查 RFC 1034。

TTL 是快取資訊的有效期限參數，不是完整故障轉移 SLA。即使所有解析器都在 30 秒後重新查詢，客戶端仍可能持有既有連線；應用程式自身的解析快取、連線池與平台行為也會影響切換。把 TTL 從五分鐘改成五秒，會增加解析負載，卻不會主動搬移已建立的長連線。計畫切換時要同時考慮舊地址的保留期和連線排空。

文件平台的公開入口可以叫 api.example.test，對應穩定的負載平衡層；內部 worker 則使用服務名稱。若把每台短生命週期 worker 的 IP 寫死在程式中，每次擴容和替換都要重新部署客戶端。改用穩定名稱降低耦合，但會新增 DNS 可用性與錯誤處理責任：查詢超時、找不到名稱與「查到了但無法連線」應分類記錄，不能都回一個籠統的 500。

故障情境：區域 A 的 IP 已失效，部分客戶端繼續使用舊連線池，另一批解析到區域 B。此時需要為單次連線設定合理超時，失敗後清理不可用連線並重新解析，對冪等請求作受控重試。若是建立轉換工作的 POST，網路超時不能證明伺服器沒建立工作，仍需 idempotency key。地址探索與業務重試語意必須一起設計。

知道 IP 也不表示應該信任對方。TLS 主機名稱驗證、憑證與服務身分用來檢查連線對象，DNS 回覆與可用性探測則回答不同問題。不要為了「IP 變了連不上」就關閉憑證驗證；探索流程應保持原來的授權與信任邊界。

練習：30 秒 TTL 能否保證主機故障後 30 秒內全部恢復？

不能。故障偵測時間、DNS 更新時間、解析快取、既有連線、重試退避和新區域容量都可能拉長恢復。應分別設計並量測這些時間，讓健康檢查、排空、客戶端重連與冪等處理共同支持目標。

8.3 Service discovery：找到「現在可提供能力」的實例

Service discovery 進一步回答：「哪些實例能處理 OCR v2，而且現在適合接收工作？」除了地址與 port，還可能涉及版本、區域、權重、協定與健康狀態。Host 是網路位置，service 是能力集合；同一主機可執行多種服務，一種服務也可跨越許多主機。不要因為兩者都常借助 DNS 就忽略層次差異。

客戶端探索模式由客戶端取得可用端點並自行選擇，例如從 registry 訂閱更新；伺服器端探索則讓客戶端只連一個穩定入口，由代理或負載平衡層挑選後端。前者少一層轉送但要求每種客戶端維護一致的探索、負載平衡與重試程式；後者集中策略，卻需管理代理容量與故障域。兩者也能混合，不能只靠「多一跳」判定優劣。

Kubernetes Service提供穩定的服務抽象，後端端點可隨 Pod 變動；headless Service 則讓客戶端直接發現後端。這些機制使動態實例比較容易使用，但「端點存在」不代表每個請求都能成功。readiness、程序活著、依賴是否可用、單租戶配額是否耗盡，是不同維度的判斷。

常見 registry 使用定期心跳與租約判斷實例是否仍在。假設每 5 秒心跳、租約 15 秒，程序掛掉不會瞬間從所有客戶端消失；最後心跳、過期判斷及更新傳播都有延遲。客戶端必須承受暫時過期的名單。另一方面，短暫網路分割也可能讓健康實例被誤判失效，因此 registry 名單不能直接證明某個實例具有唯一的寫入權；寫入擁有權另需版本或 fencing 等機制。

平台取捨：OCR worker 的新工作可透過佇列分配，不一定直接對每個 worker 發 RPC；查詢服務則可使用穩定服務入口。若 registry 暫時無法連線，已有資料面請求可在有界時間內繼續用最後已知端點，並搭配失敗端點剔除。若需要新增實例或更換領導者，不能假裝舊名單仍是即時真相。要分清楚「可暫時服務」與「可正確重新配置」。

練習：服務實例在關機前立即從 registry 刪除，長請求會自然完成嗎？

不一定。既有連線與快取端點仍會存在。完整排空程序通常先停止接受新工作／標記不就緒，再等待更新傳播與在途請求完成，最後才關閉程序；有最大排空期限，且客戶端具備超時及安全重試。對長連線服務，還要安排客戶端有抖動地重連。

8.4 Peer discovery：沒有完整中央名單時怎麼加入網路

對等系統中的節點通常既是客戶端也是伺服器。新節點沒有全網名單，需要先知道少量 bootstrap peers，再逐步發現其他節點。探索可以用固定種子、區域網路的發現機制、rendezvous、gossip 或分散式雜湊表（DHT）。這些方式不是同一件事：找鄰居、維護成員狀態、定位某個 peer、尋找內容提供者，可以分成不同協定。

Gossip 的想法是每個節點只與少數其他節點交換消息，讓加入、離開或疑似故障逐步擴散。這能避免所有節點互相心跳造成約 n² 個配對，但資訊通常不是每一瞬間都一致。某節點「沒回應」可能是故障，也可能是慢、網路阻塞或暫時分割；可引入疑似狀態與間接探測降低誤判，仍不能從可達性推導全域共識。

DHT 則把節點或內容鍵映射到識別空間，透過部分路由資訊逐步找到較接近目標的節點。libp2p 的 DHT 說明區分 peer routing 與內容提供者探索。找到「聲稱有內容的節點」之後，仍要真的連線、驗證身分與內容，並處理 NAT、防火牆、節點離線和回傳過期資訊。DHT 不會自動保證內容可用，更不等於把大文件本身塞進 DHT。

平台案例：假設同一個租戶有多個受控邊緣轉換節點，希望在私有網路內共用已下載的不可變字型或模型檔，可探索附近 peer，依內容雜湊驗證下載，失敗再回到可信任來源。租戶私有文件不能只因「找到相同 hash」就允許跨租戶讀取；內容是否相同與誰有權讀取是兩個問題。P2P 省下來源頻寬的同時，也擴大了節點身分、配額與資料流向管理的責任。

選擇邊界：公司資料中心裡已有可靠控制面、節點數有限時，中央 registry 往往比較容易治理。跨自治組織、節點快速加入離開或無單一管理者的環境，peer discovery 才可能值得。不要為了一句「去中心化」引入難以追蹤的錯誤擴散與信任模型，也不要以為存在 bootstrap 節點就必須讓所有資料永遠經過它。

練習：所有 bootstrap 節點失效，整個 P2P 網路會立即停擺嗎？

未必。已加入且仍保有可用鄰居的節點可能繼續交換資料；全新或丟失狀態的節點則可能無法加入。需要多個可信 bootstrap 來源、持久化已知鄰居及重新探索策略。答案取決於其他協定是否把 bootstrap 也當作唯一授權或路由中心。

8.5 How to choose a network protocol：從需求走到協定

先分層再比較。TCP 提供可靠、有序的 byte stream，UDP 提供 datagram，QUIC 在 UDP 上建立加密、連線與可靠串流等能力；HTTP 在應用層定義請求與回應語意，gRPC 在其生態中定義 RPC 介面與訊息交換。直接問「用 TCP 還是 REST」跨了不同層次，像問「走高速公路還是寄包裹」。JSON／Protocol Buffers 是資料編碼選擇，TLS 則處理傳輸安全，也不是互相替代的同級方案。

第一步問資料是否必須完整、是否必須有序、互動是一問一答還是連續串流。文件內容必須完整，傳輸中遺失的 bytes 不能用下一張影格取代；即時通話中的過期音訊可能寧可丟棄，避免等重傳累積延遲。第二步問客戶端環境：瀏覽器、手機、企業代理及第三方整合各有不同支援。第三步才算序列化大小、連線建立、壓縮、流控、可觀測性與維運成熟度。

HTTP/2 允許在一條連線上多工不同 stream，但傳統 HTTP/2 over TCP 遺失底層封包時，仍可能因 TCP 的有序交付影響同連線的其他 stream。HTTP/3 使用 QUIC，使不同 stream 的資料交付不必因另一 stream 的缺口一起等待；然而共用擁塞控制、頻寬與 CPU 仍會互相影響，所以「HTTP/3 完全没有隊頭阻塞」說得過頭。分別見 HTTP/2、HTTP/3與 QUIC 標準。

延遲預算：假設某流程要依序呼叫三個外部 API，而且每一次 API 呼叫從呼叫端到該服務的 RTT 都是 80 ms、每個服務各處理 10 ms，這三次串行呼叫就可能累積約 3×(80＋10)＝270 ms，還不含握手、排隊與資料傳輸。換較短的欄位名稱通常救不了這種串行依賴；批次、合併請求或改變資料流可能更有效。反過來，在每秒百萬筆很小的内部 RPC 上，編碼、配置記憶體與 CPU 就可能成為主要成本。

所有協定都要有應用層 deadline。若入口的總預算只有 2 秒，依序呼叫的每一層不能各自再等 2 秒、再重試三次。把剩餘期限往下傳，取消已無用的工作，並將重試限於安全操作。gRPC deadline 文件提醒用戶端應明確設定期限；協定能傳遞 deadline，不代表你的程式已正確處理取消。

練習：客戶端超時並取消 RPC，伺服器的文件轉換一定停止了嗎？

不一定。取消訊號可能尚未到達，正在執行的運算也可能不支援即時中止。更重要的是結果可能已提交。要設計可查詢的 job_id、冪等提交與取消狀態機；取消成功的語意是「不再接新階段」「已停止計算」還是「結果不再發布」，應由 API 明確定義。

8.6 Network protocols in real-life systems：沿著完整流程選擇

成熟系統通常同時用多種協定，因為不同路徑的需求不同。文件上傳用 HTTPS；內部結構化的短 RPC 可考慮 gRPC；進度串流可用 SSE；背景通知可經平台 push；大型不可變結果走物件儲存與 CDN。每個邊界都要說明選擇理由；全公司統一成某個「最新協定」，本身不足以支持這些決定。

gRPC 官方核心概念定義 unary、server streaming、client streaming 與 bidirectional streaming 四類 RPC。它們適合表達不同資料流，但串流不是無限大的可靠佇列。若 worker 做完工作前入口服務必須持續維持一條 RPC，部署或網路斷線就會干擾任務生命週期；將長任務存成可查詢的工作，通常更容易恢復。

HTTP 的方法語意也值得認真使用。GET 用來取得資料，操作不應靠 GET 觸發轉換計費；但使用 POST 仍不會自然得到「恰好建立一次」。PUT 的冪等語意、條件請求與狀態碼在 HTTP Semantics中有定義，具體業務 API 還是要處理重試與版本衝突。傳輸成功只代表所定義的通訊步驟完成，不表示任務計算、通知或第三方副作用全部完成。

故障情境：儲存已完成上傳，但「建立工作」API 失敗，留下孤兒物件；反之，工作已建立但檔案還沒完整上傳，worker 提早開始。可用 upload session 或文件狀態機：先建立有期限的上傳意圖，完成後驗證大小與雜湊，再原子發布可處理狀態；過期未完成的意圖由清理流程回收。這個問題不會因為 HTTP 換成 gRPC 就消失。

練習：所有微服務都改用二進位 RPC，效能一定變好嗎？

不一定。若瓶頸是資料庫掃描、串行依賴或大文件頻寬，序列化可能只占很小比例。先量測每段耗時與 CPU，評估除錯、瀏覽器支援、相容性和代理工具成本。合理做法是把高頻、結構穩定、可衡量受益的路徑列為候選。

8.7 Video over HTTP：把連續媒體拆成可取得的片段

影片看起來是連續資料，但點播可以用「索引＋分段」來交付。伺服器事先把同一內容編碼成幾種解析度與位元率，再切成片段；播放器取得 manifest／playlist，按目前頻寬、緩衝與裝置能力選擇接下來下載哪個版本。這使片段可以利用一般 HTTP 快取和 CDN，不必每個觀眾都對來源維持專用媒體串流。HLS 的 playlist、媒體分段與 variant stream 基礎見 RFC 8216。

假設某訓練影片位元率 4 Mb／秒，一個 4 秒片段約 16 Mb＝2 MB。10 分鐘影片約 300 MB；10 萬人同時以此位元率觀看，總輸出約 400 Gb／秒，未含協定開銷。這通常不是單一應用伺服器可以隨手承受的數量級。若每 4 秒請求一段，穩態平均約 25,000 次 segment requests／秒，還有 manifest、音訊和重試請求。

短片段讓切換品質與接近直播邊緣更靈活，但增加請求、manifest 更新與編碼邊界成本；長片段常有較好的請求攤提，卻會增加啟動等待或追趕延遲。不能說「片段越短，延遲必定越低」，因為播放器預取、編碼、封裝、CDN 與網路抖動一起決定端到端延遲。直播還要區分事件發生到畫面出現的 glass-to-glass 延遲，與單次 HTTP 請求延遲。

自適應位元率（ABR）不應只看最近一個片段的下載速度。假設一段下載很快，播放器立刻升級到高位元率，下一段網路稍慢就緩衝見底，畫質可能不斷震盪。策略應同時考慮可用緩衝、估測頻寬與切換成本。若不同畫質的切點不對齊，切換也可能造成解碼或時間線問題；封裝與編碼梯度要一起設計。

平台延伸：文件系統若增加「簡報轉成旁白影片」，轉換結果可產出多個 rendition 與不可變 segment，以版本化 URL 發布。只有所有必要片段完成後才發布對應 manifest，避免播放到一半才發現後續檔案不存在。私有培訓內容在 manifest 和 segment 都要有授權設計，不能只保護第一個網頁。

練習：把全部影片包成一個 MP4，HTTP Range 可以取片段，還需要 HLS 嗎？

不一定每個情境都需要 HLS。簡單短片可透過支援 Range 的檔案服務供播放器按需取得；若需要多位元率切換、直播與較完整的串流流程，playlist／分段格式更方便。要根據播放端相容性、封裝方式、快取與權限要求選擇，不能把「影片走 HTTP」當成單一方案。

8.8 CDN：把重複傳輸搬到靠近使用者的地方

CDN 讓分散的邊緣節點回應可重用內容，降低來源頻寬與遠距離傳輸延遲。典型流程是：使用者被導向邊緣節點，節點命中 cache 就回傳，miss 則向來源或上層節點取得並按規則保存。CDN 不只是一堆 proxy，還涉及路由、cache key、過期、重新驗證、失效與來源保護；本節重點是能推導這些機制的後果。

先區分 request hit ratio 與 byte hit ratio。假設 99 個 10 KB 圖片命中，1 個 1 GB 文件未命中，請求命中率是 99%，但大部分 bytes 仍來自來源。若平台每天輸出 20 TB，byte hit ratio 95%，簡化估計來源內容流量約 1 TB／日；還要另計重新驗證、上傳、失敗重試與區域間流量。不能用請求命中率直接乘所有資料量。

快取鍵就是隔離的一部分。若 URL 都是 /preview/latest，伺服器依 Cookie 決定租戶內容，但 CDN 沒有正確區隔且允許共享快取，A 的預覽可能被 B 拿到。安全設計可使用不可變、租戶／物件／版本明確的路徑，並保證每次 cache hit 仍執行必要授權；或對敏感個人化回應禁止共享快取。簽名 URL 的 cache key 與驗證順序要依 CDN 實作仔細設計，不能單純忽略所有 query parameters 以提高命中率。

HTTP Caching 標準中，private、no-store、no-cache 與重新驗證的語意不同。no-cache 不是「完全不存」，而是使用前需要相應驗證；no-store 是不儲存；private 用於限制共享快取。這些標頭是協定與快取策略，不能替代登入與授權。代理配置若覆寫來源規則，也要列入安全測試。

版本化 URL 讓內容更新更容易：v17 的内容永遠不變，新的版本使用 v18，客戶端更新小型索引即可。可撤銷性仍要另算：若授權在邊緣驗證，撤銷後需讓驗證狀態及時更新；已下載到用戶端的 bytes 無法靠清 CDN 保證收回。若文件依法規或使用者操作要求刪除，也要把來源、衍生檔、邊緣快取及備份保留規則一起納入，不能僅返回刪除成功。

故障情境：熱門文件剛上架，所有邊緣都 miss，同時向來源請求，形成 cache stampede。可考慮請求合併、上層 shield、受控預熱與來源限流；對可接受稍舊的公開內容，可明確設定允許的 stale 策略。私有權限與刪除狀態則不能為了可用性任意使用過期資訊。

練習：把 TTL 設一年，來源流量最小，所以是否最好？

只有不可變內容且更新／撤銷模型已處理時才可能合理。動態狀態、權限與個人化回應不適合一概長期共享快取。長 TTL 還可能放大錯誤內容傳播與修正成本；應區分內容本體、版本指標和授權資訊的生命週期。

8.9 Push and pull technologies：把名稱拆成可比較的機制

Short polling：每隔固定或自適應間隔發一次查詢，實作簡單，容易使用一般 HTTP 基礎設施。配合 ETag／條件請求可減少回應內容，卻不會消除請求本身。間隔加入 jitter，避免所有客戶端整點一起醒來；頁面在背景時可降低頻率，但完成事件仍要有下次同步方式。

Long polling：客戶端發出請求，伺服器在有事件或到達等待上限才回應，客戶端接著再發下一個。這把許多空回應變成懸掛請求，需控制同時等待數量，並設置比代理超時更適合的應用層等待時間。舊請求結束到新請求開始之間可能有空檔，因此每次都應帶游標，補上兩次請求之間可能漏掉的事件。

SSE：伺服器以 text/event-stream 回應，適合伺服器到瀏覽器的文字事件。瀏覽器 EventSource 有重連與 Last-Event-ID 相關行為，規範見 HTML Standard 的 Server-sent events；伺服器仍需保存可補送事件並正確解讀 ID，否則自動重連只會建立一條新的空通道。客戶端送指令可另用一般 HTTP，不必為了單向進度硬選雙向協定。

WebSocket：握手後交換雙向訊息，適合互動密集的連線。RFC 6455定義 framing、控制訊息及關閉流程，但沒有替你定義持久化 inbox、業務 ACK、斷線重播或恰好一次副作用。底層連線有序，只表示該連線的傳輸順序；若重連到另一台 gateway，舊訊息是否遺失、是否重複、如何跨連線排序，仍是應用程式的工作。

Webhook 與裝置 push：Webhook 是伺服器對伺服器呼叫接收者提供的 HTTP 端點，通常要簽章、時間戳、防重播、重試及去重；裝置 push 則由平台服務替背景客戶端管理交付，涉及使用者授權、裝置 token、TTL 與節電政策。它們都叫 push，卻有不同的信任邊界和生命週期。Web Push 的基本角色與過期行為可看 RFC 8030。

背壓算例：某客戶端只能接收 10 筆／秒，伺服器產生 100 筆／秒，每筆 1 KB，若不限制，10 分鐘會積欠約 (100−10)×600×1 KB＝54 MB。10,000 個這樣的客戶端就約 540 GB。這時需要合併最新狀態、丟棄允許丟棄的資料、降低訂閱量、改用補抓或中止連線，不能只增加 gateway 記憶體。

練習：WebSocket send 回傳成功，能在資料庫標記「使用者已讀」嗎？

不能。send 成功可能只代表資料進入本機或協定緩衝。即使收到應用層「已收到」ACK，也不代表人已閱讀。至少區分事件持久化、傳輸提交、客戶端接收、畫面呈現及使用者已讀；產品需要哪個指標，就為那個語意設計明確事件。

8.10 Push and pull technologies in real-life systems：混合通常更合理

真實系統常把 push 與 pull 分配到不同邊界。Apache Kafka 的設計文件說明消費者 pull 的取捨：消費者可依自己的速度取資料，並透過批次攤提成本。生產者把事件送進 broker，是另一個邊界。把整套 Kafka 一句話歸類成「push 系統」或「pull 系統」，會把真正控制流量的地方抹掉。

監控是另一個例子：Prometheus 通常主動抓取目標的 metrics，使抓取間隔與目標是否可達都較容易掌握。短暫批次工作可能在下次抓取前就結束，特定情境可以把結果送進 Pushgateway 再由 Prometheus 抓取。官方Pushgateway 使用指引提醒它不是把所有目標改成 push 的通用替代品，過期序列與生命週期需要管理。使用哪一種方式，取決於誰能可靠存活到下一次交換。

手機通知也不是 durable inbox 的替代品。Firebase Cloud Messaging 的訊息存活時間文件說明訊息可能因 TTL、裝置狀態等條件延後或過期。因此本平台發送「你有新的處理結果」後，應用程式仍以授權 API 取得 inbox 與最新工作狀態；push payload 只放最少必要資訊，不能把唯一完成紀錄寄存在某次推播裡。

一條完整流程：worker 完成後提交狀態與 outbox；relay 將事件送到 broker；通知服務消費後寫入收件者 inbox；線上 gateway 推送事件或變更提示；離線使用者可收到平台 push；使用者開啟頁面時以 last_seen 游標拉取未同步事件。每個步驟都有自己的重試與確認點，也各有可能重複的範圍。端到端去重通常依 event_id／recipient_id；設計時必須容許各條通道重試。

租戶 webhook 的額外責任：客戶提供的回呼 URL 不應讓服務任意連到內網管理端點。建立端點時驗證所有權與允許目的地，處理 DNS 重新解析、重新導向與私有位址限制，使用短逾時及有限重試。為避免文件處理被客戶接收端拖慢，webhook 應由獨立佇列與速率限制工作者送出。端點回覆 2xx 要由契約定義為「已接收」還是「已持久化」，不能憑狀態碼猜測對方完成所有業務。

順序案例：完成事件在重試後比權限撤銷晚到，客戶端不能因它較晚抵達就回復舊權限。每份文件狀態使用版本號，接收端拒絕套用較舊版本；存取內容時仍重新驗證權限。事件時間戳只能提供線索，跨機時鐘不保證業務順序。若要求每個收件者固定順序，可將同一收件者的事件路由到穩定分區，但需評估大租戶或熱門使用者的熱點。

練習：Webhook 連續三次超時，能判定客戶一次都沒收到嗎？

不能。對方可能已持久化甚至完成處理，只是回應遺失或太慢。每次重試保持相同 event_id，接收方需去重；提供事件查詢與人工重送介面時也保留這個識別。寄送狀態應記錄「未確認」，不能自行推論成「未執行」。

8.11 Large-scale push architectures：讓斷線成為正常情況

大型推送系統應把「事件是否存在」與「使用者現在連在哪裡」分開。持久化 inbox／事件串流保存可恢復資料；gateway 保存短生命週期連線；presence registry 保存 user／device → gateway 的暫時映射。Gateway 可隨時失效，presence 也可能短暫過期，不能讓這些暫態資訊成為通知唯一的儲存位置。

把數量算出來：100 萬份／日 × 5 事件＝500 萬事件／日，平均約 57.87 事件／秒，10 倍尖峰約 578.7／秒。每事件平均 3 個收件者，就是尖峰約 1,736 次收件者投遞／秒；若每則通知含封裝平均 1 KB，純 payload 約 1.736 MB／秒。這不包含同一使用者多裝置、心跳、TLS、重播與大型廣播。對比 10 萬條連線，連線管理可能比平常事件頻寬更值得先關注。

不能只用均值設計扇出。假設某租戶一次發布結果給 10 萬個人，單個事件就帶來 10 萬個 inbox 寫入與推送。可把收件者集合切成可恢復的批次工作，用進度游標與唯一鍵重試；每租戶各自限制處理速率，避免大量廣播擠掉其他租戶的完成通知。Fanout-on-write 提前寫入每個收件者 inbox，讀取簡單但寫入昂貴；fanout-on-read 保留共享事件、讀時合併，降低廣播寫入卻增加讀取與權限判斷。大規模產品常依受眾大小混合。

連線容量：假設壓測證明一台 gateway 在目標 p99 與記憶體預算下可安全維持 20,000 條連線，10 萬條的最低算術值是 5 台，不是上線配置。若部署 8 台平均承載 12,500 條，少一台後約 14,286 條；但若一整個區域／可用區移除三台，剩五台每台 20,000，已沒有餘裕。還要考慮連線是否均勻、CPU、檔案描述符、TLS 握手與慢端緩衝。真正限制取決於壓測，不由某個固定「每台最多連線」傳說決定。

重連風暴：若 10 萬個客戶端在十秒內同時回來，是每秒一萬次連線與驗證請求，還會觸發補抓。客戶端採指數退避與 jitter，伺服器限制新握手速率並保留快速失敗策略，部署時分批排空。縮短心跳有助較快發現斷線，卻增加流量與手機喚醒；10 萬連線每 30 秒一次心跳約 3,333 次／秒，回應還要再算一趟。心跳只能證明某時間點通道可用，不能證明某則業務訊息已被處理。

避免補抓與即時串流之間的缺口：客戶端帶 last_applied_cursor 連線，伺服器先建立可銜接的事件訂閱位置，取得高水位 H，重播 (cursor, H]，再交付 H 之後的事件。也可以讓同一持久化串流直接從 cursor 接續。關鍵是有單一、明確的邊界，不能先查完資料庫、隔幾秒才開始訂閱。跨多分區的系統可能需要多個游標或向量，而不是假裝存在全域連號。

ACK 的設計也要有語意。客戶端只有在已按契約處理或持久化事件後才回報游標；批次 ACK 要表示「連續套用到哪裡」，不能跳過中間缺口。Gateway 收不到 ACK 就重送，可能造成至少一次投遞，因此客戶端按 event_id 去重、按 document_version 避免回退。多裝置的同步游標、使用者的已讀狀態、通知是否已送達手機是不同欄位，不能用一個 last_seen 混為一談。

安全與營運：連線初始驗證成功不等於永久有權訂閱。Token 過期、租戶切換、文件撤權都要重新評估；訂閱 topic 不能由客戶端任意猜到即加入。量測連線數、建立失敗率、ACK lag、inbox oldest age、每租戶積欠、重連率與丟棄的可覆寫進度。若只看 gateway CPU 平均 30%，可能完全漏掉某租戶通知已經延遲十分鐘。

練習：gateway 在送出完成事件後、記錄 ACK 前掛掉，應如何處理？

新的 gateway 根據持久化 inbox 和客戶端游標重播，客戶端可能再次收到相同 event_id，但不應再次執行不可重複副作用。若第一次只顯示畫面，去重與版本比較可處理；若涉及扣款或寄信，應由具冪等保護的後端執行，不交給瀏覽器收到通知就直接觸發。斷線可恢復靠的是應用協定，並不是 WebSocket 自帶可靠投遞。

章末設計演練：讓「完成通知」可證明、可恢復

為文件平台設計兩條使用者路徑：線上頁面希望 2 秒內看到完成；離線一天後回來必須看得到所有仍在保留期內的結果。要求單租戶爆量不得無限擠占其他租戶，gateway 重啟不遺失永久通知，通知重複不得造成重複副作用。畫出服務探索、持久化來源、連線路由與補抓的邊界，然後依次推演「資料庫提交後 relay 掛掉」「手機離線超過 push TTL」「整個 gateway 群滾動部署」。

參考答案：先保留事實，再加即時通道

把工作完成狀態與 outbox 以同一交易提交；relay 可重試發送，通知處理器按事件與收件者的唯一鍵寫入 inbox。線上先選單向 SSE 或可解釋需求的 WebSocket，使用有界佇列與按游標恢復；離線裝置的 push 只是提醒，回來時拉取持久化 inbox。若 cursor 已超出保留期，回應明確的 reset-required，重新取得狀態快照與新的同步點，不能默默當作沒有新事件。

每租戶有入口與 fanout 配額，批次任務可暫停／續跑；gateway 連線位置是可過期資訊，錯路由不會丟掉 inbox 的事件。滾動部署時先停止新連線、逐批排空，客戶端退避重連並補抓。2 秒是服務目標，要拆成 outbox lag、broker lag、fanout lag、gateway queue 與網路時間，再對每一段監測；離線裝置不應被算成可保證兩秒送達的對象。

最重要的四個句子：探索結果可能過期。通道成功不等於業務完成。任何無界佇列只是把過載延後成故障。即時提示必須能回到可查詢、可恢復的真實來源。
