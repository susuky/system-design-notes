第六章 · Queues

佇列：把容量不足變成可管理的等待

佇列把短暫超過處理能力的流量保留下來，讓工作稍後完成。本章從 FIFO 推導有界等待、背壓、工作租約與跨機器計算。

共同基準。多租戶文件處理與通知平台有 1 萬租戶、每日 100 萬份文件、平均原件 5 MB（十進位）、尖峰日均 10 倍、每份轉換平均 2 CPU-seconds。日均約 11.57 份／秒，尖峰約 115.74 份／秒，原件每日約 5 TB。各節再指定佇列大小、工作池、等待時間與利用率，用來推導容量。

6.1 佇列（Queue）

佇列的最小抽象是先進先出（first in, first out，FIFO）：enqueue 把項目放入尾端，dequeue 從前端取出。這個抽象只說明取出順序；它沒有自動提供持久性、跨機器傳輸、重試、權限或故障接管。程序內的容器與跨機器的訊息服務都可能叫 queue，卻有很不同的承諾。

在文件平台中，我們把提交者稱為生產者（producer），辨識工作者稱為消費者（consumer）。佇列讓兩者不必同時有空：生產者先留下工作意圖，消費者稍後領取。若要在程序崩潰後恢復，就需要持久工作紀錄；若要在工作者崩潰後重送，就不能在領取時把唯一紀錄永久刪除。常見做法是先租給工作者，等明確完成後才結束責任。

等待量怎麼算？在穩定、長期平均與邊界一致的條件下，平均系統內數量 L＝到達率 λ×平均停留時間 W。如果只看等待佇列，應用 Lq＝λ×Wq；如果把執行中也算進來，就使用端到端停留時間。例如假設每秒到達 12 件，平均排隊 30 秒，平均執行 2 秒，則等待中約 360 件，執行中約 24 件，總在途量約 384 件。L 與 W 都採同一段觀察期間的平均值。來源：Little，A Proof for the Queuing Formula（1961）。

FIFO 領取不等於 FIFO 完成：工作 A 需 30 秒，後領的 B 只需 1 秒，在兩名工作者下 B 會先完成。若文件 v2 不可被 v1 的遲到結果覆蓋，就要用版本檢查或按文件鍵序列處理。只說「底層是 FIFO」仍不足以保證結果正確。有多個生產者時，也要定義以何處的接受順序為準，不能把各自的本機時間當作全域順序。

常見錯誤：把入列成功等同工作成功；只看 queue depth，不看最老工作年齡；把「移出等待佇列」當成可刪除最後一份證據；以重試後的重新入列時間掩蓋工作真正等待多久。應同時保存原始建立時間與本次排程時間。

機制參照：Python queue 文件說明程序內同步佇列；RabbitMQ 可靠性指南說明跨程序交付需要額外確認。

練習：儀表板顯示佇列已清空，可以宣布全批文件完成嗎？

不可以。工作可能已被領取但仍在執行，也可能在重試計時器、死信或未知狀態。應以批次中的持久工作狀態統計，區分 succeeded、failed、cancelled 與尚未終結，並驗證預期數量，而不是只看一條佇列的深度。

6.2 滿佇列與空佇列問題（Full and empty queue problems）

有界佇列（bounded queue）同時有兩個邊界：空時不能憑空取出項目，滿時不能無限配置記憶體。環狀緩衝區（ring buffer）的 head 與 tail 相同，可能代表空，也可能代表剛好繞一圈後的滿；必須額外保存 count、使用世代位元，或刻意留一格。這是資料結構層面的狀態辨識，不是靠稍後重試就會自然正確。

把工作者加倍，排隊一定會消失嗎？

設定到達率與工作者數量，再按「前進 1 秒」。每位工作者每秒可完成 10 件；等待容量 120 件。這是離散秒教學模型：先處理本秒可完成的工作，再計算剩餘積壓與超量拒絕。

預設每秒進 50、出 30，積壓每秒增加 20 件；容量再大也只能延後滿載。

算例與假設

初始積壓 0，50 件／秒抵達、30 件／秒完成，6 秒後等待區累積 120 件。第 7 秒維持相同速率，拒絕 20 件。若此時改成 8 位工作者且到達率仍為 50，每秒可額外消化 30 件積壓，需 4 秒清空。此處每項工作成本相同，並以整秒結算；加入工作大小分布或下游限流後，可用處理率也會改變。

多執行緒時，「先檢查不滿，再放入」不是單一原子操作。兩名生產者可能同時看到最後一格，隨後都嘗試寫入。Python 文件因此提醒 qsize、empty、full 只能作近似觀察，不能保證接下來的 get 或 put 不會阻塞。來源：Queue 的容量檢查語意。正確性應靠帶鎖的條件檢查與操作，或成熟的並行佇列實作。

滿佇列不是例外角落，而是產品政策
滿時策略適用情境主要風險
阻塞／等待至期限上游允許承受背壓（backpressure）占用呼叫者資源；不能無限等到請求全逾時
明確拒絕並建議稍後重試無法保證完成期限的新文件工作客戶端需退避、抖動與相同冪等鍵
降級或合併可用最新進度覆蓋舊進度通知不可擅自丟棄必須逐項處理的業務事件
轉存持久佇列有獨立容量與明確責任轉移只是把上限搬到磁碟，仍需配額、延遲及滿載政策

算例。假設有 10,000 格，起始為空，尖峰到達率 115.74 件／秒，服務率固定為 80 件／秒。忽略隨機波動，淨累積率為 35.74 件／秒，約 10,000÷35.74＝279.8 秒後填滿，僅約 4.66 分鐘。容量加倍只把時間加倍，沒有修復尖峰期間的服務不足。若每格描述符為 2 KiB，原始描述符占約 19.53 MiB；若誤把 5 MB 文件本體放進 10,000 格，單份資料總量已達 50 GB。

空佇列時，消費者應等待通知、長輪詢或依節奏退避，不要以 while empty 的忙等迴圈燒 CPU。滿佇列時，要在更靠近入口處限制新工作，不要等所有 HTTP 執行緒都堵在 put。多租戶還需每租戶配額或公平排程，否則一個租戶可占滿全部格子，讓其他租戶即使流量很低也無法提交。

常見錯誤：把無界當作沒有上限；佇列越長越安全；拒絕後讓客戶端立即重試；只設項目數上限而不限制單項大小。佇列還應受等待期限約束：即使仍有空間，如果新工作預估等待已超過承諾，也該拒絕、延後或明確降級。

練習：到達率持續每秒 120 件，處理率只有 100 件。把容量從一萬加到十萬，能達成長期穩定嗎？

不能。淨累積每秒 20 件，從空到滿分別約 500 秒與 5,000 秒。要長期穩定，必須降低接納率、增加有效服務率、減少每件工作，或改變可接受工作集合。容量只吸收有限時間的差額。

6.3 從簡單方案開始（Start with something simple）

簡單方案也要處理故障。目標是用最少的部件滿足目前契約。若只是可丟棄的本機預覽，一個有界記憶體佇列與固定工作池可能足夠；若平台已承諾接受的文件工作能在重啟後找回，就至少需要持久工作紀錄。初期可先用既有關聯式資料庫的 jobs 表，不必立即新增一整套訊息叢集。

工作表至少保存 tenant_id、job_id、document_version、state、available_at、attempts、lease_until、lease_token、created_at。提交 API 在同一交易中保存業務工作與可供領取的狀態。工作者用短交易領取，再在交易之外做昂貴辨識，避免長時間持有資料庫鎖。PostgreSQL 的 SKIP LOCKED 可略過其他工作者鎖定的資料列，官方明確指出它可用於 queue-like table，但會產生不完整視圖，不是一般一致性查詢的萬用選項。來源：PostgreSQL SELECT 鎖定條款。

BEGIN;
SELECT tenant_id, job_id
FROM jobs
WHERE (state = 'queued' AND available_at <= now())
   OR (state = 'running' AND lease_until < now())
ORDER BY created_at, job_id
FOR UPDATE SKIP LOCKED
LIMIT 1;

-- 若有結果，在同一短交易更新該筆；期限為本案例假設
UPDATE jobs
SET state = 'running', lease_until = now() + interval '60 seconds',
    lease_token = lease_token + 1, attempts = attempts + 1
WHERE tenant_id = :selected_tenant_id AND job_id = :selected_job_id
RETURNING lease_token;
COMMIT;
-- 交易外執行；完成提交時原子檢查 tenant_id + job_id + lease_token

工作以（tenant_id, job_id）為唯一鍵，lease_token 與 attempts 從 0 起算。提交領取交易後，資料列鎖便釋放，後續擁有權由租約與 token 維持。queued 與 running 工作分別需要適合 available_at、lease_until 篩選的索引；輪詢與重試再按租戶限制。租約依工作時間設定，長工作定期續租；達重試上限要轉成可觀察的終止／人工處理狀態。完成時以 tenant_id、job_id、lease_token 及 state = running 作原子條件更新，並在同一交易寫入結果與後續 outbox；若影響列數為零，代表擁有權已變更，舊工作者不能提交。如果先寫外部物件，應使用版本化暫存結果，未被引用者再由清理機制回收。

故障時間線。工作者 A 取得 token 7，暫停超過租約；B 接管取得 token 8。稍後 A 恢復，即使它手上結果正確，也不能用舊 token 覆蓋 B。對「是否允許舊持有人完成」可以設不同契約，但必須用原子條件提交實作；單純在記憶體裡檢查一次到期時間不夠。

本平台起初可使用四名工作者，每名完整占一核心、平均每份 2 CPU-seconds，理想能力只有每秒 2 份，明顯低於日均 11.57 份，故這個小配置只能用於開發或小流量試點。簡單方案是否夠用，要用負載來判斷；光看元件名字無法決定。若資料庫領取延遲、輪詢成本、積壓、保留量或跨服務扇出超過預算，再加入專用代理；沿用既有 job_id、冪等與狀態介面可降低遷移風險。

常見錯誤：在整段 OCR 期間持有資料列鎖；領取後立即刪除工作；以 SKIP LOCKED 宣稱嚴格全域 FIFO；只新增代理卻保留 API 雙寫漏洞。代理不會自動讓資料庫更新與訊息發布成為同一交易。

練習：60 秒租約的工作實際跑 90 秒，是不是把租約改成兩分鐘就完全修好？

沒有。期限應依工作分布與故障恢復目標設定，可能需要續租；兩分鐘仍可能被更慢工作超過。無論期限多長，都要防止過期工作者與接管者同時提交，並讓副作用可冪等。太長的租約也會延後崩潰後的恢復。

6.4 阻塞佇列與生產者—消費者模式（Blocking queue and producer-consumer pattern）

現在把視角縮回單一程序。解析上傳、讀取物件與文字辨識可能是不同階段；前一階段產生工作，後一階段消費。阻塞佇列在空時讓 get 等待，在滿時讓 put 等待，使兩端不必自己寫忙等。它提供的是執行緒間的協調，並不自動具備程序崩潰後的保存能力。

核心是互斥鎖（mutex）加條件變數（condition variable）。等待時要原子地釋放鎖並睡眠，醒來再取得鎖；條件判斷使用 while，不使用 if，因為被叫醒時條件可能已被另一個執行緒改變，也可能有虛假喚醒。不要在持有佇列鎖時執行辨識，否則其他執行緒連放取工作都會被阻擋。機制參照：Java Condition 的等待與虛假喚醒契約。

put(item):
    with lock:
        while count == capacity and not closed:
            not_full.wait(lock)
        if closed: raise QueueClosed
        append(item)
        count += 1
        not_empty.notify_one()

get():
    with lock:
        while count == 0 and not closed:
            not_empty.wait(lock)
        if count == 0 and closed: return END
        item = remove_front()
        count -= 1
        not_full.notify_one()
        return item

close():
    with lock:
        closed = true
        not_full.notify_all()
        not_empty.notify_all()

這個版本定義為關閉後不再接受新項目，但允許消費者排空既有項目，最後返回 END。若需求是立即中止，必須另外定義未做工作如何保存、重送或標記取消。使用哨兵項目（sentinel）也可實作結束，但多名消費者需要明確傳播規則，且佇列已滿時生產者不能卡住到無法送入哨兵。

容量算例。假設載入後每份文件占 8 MiB，程序可給這條流水線 256 MiB，四名消費者各持有一份。如果佇列存完整載入內容，忽略所有其他記憶體後，最多也只有 256÷8−4＝28 格。這只是理想上限，解析暫存與複本會使可用值更小。若改為排 2 KiB 描述符，可以大幅減少等待區記憶體，但消費者真正載入後的 32 MiB 仍然存在。

Python 的 task_done／join 可追蹤已取出的項目是否完成了本機的工作記帳，但不應把它們當成跨服務成功保證。來源：Queue 工作追蹤。消費者需在 finally 做平衡記帳，另把失敗送到明確的重試或錯誤通道；否則 join 可能永久等待，或雖然返回卻有工作失敗未被呈現。

常見錯誤：滿時一邊持有別的資源鎖一邊等待，形成鎖順序死結；每處理一項就新建一條執行緒；失敗後把工作無限送回同一個已滿佇列。消費者自己回填滿佇列、而所有消費者都同樣阻塞時，沒有任何人能再取出項目。

練習：為什麼條件變數 wait 返回後還要重新檢查佇列是否為空？

通知只表示某個時間點可能有進展，不會保留一件項目給特定醒來者。另一個消費者可能先拿走了工作；某些實作也允許虛假喚醒。while 重新檢查保護不變量；if 則可能從空佇列取出，造成錯誤或破壞狀態。

6.5 執行緒池（Thread pool）

阻塞佇列解決交接，執行緒池則決定同時有多少工作真正執行。固定池重用工作者，避免每項任務都付出建立與銷毀成本，也提供並行上限。真正需要配置的至少有三個數字：活動工作者數、待執行佇列容量，以及拒絕／等待期限；只調執行緒數而保留無界佇列，常把超載偽裝成越來越長的延遲。

CPU 與等待分開算。假設一台機器有八個可用核心，一份工作需 2 CPU-seconds，全部資源都給獨立轉換時的理想上限是 8÷2＝4 份／秒。此處假設執行環境可同時利用八核心；若語言執行器限制 CPU 平行，還需選擇多程序等適合的方法。開 80 條 CPU 密集執行緒不會變成每秒 40 份，反而可能增加排程與快取成本。若工作平均占 CPU 10 ms、等待外部 I/O 90 ms，則在理想條件下，單個核心要維持忙碌可能需約十項在途工作；但這只是初始模型，仍受連線數、下游配額與記憶體限制。

等待多不表示可以無限並行。若資料庫只有 20 條允許使用的連線，建立 200 個同時需要資料庫的工作者，可能只把另外 180 個工作移到連線池等待。平台可把 CPU 辨識池、物件下載池和通知 I/O 池分開，讓某個外部供應商的慢回應不會占滿全部工作者。這種隔離有成本：各池保留容量可能不均衡，因此仍需觀察並調整。

拒絕策略必須符合呼叫執行緒的角色
策略可能好處平台風險
明確拒絕快速暴露超載，保護既有工作要回報可辨識原因，並避免客戶端重試風暴
呼叫者執行（caller-runs）讓提交者自行做工作，形成背壓若提交者是事件迴圈，會卡住其他連線；關閉語意也須檢查
有限等待吸收很短的尖峰需期限及取消傳播；不要占著資料庫交易等待
丟棄適合明確可損失的遙測或可覆蓋進度不能用於已承諾完成的文件工作

Java ThreadPoolExecutor 的具體規則說明了為何設定名稱不能代替理解：無界工作佇列可能使 maximumPoolSize 在一般擴張路徑中沒有作用，因為超出 corePoolSize 的工作先持續排隊；CallerRunsPolicy 則由呼叫 execute 的執行緒執行被拒絕工作，executor 關閉時有另外的丟棄行為。這些是該 API 的契約，不應套到所有框架。來源：Java 21 ThreadPoolExecutor。

故障案例。四條工作執行緒各執行一個父任務，父任務都提交子任務到同一個四執行緒池，然後同步等待子任務結果。四條執行緒全被父任務占住，子任務沒有執行機會。增加佇列容量毫無幫助；應避免在同一受限池中同步等待其子任務，改用非阻塞組合、分離池或有明確保證的工作協作機制。機制參照：Python ThreadPoolExecutor 的 Future 等待死結警告。

常見錯誤：把執行緒數當吞吐量；忽略工作分布，混放毫秒任務和數分鐘任務；逾時只停止等待卻不限制仍在執行的背景工作；關閉程序時直接遺失池內排隊項目。持久工作責任應在本機池之外保留。

練習：八核心、每件 2 CPU-seconds，每秒持續到達六件。四十條執行緒能避免積壓嗎？

在題目假設的純 CPU 工作下不能。理想服務能力每秒四件，每秒至少累積兩件。必須提高有效 CPU 容量、減少每件 CPU 成本或限制接納率。執行緒池大小只能管理競爭，不能創造核心。

6.6 大型計算架構（Big compute architecture）

當一台機器無法在期限內處理文件量，我們才把工作池擴展成跨機器計算。核心抽象仍未改變：有工作描述、有可用資源、有誰擁有執行權、有結果提交點。控制平面（control plane）管理任務與排程，資料平面（data plane）搬文件與中間結果；把兩者分開可避免大型文件把排程通道擠滿。

本平台把一項工作表示成有向無環圖（directed acyclic graph，DAG）：檢查原件 → 按頁辨識 → 彙整 → 建立索引／通知。只有在前置結果可用後才排下一階段。小文件可整份處理，超大文件可按頁或固定範圍分片；過細會增加排程與儲存操作成本，過粗則使少數慢分片控制全批完成時間。原始 MapReduce 論文展示了拆分工作、資料接近運算與慢任務備份等設計思路；本例以這些機制安排分片、資料讀取與慢任務接手。來源：Dean 與 Ghemawat，MapReduce 原始論文。

先把共同基準換成資源。每天 100 萬份×2 CPU-seconds＝200 萬 CPU-seconds。除以 86,400 秒，日均約需 23.15 個完全忙碌的核心；尖峰約需 231.48 個。若規劃以 70% 作為平均可用 CPU 預算，尖峰需要 231.48÷0.7≈330.69，至少約 331 核心的計算預算。這 331 核先滿足轉換的 CPU 預算；容錯餘裕、記憶體、I/O 與排程容量另計。

尖峰原件輸入約為 115.74×5＝578.7 MB/s，尚未計重讀、分片、中間輸出與複本。就算 CPU 足夠，跨區讀取或物件服務限制仍可能成為瓶頸。每份文件的服務時間也不只由 CPU 決定：兩個 CPU-seconds 可以是單核跑兩秒，也可能在可並行部分用多核縮短，但不能假設任意工作都能線性拆分。

局部批次算例。假設 1,000 份文件，每份恰好需要 2 CPU-seconds，100 核心的理想純計算下界為 2,000÷100＝20 秒。若另作一個簡化模型，假設全程只有 70% 核心有效處理，則為約 28.57 秒，仍未加上不可重疊的輸入、彙整與啟動。要估 p99 完成時間，還需各分片耗時分布與它們共同受阻的情況。

故障恢復採用可重試分片、檢查點（checkpoint）與條件提交：每個輸出以租戶、文件版本、演算法版本及分片編號命名，完成清單只接受有效擁有者的一份結果。備援執行（speculative execution）可對異常慢分片啟動另一份嘗試，但會增加成本，且要求多次計算不會產生多次不可撤回副作用。寄信應放在最終提交後的獨立階段，不要讓每個備援分片各寄一次。

擴縮容不能只看 CPU。最老工作等待時間反映承諾是否受威脅；待處理估計工作量比單純項目數更能反映大文件；租戶公平性防止大戶占滿資源。擴容還有啟動延遲，縮容則須排空、轉移或讓租約安全到期。若熱門租戶送入一百萬頁，將「每份文件一個公平份額」視為公平，也可能讓其他租戶遭受長時間延遲。

常見錯誤：先採用大型框架再尋找需求；只加工作者卻沒增加物件吞吐；把重複分片完成訊息當成不同分片；讓彙整器在記憶體保留唯一進度；以機制推論固定倍數加速。架構評估應有可重現負載、工作大小分布、成本與故障測試。

練習：一份文件預期十個分片，彙整器收到十次「完成」，能開始發布結果嗎？

不能只數訊息。它們可能包含同一分片的重複投遞，或舊文件版本的遲到結果。應以預期集合為準，確認十個不同分片的有效結果都存在，版本及演算法相符，且彙整提交是原子的。最後的通知意圖再由 outbox 可靠建立。

整體串接。通訊契約告訴使用者何時接受、何時完成；去重與版本化讓重試可控；有界佇列與工作池讓超載可見；大型計算再把同一套責任延伸到多台機器。可恢復、可觀察、能拒絕超載的簡單系統，比沒有邊界的大型系統更接近可靠。
