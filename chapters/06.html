第 06 章

工作排起隊之後

佇列把立即的請求壓力改成待處理工作。你需要同時知道進來多少、做完多少、等了多久，才能決定接下來要加人、暫停還是拒絕。

尖峰結束，為什麼還要排六分鐘

每秒進來 70 份工作，worker 每秒完成 40 份，積壓每秒增加 30 份。這樣持續兩分鐘就累積 3600 份。之後流量降到每秒 30 份，淨消化速度剩每秒 10 份，再花六分鐘才追平。

因此佇列除了長度，也要看最老工作年齡與到期量。100 份一秒的小工作和100份十分鐘的大工作，代表不同的等待時間。依工作成本、租戶或優先權分隊列，能讓短工作和急件有自己的完成機會。

FIFO 描述取出順序；若多個 worker 並行、工作耗時不同，完成順序可以改變。需要同一文件有序更新時，以文件 key 分區，或在寫入端檢查版本。

調整每拍流量與背壓

積壓1200份，每秒來80份、完成100份，多久清完？

看推導

淨消化率100−80＝20份／秒，1200÷20＝60秒。

佇列滿了，新工作放哪裡

滿佇列代表新工作要有明確去處。可立即拒絕並讓客戶稍後再試，也可透過背壓讓來源暫停送入；後者的待送工作仍占來源的資源，所以來源也要有容量與期限。把工作接受後丟進永遠等待的列表，會讓使用者一直停在未完成。

空佇列時，consumer 可阻塞等待通知，或使用有適當間隔的拉取。檢查 qsize 後再取出會遇到競爭，因為另一個 consumer 可能先取走；直接使用具原子語意的取出操作與 timeout，讓結果決定後續動作。

工作已到期時，先檢查是否仍有業務價值。超時的即時查詢可以取消，已受理的文件批次可轉入逾時狀態並提供重送入口。

把工作者加倍，排隊一定會消失嗎？

設定到達率與工作者數量，再按「前進 1 秒」。每位工作者每秒可完成 10 件；等待容量 120 件。這是離散秒教學模型：先處理本秒可完成的工作，再計算剩餘積壓與超量拒絕。

算例與假設

初始積壓 0，50 件／秒抵達、30 件／秒完成，6 秒後等待區累積 120 件。第 7 秒維持相同速率，拒絕 20 件。若此時改成 8 位工作者且到達率仍為 50，每秒可額外消化 30 件積壓，需 4 秒清空。此處每項工作成本相同，並以整秒結算；加入工作大小分布或下游限流後，可用處理率也會改變。

背壓讓來源暫停，積壓真的消失了嗎？

看推導

工作改留在來源。檢查來源待送量、持有連線和記憶體，就能知道壓力移到哪裡，並設定它的容量政策。

用jobs表開始派工

工作量小、已經使用關聯式資料庫時，可以把 jobs 表作為待處理工作清單。欄位至少含狀態、建立時間、下一次可執行時間、嘗試次數與租約到期時間。worker 在短交易內鎖定並領取一批工作，離開交易後才做慢的 OCR。

多個 worker 可使用符合資料庫語意的 SKIP LOCKED 分攤候選列；狀態更新仍在交易內完成。完成時檢查租約版本，避免已失去資格的舊 worker 覆蓋新結果。索引集中在待領取條件，已完成資料依保留政策移出熱路徑。

當掃描、鎖競爭、保留量或多種消費者需求成為瓶頸，再選專用 broker 或可重播日誌。這時已有實際吞吐、延遲和恢復需求，可以直接比較方案。

先領工作，提交結果時再檢查租約版本

BEGIN;
SELECT tenant_id, job_id
FROM jobs
WHERE (state = 'queued' AND available_at <= now())
   OR (state = 'running' AND lease_until < now())
ORDER BY created_at, job_id
FOR UPDATE SKIP LOCKED
LIMIT 1;

-- 有選到工作時，在同一交易中更新它：
UPDATE jobs
SET state = 'running',
    lease_until = now() + interval '60 seconds',
    lease_token = lease_token + 1,
    attempts = attempts + 1
WHERE tenant_id = :selected_tenant_id AND job_id = :selected_job_id
RETURNING lease_token;
COMMIT;

沒有選到工作就結束這次領取。取得租約的 worker 在交易外執行 OCR，再用下面的條件提交；零列表示這份責任已被交給別人。結果紀錄與狀態更新放在同一筆交易。

UPDATE jobs
SET state = 'succeeded', result_ref = :result_ref
WHERE tenant_id = :tenant
  AND job_id = :job
  AND state = 'running'
  AND lease_token = :my_lease_token
RETURNING job_id;

為什麼領工作時不把資料庫交易一直開到OCR結束？

看推導

OCR可能花數十秒，長交易會持有鎖和連線，放大資料庫負擔。先用短交易取得有期限的工作資格，慢工作在交易外完成，再用短交易提交結果。

被喚醒後，為什麼再看一次佇列

有界阻塞佇列讓 producer 在滿載時等待，consumer 在空隊列時等待。共享狀態由鎖保護；等待條件時釋放鎖，被喚醒後重新取得鎖並再次檢查條件。這個迴圈處理多個等待者競爭與假喚醒。

將「隊列目前是否可取」的判斷與取出操作放在同一同步範圍。停止服務時也要定義喚醒方式：關閉旗標、停止訊息或取消訊號，讓等待者可離開，而非永久等在空隊列。

背壓要一路走回能控制輸入的地方。HTTP層持有全部連線等待記憶體隊列空位，可能先耗盡連線；有時間預算的取得、清楚的拒絕與客戶重試間隔，能保持服務可回應。

醒來後，再看一次條件

put(item):
    with lock:
        while count == capacity and not closed:
            not_full.wait(lock)
        if closed:
            raise QueueClosed
        append(item)
        count += 1
        not_empty.notify_one()

get():
    with lock:
        while count == 0 and not closed:
            not_empty.wait(lock)
        if count == 0 and closed:
            return END
        item = remove_front()
        count -= 1
        not_full.notify_one()
        return item

close():
    with lock:
        closed = true
        not_full.notify_all()
        not_empty.notify_all()

wait 釋放鎖並等待，返回前重新取得鎖。通知發出後，其他消費者可能先拿走項目，所以用 while 再檢查目前條件。這個關閉規則會拒絕新 put，讓 get 把既有工作取完，最後回傳 END。

條件變數被喚醒後，為什麼要用while重新檢查隊列？

看推導

另一個consumer可能在你重新拿到鎖前取走工作，也可能發生假喚醒。重新確認條件後才取出，才能保住共享狀態。

八條執行緒，多少工作可以等待

執行緒池限制同時執行的工作數，也需要限制等待工作數。八條執行緒配無上限待辦清單，仍會在流量過大時累積記憶體與等待時間。選並行數時，把 CPU工作、I/O等待、資料庫連線和外部配額分開量測。

若每個工作花20ms CPU加80ms等待，在假設等待可重疊、CPU沒有其他負載的簡化模型下，一顆核心約可支撐五個同類在途工作。實際配置用吞吐和尾延遲校正；當資料庫只給20條連線，100條工作執行緒也可能只是多80個等待者。

不要讓持有池內執行緒的任務等待同一個已滿工作池中的子任務。把相依工作串成完成回呼，或調整執行模型，讓完成所需資源有機會被取得。

策略容量效果執行方式
拒絕立即釋放呼叫端回覆可判讀的忙碌狀態，沿用原工作識別重試

池內只有兩條執行緒，兩個父任務都等待同池新排入的子任務，會發生什麼？

看推導

兩條執行緒都被父任務占住，子任務無法開始，形成等待循環。改成非阻塞組合或重新安排工作依賴。

最後一份慢工作拖住所有人

大量文件可切成獨立工作，先做 map：每份文件擷取文字和特徵；再做 reduce：依租戶彙總結果。切分大小要在排程成本與重做成本間取捨，太小會花很多時間派工，太大則容易被單一慢任務拖住尾巴。

把原件留在物件儲存，訊息傳位置與版本，worker就近讀取。中間產物用工作ID和分片ID定位，完成狀態單獨提交；重跑同一分片可重用已成功的階段，減少重算。

慢尾工作可採推測執行，在資源允許且輸出可安全去重時，讓另一台重做仍未完成的分片，接收先完成的合法結果。資料偏斜則要重新切分熱鍵或較大的檔案，讓工作量更平均。

總任務剩一份大文件，增加一百台worker為何幫助有限？

看推導

目前只剩一份可派發工作。若文件格式允許，可依頁面或區塊切分後合併；若需完整順序處理，就改善這個單一工作或用可安全重複的推測執行。
