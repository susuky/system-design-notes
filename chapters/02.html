第 02 章 · How to define system requirements

定義系統需求：把形容詞變成可驗證的承諾

需求要指明對象、工作負載、時間窗口、成功條件與測量邊界。把「高可用、可擴充、低延遲」轉成規格後，才能比較方案並設計驗收。

2.1 系統需求（System requirements）

系統需求回答兩組問題：系統必須做什麼，以及在什麼條件下要做到什麼程度。前者是功能需求（functional requirements），例如提交文件與查詢任務；後者常稱品質屬性或非功能需求（quality attributes / non-functional requirements），例如在尖峰負載下維持接收成功率。後者不是「功能做完以後才補」，因為它往往直接改變功能的呈現方式。

例如，產品希望「文件處理後立刻收到通知」。如果允許通知暫時延遲，就能讓轉檔與通知各自重試；若規定通知供應商完成投遞才算文件完成，外部供應商故障就會直接降低整體可用性。需求的措辭已經決定元件之間的耦合程度。設計者應把這件事拿回來討論，而非在畫完架構後才發現所有元件都被要求同步成功。

有效規格需要四個相連的層次：業務結果、使用者旅程、可測量指標、實作機制。例如業務結果是客戶能準時取得報表；旅程是上傳到下載結果；指標是特定工作類型的完成時間；機制才是工作池、佇列與擴縮。不能反過來用「一定要 Kubernetes」冒充使用者需求，除非它確實是既有平台、合約或團隊能力等約束。

文件平台規格項目示例它的性質
使用者結果租戶只能存取自己的原件與結果必須維持的安全不變條件
負載模型每日一百萬份，平均 5 MB，尖峰十倍目前教學假設，須由流量資料修正
服務目標30 日內有效提交請求成功率至少 99.9%待實作、量測與營運支持的 SLO
限制原件保存 30 日，過期後依政策刪除會影響儲存、備份與刪除流程的產品規格
排除範圍第一版不支援多人即時共同編輯防止無限擴張的邊界

常見誤區：把所有需求都列為最高優先。當成本、延遲和可靠度衝突時，這份規格無法協助選擇。應區分不可違反的安全條件、主要服務目標與可降級的附加功能，再定義每項的驗收方式。

練習：「支援所有檔案，永不遺失，任何時候一秒內完成，而且成本最低」有哪些欠缺？請把其中一項改寫為可設計的需求。

參考解答與推理

欠缺格式與大小限制、故障模型、完成的定義、流量範圍、保存期限與成本上限。可以改成：「對不超過 10 MB 的指定 PDF 類型，在每秒 100 份的測試負載下，99% 的已接收任務於 60 秒內產生可下載結果；原件保留 30 日。」再另外定義資料遺失與區域災難的目標。有限範圍使測試成為可能，也暴露應拆開討論的承諾。

2.2 功能需求（Functional requirements）

功能需求應描述外部可觀察行為，並包含失敗與重複操作。對文件平台，最基本流程是建立上傳、確認原件可用、建立處理任務、查看狀態、下載結果，以及管理通知目的地。先把主體定義清楚：tenant 是權限與配額邊界；document 是原件與版本；job 是對某個文件版本執行一組處理選項；notification 是某次結果事件向某個目的地的投遞工作。

這個拆分避免常見混淆：同一文件可以有兩個不同的轉換工作；一個完成的工作可以產生多次通知嘗試；通知重試不應再轉檔一次。對每個實體寫出狀態機，比只有 CRUD 清單更有用。狀態轉移應說明觸發者、前置條件與不能回退的終態。

文件：UPLOADING → READY → DELETED
任務：QUEUED → RUNNING → SUCCEEDED
                     ↘ RETRY_WAIT → QUEUED
                     ↘ FAILED
通知：PENDING → SENDING → ACCEPTED_BY_PROVIDER
                    ↘ RETRY_WAIT → PENDING
                    ↘ DEAD_LETTER

上圖是簡化模型。供應商「接收」通知，不等於人類已讀，也不一定等於郵件最終送達；若要展示 delivered 或 bounced，還需要相應回報與狀態。任務重試也不能無限回圈：必須定義可重試錯誤、次數或總期限，以及永久失敗後的可見結果。若允許取消，還要處理「取消與完成同時發生」的競爭，不能只在資料表增加 CANCELLED 字串。

提交介面可接受租戶範圍內的冪等鍵（idempotency key）。同一個鍵與相同參數的重送應取得同一邏輯任務；同一個鍵搭配不同參數則拒絕，避免悄悄重用錯誤工作。鍵需要保存期限與範圍，不能只靠「檔案內容相同」推斷使用者意圖，因為使用者可能真的想用不同選項處理同一份文件。這是應用程式契約，不是 HTTP 方法名稱自動提供的功能。

HTTP 202 表示請求已接受處理，但處理尚未完成，本身不保證日後一定成功。若平台要承諾「回覆接收後可追蹤」，應先讓原件與任務紀錄達到約定的持久化條件，再回傳任務 ID 與查詢位置。跨物件儲存與資料庫未必有共同交易，需用可恢復的流程處理「文件已上傳但未建立任務」等中間狀態。RFC 9110 的 202 語意刻意保留這個非同步邊界。

常見誤區：把「支援上傳」寫完就算需求完成。逾時重送、部分上傳、檔案格式錯誤、租戶越權與配額超限，都會影響 API 的實際契約。

練習：客戶提交任務後連線中斷，不知道伺服器是否已建立任務。直接再送一次，會有什麼風險？你會如何設計回覆與去重範圍？

參考解答與推理

原請求可能已成功，重送會多建任務並重複計費。讓客戶在首次提交前產生冪等鍵，伺服器對 tenant_id 與 key 加唯一約束，並記錄參數摘要與邏輯結果；並發重送也必須原子地取得同一任務。若參數不同，回覆衝突。這只解決任務建立的重複，worker 和通知的外部副作用仍需各自處理。

2.3 高可用性（High availability）

可用性首先是一種使用者結果的比例，並非「機器有開機」。服務水準指標 SLI（service level indicator）是量測值；SLO（service level objective）是對該值的目標；SLA（service level agreement）是對外約定，可能包含適用範圍、計算方式與未達標的補償。三者不能互換。供應商的 SLA 也不會自動變成你的端到端保證。

事件型可用性可以定義為「良好事件數 ÷ 有效事件總數」。文件提交 SLI 的有效事件，可包含已通過身份、格式和已約定配額規則的提交嘗試；良好事件則要求在截止時間內正確接收並回覆任務 ID。分母必須事先定義且穩定：若請求因平台過載而被拒絕，不能臨時把它移出分母來美化可用性。也不要一律排除所有 4xx，因為錯誤的限流或權限設定可能正是平台故障。

假設窗口：固定 30 日；有效請求：10,000,000 次
SLO：99.9% 良好請求
允許不良事件 = 10,000,000 × (1 − 0.999) = 10,000 次
若已失敗 2,500 次：已使用錯誤預算的 25%

時間型可用性則以觀測期間的可用時間為分子。只有當你採取這種定義，且清楚說明何時算整體不可用，才能將「幾個九」換算為停機時間。30 日共有 43,200 分鐘；99.9%、99.95%、99.99% 分別對應 43.2、21.6、4.32 分鐘的不可用預算。這不是事件型 SLO 的通用換算：同樣五分鐘，尖峰全站故障與深夜少量請求故障，消耗的請求預算可能差很多。

觀測位置同樣重要。應用伺服器日誌只記錄成功到達它的請求，可能漏掉入口、名稱解析或網路問題；合成探測可以發現部分黑箱故障，但未必代表所有租戶。實務上可結合入口指標、使用者端觀測和典型旅程探測，並按租戶級別、區域或工作類型切分。全體 99.9% 仍可能掩蓋某個小租戶持續失敗。

增加副本有幫助，但收益依賴故障是否相關。若兩個元件皆需成功，且故障獨立，各為 99.9%，組合約為 99.8001%；若兩份副本任一可服務，且真的獨立、切換可靠，理想化結果為 1 − 0.001² = 99.9999%。同一機櫃電源、同一份錯誤設定與同一個資料庫，都會破壞獨立假設。這些算式用於分析依賴關係；對外 SLA 需另外納入故障相關性與切換行為。

常見誤區：「三台 API 主機」就叫高可用。如果三台都依賴同一個不可恢復的資料庫，或者故障後其餘兩台沒有足夠容量，使用者仍會一起受影響。Google SRE 的 SLO 實作章可用來核對指標分母與錯誤預算方法。

練習：某月一千萬個有效請求，其中四千次逾時、兩千次平台過載拒絕、另外五千次輸入格式無效。若格式無效事先排除，另外兩類算不良，99.9% 目標是否達成？

參考解答與推理

題目的一千萬已是有效請求分母，因此不再扣一次那五千次格式無效。不良數為 6,000，SLI = 1 − 6,000 / 10,000,000 = 99.94%，高於 99.9%，使用了 60% 的錯誤預算。若「一千萬」原本包含格式無效，答案會略有不同，這正是規格必須寫清楚分母的原因。

2.4 容錯、韌性與可靠性（Fault tolerance, resilience, reliability）

這三個詞常被混用，本書採取實務上的區分。可靠性（reliability）關心系統在指定條件與期間內，持續提供正確結果的能力；容錯（fault tolerance）描述在明列的故障模型下仍維持服務的機制；韌性（resilience）強調遇到意外擾動時能限制影響、適度降級與恢復。單次請求成功率很高，不代表長時間工作不會中途遺失；也不代表每次錯誤都能自動復原。

先列故障模型，再談容錯。單一 worker 程序終止、伺服器斷電、可用區中斷、資料毀損、人為誤刪、依賴回應過慢，是不同的問題。兩台 worker 可處理程序終止，卻不能修復兩台都會觸發的解析器漏洞。資料複寫能減少單機故障影響，卻可能立即把誤刪複寫到所有節點。故障域、版本隔離、備份與操作流程因而缺一不可。

對文件工作，最危險的時刻往往在「做完事」與「記下已做完」之間。worker 寫入轉換結果後、更新 job 狀態前當機，重新執行可能再次產生結果。若結果以 job_id 和版本作為穩定識別，重做可先驗證已存在的有效結果，再安全地完成狀態轉移。若外部副作用是寄信，平台未必能撤銷，也未必能知道供應商是否已接收，應結合供應商冪等能力或接受、揭露可重複投遞的邊界。

恢復機制也有代價。無限制重試在依賴變慢時會放大負載；只靠很短逾時會把仍在執行的工作重送多次；過度敏感的健康檢查可能同時移除健康但忙碌的節點。可用的做法包括總截止時間、有限重試、退避與隨機抖動、獨立工作池及可觀測的死信處理，但每項都要由故障場景驗證。AWS 的逾時與重試說明特別強調重試會額外增加負載。

降級必須守住安全條件。通知供應商失效時，可以讓文件結果先完成、通知稍後補送；搜尋索引更新落後時，可以顯示「結果更新中」。但授權服務不明時，不能為了可用性直接允許下載其他租戶文件。把功能分級後，才知道哪些操作可排隊、哪些可讀舊資料、哪些必須安全拒絕。

常見誤區：認為「自動重啟」等於容錯。重啟只能恢復程序，不能自動恢復丟在記憶體的任務、消除重複副作用，或修復壞資料。

練習：通知供應商停機一小時。文件仍可轉換，但目前所有 worker 都同步等待寄信，最後耗盡執行緒。如何讓同一故障不再拖垮轉檔？

參考解答與推理

將「結果已完成」與「通知待投遞」持久地記錄，通知由獨立且有上限的工作池處理。對供應商設逾時、退避、總重試期限和限速；監測通知積壓年齡。恢復後需有受控清空速度，避免再次打垮供應商。這個方案保持文件服務可用，但通知延遲仍應計入通知自己的服務目標，不能假裝故障不存在。

2.5 可擴充性（Scalability）

可擴充性要看負載增加時，能否用可接受的成本維持目標。光是「能放很多機器」還不夠。負載有多個維度：每秒請求、活躍租戶、文件大小、保存資料量、同時工作數與熱點集中程度。只有每日文件數的規格不足以決定容量，因為每日一百萬份在全天均勻到達，與在十分鐘內全部到達，所需系統完全不同。

垂直擴充（scale up）提高單機資源，通常改動較少，但有規格上限與較大的單點影響；水平擴充（scale out）增加節點，要求工作能分配，狀態能協調，且下游不被新的並行度壓垮。增加無狀態 API 副本相對直接；增加同時修改相同租戶配額計數器的節點，則可能只增加鎖競爭。

教學假設：每日 1,000,000 份，每份平均 2 CPU-seconds
總計算需求 = 2,000,000 CPU-seconds／日
全天平均忙碌核心數 ≈ 2,000,000 ÷ 86,400 = 23.15
尖峰十倍時：≈ 231.48 個忙碌核心
若以 60% 目標利用率估算：231.48 ÷ 0.60 ≈ 385.80
因此先估約 386 個等效核心，再用實際工作負載驗證

這個估算採相同核心效能與足夠可平行的工作，並把 CPU 視為容量瓶頸。2 CPU-seconds 是一份工作累計消耗的 CPU 時間；等待磁碟或網路會拉長完成時間，多核心平行則可能縮短它。CPU 成本用來算算力，包含等待的停留時間用來算在途工作與記憶體。應按格式與大小量測兩種分布，並核對機型的 vCPU 定義；容錯預留容量另見第 3.1 節。

多租戶系統特別需要公平性。假設一個租戶在十秒內送入十萬份文件，單純先到先服務的共享佇列可能讓其他租戶等很久。可以用租戶配額、每租戶併發上限或加權排程，將「整體吞吐量」和「每租戶可得到的服務」分開管理。這可能使部分硬體短暫閒置，卻換得更可預測的服務，而不是讓付費方案只存在於帳單上。

還要檢查擴充效率。若一台工作節點穩定處理每秒十份，十台只達到每秒四十份，就應找共享資料庫、序列化鎖、讀取頻寬或第三方限制。新增機器只是提供資源；分散工作、降低共享協調成本與保留容量，才是利用資源的設計。

常見誤區：用平均 CPU 很低來證明沒有瓶頸。某個單執行緒可能滿載、記憶體頻寬可能飽和、worker 可能全在等待同一把鎖；整機平均無法看出這些限制。

練習：五台 worker 總服務率每秒 100 份，工作以每秒 120 份持續進入十分鐘。沒有拒絕或丟棄時，積壓增加多少？之後流量降為每秒 80 份，需要多久清完新增積壓？

參考解答與推理

十分鐘新增積壓 = (120 − 100) × 600 = 12,000 份。流量降低後，淨清空速度 = 100 − 80 = 20 份／秒，所以仍需 600 秒，即十分鐘。這是假設服務率固定且無重試的理想化結果。佇列可以吸收短暫尖峰，不能解決長期到達率超過服務率。

2.6 效能（Performance）

吞吐量（throughput）是單位時間完成多少工作，延遲（latency）是單一操作花多久，併發量（concurrency）是在指定邊界內同時存在多少工作。三者相關，卻不是同一指標。一次處理更多文件可能提高吞吐量，同時讓單份等待更久；快取可縮短命中請求，但冷資料與失效時的尾延遲仍可能很差。

文件平台要至少分開量測：接收 API 延遲、上傳傳輸時間、佇列等待、實際轉換、結果保存與通知等待。對使用者而言，重要的可能是從按下上傳到可下載的總時間。如果只量 worker 的 CPU 時間，系統排隊半小時仍可能顯示「處理只需兩秒」。每個指標都要註明起點、終點與失敗請求如何處理。

沿用上圖的一百次請求：九十五次各需 100 ms，四次各需 500 ms，一次需 3,000 ms。平均是 145 ms；以最近秩法（nearest rank）取排序後第 ⌈p × n⌉ 筆，p95 是第 95 筆的 100 ms，p99 是第 99 筆的 500 ms，最慢的第 100 筆是 3,000 ms。少量樣本的 p99 仍可能漏掉最慢請求，因此要同時看逾時、最大值與樣本數。不同工具使用的分位數或直方圖近似方式有別；SLO 可以直接定義「低於某門檻的比例」。

平均 = (95 × 100 ms + 4 × 500 ms + 1 × 3,000 ms) ÷ 100 = 145 ms
端到端延遲 = 傳輸 + 排隊 + 服務時間 + 其他等待
穩定系統中的平均在途工作數 L = 平均到達率 λ × 平均停留時間 W
例：λ = 100 份／秒、W = 0.8 秒，L = 80 份

最後一個等式是 Little’s law 的常用形式。使用時三者必須對應同一系統邊界，並採長期穩定平均；不能把 p99 延遲代入後聲稱得到 p99 併發量，也不能在無限增長的佇列上假裝已達穩態。若邊界包含排隊，L 就包含等待中的工作；若只看執行區間，則不能把排隊時間加進 W。

效能測試還必須能重現工作混合與到達模式。只測小文件、熱快取與成功路徑，會得到過度樂觀的結果。測試工具若等上一個請求完成才發下一個，服務變慢時反而降低發送率，也可能低估真實外部到達負載下的排隊。要同時觀察成功量、錯誤、逾時、延遲分布、資源使用與積壓，才能判斷是變快了，還是丟掉更多工作。

常見誤區：平均各台機器的 p99 得到全站 p99。應彙整原始觀測或相容的直方圖計數，再求全體分布；各機器的分位數平均沒有這項語意。

練習：你把 batch size 從 1 改成 100，吞吐量翻倍，但低流量時延遲變高。這是否代表優化失敗？如何調整？

參考解答與推理

不一定失敗，而是達成了不同目標。低流量時湊滿一批的等待主導延遲。可用「最多一百份或最多等待二十毫秒，先到者觸發」的策略，並按使用者旅程驗證。二十毫秒只是候選設計值，需要考慮總延遲預算。必須同時比較吞吐量、每份成本與尾延遲，不能只選一個好看的數字。

2.7 持久性（Durability）

持久性關心已確認的資料能否在約定的故障與保存期間後仍被找回。可用性問「現在讀不讀得到」，持久性問「是否永久失去」。資料可以暫時不可讀但仍完整存在，也可以服務正常卻早已悄悄丟失一部分舊資料。因此不能用成功回應率取代持久性驗證。

首先定義確認點（acknowledgment point）。資料只在程序記憶體、作業系統緩衝區、本機持久媒體或另一個故障域的副本，提供不同的保護。資料庫的預寫日誌 WAL（write-ahead log）要求相關日誌在對應資料頁落盤前先符合寫入規則，以便崩潰後重做；但實際提交保障仍取決於同步設定、儲存堆疊與複寫模式。PostgreSQL 的 WAL 說明和同步／非同步複寫文件可用來查核具體語意。

副本（replica）與備份（backup）服務不同目的。線上副本能快速接管，卻可能同步收到誤刪與壞更新；具備歷史版本、隔離權限和保留策略的備份，才能在發現問題後回到較早狀態。備份成功訊息也不等於能恢復，必須測試還原的完整性、金鑰可用性、依賴順序與所需時間。

兩個常用目標是復原點目標 RPO（recovery point objective）與復原時間目標 RTO（recovery time objective）。RPO 指復原點與故障發生之間可容忍的資料缺口；RTO 指恢復指定服務能力的時間目標。例如 RPO 五分鐘、RTO 三十分鐘，代表要能還原到故障前五分鐘以內的資料狀態，並在約定起算點後三十分鐘內恢復服務。演練要驗證備份可還原、日誌連續、金鑰可用，以及跨區域故障時能取得復原資料。

每日原件：5 TB
保留 30 日的原件邏輯容量：5 × 30 = 150 TB
假設衍生結果大小是原件的 40%：再加 60 TB
總邏輯有效資料：210 TB
若自管且三份完整複寫：約 630 TB，尚未含備份、索引與預留空間

自管模型採三倍實體容量估算。託管物件儲存可能用不同內部編碼與計價方式，不能把內部複寫倍數再加到按邏輯容量計費的帳單上。保留期限也要涵蓋衍生結果、索引、快取與備份；刪除功能若只刪主資料表，未必達成實際的資料生命週期要求。

常見誤區：把供應商的年度耐久性設計指標解讀成「這個檔案永遠不會丟」。任何指標都有計量單位、期間與適用條件；它也不涵蓋應用程式主動刪除、帳號失誤或自行遺失解密金鑰。

練習：每小時備份一次，某次備份剛完成五十九分鐘後資料庫損毀。若沒有可用交易日誌或副本，能宣稱 RPO 五分鐘嗎？

參考解答與推理

不能。最壞可能失去將近一小時的更新，而且備份失敗時可能更久。要縮小 RPO，需要更頻繁且受監測的備份、持續日誌歸檔或符合要求的複寫；RTO 則取決於還原、重建索引、驗證與流量切換時間，必須另外演練。

2.8 一致性（Consistency）

「一致性」至少有兩種容易混淆的意思。資料庫交易中的一致性常指資料符合業務不變條件，例如租戶配額不可變成負數；分散式一致性模型則描述多個讀寫操作能看到什麼順序與結果。選型時不要只問某資料庫「強不強一致」，而要問哪個操作、哪個範圍、哪個讀取模式，以及故障時有什麼保障。

複寫像送帳本：寫完了，為什麼讀不到？

線性一致性（linearizability）讓每個操作看起來在呼叫與回覆之間的某一瞬間生效，並尊重不重疊操作的真實時間先後。若某次寫入已成功回覆，之後開始的讀取不能返回更早的值，除非中間又有其他寫入。這不是要求所有實體副本在同一奈秒完成更新，而是要求外部可見歷史符合該模型。

最終一致性（eventual consistency）通常表示在沒有新更新、且通訊與修復持續進展的條件下，副本最終收斂；這句話本身沒有給出「最多兩秒」的期限，也沒有保證讀己之寫（read-your-writes）或單調讀取（monotonic reads）。若產品需要「自己剛上傳就一定看得到」，應明確要求會話保障、讀取路由或版本條件，而非讓前端不斷猜測。

文件平台可以按資料用途選擇不同保證。授權與租戶配額需保護不變條件，搜尋索引可容忍短暫落後，但必須給出產品能接受的更新目標。任務狀態可使用版本編號，避免慢到的 RUNNING 更新覆蓋較新的 SUCCEEDED。刪除後搜尋索引即使尚未更新，真正下載時仍應檢查權威授權與刪除狀態，不能把索引當安全邊界。

CAP 的精確限制是：在允許網路分割的非同步分散式模型中，無法對所有執行同時保證線性一致性與每個送達非故障節點的請求都最終得到符合服務規格的回應。這裡的 availability 是形式化進展條件，不是每月 99.9% 的 SLO；單純回傳錯誤也不是「全部都可用」。因此「三選二」是過度簡化：分割發生時，系統要在某些操作上等待／拒絕，或容許較弱的可見性，並設計恢復後如何協調。Gilbert 與 Lynch 的原始論文明列了模型與條件。

交易隔離又是另一個軸。可序列化（serializability）要求並行交易結果等同某個序列順序，但單獨的這個性質不必尊重真實時間順序；不要把它當作線性一致性的同義詞。具體資料庫的預設隔離可能低於可序列化，也可能要求應用程式重試序列化失敗。PostgreSQL 的隔離等級文件展示了為什麼必須讀實際語意，而非只看「支援 ACID」。

常見誤區：用 eventual consistency 代替錯誤修復方案。如果兩份副本永遠沒有衝突解決、重送或反熵流程，「等一下就好」沒有任何保證。

練習：租戶只剩一個任務額度，兩個 API 節點各自從快取讀到剩餘值一，然後都接受任務。問題出在哪裡？

參考解答與推理

「先讀再減」不是原子操作，且快取可能過期。若不能超賣，可在權威儲存使用條件更新或適當交易，把檢查額度與扣減放在同一原子決策內；失敗者拒絕或排隊。仍需處理任務建立失敗後如何歸還額度與重送去重。若業務容許短暫超額，可選另一種模型，但超額界限與補償必須明確，而不是意外產生。

把配額條件放進寫入

在 PostgreSQL 中，可把「還有額度」與「扣一份」寫成同一個條件更新。下例以 tenant_id 為唯一鍵；RETURNING 回傳一列表示扣額成功，零列表示租戶不存在或額度已用完。

UPDATE tenant_quotas
SET remaining = remaining - 1
WHERE tenant_id = $1 AND remaining > 0
RETURNING remaining;

兩個請求競爭最後一份額度時，後取得列鎖者會依更新後的資料重查條件，因此只有一個能扣額。把冪等鍵認領、扣額、任務建立及 outbox 放在同一交易內，任一步驟失敗就整筆回滾；重送已成立的冪等鍵則直接回讀原任務。Read Committed 的並行更新規則與UPDATE RETURNING定義了這個行為。

2.9 可維護性、安全與成本（Maintainability, security, cost）

可維護性是未來改變系統的能力：新同事是否看得懂責任邊界，值班者是否能定位失敗，修改是否能逐步發布並回滾，資料結構是否能相容演進。它不是抽象的「程式碼漂亮」。如果每次新增文件格式，都必須同步更改十個服務和三個資料庫，可維護性的問題會直接表現成部署風險與修復時間。

平台可從模組化單體開始，把租戶身份、任務生命週期、轉換器與通知器分成清楚模組。當計算資源、部署頻率或故障隔離的需求真的不同時，再分成獨立程序或服務。用 job_id、tenant_id、版本與錯誤類型串起日誌和追蹤，有助於定位問題；但完整文件內容、憑證與秘密不應隨手寫進日誌。

安全需求要變成可測試不變條件。每次讀寫都確認租戶範圍，不依賴呼叫者提交的 tenant_id；下載連結採有限範圍與到期時間；轉檔程序以最小權限執行，限制 CPU、記憶體、檔案大小與執行時間。文件是外部輸入，可能含惡意結構、壓縮炸彈或讓解析器耗盡資源的內容。把它放進 container 只是一層隔離，不能取代修補、權限、網路限制與安全檢查。

成本應依工作單位分析，而非只看每月總額。每份文件成本可能包括原件與結果儲存、讀寫請求、CPU 時間、佇列操作、跨區域傳輸、日誌、通知和人力。高可靠度的閒置容量也是成本，但完全榨乾資源可能換來更長排隊與故障時崩潰。要比較方案，應在相同需求、保存期限與故障承諾下比較。

假設某月全部平台成本是 12,000 個成本單位
成功處理 30,000,000 份文件
每份平均成本 = 12,000 ÷ 30,000,000 = 0.0004 成本單位
若 1% 的文件耗用 40% 的 CPU，應再按格式／大小拆成本

安全與成本也會互相影響：不設每租戶限制，既可能造成拒絕服務，也可能產生意外帳單；無限制保存除增加容量，也增加敏感資料暴露面。相反地，為了節省觀測成本而完全移除審計，又可能讓故障和濫用難以追查。應先定義必要事件、取樣與保留期限。無差別地全部記錄或全部不記錄，都無法處理這個取捨。

常見誤區：把託管服務理解為「安全和維運都由別人負責」。供應商會負責一部分基礎設施，你仍要負責應用程式行為、資料分類、權限與設定；具體分工依服務模式而異。

練習：為節省工程時間，團隊打算讓所有 worker 使用可讀寫所有租戶資料、可刪備份的管理者權限。請指出風險並給出可落地的最小改進。

參考解答與推理

任一解析器漏洞或程式錯誤都可能跨租戶存取、毀損全部資料並刪除救援副本。至少將處理與管理權限分離，worker 只取得該工作需要的物件讀取和結果寫入權限，不能刪備份或管理金鑰；對不需網路的轉換器限制外連，並記錄授權失敗。更細的隔離可逐步導入，但不能以「內部服務」合理化無限權限。

2.10 系統需求總結（Summary of system requirements）

需求階段做到什麼程度才算完成？對每個核心旅程，你應能說出何謂成功、何謂失敗，以及用哪些資料判斷。堆上更多形容詞並不會讓需求更完整。文件平台有三條容易混淆的承諾：提交被可靠接收、結果正確產生、通知獲得合理處理。把它們分開後，架構才能在外部通知故障時保留文件服務，而不掩蓋通知目標的失敗。

品質應回答的問題文件平台的驗證方法
可用性哪些有效請求在什麼時間窗口成功？入口與使用者旅程 SLI，含過載與逾時
可靠性／容錯哪些故障發生後仍保持正確？在提交、保存、確認之間終止程序，檢查恢復
可擴充性負載成長哪個維度時，成本如何變化？多租戶混合負載、熱點與故障後容量測試
效能在哪個邊界量測何種延遲與吞吐量？分階段延遲、尾部、積壓年齡與完成率
持久性確認後保護什麼資料，保護到何時？崩潰復原、備份還原與 RPO／RTO 演練
一致性哪些狀態可落後，哪些不變條件必須守住？並行額度扣減、讀己之寫、版本競爭測試
維護／安全／成本如何安全變更，如何限制權限與每份成本？分階段發布、跨租戶測試、成本分組追蹤

需求表也應記錄待確認事項。例如目前不知道文件轉換的 CPU 成本分布，就應標註「待量測」，並說明它可能改變 worker 配置。明列待量測項目，讓後續設計決策有依據。好的設計審查不只看當下答案，還看你是否知道哪個假設一旦不成立就必須改方案。

最後，以衝突情境檢查優先順序：區域分割時是否可接受拒絕配額扣減？通知延遲十分鐘是否比文件處理中斷更可接受？為保住原件是否願意讓上傳確認稍慢？沒有普遍正確的排序，但跨租戶資料洩漏通常不能用整體可用性來補償。所有可容忍的降級都應透明呈現，並有恢復與追蹤方式。

常見誤區：需求文件寫完後永不更新。負載、租戶組合與外部依賴都會改變；用真實事件修正假設，同時保留變更理由，才能避免系統逐漸偏離原來的承諾。

綜合練習：請為第一版文件平台寫出五行需求，每行分別涵蓋功能、可用性、效能、資料保護與租戶隔離，並替其中一行提出驗收測試。

參考解答與推理
  1. 使用者可提交指定格式文件，取得穩定任務 ID，查詢終態並下載結果；同一租戶冪等鍵重送不建立第二個工作。
  2. 固定 30 日內，有效任務提交的良好事件比例目標為 99.9%，明列有效與良好事件定義。
  3. 在約定文件混合與尖峰負載下，99% 的接收 API 於 300 ms 內完成；轉檔完成時間另設目標。
  4. 接收後原件保存 30 日，明列保護的故障域與 RPO／RTO；定期從備份還原驗證。
  5. 租戶 A 的身份無法查詢或下載租戶 B 的任務及物件，即使知道其識別碼。

驗收隔離可建立兩個測試租戶，以 A 的憑證對 B 的讀、改、刪、下載與通知設定介面逐一測試；同時驗證錯誤訊息不洩漏敏感內容。
