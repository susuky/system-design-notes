第 02 章 · How to define system requirements

定義系統需求：把形容詞變成可驗證的承諾

真正合格的系統需求，必須講清楚服務對象、工作負載特徵、觀測時間窗口、成功條件與測量邊界。只有把「高可用、可擴充、低延遲」這些空泛的形容詞落實為工程規格，我們才能理性比較技術方案，並設計出自動化的驗收測試。

2.1 系統需求（System requirements）

在動手畫架構圖之前，系統需求要先回答兩大核心問題：第一，系統到底要做什麼？第二，在怎樣的約束條件下要做到什麼程度？前者通常被稱為功能需求（Functional Requirements），像是「提供 API 讓使用者上傳文件」或「支援進度查詢」；後者則通常稱為品質屬性或非功能需求（Quality Attributes / Non-functional Requirements），例如「在尖峰每秒一百次請求的衝擊下，依然維持 99.9% 的接收成功率」。千萬不要以為非功能需求可以等「主功能做完再回頭補」，因為非功能需求往往會從根本顛覆功能的實作架構與介面設計。

舉個具體例子：產品經理常常會說「希望文件轉檔完成後，客戶能立刻收到通知」。如果我們追問業務細節，發現業務其實能接受幾秒鐘的非同步延遲，那麼架構上就可以把「文件轉檔」與「發送通知」拆開，讓兩者各自排隊、各自獨立重試；反之，如果規格硬性規定「必須等外部簡訊供應商回傳發送成功，這份文件的轉檔才算完成」，那麼只要簡訊商短暫斷線，你的整套文件處理服務就會跟著停擺。你看，光是一句需求的措辭，就已經直接決定了元件之間的耦合程度。架構師的職責，就是在專案初期就把這類隱含的取捨抓出來討論，而不是等畫完了整張微服務架構圖，才發現系統被逼著同步等待所有第三方服務。

一份具備工程約束力的規格說明，通常包含四個層層相扣的維度：業務成果、使用者旅程、可測量指標、實作機制。舉例來說，業務成果是「企業客戶能按時產出合規報表」；用戶旅程是「從上傳原檔到順利下載結果」；指標是「指定檔案大小在尖峰下的 p95 完成耗時」；而實作機制才是「採用執行緒池、工作佇列與自動水平擴展」。在技術討論時，最忌諱反客為主——絕對不能把「我們一定要用 Kubernetes 或 Kafka」當成使用者需求，除非那是公司既有的基礎設施規範或不可變更的合約約束。

常見思維誤區：在規格書裡把所有指標都標記為「最高優先級」。當成本、網路延遲與系統可用性發生物理衝突時，這種「全都要」的規格完全無法給予工程團隊指引。合理的做法是明確區分不可妥協的安全邊界、主要服務承諾（SLO），以及在遭遇過載時可以主動降級的附屬功能，並替每項承諾定義驗收標準。

實戰思考：當主管或客戶開出這樣的需求：「我們的系統要支援所有格式檔案，資料永不遺失，任何時候都在一秒內完成，而且整體建置成本要最低。」這段話在工程上有哪些嚴重缺漏？你會如何把其中一項改寫為合格的架構需求？

參考解答與推理

這段話完全缺乏工程邊界：沒有定義檔案格式清單與大小上限、沒有設定故障模型、沒有定義什麼叫「完成」（是接收完成還是轉檔完成？）、缺乏流量規模假設，也沒有明定保存年限與可承受的預算上限。改寫範例：「針對不大於 10 MB 的標準 PDF 格式，在併發吞吐每秒 100 份的測試負載下，99% 成功被接收的轉檔任務需在 60 秒內產出可供下載的結果；原件與結果檔線上保留 30 天。」有了明確的量化數值，架構才能評估硬體配置，測試團隊也才能據此設計壓測腳本。

2.2 功能需求（Functional requirements）

功能需求不該只是一張冰冷的 CRUD 清單，它必須清楚勾勒出系統的外部可觀察行為，特別是遇上網路失敗、用戶超時重送等邊界情況下的反應。對於這個文件處理平台，最核心的主流程包括：初始化上傳通道、校驗原件完整性、正式建立處理任務、查詢執行狀態、安全下載結果，以及設定完成通知的 Webhook 地址。在開始寫程式碼前，先把領域主體的職責邊界切乾淨：tenant（租戶）是資料權限與用量配額的隔離邊界；document（文件）代表上傳的原件本體與版本資訊；job（任務）代表針對某個文件版本所觸發的一組轉檔作業；notification（通知）則是當任務結束時，向指定端點發起的單次交付動作。

把這些實體拆分清楚，能有效避免實務上的狀態混淆：例如同一個原始文件可能需要觸發兩種不同的轉檔選項（產出兩種 job）；一個已經轉檔成功的 job，可能因為網路抖動經歷了三次 Webhook 投遞嘗試（3 次 notification）；而通知的重試，絕不應該回頭把已經完成的轉檔重跑一次。為每個實體繪製清晰的有限狀態機（Finite State Machine），遠比單純列出資料表欄位更能理清邏輯。在狀態流轉中，必須清楚標註是由誰觸發、有哪些前置條件，以及哪些終態（Terminal State）是一旦進入就不可逆的。

文件：UPLOADING → READY → DELETED
任務：QUEUED → RUNNING → SUCCEEDED
                     ↘ RETRY_WAIT → QUEUED
                     ↘ FAILED
通知：PENDING → SENDING → ACCEPTED_BY_PROVIDER
                    ↘ RETRY_WAIT → PENDING
                    ↘ DEAD_LETTER

上面是一套經過收斂的領域狀態模型。需要特別警惕的是：第三方供應商「已接收通知」，只代表對方的 API 回傳了 HTTP 200，既不代表終端用戶已經讀取，甚至不保證郵件不會在幾分鐘後被退信（Bounced）。如果你需要在儀表板上顯示精準的投遞狀態，系統就必須有獨立的 Webhook 回調通道來更新狀態。另外，背景任務的重試絕對不能陷入無窮迴圈：必須嚴格定義哪些是「可重試錯誤」（如網路短暫逾時）、哪些是「不可重試錯誤」（如檔案本身格式損毀），並設定最大重試次數與死信（Dead-letter）機制。如果業務支援「手動取消任務」，還必須小心處理「使用者點擊取消」與「背景剛好轉檔完成」這兩件事同時發生的競爭條件，絕不能只在資料表草率寫入一個 CANCELLED 字串就當作了事。

在對外開放的 API 設計上，通常會要求客戶端帶上租戶範圍內的冪等鍵（Idempotency Key）。同一個客戶端帶著相同的冪等鍵與完全相同的參數重試時，伺服器必須保證只建立同一個底層任務並回傳相同的結果；但如果同一個冪等鍵卻搭配了不同的處理參數，系統則應果斷回傳衝突錯誤（409 Conflict），避免系統悄悄張冠李戴。冪等性是應用層的業務契約，不能光靠「兩次上傳的檔案內容 Hash 相同」來臆測使用者意圖，因為使用者完全可能想用不同的解析參數重跑同一個檔案；更不能天真地以為改用 HTTP POST 或 PUT 就會自動獲得防重複能力。

在非同步架構中，API 回應 HTTP 202 Accepted 僅代表「系統已經安全收件並準備處理」，並不保證幾分鐘後轉檔一定大功告成。如果平台向客戶承諾「只要收到 202 就可以透過 Job ID 追蹤狀態」，那麼在回傳 HTTP 202 之前，系統就必須確保檔案原件與任務紀錄已經確實寫入具備持久化保證的儲存體。由於跨物件儲存與關聯式資料庫很難走傳統分散式交易，我們必須用可補償、可重試的流程來處理「檔案已經傳上 S3，但資料庫建立 Job 剛好斷線」的中間斷裂狀態。RFC 9110 關於 202 Accepted 的標準規範特別保留了這種非同步解耦的語意空間。

常見思維誤區：以為 API 介面寫完「檔案接收成功」就等於搞定了功能需求。事實上，客戶端傳輸中途斷線重送、分片上傳缺漏、惡意副檔名欺騙、跨租戶越權存取，以及帳號額度耗盡等種種例外邊界，才是真正決定系統是否穩健的關鍵所在。

實戰思考：客戶端發起任務建立請求，但在等待伺服器回傳時網路中斷，客戶端無法得知請求到底成功了沒有。如果客戶端毫無防備地直接發起重送，會面臨什麼風險？你在伺服器端會如何設計去重機制與快取邊界？

參考解答與推理

原本的請求很可能已經在資料庫成功落盤，客戶端盲目重發會導致系統建立兩筆重複的轉檔任務，甚至引發重複扣款與計費爭議。解決方案是：要求客戶端在首次發起時自行產生唯一的 Idempotency-Key。伺服器在資料庫中對 (tenant_id, idempotency_key) 建立唯一約束，並在同一事務中記錄請求參數摘要與產生的 job_id；當並發的重試進來時，依靠資料庫鎖或唯一索引原子地取得既有紀錄。如果同鍵但參數變更，回傳 409 Conflict。需要注意的是：這個機制只能保證任務建立這一步不重複，後續 worker 執行與外部通知發送的冪等性，仍須由各模組獨立處理。

2.3 高可用性（High availability）

可用性衡量的是「終端使用者拿到預期結果的比例」，絕不是單純看「伺服器作業系統有沒有開機」。在工程界有三個必須嚴格區分的專有名詞：服務水準指標 SLI（Service Level Indicator）是我們實際量測到的數值；服務水準目標 SLO（Service Level Objective）是團隊內部設定的合格目標；而服務水準協議 SLA（Service Level Agreement）則是白紙黑字寫進客戶合約的法律承諾，通常伴隨違約賠償條款。三者不可混為一談，而且千萬別天真地以為雲端基礎設施廠商給你的 SLA，能直接等同於你對外承諾的端到端服務可用性。

在現代微服務中，以事件為基礎的可用性計算公式通常是「良好請求次數 ÷ 有效請求總數」。以文件平台的 API 為例，有效請求的分母必須清楚定義為：通過身份認證、檔案格式合法且在正常配額內的請求嘗試；而分子所要求的良好請求，則是在約定逾時門檻（例如 500 ms）內成功回傳 Job ID 的請求。計算分母的標準必須在前期就凍結且長期穩定：如果因為系統過載打掛了，伺服器回傳 503 Service Unavailable，你絕對不能把這些失敗請求踢出分母來美化報表；同理，也不能把所有 4xx 錯誤全當成客戶端問題，因為如果系統程式碼出錯把合法的存取誤判成 403 Forbidden，那本質上就是嚴重的系統可用性故障。

假設觀察時間窗口：連續 30 天；統計有效請求總數：10,000,000 次
內部設定的 SLO 目標：99.9% 良好請求
整個週期允許的不良請求上限 = 10,000,000 × (1 − 0.999) = 10,000 次
如果目前已累計失敗 2,500 次：代表團隊已消耗掉本月「錯誤預算（Error Budget）」的 25%

另一種常見的定義是以時間為維度（Uptime），也就是將「可正常服務的分鐘數」作為分子。只有當你採用這種時間定義、且明確規範怎樣的故障程度算「整體不可用」時，「幾個九」換算成停機時間才有意義。以 30 天為例，總共有 43,200 分鐘；99.9%、99.95% 與 99.99% 的可用性，分別對應著每個月只能容忍 43.2 分鐘、21.6 分鐘與 4.32 分鐘的停機時間。但這套算法不能跟前面提到的事件型 SLO 混用：同樣是當機五分鐘，發生在半夜離峰只有幾十次請求，跟發生在全天最高峰的流量狂潮下，所消耗掉的業務請求成功率預算完全是天壤之別。

監控探針埋在什麼位置，會徹底決定你的可用性數據是否真實。如果你的統計全部來自後端 API 伺服器的 Log，那只要外部 DNS 出錯、負載平衡器設定壞掉，或是入口閘道網路中斷，這些連後端都沒碰到的悲劇就完全不會出現在日誌裡；而第三方的定期探活撥測（Synthetic Probing）雖然能發現黑箱故障，卻無法反映多租戶長尾請求的真實體驗。在實務上，成熟團隊會將邊緣入口指標、用戶端錯誤回報與合成探測結合起來，並且按照租戶規模與核心功能分別切分。光看全站平均的 99.9%，很可能掩蓋了某個營收貢獻極大的大客戶已經連續一週轉檔失敗的慘劇。

多加機器做副本確實能提高可用性，但這招管用的唯一前提是：各節點的故障必須彼此獨立。如果一個業務流程需要串聯兩個元件 A 與 B，兩者各自的獨立可用性都是 99.9%，那麼串聯後的整體可用性其實會下降為 99.9% × 99.9% ≈ 99.8001%；反過來說，如果兩台伺服器互為備援，任一台都能扛下全站流量，而且切換機制百分之百可靠，理性的並聯可用性就能提升到 1 − (1 − 0.999)² = 99.9999%。但現實往往很殘酷：共用同一個機櫃的電源、共用同一份寫爛的設定檔，或是依賴同一個後端資料庫，都會瞬間打破「故障獨立」的假設，讓備援副本在同一瞬間一起暴斃。

常見思維誤區：以為「在雲端開了三台 API 主機」就自動達到了高可用架構。如果這三台虛擬機底層連向同一個未做主從切換的單點資料庫，或者一旦其中一台掛掉、剩餘兩台的算力根本吃不下全站流量而接連引發雪崩，那麼表面上的三副本架構在實戰中根本不堪一擊。Google SRE Workbook 的 SLO 實作章節是梳理指標分母與錯誤預算管理的權威參考。

實戰思考：某個月份系統共收到一千萬個有效請求，其中四千次遇到逾時、兩千次因伺服器過載而被 503 限流拒絕，另外有五千次是使用者未通過格式校驗。如果事先約定格式無效排除在分母外，但逾時與過載拒絕都算不良事件，請問系統是否達成了 99.9% 的可用性目標？

參考解答與推理

題目給出的一千萬次已經是扣除格式無效後的有效請求分母。不良事件的總數是 4,000 + 2,000 = 6,000 次。實際達成的 SLI = (10,000,000 − 6,000) ÷ 10,000,000 = 99.94%。因為 99.94% 大於 99.9%，所以達成了目標，並消耗了 60% 的錯誤預算（允許 10,000 次，發生了 6,000 次）。如果一千萬次是包含格式無效的原始總量，算法就會不同——這正凸顯了在需求簽訂時，必須精確定義分母過濾規則的原因。

2.4 容錯、韌性與可靠性（Fault tolerance, resilience, reliability）

在技術討論中，這三個名詞經常被混為一談，但它們在系統設計中有著明確的分工。可靠性（Reliability）描述的是系統在特定的環境條件與時間範圍內，持續給出正確結果的綜合能力；容錯（Fault Tolerance）指的是當特定硬體或軟體故障發生時，系統能依靠預設的冗餘機制「無縫維持服務」的工程手段；而韌性（Resilience）強調的則是一種系統生命力：當遇到超出預期的劇烈衝擊時，系統能主動限制爆炸半徑、從容降級，並在風暴過後安全自我復原。單次 HTTP 呼叫的成功率很高，不代表背景長任務不會在中途悄悄遺失，更不代表系統遇到連環車禍時具備自我治癒的能力。

談容錯之前，必須先明確你的「故障模型（Fault Model）」是什麼。單一 worker 行程崩潰、實體伺服器斷電、整個可用區網路光纖挖斷、資料磁碟壞軌、運維人員手滑誤刪資料，或是下游供應商反應變慢，每一種都是完全不同等級的災難。開兩台 worker 可以輕鬆應對行程隨機當機，但如果遇到的是惡意 PDF 觸發的解析器記憶體洩漏漏洞，那麼兩台 worker 只會前仆後繼地一起崩潰；資料庫的主從複寫能秒級抵禦單機硬體故障，但如果是人為下了錯誤的 DROP TABLE 指令，這條誤刪操作只會在毫秒之內同步抹平所有副本。因此，實體故障域、金鑰權限隔離、冷備份與發布防護流程，在系統韌性中缺一不可。

對於非同步的文件轉檔流程，整個架構中最兇險的時刻，往往發生在「事情剛做完」但「還沒來得及把狀態記下來」的中間空檔。舉例來說，worker 剛剛把轉好的預覽圖傳上 S3，正準備向資料庫回報任務成功，機器卻在這一瞬間斷電重啟。另一台 worker 接管任務後再次執行，就會引發重複轉檔。如果系統在設計時就將 Job ID 與檔案雜湊當作穩定的冪等識別碼，那麼接手的 worker 就能先檢查儲存桶是否已有合法結果，直接推進狀態，避免重複浪費 CPU。而如果產生的外部副作用是寄送 Email，由於我們很難確認第三方郵件伺服器到底收到了沒有，系統就必須仰賴下游服務的冪等 API，或在產品合約上誠實揭露「在極端重試下可能收到重複通知」的邊界。

任何自我復原機制本身都是一把雙面刃。在下游依賴開始變慢時，盲目且無上限的即時重試只會瞬間形成重試風暴，直接把苟延殘喘的下游徹底打死；將逾時時間設得過短，又會把明明還在正常運行的長任務誤判為超時而反覆重發；如果健康檢查機制太過神經質，甚至會把只是暫時 CPU 滿載的健康節點直接從叢集踢掉，引發剩餘節點相繼過載的骨牌效應。成熟的韌性設計必須綜合運用：全域最大截止時間（Deadline）、有限重試次數、指數退避與隨機抖動（Exponential Backoff with Jitter）、隔艙化執行緒池，以及具備報警通知的死信佇列。AWS Builders' Library 關於逾時與重試抖動的專文特別指出了不當重試如何加劇系統過載。

在面對超載時，降級必須死守系統的安全底線。當第三方通知發送系統故障時，我們可以讓文件轉檔正常推進，把通知發送暫存排隊，等外部系統修復後再補寄；當 Elasticsearch 搜尋索引更新延遲時，我們可以在畫面上提示使用者「搜尋索引同步中，部分最新文件可能稍後出現」。但是，當認證授權伺服器反應超時時，我們絕對不能為了所謂的「服務可用性」而大開後門、允許未授權用戶直接下載文件。只有事先將業務功能劃分出輕重緩急的層級，團隊在災難來臨時才知道哪些操作可以排隊非同步化、哪些可以返回快取舊資料，而哪些操作必須寧可報錯也堅決拒絕。

常見思維誤區：誤以為把服務跑在 Docker 裡並設定「自動重啟（Restart Policy）」，系統就自動擁有了容錯能力。自動重啟頂多只能把死掉的作業系統行程重新拉起來，它既無法找回死前存留在記憶體裡的未完成任務，也無法抹除已經向外部產生的重複扣款副作用，更不可能自動修復已經寫壞的資料庫記錄。

實戰思考：第三方通知服務商突然發生全面停機一小時。此時文件轉檔模組完全正常，但因為舊版程式碼採用了同步呼叫方式等待郵件發送結果，導致所有 worker 的執行緒全被卡住，最終引發全站無法接收任何新文件。你會如何重構架構，確保通知商的停機不再拖垮文件核心業務？

參考解答與推理

關鍵在於徹底切斷兩者的執行序生命週期。將「轉檔成功」與「待發送通知」拆為兩個獨立的持久化步驟：轉檔完成後僅在資料庫或佇列中寫入一筆 notification_pending 紀錄，隨即釋放 worker 繼續轉下一份文件。通知的投遞由獨立的發送池負責，並配置嚴格的連線逾時、指數退避、重試上限與速率限制（Rate Limiting）；同時監控通知佇列的堆積時間（Lag Age）。在第三方服務商復原時，以平緩受控的速度消化積壓，避免剛開機又被瞬間打爆。這樣即使通知系統癱瘓，核心轉檔依然暢行無阻；但同時通知系統本身的延遲指標也必須誠實告警，不能假裝問題不存在。

2.5 可擴充性（Scalability）

可擴充性檢驗的是：當業務負載持續成長時，系統能否藉由投入成比例的資源成本，依然維持原本承諾的效能與可用性指標。光嘴上說「我們的架構只要多加機器就能跑」是遠遠不夠的。負載從來就不是單一維度：每秒併發請求量（QPS）、活躍客戶數、單檔大小上限、長期累積的總儲存容量、併發長任務數量，以及個別大客戶的資料集中度（熱點），全都是完全不同的負載向量。光拿「我們預估每天有一百萬份文件」這句話，根本不足以進行硬體選型——因為這一百萬份若是全天均勻進來，跟在一場一小時的促銷活動中集中湧入，所需要的系統架構完全是天差地別。

垂直擴充（Scale Up，向上提升單機配置）是透過換裝更強大的 CPU、更大的記憶體或更快的 NVMe SSD 來硬扛流量。這種方式通常最不需要改動應用程式架構，但實體機器有硬體規格的天花板，而且單機故障時造成的爆炸半徑也更大；水平擴充（Scale Out，向外增加節點）則是透過堆疊廉價的通用伺服器來分攤負載，但它的先決條件是工作必須能被拆解分配、分散式狀態必須協調一致，而且暴增的節點不能反手把下游的關聯式資料庫壓垮。增加無狀態的 Web API 節點相對輕鬆，但如果多個節點都在同時嘗試修改同一個企業租戶的即時配額計數器，那麼加再多節點也只是把時間浪費在資料庫的鎖競爭（Lock Contention）上。

教學情境假設：全天處理 1,000,000 份文件，每份轉檔平均耗時 2 個 CPU-seconds
全天累計的總算力需求 = 1,000,000 × 2 = 2,000,000 CPU-seconds／日
若流量完全平攤，全天平均需要的忙碌核心數 ≈ 2,000,000 ÷ 86,400 ≈ 23.15 核
若尖峰負載為均值的 10 倍：尖峰所需忙碌核心 ≈ 231.48 核
實務上伺服器不能跑在 100% 滿載，若以 60% 安全目標利用率預估：231.48 ÷ 0.60 ≈ 385.80 核
因此我們在容量規劃初期，先以約 386 個標準等效核心為基準，再進一步校準真實負載

上面的數學推導建立在單純的理想假設上：假設所有 CPU 核心效能一致，且後端有足夠的工作可以完全平行化。請特別分清這兩個概念：2 個 CPU-seconds 代表的是單份文件累計消耗的純算力時間；如果在轉檔過程中需要頻繁等待磁碟讀寫或網路下載，那麼整份工作的「停留時間（Elapsed Time / Latency）」就會被大幅拉長；反之，如果使用了多核心平行轉碼，實際的鐘錶時間也可能縮短。在系統設計中，純 CPU 耗時是用來規劃伺服器算力規模的，而包含了排隊與 I/O 等待的總停留時間，則是用來計算系統中同時並存的工作總量與記憶體消耗的。這兩種指標必須針對不同副檔名與容量分布進行基準實測，千萬不能混為一談；至於跨可用區容災所需的備份算力預留，我們會在第 3 章詳細推導。

在多租戶雲端架構中，最核心的擴充挑戰其實是「資源分配的公平性（Fairness）」。試想一下：如果有某個重量級客戶在短短十秒鐘之內，一口氣倒進了十萬份超大文件，若後端只用一個共用且採用先到先服務（FIFO）的傳統佇列，那麼其他所有普通客戶的上傳任務就會被硬生生卡在隊伍最後面，等待數小時之久。成熟的架構會導入每租戶併發限額、權杖桶或加權公平佇列（Weighted Fair Queueing），把「整體系統的極限吞吐量」與「個別客戶得到的服務品質」分開治理。這樣做雖然可能會在某些時刻讓部分伺服器出現短暫的運算空檔，但它換來的是整個平台穩定可預測的 SLA，而不是讓高級付費客戶的特權只存在於宣傳合約上。

最後，我們必須時刻評估擴充的「轉換效率」。如果一台工作節點每秒能穩穩處理 10 份文件，但當你把節點增加到 10 台時，整體吞吐量卻只提升到每秒 40 份，這就說明系統遇到了非線性的擴展瓶頸：可能是全體都在搶同一個資料庫的全局鎖、儲存系統的讀取頻寬被吃滿，或是遇到了第三方 API 的頻率限制。光是砸錢加機器只是單純堆積硬體；唯有把資料打散、消除不必要的跨節點同步協調，並精準預留容錯空間，才是真正體現架構功力的可擴充性設計。

常見思維誤區：拿整台主機的「平均 CPU 使用率很低」來斷定系統效能沒有瓶頸。現實中，很可能是某個關鍵的單執行緒模組已經 100% 跑滿、記憶體匯流排頻寬已經飽和，或者十幾個 worker 執行緒正陷入對同一把資料庫列鎖的漫長等待中；粗糙的整機平均指標往往會成為掩蓋致命瓶頸的偽裝。

實戰思考：目前有 5 台 worker，全體每秒極限處理能力為 100 份文件。突然湧入了一波持續 10 分鐘、每秒 120 份的突發流量。在完全不丟棄、不拒絕任何請求的假設下，內部佇列會堆積多少檔案？風暴過後流量降回每秒 80 份，系統需要額外花費多久時間，才能徹底清空這波突發帶來的積壓？

參考解答與推理

在突發的 10 分鐘（600 秒）內，流入速率比處理速率每秒多出 20 份，因此佇列會累積 (120 − 100) × 600 = 12,000 份未處理文件。當進水速度降為每秒 80 份時，伺服器每秒能擠出 100 − 80 = 20 份的剩餘算力來消化前面積壓，因此需要 12,000 ÷ 20 = 600 秒（整整 10 分鐘）才能徹底恢復正常。這個算例生動揭示了系統動力學的現實：工作佇列只能在短暫的峰值波谷間發揮削峰填谷的緩衝作用，一旦長期的平均抵達率超越了後端處理能力，任何佇列最終都只會走向記憶體爆滿或排隊時間無窮大的崩潰結局。

2.6 效能（Performance）

在評估系統效能時，有三個關鍵維度必須精確區分：吞吐量（Throughput）代表單位時間內系統能完成的工作總量（如每秒處理多少份文件）；延遲（Latency）指的是單次特定操作從發起呼叫到取得回應所耗費的總時間；而併發量（Concurrency）則是指在某個特定時間點，正停留在系統管線內被同時處理的工作總數。這三者高度關聯，但絕對不是同一回事。舉例來說，如果改採批次打包處理，系統的整體吞吐量可能大幅上升，但代價卻是單一請求因為等待湊批而導致延遲惡化；快取能讓高頻存取的熱資料在幾毫秒內極速返回，但一旦遇到冷啟動或快取失效（Cache Miss），後端被擊穿時的尾端延遲（Tail Latency）可能會瞬間飆到令人無法接受的高點。

對於我們的文件平台，延遲指標絕對不能混為一談，必須拆解成多個獨立的監控斷點：客戶端連線到接收 API 的延遲、檔案原件的網路傳輸耗時、任務進入訊息佇列的排隊等待時間、背景 worker 的純轉檔運算時間、產出檔案寫入儲存桶與更新資料庫的耗時，以及最後等待通知被下游接收的延遲。站在終端使用者的角度，真正有感的是「從按下上傳按鈕，到最終能下載預覽檔案」的端到端總時間。如果你只去量測 worker 的純 CPU 耗時，就算內部轉檔只需 2 秒，但如果檔案在佇列裡乾等了半小時，這在使用者眼裡就是徹頭徹尾的卡頓與不可用。每個監控指標都必須白紙黑字定義清楚：起點從哪裡算起、終點在哪裡截止，以及失敗或逾時的請求到底有沒有算進去。

看看上圖這組典型的一百次請求分布：其中有 95 次非常迅速，只需 100 ms；有 4 次稍慢，花了 500 ms；而有 1 次遇到了長尾卡頓，整整耗費了 3,000 ms。如果單純計算算術平均數，結果是看似很不錯的 145 ms；若採用最近秩法（Nearest Rank Method，取第 ⌈p × n⌉ 筆），第 95 百分位數（p95）是 100 ms，第 99 百分位數（p99）是 500 ms，但那個高達 3,000 ms 的極端值就被完完全全忽視掉了。這告訴我們：在樣本數有限的情境下，光看 p99 依然可能漏掉最糟糕的長尾請求。因此在制定 SLO 時，務必將逾時上限、最大極端值（Max Latency）與有效樣本規模放在一起綜合研判，甚至可以直接約定「要求 99.5% 的請求延遲必須壓在 500 ms 以下」。

平均延遲 = (95 × 100 ms + 4 × 500 ms + 1 × 3,000 ms) ÷ 100 = 145 ms
端到端完整延遲 = 網路傳輸時間 + 佇列排隊時間 + 服務運算時間 + 外部依賴等待時間
利特爾法則（Little’s Law）：在長期穩態的排隊系統中，平均在途工作數 L = 平均抵達率 λ × 平均停留時間 W
試算：若平均每秒進來 λ = 100 份文件，每份平均在系統停留 W = 0.8 秒，則平均並存的處理中工作數 L = 80 份

上面列出的最後一個數學公式，就是排隊理論中最著名的利特爾法則（Little’s Law）。在套用這個經典定律時，必須銘記一條嚴格的前提：公式中的三個變數必須對應於完全相同的系統邊界，且系統必須處於長期穩定的平衡狀態中。千萬不要犯常識性錯誤——把 p99 的延遲數字直接乘上平均到達率，然後宣稱自己算出了「p99 的併發數」；更不能在一個正在瘋狂積壓、早已失衡的佇列上假裝穩態成立。如果你的計算邊界包含了前面的排隊緩衝區，那麼 L 算出來的就是包含了排隊在內的總任務數；反之，若你只關注 worker 的當下併發，那麼在計算 W 時就絕對不能把前面的佇列排隊時間給加進去。

進行壓測與效能基準測試時，最關鍵的挑戰在於「能否精準還原生產環境的混合負載與到達模式」。如果你在壓測時只拿 100 KB 的極小檔案測試、讓所有請求都打在已經預熱好的快取上，而且只測試一帆風順的正常路徑，那你得到的不過是一張自欺欺人的漂亮成績單。更有甚者，許多常見的壓測工具會採用「等上一個請求回應了才發下一個請求」的閉迴路模型（Closed-loop System），當伺服器一旦變慢，壓測工具發起請求的速率就會跟著自發性放緩，反而掩蓋了真實世界中外部流量依然無情湧入所引發的嚴重排隊現象。唯有同時觀測成功吞吐量、錯誤率、各分位數延遲分布、系統硬體資源飽和度與積壓任務年齡，你才能客觀判定：系統是真的變快了，還是只是因為崩潰而悄悄丟掉了更多的請求。

常見思維誤區：把叢集裡每台伺服器的 p99 延遲數字拿來算「平均值」，當作全站的 p99 延遲。百分位數在數學上不具備可加性！正確的做法是收集所有原始請求耗時，或者依賴相容的直方圖資料結構（如 HDR Histogram）進行全域合併統計；把各機器的 p99 平均起來得到的數字，在統計學上毫無意義。

實戰思考：為了解決資料庫寫入效能，工程師把批次處理的 Batch Size 從 1 調高到 100，系統的極限吞吐量立刻翻了一倍；但在半夜低流量時段，客戶端卻抱怨請求延遲明顯變高。這是否代表這次優化是失敗的？如果是你，會如何動態調整策略？

參考解答與推理

這並不代表優化失敗，而是不同策略在吞吐量與延遲之間的經典權衡。在低流量時，為了湊滿 100 筆資料，第一筆進來的請求必須在記憶體裡苦等後續請求抵達，這個「湊批等待」成了延遲元兇。工業界的標準解法是引入雙觸發條件的緩衝策略：「只要累計達到 100 筆，或者距離第一筆抵達已經過去了 20 ms，任一條件先滿足就立刻刷盤（Flush）」。其中 20 ms 的時間上限需根據整體的端到端延遲預算進行校準。架構設計需要同時衡量尖峰吞吐量、單位資源成本與離峰長尾延遲，而不是盲目追求某一個極端數字。

2.7 持久性（Durability）

持久性（Durability）關注的是：那些已經向用戶確認寫入成功的資料，能否在面臨硬體故障、斷電重啟及約定的保存期限內，依然完好無損地被找回來。可用性問的是「我現在點擊這筆資料，能不能立刻讀出來？」而持久性問的則是「這筆資料到底有沒有真的徹底遺失？」這兩者有本質區別：一個儲存叢集可能因為網路隔離暫時無法讀取，但底層硬碟上的資料其實毫髮無傷；反之，一個系統的 API 可能長年維持 99.99% 的響應成功率，但背景卻因為靜默資料毀損（Silent Data Corruption）早已悄悄遺失了一半的歷史舊檔。因此，成功率再高的 HTTP 回應，也無法替代真實的持久性驗證。

在設計持久性機制時，首先要定義明確的「確認點（Acknowledgment Point）」。當伺服器向客戶端回覆「寫入成功」時，這份資料到底只是躺在該程序的暫存記憶體裡？還是已經進了作業系統核心的 Page Cache？還是真的已經透過 fsync 刷進了本機實體 SSD 的非揮發性介質？抑或是已經成功複寫到了另一個實體機櫃的備份節點上？不同的確認時機，給予的持久性保證天差地別。在關聯式資料庫中，預寫日誌 WAL（Write-Ahead Log）要求所有針對資料頁的修改，都必須先將日誌持久化到磁碟介質之後才能落盤，以便在崩潰時能夠透過重做日誌（REDO）進行狀態復原；然而，在交易提交的那一瞬間到底有沒有強制刷盤，依然高度仰賴你的資料庫同步參數、底層儲存控制器的快取策略與主從複寫模式。PostgreSQL 關於 WAL 的底層說明以及同步與非同步複寫的官方手冊，是查證具體寫入語意的核心資料。

我們必須清楚劃分線上副本（Replica）與離線備份（Backup）的職責。線上副本的主要任務是當主節點硬體損毀時能夠幾秒內快速容錯接管，但如果有人在主節點誤下了一條 DELETE 指令，這個災難會在毫秒內無情地同步到所有在線副本上；唯有具備歷史版本追溯、權限嚴格隔離且定期驗證保留週期的離線備份，才能在發生重大邏輯錯誤時讓系統時光倒流、恢復如初。更重要的是：備份腳本回報「備份成功」絕不等於「日後真的能成功復原」，團隊必須定期進行無預警的災難恢復演練，實測備份資料的完整性、加密金鑰的可取得性、資料庫相依順序，以及把上百 TB 資料拉回生產環境所需的漫長時間。

在災難復原（Disaster Recovery, DR）的規劃中，有兩個最關鍵的黃金指標：復原點目標 RPO（Recovery Point Objective）與復原時間目標 RTO（Recovery Time Objective）。RPO 定義的是當災難發生時，系統最多可以容忍遺失多久的資料量（資料缺口）；而 RTO 定義的則是系統從災難發生到全面恢復對外服務，最多允許花費多少時間（停機時長）。舉例來說，當企業承諾 RPO = 5 分鐘、RTO = 30 分鐘時，這代表一旦主資料中心遭受毀滅性打擊，復原後的資料狀態與災難發生的當下相比最多只能有 5 分鐘的落後，而且整套復原與切換流程必須在 30 分鐘之內全數搞定。要達成這項承諾，平時就必須嚴格驗證備份鏡像的可還原性、資料庫 WAL 連續歸檔機制、異地金鑰管理，以及在遭遇跨區域光纖切斷時是否能迅速獲取備份資料。

教學情境假設：每日處理並儲存的原件規模為 5 TB
依產品法規要求需保存 30 天，原始檔案的有效邏輯容量 = 5 × 30 = 150 TB
假設轉檔產生的衍生預覽檔與 OCR 結構化結果約為原件大小的 40%：額外增加 60 TB
全站 30 天內累計的有效邏輯資料總量 = 150 + 60 = 210 TB
若採取自建自管的 Ceph 儲存叢集，並維持三份實體跨機櫃副本：實體硬碟裸容量需求約為 210 × 3 = 630 TB（此處尚未包含索引、WAL 日誌、快照與安全預留空間）

上面這個算例是以傳統自建儲存的「三副本機制」為例推導的。如果是直接使用雲端託管的物件儲存服務（如 Amazon S3 或 Google Cloud Storage），雲端廠商底層通常採用糾刪碼（Erasure Coding）等多重冗餘編碼技術，在計費時也是直接按照你實際佔用的「邏輯容量」開立帳單，這時就千萬不要在估算雲端帳單時又重複乘上三倍實體係數。此外，資料保留週期的計算必須涵蓋所有衍生結果：包括轉換後的預覽圖、搜尋引擎裡的文字索引、中繼快取與備份歸檔；如果在實作「資料到期自動刪除」功能時只刪除了關聯式資料庫的紀錄，卻讓大量物件靜靜躺在 S3 裡繼續扣款，那不僅會帶來巨額的隱形帳單，更違反了合規隱私的法規邊界。

常見思維誤區：把雲端大廠宣稱的「99.999999999%（11 個 9）年度物件耐久性設計指標」解讀成「檔案放進去就永遠不可能遺失」。任何工業指標都有特定的適用假設與計算週期；廠商的 11 個 9 頂多只能保證不會因為硬碟壞軌弄丟你的資料，但如果是應用程式自己發起了錯誤刪除、開發者帳號外洩導致被洗庫，或者你把自管的 KMS 解密金鑰徹底弄丟了，任何雲端保證都救不回你的資料。

實戰思考：某團隊採用了排程腳本，每整點對資料庫做一次全量備份。某天在 14:59 分（距離上次備份過去了整整 59 分鐘），實體伺服器發生不可逆的硬體燒毀。如果團隊平時沒有開啟持續 WAL 日誌歸檔，也沒有任何即時資料庫副本，這時他們能向客戶宣稱系統的 RPO 達成了 5 分鐘嗎？

參考解答與推理

絕對不可能。在最糟糕的情況下，團隊將徹底失去過去 59 分鐘內發生的所有用戶資料更新；甚至如果 14:00 的那次備份檔案本身損壞無法還原，遺失的時間跨度還會直接翻倍。想要把 RPO 縮小到 5 分鐘以內，系統必須引入持續性的即時交易日誌歸檔（如連續上傳 WAL）、配置異地同步/半同步資料庫副本，或者採用支援秒級持續資料保護（CDP）的儲存機制。至於系統的 RTO，則取決於從備份映像檔拉回、磁碟寫入、建立索引、資料校驗到流量 DNS 切換的全部耗時，這些環節必須透過定期的真實演練才能得出客觀數值。

2.8 一致性（Consistency）

在分散式系統的世界裡，「一致性（Consistency）」是一個極易引發雞同鴨講的詞彙，因為它至少橫跨了兩個完全不同層面的語境。在傳統關聯式資料庫的 ACID 理論中，C 代表的是「應用業務的不變條件（Invariants）」，例如帳戶餘額不能扣成負數、租戶配額不能超賣；而在分散式系統與儲存複寫的語境下，一致性討論的則是「當多個客戶端向多個分散節點併發發起讀寫時，大家到底能看到怎樣的操作順序與最新結果」。在技術選型時，千萬不要只拋出一句模糊的「這個資料庫是不是強一致性？」而是必須精確追問：在怎樣的併發操作下、跨越怎樣的資料範圍、走哪種讀取路徑，以及當網路發生分割中斷時，系統能給出怎樣的數學保證？

複寫像送帳本：寫完了，為什麼讀不到？

線性一致性（Linearizability）要求在外部看來，整個分散式系統就如同只有單一一個全域副本一樣：任何讀寫操作都在其發起與返回之間的某一個瞬時點生效，並且完全尊重實體世界的全域時間先後順序。換句話說，只要某個寫入請求已經成功回傳給客戶端，那麼在這之後發起的任何讀取操作，就絕對不能再讀到舊版本的值（除非中間又有新的寫入覆蓋）。請注意：線性一致性並不要求底層所有的實體節點必須在同一個奈秒同步完成資料搬運，它要求的是外部客戶端所觀察到的操作歷史，必須完全符合這個嚴格的時序因果模型。

最終一致性（Eventual Consistency）則相對寬鬆很多：它僅僅承諾在沒有新寫入進入、且網路通訊與故障修復持續推進的前提下，所有副本最終會收斂到完全相同的狀態。然而，這句承諾本身既沒有保證「最多幾秒內會收斂」，也完全不附帶「讀己之寫（Read-your-writes）」或「單調讀取（Monotonic Reads）」的保證。如果你的產品要求「使用者剛點擊上傳檔案，重新整理後自己的畫面就必須能立刻看到這筆紀錄」，你就必須在架構上主動提供會話級保障（Session Guarantee）、將該用戶的讀取請求強制路由回主節點，或者在前端攜帶版本號進行條件判斷，絕不能任由前端介面靠隨機輪詢來碰運氣。

在同一個平台內部，我們可以依據不同資料領域的特性，精準配置不同級別的一致性保證。帳號權限驗證與租戶用量配額，涉及嚴格的業務安全邊界，必須死守強一致性；而全站搜尋引擎的倒排索引，則可以從容容忍數秒鐘的非同步延遲，只需向產品端定義出可接受的同步 SLO 即可。在任務狀態的流轉上，資料庫應該採用樂觀鎖或版本號機制，防止因為網路延遲而慢到的「RUNNING 狀態回報」意外覆蓋掉已經寫入的「SUCCEEDED 完成狀態」。更重要的是：當使用者刪除檔案後，就算搜尋引擎的快取還來不及剔除該筆資料，使用者在點擊下載時，後端也必須對權威資料庫進行即時的權限與刪除狀態校驗，絕對不能把非同步的搜尋索引誤當成系統的安全檢查邊界。

CAP 定理在分散式理論中有著極為嚴謹的數學定義：在一個允許網路發生分區分割（Partition）的非同步分散式環境中，系統無法同時在任何情況下兼顧線性一致性（C），並保證每一個發送給非故障節點的請求都能獲得合法的非錯誤回應（A）。請務必釐清：CAP 定理中的 Availability 是一種形式化的數學進展性條件，絕非工程維運中所說的「每月 99.9% 正常上線率」；而當節點因為一致性保證而直接回覆 500 錯誤時，在 CAP 的定義裡也是被視為「不可用」的。因此，坊間常說的「CAP 三選二」其實是一種嚴重的過度簡化：在分散式系統中，網路延遲與光纖切斷等分區故障（P）是必然會發生的物理現實，因此我們真正要做的，是在分區故障發生的極端時刻，決定哪些關鍵操作寧可暫停服務或報錯以守護資料正確性（傾向 CP），哪些操作可以容許讀到舊資料以換取服務不中斷（傾向 AP），並在網路恢復後設計出自動對齊與補償協調的流程。Gilbert 與 Lynch 在 2002 年證實 Brewer 猜想的原始論文，清晰列出了這項定理的嚴格前提與數學證明。

另外，千萬別把資料庫的「交易隔離等級（Transaction Isolation）」與分散式一致性混為一談。可序列化（Serializability）保證的是多個並發交易的執行結果，在邏輯上等同於某種順序的序列化執行；但這個純粹的數學性質本身，並不保證該順序必須嚴格契合真實世界的時間先後，因此它絕非線性一致性的同義詞。而且，絕大多數生產環境關聯式資料庫的預設隔離等級都遠低於可序列化（通常是 Read Committed 或 Repeatable Read），如果遇到並發衝突，往往需要應用程式層自行捕獲異常並執行重試。PostgreSQL 官方關於交易隔離等級的詳盡手冊充分說明了：只會背「支援 ACID」是遠遠不夠的，唯有親自研讀實際的並發語意，才能寫出可靠的系統。

常見思維誤區：把最終一致性（Eventual Consistency）當作「程式寫出 Bug 時的免責藉口」。如果在你的架構設計中，根本沒有設計衝突解決策略、版本合併邏輯、重試機制或是反熵修復排程（Anti-entropy Process），那麼放任副本躺在那裡，它們只會演變成「永久不一致」，任何所謂的「最終會一致」都只是自欺欺人的幻想。

實戰思考：某企業租戶只剩下最後一次處理檔案的額度。此時該公司的兩位員工幾乎在同一微秒分別點擊了上傳，兩次請求分別打到了不同的 API 節點，且兩個節點各自從 Redis 快取中讀取到剩餘額度為 1，進而同時放行了任務建立。請問這個設計的致命錯誤出在哪裡？如果是你，會如何設計嚴謹的防超賣架構？

參考解答與推理

核心致命傷在於犯了分散式典型的「Check-Then-Act（先檢查再執行）」非原子操作錯誤，再加上快取本身的更新存在延遲或非同步漏洞。如果業務上嚴禁額度超賣，核銷邏輯必須落在具備強一致性保證的權威資料庫中：利用 SQL 的條件更新（Conditional Update）或行級鎖，將「檢查剩餘額度大於 0」與「扣除一份額度」綁在同一個不可分割的原子決策中；競爭失敗的第二個請求則直接被拒絕或排入等待佇列。同時，架構還必須處理補償邏輯：如果後續建立轉檔任務時儲存空間崩潰，系統需要有可靠機制把扣掉的額度加回來。若業務上容許短暫超額、事後再寄帳單補收，也可以採用另一種軟性扣額設計，但這必須是產品的主動約定，而不是架構疏漏所造成的非預期事故。

把配額條件放進寫入

在 PostgreSQL 等關聯式資料庫中，我們可以運用精巧的單行 SQL 條件更新，將「檢查是否還有剩餘額度」與「原子性扣除一份」無縫合為一體。在下方範例中，我們以 tenant_id 為主鍵；若扣額成功，RETURNING 會立即回傳更新後的剩餘點數；若回傳 0 列，則表示該租戶紀錄不存在，或者當下剩餘額度已經歸零：

UPDATE tenant_quotas
SET remaining = remaining - 1
WHERE tenant_id = $1 AND remaining > 0
RETURNING remaining;

當兩個請求幾乎在同一毫秒併發競爭最後一份額度時，後搶到該列行級排他鎖（Row Lock）的請求，會在前一個交易提交後、依據最新的磁碟資料重新校驗 WHERE remaining > 0 的條件，從而判定條件不成立，因此絕不可能發生扣成負數的慘劇。在實務中，最穩健的做法是把「冪等鍵認領」、「扣除額度」、「正式建立 Job 紀錄」以及「寫入待派發訊息的 Transactional Outbox」全數包進同一個資料庫本機交易中，任一環節出錯就整筆交易自動回滾；如果客戶端拿著已處理成功的同一把冪等鍵重發，則直接查詢並回傳原本已建立的任務。PostgreSQL 關於 Read Committed 隔離等級下並發更新的行重讀規則與UPDATE RETURNING 語法定義為這種高可靠寫入提供了堅實的語意背書。

2.9 可維護性、安全與成本（Maintainability, security, cost）

可維護性（Maintainability）衡量的是一個系統在未來的漫長歲月中，被工程團隊理解、修復、演進與重構的難易程度：新進工程師能否迅速摸清各模組的職責邊界？生產環境半夜報警時，On-call 人員能否順藤摸瓜在一分鐘內定位罪魁禍首？新的程式碼修改能否透過灰度發布（Canary Deployment）安全上線，並在出問題時瞬間一鍵回滾？底層的資料庫 Schema 與訊息格式能否保持向前向後相容演進？可維護性絕非空洞抽象的「程式碼好不好看」——如果團隊每次只是想新增支援一種新的檔案格式，就必須膽戰心驚地同步修改十個微服務並手動遷移三個跨庫資料表，那麼這套架構的可維護性就已經徹底破產，並會直接轉化為每一次產品發布的高昂風險與嚴重的故障修復時長（MTTR）。

在專案起步階段，最明智的策略往往是從乾淨整潔的模組化單體（Modular Monolith）開始：把租戶認證、任務狀態機、核心轉檔運算與對外通知，在同一個程式碼庫中拆分成界限分明的獨立模組。唯有當運算資源特性（如 CPU 密集型的轉檔與 I/O 密集型的 Web API）、部署更新頻率或故障爆炸半徑真的出現顯著差異時，再評估拆分成獨立的背景行程或微服務。在日誌設計上，務必使用一致的 job_id、tenant_id 與分散式 Trace ID 貫穿整條呼叫鏈，這能讓分散的日誌在 ELK 或 Grafana Tempo 中一鍵串連；但與此同時，必須嚴格守住資安紅線：用戶檔案的原件內文、認證 Token、私密金鑰等敏感資訊，絕對不能貪圖一時方便而印在日誌中。

資訊安全需求必須落實為程式碼與架構層面不可妥協的防禦性不變條件。每次存取資料庫與物件儲存時，都必須在伺服器端重新校驗當前認證使用者的租戶範圍，絕對不能盲目信任客戶端 URL 或 JSON 內隨手帶上的 tenant_id；產生的檔案預覽下載連結，必須採用具備防偽簽名與嚴格過期時限的預簽名網址（Pre-signed URL）；而負責解析各類檔案的轉檔程式，必須以最小權限原則執行在沙盒容器內，並從作業系統層級嚴格鎖死 CPU、記憶體容量、檔案大小上限與最長執行時間。請記住：任何上傳的文件本質上都是不可信的外部輸入，隨時可能包藏特製的格式畸形漏洞、壓縮炸彈（Zip Bomb）或能榨乾解析器記憶體的惡意結構。光是把程式包進 Docker 容器只是提供了一層基礎隔離，絕不能藉此省去系統漏洞修補、權限降級、網路出站限制（Egress Filtering）與檔案內容的安全掃描。

在評估架構成本時，成熟的工程師絕不會只看每個月底收到的一張雲端總帳單，而是會深入拆解到「單一業務工作單位的邊際成本（Unit Cost）」。在我們的文件中，每份文件的處理成本可能包括：原件與衍生檔的 S3 儲存租金、磁碟 API 讀寫計費、轉檔消耗的 EC2 算力秒數、訊息佇列的調用次數、跨可用區與公網頻寬流出費、日誌監控收集開銷，以及平攤在系統上的工程維護人力。在追求高可用性時預留的冗餘閒置容量本質上也是一種保險成本，但如果盲目把所有伺服器的 CPU 榨乾到 95% 以上，往往只會換來災難性的排隊延遲與一次又一次的系統崩潰雪崩。在比較技術方案時，必須將它們置於完全相同的 SLA 目標、保存年限與容錯邊界下，才能評估出誰才是真正高性價比的設計。

教學算例：假設平台某月份產生的雲端總維運成本為 12,000 個成本單位
該月份系統共計成功完成處理 30,000,000 份文件
全站每份文件處理的平均成本 = 12,000 ÷ 30,000,000 = 0.0004 成本單位
深入分析後若發現：全站最複雜的 1% 大型 CAD/PDF 文件，卻吃掉了 40% 的 CPU 總算力
這時就必須依照檔案類型建立精細的計費與配額分級，才能真實反映個別企業租戶的資源消耗

資訊安全與雲端成本之間往往有著深層的聯動關係：如果沒有為每個租戶設定合理的頻率與容量上限，外部一個簡單的爬蟲或濫用行為，不僅會造成阻斷服務攻擊（DoS），還會在短短一夜之間引發雲端帳單的大爆發；無限制地永久保存歷史檔案，除了帶來隨時間呈線性增長的巨大儲存費用外，還會大幅增加企業敏感資料在遭遇資安滲透時的洩漏風險。反過來說，如果為了一味省錢而把所有關鍵審計日誌全部關閉，那麼當系統真的遭遇資料外洩或內部舞弊時，團隊將徹底喪失追查證據的任何線索。正確的思考方式，是針對關鍵安全事件進行高可靠持久化、對日常高頻除錯日誌導入採樣與短生命週期輪替。任何一刀切的「全部記錄」或「全部省掉」，在工程實務上都是不負責任的偷懶心態。

常見思維誤區：以為採用了雲端託管服務（PaaS/SaaS），「安全與維運就全由雲端大廠包辦了」。這完全曲解了雲端大廠的「共同責任模型（Shared Responsibility Model）」：雲端廠商頂多負責底層機房實體安全、伺服器硬體正常運作與虛擬化層的隔離，而上層應用程式邏輯是否漏洞百出、資料分類與存取權限有沒有開大門、加密金鑰是否保管妥當，責任百分之百依然落在身為開發者的你身上。

實戰思考：為了解省前期開發時程，有工程師提議直接將具備全庫讀寫、甚至能隨意刪除備份的超級管理員資料庫帳號，直接寫進所有背景 worker 的設定檔中。請點出這個偷懶決策會引發哪些毀滅性的災難，並給出一套立即可落地的最小改進方案？

參考解答與推理

這個設計極度危險。背景 worker 是直接處理外部未知檔案的第一線陣地，一旦某份上傳的惡意檔案觸發了轉檔開源庫的遠端程式碼執行（RCE）或 SQL 注入漏洞，攻擊者便瞬間繼承了超級管理員身分，能夠輕易竊取所有企業租戶的機密資料、直接刪除線上資料庫，甚至把連帶的救援備份全部抹平。最小落地改進方案：立刻落實權限分離。將資料庫權限細分為受限的角色，worker 僅授予其執行業務所需的特定資料表 SELECT、INSERT 與 UPDATE 權限，堅決剝奪 DROP、TRUNCATE 與備份管理的任何權限；在物件儲存層，worker 只能取得當前任務對應的單一原件下載與特定路徑結果上傳的限時權限；同時對不需要外網連線的轉檔處理器關閉出口流量，並對所有異常越權請求進行即時告警。

2.10 系統需求總結（Summary of system requirements）

在系統設計的面試或技術評審中，究竟做到什麼程度，才算把「需求階段」真正做完整了？標準非常純粹：針對系統的每一條核心用戶旅程，你都必須能斬釘截鐵地說清楚什麼叫成功、什麼叫失敗，並且明確指出要調閱哪幾條監控指標來客觀驗證。堆砌再多空洞的讚美形容詞，都無法替系統增加半點穩健度。在我們的文件平台中，有三條常常被混在一起談的承諾邊界：第一，使用者的上傳是否被高可靠地安全收件；第二，背景轉檔是否能正確產出合法檔案；第三，下游的通知是否有被妥善投遞。唯有在架構初期就把這三件事徹底拆開，系統才能在第三方通知商突發故障時，依然從容維持核心文件轉檔的順暢運轉，而不至於讓局部的失敗演變成全域的癱瘓。

系統品質維度在架構設計時必須回答的具體問題在文件處理平台中的落地驗證手段
高可用性（Availability）在怎樣的時間窗口內，哪些有效請求被保證能成功處理？在邊緣 API 閘道建立端到端業務 SLI，精準涵蓋過載拒絕與逾時請求
可靠性與容錯（Fault Tolerance）當特定硬體或相依服務掛掉時，系統如何保證資料不壞、狀態可復原？在檔案上傳、資料庫寫入與通知發送的中間盲區隨機 Kill 行程，驗證重啟後的自我復原機制
可擴充性（Scalability）當請求量、資料量或租戶數放大十倍時，成本與延遲如何線性變化？設計混合不同檔案大小與極端熱點的併發壓測，並驗證在單一可用區斷電後的備用容量
系統效能（Performance）在怎樣的系統邊界下，我們承諾多少吞吐量與分位數延遲？拆解 API 回應、佇列排隊、純 CPU 算力與外部等待，重點監控 p95/p99 尾端延遲分布
資料持久性（Durability）一旦回覆寫入成功，這份資料能抵禦哪些災難？承諾保存多久？實測 WAL 刷盤機制、進行資料庫非同步複寫演練，並定期執行 RPO/RTO 災難還原驗證
分散式一致性（Consistency）哪些欄位可以接受非同步收斂，哪些核心業務不變條件絕對不准退讓？針對併發配額扣減進行競態條件測試，驗證讀己之寫路由，並防範版本倒退覆蓋
可維護性、安全與成本未來的版本迭代是否能安全發布？租戶間如何實體隔離？單檔成本多少？落實灰度金絲雀發布、建立跨租戶越權滲透測試，並精確拆解單一文件的各項資源開銷

一份真正優質的架構需求文件，絕不僅僅是記錄已經確定的事情，更會誠實列出那些「當前尚未確定、有待實測」的假設清單。舉例來說，如果在專案初期我們還無法掌握各類格式文件的純 CPU 耗時分布，就應該明確在架構圖旁註明「待量測」，並同步說明這個未定數可能會如何影響後續 worker 伺服器的 CPU/記憶體配比。把未知假設誠實擺上檯面，能讓後續的所有技術決策都建立在理性的數據地基之上。一場專業的系統設計評審，考察的從來就不只是你拋出的技術名詞，更是在考驗你是否深刻理解：當現實中的哪一條假設被推翻時，架構中的哪一個模組就必須跟著推倒重來。

在設計的最後一步，我們必須用「極端衝突的情境」來檢驗整套系統的優先順序取捨：當跨可用區網路發生分區中斷時，我們是寧可拒絕部分使用者的額度扣減，還是容許短暫超賣？當通知供應商反應遲緩時，延遲發送通知十分鐘，是否遠比直接阻斷文件處理更符合業務利益？為了百分之百保證檔案不遺失，我們是否願意讓 API 的上傳確認多等 20 毫秒以完成跨機櫃刷盤？在分散式工程中，不存在放之四海皆準的完美解答，但有一條鐵律必須堅守：跨租戶的資料越權與洩漏，永遠無法藉由「整體系統可用性很高」來開脫彌補。所有在極端情況下所做的降級與退讓，都必須在介面上對用戶保持透明，並且在架構中具備完備的審計日誌與事後補償機制。

常見思維誤區：把需求文件當成「開工前寫一次就打入冷宮的官樣文章」。線上流量的增長曲線、租戶的使用模式，以及外部雲端依賴的穩定性，每天都在動態變化。唯有用每一次線上事故的慘痛教訓來回頭修訂初始假設，並在架構決策紀錄中詳細寫下每次變更的深層理由，你的系統才能在長年的版本迭代中，始終如一地履行它當初向用戶許下的承諾。

綜合實戰大考驗：請為即將啟動的第一版文件平台，凝練出五條條理分明、具備可驗收性的核心架構規格（分別覆蓋核心功能、服務可用性、系統效能、資料持久性與多租戶安全），並針對其中「多租戶安全隔離」這一條，設計出可在 CI/CD 流程中自動化執行的驗收測試方案。

參考解答與推理
  1. 核心功能：使用者能穩定上傳指定白名單格式之文件，取得系統核發之唯一 Job ID，能隨時輪詢終端狀態並下載轉檔結果；支援客戶端自帶 Idempotency-Key，保證相同租戶之同鍵重試絕不建立重複任務。
  2. 服務可用性：在任意連續 30 天的時間窗口內，通過身份與格式校驗的有效任務提交請求，良好事件（500 ms 內成功回傳）達成比例不得低於 99.9%，過載拒絕與逾時皆嚴格納入不良事件計算。
  3. 系統效能：在約定的混合檔案大小（均值 5 MB）與尖峰流量負載下，接收 API 的 p99 延遲需壓在 300 ms 以內；95% 的成功任務需在 60 秒內完成背景轉檔。
  4. 資料持久性：檔案原件於確認接收後線上保留 30 天，儲存層需抵禦單一可用區（AZ）完全斷電之災難，承諾 RPO ≤ 5 分鐘、RTO ≤ 30 分鐘，且每季執行自動化備份映像檔災難還原測試。
  5. 多租戶安全：任一企業租戶的登入憑證，絕對無法讀取、修改、刪除或下載屬於其他租戶的任何文件原檔、轉檔成果、日誌或 Webhook 設定，即使攻擊者完全知曉受害者的 UUID 亦然。

自動化驗收測試設計：在 CI 測試環境中預先建立兩個獨立租戶 Tenant-A 與 Tenant-B，並讓 Tenant-B 上傳私密檔案生成 Document-ID-B 與 Job-ID-B。接著以 Tenant-A 的合法 JWT 憑證，發起一連串針對 Tenant-B 資源的惡意調用（覆蓋原檔下載、狀態查詢、任務取消、刪除請求與 Webhook 回呼更新），斷言所有請求都必須精確回傳 403 Forbidden 或 404 Not Found；同時檢查伺服器回傳的錯誤 Payload，確保未洩漏 Tenant-B 的任何路徑、檔案名稱或內部伺服器堆疊資訊，並確認後端安全日誌精準觸發了「跨租戶越權存取告警」。
