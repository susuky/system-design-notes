第五章 · Caching

快取：省掉重複工作，守住資料的責任

上一章讓我們能重試；這一章要讓重試不至於重複收費、重複通知，也讓查詢不必每次碰到主要資料庫。相同的快取技術，在不同責任下需要不同的失效策略。

沿用文件平台尖峰 115.74 份／秒；下列算例分別設定讀取次數、命中率與紀錄保留期。

5.1 去重快取（Deduplication cache）

當發布確認遺失、消費者提交後崩潰，或使用者重按送出，相同意圖可能出現多次。去重（deduplication）必須先界定「相同」：相同文件內容，可能是兩次合法作業；相同使用者的一次重試，才可能是同一項業務意圖。因此檔案雜湊可以協助辨識內容，卻不應單獨決定是否建立工作、寄信或計費。

本平台讓提交者產生 idempotency_key，範圍定為「租戶＋操作類型＋鍵」。紀錄另保存請求摘要與工作編號；同一鍵搭配不同文件版本或處理選項時，回報衝突。AWS 的 Making retries safe with idempotent APIs 以明確請求識別碼表達意圖，並核對重試參數。

為什麼不能只用一個 SET NX？若先寫「看過此鍵」再執行，工作失敗後的重試可能被錯誤略過；若先執行再寫鍵，兩個並行請求可能都執行。即使插入鍵是原子的，它與另一個資料庫的更新或外部寄信也未必是同一個原子操作。資料庫可在同一交易中，用唯一約束把冪等紀錄與工作建立綁在一起；競爭失敗者回讀既有紀錄，才知道下一步。

handle_create_job(request):
    authorize_request_now(request)
    key = (request.tenant_id, "create_job", request.idempotency_key)
    digest = canonical_intent_digest(request)
    cached = request_result_cache.get(key)
    if cached exists and cached.digest == digest and cached.is_valid:
        return cached.response
    transaction:
        record = insert_unique_or_read_locked_idempotency_record(key, digest)
        if record.digest != digest: fail_conflict()
        if record.job_id exists: response = existing_job_response(record)
        else:
            job = create_job_and_outbox(request)
            save_job_reference(record, job.id)
            response = accepted_job_response(job)
    commit
    best_effort_cache_result(key, digest, response)
    return response
// 偽碼中的「插入或讀取」需按資料庫的衝突／交易語意實作

上例快取已持久成立的「提交請求結果」，包含 accepted 與工作編號。每次請求先驗證授權，再讀取快取；背景進度由工作資源查詢。

長工作另有 pending、running 與 completed。看到 running 不代表永遠不用再做：原工作者可能已死；要有期限、租約（lease）和接管流程。租約過期也不證明舊工作者已停止，提交結果時可檢查版本或單調增加的 fencing token，拒絕舊擁有者寫回。對外寄信仍要使用供應商能辨識的冪等鍵，或保留「結果未知」等待核對。

保留期算例。若每日 100 萬項業務意圖，每筆去重紀錄假設占 160 bytes，保存一天的原始紀錄約為 160 MB；保存七天為 1.12 GB。這不含索引、物件額外成本、複本、事件放大與配置碎片。若死信可在七天內重放，但冪等證據只保存一天，第六天重放就可能再次寄信。保留期限必須涵蓋最晚合法重試／重放；快取記憶體能裝多少，不能決定這項契約。

Redis 的到期與容量淘汰是不同機制；設定 TTL 的鍵也可能依淘汰政策在期限前消失。因此不能將「TTL 為七天」解讀為「七天內一定記得」。來源：Redis Key eviction。快取失效時應回到持久紀錄；若持久層也不可用，不能為追求可用性而無條件執行不可重複的副作用。

常見錯誤：跨租戶共用一個裸 idempotency_key；把兩次相同內容當同一次意圖；把 cache miss 當成未做過；把 Bloom filter 的「可能存在」直接用來丟棄工作。機率式結構可作快速篩選，但假陽性不應使合法文件永久消失；真正略過前仍需權威證據。

練習：去重快取 TTL 是 24 小時，代理保存失敗訊息七天。只把快取改成七天就足夠嗎？

不夠。還要考慮容量淘汰、故障遺失、重放是否超過七天，以及原子提交範圍。應明確界定重放契約，讓持久冪等紀錄涵蓋該期間，快取只加速讀取。若允許更晚的人工作業，須另定新業務意圖或延長／永久保留必要證據，不能默認它安全。

5.2 中繼資料快取（Metadata cache）

文件列表常常不需要讀取 5 MB 原件，只需要名稱、頁數、狀態、版本和結果位置。這些描述文件的資料稱為中繼資料（metadata）。把它們快取起來，可以降低主要資料庫壓力；但「這些欄位都很小」不代表可以使用同一套新鮮度政策。標題慢幾秒更新與撤銷權限慢幾秒生效，後果完全不同。

最容易起步的是旁路快取（cache-aside）：先查快取，未命中則讀資料庫並回填。命中率高會降低後端讀取，但也增加一個維護層。假設尖峰每份文件帶來十次中繼資料讀取，請求量為 115.74×10＝1,157.4 次／秒；若命中率為 95%，回源約為 57.87 次／秒。快取全冷時卻可能立刻回到 1,157.4 次／秒，因此不能只按 58 次／秒配置唯一的資料庫保護策略。

若快取查詢固定花 1 ms，回源額外花 20 ms，忽略填入成本的平均延遲估算為 1＋0.05×20＝2 ms。這是條件化的平均模型，不代表第 99 百分位也是 2 ms；未命中、連線池等候及熱鍵集中，都可能讓尾端延遲相差甚遠。另假設常駐 10 萬筆、每筆資料 256 bytes，內容本體為 25.6 MB，實際記憶體仍須另外算鍵、索引、複本與物件成本。

失效競爭。讀者 A 未命中，開始讀舊版本 v4；寫者 B 提交 v5 並刪除快取；A 隨後把 v4 回填，舊資料就復活。版本化鍵可讓 v4 與 v5 分別儲存，另一種做法是保留單調版本下限／墓碑並拒絕舊寫入；刪除快取時需保留判定版本所需的證據。在快取旁路實驗選擇「刪除後，舊讀取回填」，可逐步觀察這條競爭時序。

// 不變版本資料：版本參照與授權必須另有正確性契約
get_document_metadata(tenant, document, wanted_version):
    authorize_current_access(tenant, document)
    key = (tenant, document, wanted_version)
    cached = cache.get(key)
    if cached exists: return cached
    value = read_exact_immutable_version(key)
    best_effort_cache_put(key, value, ttl_with_jitter())
    return value
// 若要「最新版本」，先解決 latest 指標的新鮮度，不能靠命名假裝解決

快取雪崩與擊穿是不同的負載形狀。大量鍵同時到期，可用 TTL 抖動分散；同一熱鍵大量同時未命中，可用單鍵合併請求（single-flight）減少重複回源。程序內 single-flight 合併的是同一程序的請求；二十個 API 程序仍可能各自讀庫一次，因此共享資料庫還需要總回源並行上限與超載回應。顯示資料可按契約短暫返回舊值，授權與刪除狀態則沿用各自的新鮮度要求。

單靠 TTL 無法界定資料最舊會到什麼程度：若來源複本落後，快取可能把已經很舊的值重新保存一整段 TTL；若更新失效事件遺失，同樣不能承諾立即一致。需要精確界限時，要把來源新鮮度、讀取起點和失效傳播一起計算。HTTP 層的 no-cache 表示使用前須驗證，no-store 才是要求不要儲存；兩者不能混用。來源：HTTP Caching 的快取控制語意。

常見錯誤：鍵缺少租戶；把帶權限的結果用文件 ID 全域共用；快取查詢逾時後無限回源；只觀察總命中率而忽略某一大租戶；以 metadata hit 直接放行原件下載。讀取成本優化與授權判定必須分別設計。

練習：命中率 99.9%，但使用者撤銷分享後，對方仍能下載一分鐘。這能以效能優良作為理由嗎？

不能。先釐清產品允許的撤銷生效界限；若要求立即生效，就應在下載前驗證目前權限，並處理已簽發連結與進行中下載的契約。顯示資訊可以繼續快取，但不能把高命中率當作存取控制正確性的證據。

章末決策：去重快取後方有持久冪等紀錄；中繼資料依版本與風險分級；租戶隔離在每個鍵與讀取路徑上落實。接下來的佇列會把負載轉成等待，這些去重與版本規則將成為安全重送與擴充的前提。
