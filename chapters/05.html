第 05 章

快取裡的值，什麼時候還能相信？

讀取快了，下一個問題就變成資料的新舊。這章先處理同一操作重送，再追一條「讀到舊值、更新、回填」的競爭時間線。

提交重送了，怎麼找回原任務

客戶按一次提交，網路中斷後又送一次；兩次請求其實是同一個操作。由客戶產生穩定的操作 ID，接收端以「租戶＋操作 ID」找既有結果。相同操作 ID 配相同參數就回既有 job_id；若參數不同，回報衝突，讓客戶修正。

同時收到兩份相同請求時，查詢後再插入會留下競爭窗口。把操作 ID 設唯一約束，讓建立任務和保存去重結果放進同一交易；其中一份取得建立權，另一份讀到既有結果。單純快取可加速這次查詢，真正的業務規則由這個原子提交維護。

去重紀錄的保留期要覆蓋允許的重試窗口。若保存一天、客戶可在三天內重試，第二天的重送會失去原操作的紀錄。對外部付款或寄信，接收方也要接受穩定操作 ID，或由你保存可查的交付狀態。

這裡的兩種重用要看鍵：相同操作 ID 是重送；不同操作 ID 可能剛好帶相同內容，仍是兩個合法工作。文件內容重用可以另做產品功能，與業務提交的識別各自定義。

同一鍵，直接比較同一份業務參數

handle_create_job(request):
    authorize_request_now(request)
    key = (request.tenant_id, "create_job", request.idempotency_key)
    intent = (request.document_id,
              request.document_version,
              request.conversion_profile_version)

    cached = request_result_cache.get(key)
    if cached exists and cached.intent == intent and cached.is_valid:
        return cached.response

    transaction:
        record = insert_unique_or_read_locked_request(key, intent)
        if record.intent != intent:
            fail_conflict()
        if record.job_id exists:
            response = existing_job_response(record)
        else:
            job = create_job_and_outbox(request)
            save_job_reference(record, job.id)
            response = accepted_job_response(job)
    commit

    cache_result_if_available(key, intent, response)
    return response

唯一鍵決定哪一筆請求先建立紀錄；衝突的請求等待該筆交易完成，再讀取並鎖定既有紀錄。文件 ID、版本與轉檔設定逐欄比對：相同就接回原 job，改過任何一項就屬於新的意圖。快取過期後，資料庫的業務紀錄仍能找回同一份結果。

兩個客戶分別建立內容完全相同的工作，是否應只保存一筆任務？

看推導

各自保存任務。操作 ID 不同代表兩次使用者意圖；底層若允許重用計算產物，可以讓兩筆任務引用同一份產物，權限、計費與狀態仍分開。

刪完快取，舊值為何又回來

快取旁路（cache-aside）的讀取流程很短：先查快取，miss 時讀權威資料庫，再把結果放回快取。假設快取耗時 1 ms、資料庫耗時 20 ms、命中率 95%，串行查詢的平均時間約為 0.95×1＋0.05×21＝2 ms；資料庫讀取量也降為原請求量的 5%。

寫入後刪快取，可讓後續 miss 重新取新值。不過已在途的舊讀取可能較晚回填：讀者 A 先取到 v1，寫者提交 v2 並刪快取，A 最後把 v1 放回去。解法依時效需求選擇：接受短時間舊值可設 TTL；要維持版本順序則讓回填附版本，並在同一原子比較中拒絕低於已知版本的值。

熱門鍵過期時，許多 miss 可能一起打到資料庫。把相同 key 的回源合併成一份在途工作，其他讀者等待這份結果；不同 key 的過期時間加入分散，降低同時失效。舊資料可否先回覆、權限變更多久要生效，直接寫在快取政策裡。

空間用完時，LRU 偏向保留最近用過的值，LFU 偏向保留常用的值。觀察命中率、回源延遲、逐出量和熱門 key 的流量，決定容量與策略。快取 key 包含租戶、資源與會改變回應的參數，讓不同權限或不同版本的結果有正確邊界。

get_document_metadata(tenant, document, wanted_version):
    authorize_current_access(tenant, document)
    key = (tenant, document, wanted_version)
    cached = cache.get(key)
    if cached exists:
        return cached

    value = read_exact_immutable_version(key)
    cache_put_if_available(key, value, ttl_with_jitter())
    return value

這段先以當下權限判斷是否可讀，再使用固定版本的快取。查「最新」時，先取得符合新鮮度目標的 latest 版本指標，再讀那個版本；latest 指標的更新也要處理舊讀取回填的競爭。
