第五章 · Caching

快取：省掉重複工作，守住資料的責任

上一章我們建立了健全的重試機制；但如果系統沒有防護，重試就可能演變成重複扣款、重複發信與重覆執行。同時，高頻的查詢也不該無限制地直接撞擊核心資料庫。看似相同的快取技術，在「防止重複運算」與「加速資料讀取」兩種截然不同的責任場景下，需要完全不同的失效策略與正確性邊界。

情境設定：沿用文件平台尖峰 115.74 份／秒的負載基準；下列各小節的推算算例，將分別明確設定讀取倍率、快取命中率與冪等紀錄保留期限。

5.1 去重快取（Deduplication cache）

在分散式網路環境中，無論是因為訊息代理的確認訊號（ACK）遺失、背景工作者提交結果後隨即重啟，還是使用者在前端介面上不耐煩地連續點擊「送出」，同一個請求意圖都極可能在極短時間內重複抵達後端。此時，系統在做去重（Deduplication）之前，必須先嚴格定義何謂「相同」。兩份內容位元組完全相同的文件，可能是同一個使用者在兩天後的兩筆完全合法的獨立業務上傳；而同一個使用者在十秒鐘內發起的兩次重試，才代表同一項業務意圖。因此，檔案的 SHA-256 雜湊值只能用來識別內容特徵，絕不能單獨拿來作為「要不要建立任務、要不要寄出通知、要不要扣除額度」的業務決策依據。

在工程架構上，標準的做法是由呼叫端明確產生一個冪等識別碼（idempotency_key）。在後端儲存中，該鍵的有效作用域必須綁定「租戶識別碼 ＋ 操作名稱 ＋ 鍵值」，例如 (tenant_id, "create_job", client_key)。除了鍵值本身，資料庫記錄還必須儲存請求內核的摘要雜湊（Request Digest）與對應產生的工作編號。當相同的鍵值再次出現時，如果呼叫端傳入的文件版本或處理參數發生改變，系統應果斷回報 409 Conflict 衝突錯誤，防止惡意或手誤覆寫。AWS 在其架構指南 Making retries safe with idempotent APIs 中對這種參數比對與重試合約進行了深入闡述。

為什麼不能只靠 Redis 的 SET NX？許多初學者喜歡用 redis.set(key, 1, nx=True, ex=60) 來防重送。但只要仔細分析時序，就會發現這個方案漏洞百出：若先執行 SET NX 再執行業務，一旦後續工作在執行途中當機，下次重試就會被 Redis 判定為「已處理」而被錯誤略過；若反過來先執行業務再寫 Redis，那麼兩個並行請求在第一步檢查時都會發現 Key 不存在，雙方都會執行業務，防重宣告徹底破功！更致命的是，即使 SET NX 在 Redis 內部是原子的，它與關聯式資料庫的更新也絕不可能具備跨系統的跨庫原子性。真正的可靠邊界在於關聯式資料庫本身：利用資料庫的唯一約束（Unique Constraint）與本機交易，把冪等紀錄與任務建立死死綁在同一個 Commit 中；並行競爭失敗的一方會觸發唯一鍵衝突回滾，接著重新讀取既有記錄回傳。

handle_create_job(request):
    authorize_request_now(request)
    key = (request.tenant_id, "create_job", request.idempotency_key)
    digest = canonical_intent_digest(request)
    cached = request_result_cache.get(key)
    if cached exists and cached.digest == digest and cached.is_valid:
        return cached.response
    transaction:
        record = insert_unique_or_read_locked_idempotency_record(key, digest)
        if record.digest != digest: fail_conflict()
        if record.job_id exists: response = existing_job_response(record)
        else:
            job = create_job_and_outbox(request)
            save_job_reference(record, job.id)
            response = accepted_job_response(job)
    commit
    best_effort_cache_result(key, digest, response)
    return response
// 偽碼中的「插入或讀取鎖定」依各資料庫的 ON CONFLICT 或 FOR UPDATE 語意實作

上述流程中，快取只扮演「加速層」的角色——快取命中時立刻返回已持久化的 Accepted 回應與任務編號；快取若失效或遺失，依然有資料庫作為權威防線。但請特別留意：在檢查快取之前，必須先對請求執行當下的租戶授權驗證，絕不能因為快取裡有結果就略過身分安全檢查。

對於長週期的非同步任務，狀態機中會出現 pending、running 與 completed。在分散式架構中，看到 running 並不代表永遠不需再做：原本接手的工作節點可能已經無預警猝死。系統必須設計租約逾期（Lease Timeout）與接管搶佔機制。但請務必牢記：租約過期並不證明舊工作者已經真正停止執行（它可能只是陷入了長達數十秒的 Stop-the-World GC 暫停）！為防範腦裂回寫，工作者提交最終結果時必須附帶單調遞增的 Fencing Token 或資料版本號，資料庫一律拒絕舊租約擁有者的寫入請求。至於對外寄發 Email，則必須依賴郵件服務商提供的冪等鍵，或者記錄為「結果未知」交由對帳程序處理。

去重紀錄保留期的容量與合約估算。假設平台每日承接 100 萬次業務請求，每筆去重紀錄包含鍵值、時間戳與雜湊摘要約占 160 個位元組。若只保留一天，原始資料體積約為 160 MB；保留七天則約為 1.12 GB（未計 B-tree 索引、WAL 與多節點複本開銷）。此時必須回答一個核心合約問題：死信佇列（DLQ）的訊息最長保留期限是多久？如果訊息代理允許工程師在第七天重放失敗訊息，但你的冪等資料表卻在 24 小時後就自動被排程清空，那麼在第六天手動重放死信時，系統將把歷史訊息當成全新請求，再次對用戶重複扣款或重複寄信！冪等證據的保留期，必須嚴格大於等於系統中最晚合法的重試與死信重放週期。快取記憶體裝得下多少，絕對不能成為制定業務可靠性契約的決定因素。

此外，Redis 的「鍵值 TTL 到期」與「記憶體滿載淘汰（Maxmemory Eviction）」是兩個層次的行為。在記憶體吃緊且配置為 allkeys-lru 的叢集裡，即使設定了 7 天 TTL 的 Key，也可能在第 3 小時就因為空間不足被提早逐出。因此，絕對不能把「在 Redis 設了 7 天 TTL」天真地等同於「7 天內一定記得」，詳見 Redis 記憶體淘汰機制手冊。去重快取是隨時可以丟棄的加速層，真正決定生死的是後方具備 ACID 保證的持久化冪等表。

常見錯誤：跨租戶共用同一個全域的裸 idempotency_key；誤把兩次相同內容的檔案上傳當成同一次請求意圖；把快取未命中（Cache Miss）直接等同於「這筆請求從未發生過」；以及把布隆過濾器（Bloom Filter）的「可能存在」直接用來丟棄請求。布隆過濾器存在假陽性（False Positive），其假陽性會讓合法的使用者工作永久消失；只有真正的權威儲存才能給出確定結論。

練習：系統中去重快取在 Redis 設為 24 小時到期，但訊息佇列設定的重試與死信保留時間長達 7 天。此時若只把 Redis 的 Key TTL 改成 7 天，是否就徹底安全了？

遠遠不夠。首先，Redis 遭遇記憶體淘汰或節點故障重啟時，記憶體資料會提早遺失；其次，這沒有解決並行請求的跨庫原子性問題。正確架構是：將業務狀態與唯一冪等鍵持久化寫入資料庫，並讓資料庫去重紀錄的保存期嚴格覆蓋 7 天以上的重放窗口。Redis 僅用於毫秒級的讀取命中加速，絕不能作為唯一的合約底線。

5.2 中繼資料快取（Metadata cache）

在文件管理平台中，使用者最頻繁呼叫的「查看文件列表」與「檢視詳情」請求，並不需要將 5 MB 的 PDF 實體檔案從物件儲存拉出，而只需要文件的名稱、頁數、處理狀態、最新版本號以及下載連結。這些用來描述核心資產的輕量資料被稱為中繼資料（Metadata）。將中繼資料載入快取能大幅分擔主資料庫的讀取壓力；但切忌一視同仁地套用相同的過期政策——「文件標題慢 3 秒更新」與「使用者的存取權限撤銷慢 3 秒生效」，在資安與合規上的嚴重程度完全不在同一個量級。

業界最通用的快取拓撲是旁路快取（Cache-Aside）：應用程式讀取時先查快取，若未命中則轉向主資料庫讀取權威資料，並主動回填快取。高命中率雖然能大幅卸載資料庫負擔，但架構師必須清醒地預防「快取全冷」的極限情境。假設在尖峰時刻每份文件衍生出 10 次中繼資料查詢，總請求量達到 $115.74 \times 10 = 1,157.4$ QPS；在平時 95% 命中率下，資料庫承受的實際回源負載僅有 $1,157.4 \times (1 - 0.95) \approx 57.87$ QPS。但如果快取叢集發生網路分割或整機重啟，回源負載將在數毫秒內瞬間暴增 20 倍直撲資料庫！因此，資料庫連線池與熔斷保護機制，絕不能只按照平時的 58 QPS 來規劃。

在延遲模型方面，若本機或分散式快取的查詢耗時固定為 1 ms，資料庫回源平均耗時 20 ms（不計寫入回填耗時），則整體平均延遲的期望值為 $E[\text{Latency}] = 1 + (1 - 0.95) \times 20 = 2$ ms。但請注意：這只是理想條件下的數學均值，絕對不代表系統的 P99 尾端延遲也是 2 ms！一旦遭遇快取未命中、資料庫連線集體排隊等待，或者某個熱門文件的快取 Key 發生集中打擊，P99 延遲往往會暴增至數百毫秒。另外，若常駐快取包含 100,000 筆文件，每筆中繼資料 JSON 體積約 256 bytes，表面上淨資料量只有 25.6 MB；但在實際的 Redis 記憶體中，加上 dictEntry、robj 結構標頭、記憶體對齊（jemalloc slab）與鍵名儲存，實際常駐記憶體開銷往往達到淨資料量的 3 到 5 倍以上。

旁路快取中最經典的並行回填競爭（Race Condition）。這是一個極具殺傷力的時序陷阱：讀取執行緒 A 查詢快取未命中，轉向資料庫讀取到了舊版本 $v_4$；此時寫入執行緒 B 剛好提交了新版本 $v_5$ 到資料庫，並依照規範清除了快取中的該鍵；隨後，執行緒 A 才從慢網路中甦醒，將它手中早已過時的 $v_4$ 寫回快取！結果就是：快取中的資料被舊版本成功復活，後續所有使用者將長期讀到過期的 $v_4$，直到 TTL 自然過期！

防禦這種過期復活的優雅解法有兩種：其一是不可變版本化鍵（Immutable Versioned Key），將快取鍵命名為 doc:{tenant_id}:{doc_id}:{version}，每個版本的內容一旦產生就永不更改；其二是在快取中維護單調遞增的版本號下限或墓碑標記（Tombstone），回填時比對版本號，嚴格拒絕舊版本的寫回覆蓋。你可以在文中的「快取旁路實驗」中選擇「刪除後，舊讀取回填」情境，親自步進觀察這條競爭時序的演進。

// 不變版本資料：版本參照與授權必須另有獨立的正確性契約
get_document_metadata(tenant, document, wanted_version):
    authorize_current_access(tenant, document)
    key = (tenant, document, wanted_version)
    cached = cache.get(key)
    if cached exists: return cached
    value = read_exact_immutable_version(key)
    best_effort_cache_put(key, value, ttl_with_jitter())
    return value
// 若要查詢「最新版本」，必須先解決 latest 指標的新鮮度，絕不能靠命名自欺欺人

擊穿、雪崩與 Thundering Herd 的工程對策。在大型系統中，快取崩塌有兩種典型形態：快取雪崩（Cache Avalanche）指的是大量快取 Key 在同一秒內集體過期，防範手段是在基礎 TTL 上加上隨機抖動（Jitter，例如 300 秒 $\pm 30$ 秒的均勻分佈），將回源壓力打散；而快取擊穿（Cache Breakdown）則是單一超級熱點 Key 在過期的瞬間，數千個並行請求同時未命中而集體湧向資料庫。在單一伺服器程序內，可以使用 Single-flight 機制（如 Go 的 golang.org/x/sync/singleflight），讓成百上千個並行請求共用同一個回源 Promise，只有第一個協程真正去查資料庫，其餘請求在記憶體中等待其廣播結果。

但必須保持清醒：程序內的 Single-flight 只能合併同一個行程內部的請求。若你的 API 叢集部署了 30 個 Pod，依然會有 30 個查詢並行穿透至資料庫。因此，資料庫層必須配備嚴格的有界信號量（Bounded Semaphore）控制總並行度。同時，在 HTTP 快取層面，必須分清 no-cache（意指端點每次使用快取前，必須先向來源伺服器發起 304 ETag 驗證）與 no-store（徹底禁止任何中間代理與本機儲存快取）的本質區別，詳細規範可參閱 RFC 9111 HTTP 快取規範。

常見錯誤：快取鍵忘記帶上 tenant_id 引發嚴重跨租戶資料洩漏；將帶有特定使用者個人存取權限的結果以 document_id 存入全域快取；快取連線逾時（Timeout）後未做熔斷降級，反而無上限轉向資料庫直接引發連鎖雪崩；或者誤以為「中繼資料快取命中」就能直接放行使用者下載底層實體檔案。效能最佳化與安全性鑑權必須在架構上徹底脫鉤。

練習：中繼資料快取命中率高達 99.9%，但當文件管理者撤銷某位同仁的存取權限後，該同仁在接下來的一分鐘內依然能正常檢視與下載文件。這項延遲能否以「快取命中率優異」為由合理化？

絕對不行。這暴露出系統將「存取控制（Authorization）」與「資料快取（Data Cache）」錯誤揉合的致命瑕疵。權限撤銷是否允許數十秒延遲，屬於核心資安合規合約。若合約要求即時生效，每次呼叫前必須對權威授權層進行驗證，或在撤銷權限時主動推播全域版本失效事件（例如單調遞增使用者權限版本號），絕不能用高命中率作為資安漏洞的藉口。

本章帶走的設計思維：去重快取的背後，必須有持久化且跨交易的唯一冪等記錄作為真正的安全底線；中繼資料的快取必須按照資料變更頻率與安全風險嚴格分級治理；租戶隔離原則必須無條件貫徹在每一個快取鍵與存取路徑上。下一章我們將進入佇列系統，探討如何將突發負載轉化為受控的排隊等待，而本章建立的去重與版本防線，將是佇列重送與彈性擴充不可或缺的前提基石。
